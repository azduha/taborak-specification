# Removed Concepts

A lookup for names that are **not in the model**. Every spec page states the design as it is now and
carries no history, so this is the one page where a dead name is written down — with what it was, why
it went, and the decision that took it. The argument is in the [decision log](../decisions/index.md); the
row here is only an index to it.

Read it when a word from an older draft, another system, or a conversation does not appear anywhere in
these pages. The organization may still use the word — a removal from the model is not a removal from
its vocabulary.

| `is_member`, `member_type`, `is_child` | flags on the person row saying what kind of human this row was | personhood is not a type, and one person can be a member twice with a gap between | `membership` rows, and `is_current_member()` on the date asked about | [D-001](../decisions/round-01a.md#d-001--person-account-and-membership-are-three-separate-things) |

| `locality`, "the nearest scope wins" | a tie-break ordering allows by how specific their scope was | a grant answers one code yes or no, so there is nothing to order; what survived is that a deny is absolute | allow iff some live allow applies and no live deny applies | [D-099](../decisions/round-10a.md#d-099--a-grant-allows-or-denies-one-permission-there-is-no-level-and-no-locality) |
| `access_level`, `permission_level`, `level_satisfies()`, `revoked < view < contribute < manage` | a rank saying how much authority a grant carried, compared against a permission's rank | a grant allows or denies exactly one code; roles and audiences are the bundle a broad office gets | one `access_grant` row per code, plus the seeded starting grant set | [D-099](../decisions/round-10a.md#d-099--a-grant-allows-or-denies-one-permission-there-is-no-level-and-no-locality) |

| `medical.*`, the medical record | a class of personal data with its own storage and its own permissions | personal data is one class; sensitivity is graded by what a grant exposes, not by which table it reads | the attribute layer, and `person.view` read with that cost in mind | [D-083](../decisions/round-07-08.md#d-083--there-is-no-medical-record-personal-data-is-one-class-of-data) |
| the membership gate, `requires_membership`, `system.gate_exempt` | a resolver clause honouring an office only while its holder was a paid-up member, with a waiver list | the test is now an operand the grant's writer puts in, so the posture is opt-in per grant | `MEMBERS * ROLE(x)`; the exemption is `+ PERSON(y)` in the same grant | [D-100](../decisions/round-10a.md#d-100--a-role-is-an-office-and-a-group-is-company-two-tables-of-the-same-shape) |
| `org_unit`, `org_unit_type`, `org_unit_name`, `org_unit_relationship` | nodes of a nested unit hierarchy: types, renamed names, and split/merger/succession edges | the corpus names no units and a unit restricted nothing, so the structure carried no information | the unit is a scope, never a row; groups are the sets of people | [D-097](../decisions/round-10a.md#d-097--there-are-no-sub-units-the-unit-is-a-scope-not-a-row) |

**Two habits this page is meant to prevent.** Naming a removed thing in a spec page, which is what put
the history back into the pages this appendix exists to keep clean; and re-adding one quietly, which is
why every row ends in a decision — a concept comes back by a decision entry, or it does not come back.
