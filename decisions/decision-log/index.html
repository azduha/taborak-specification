    Decision Log¶

    Decisions taken, with the reasoning that produced them. Recorded so they are not re-litigated from scratch — and so that when a decision is reversed, the reason for the original choice is visible.

    Status values: decided — settled, the data model reflects it (since D-072: the documents, not a schema file). proposed — recommended, awaiting your confirmation. assumption — taken by default, stated in italics in the docs, easily reversed. reversed — no longer in force; the entry is kept, marked, and the replacement is linked. Reversals are also listed together in Reversed decisions, which sits where it was written — mid-way through this log, between D-080 and D-081, not at the end. It has not been moved, because a section with a stable anchor is worth more than a section in a tidier place.

    Five SQL fences survive in this log, and only here. D-072 moved the schema out of the documentation, but it did not rewrite the entries that had been written in the schema — at D-035, D-041, D-060, D-066 and D-068. Each is a quotation of the shape a decision was made in, and each says below it where the requirement actually lives now. No later entry adds a fence: the rule for writing this log from here is D-081 — state the requirement, name the layer that owes it, and let an identifier be a name rather than an actor.

    D-001 — Person, account, and membership are three separate things¶

    Status: decided (from your requirements) Date: initial design

    Decision. person holds identity only. account holds login credentials and is optional. membership holds participation and is temporal. No member flags, no child/adult flag, no is_member on person.

    Why. You described a person who was a member 1990–2010 and again from 2024. That is one person and two membership periods. Any design with person.is_member cannot express it, cannot answer "who was in Troop 12 in 1998?", and silently destroys 36 years of history the first time someone corrects a record.

    Consequence. Membership questions are always date-qualified: ../data-model/03-membership.md provides is_current_member(), was_member_on(), current_member_category(), and membership_years().

    D-002 — Everything temporal is a period, never a boolean¶

    Status: decided Date: initial design

    Decision. valid_from / valid_to with valid_to IS NULL meaning "still true", and half-open [from, to) ranges. Overlap prevented by EXCLUDE USING gist constraints.

    Why. Required by D-001, guardianship expiry, unit membership history, role terms, and grant expiry. Enforcing overlap in the database rather than in application code is essential: an import script, a manual SQL fix, or a future API will bypass application validation.

    Consequence. Requires PostgreSQL with btree_gist. On MySQL, the guarantee weakens to triggers plus nightly checks — a materially weaker invariant to be recorded as an accepted risk if that platform is chosen.

    D-003 — Never hard-delete; merges leave tombstones¶

    Status: decided Date: initial design

    Decision. No deleted_at, no business-data DELETE, no ON DELETE CASCADE anywhere. Ended periods get valid_to. Merged people keep their row with merged_into_person_id. Erasure is redaction, not deletion.

    Why. "Who attended this camp in 2003?" must resolve forever. A hard delete breaks the safeguarding record. Merges must be reversible because bad matches are inevitable.

    Consequence. Every query must exclude merged and redacted rows — hence the v_person view and resolve_person() function, which exist so application code cannot forget.

    D-004 — No automatic merging, ever¶

    Status: assumption ⚠ confirm or overrule

    Decision. Every identity match, however strong, requires human confirmation. There is no confidence threshold above which the system merges on its own.

    Why. A false-positive merge is a privacy incident: the survivor gains the absorbed person's permissions, and two people's records become one. A false negative is an inconvenience someone can fix. The asymmetry justifies the cost.

    Reverse if: the volume of historical data makes manual review infeasible. If so, the high-confidence tier should be narrow (exact external identifier match only) and its application must be logged and alerted.

    See: ../domain/03-identity-and-legacy.md

    D-005 — Permissions are grants, never derived from identity¶

    Status: decided (from your answer) Date: initial design

    Decision. Being a parent, a member, a leader, or a long-serving volunteer grants nothing. Every capability comes from an explicit, dated, revocable row.

    You answered that both read and write access should be explicit for caretakers.

    Why. The classic failure: a relationship ends (custody changes, a leader steps down) but access persists, because it was implied rather than granted. Explicit grants make access auditable and revocable.

    Consequence. A guardianship row alone grants nothing; guardianship_permission rows do. A position_assignment alone grants nothing; role_assignment does.

    D-006 — Per-item permissions are capabilities on the item¶

    Status: decided (from your answer) Date: initial design

    Decision. You clarified that "per-item permission" means capability on that item — "person X may act on item Y" — not a participation record and not an eligibility gate. Implemented as access_grant with an ordered level (revoked < view < contribute < manage < admin).

    Why. Isolates authorization from participation (D-005) and from eligibility, which will be a separate concept when events are specified.

    Consequence. permission_level connects permission codes to the level they require, so one grant level serves many permissions without a hardcoded mapping.

    D-007 — Every resource has an admin level that subsumes narrower ones ⚠ REVERSED¶

    Status: ~~decided~~ reversed by D-068 Date: initial design · reversed refinement round 5

    Reversed. The per-resource <resource>.admin permissions and the resolver's prefix match are gone. The admin grant LEVEL (rank 40) is untouched — this decision conflated the two, and the collision is what made it hard to reverse cleanly. See D-068.

    Decision. Per your instruction, every grantable resource exposes <resource>.admin, checked by prefix match, plus a single top-level system.admin.

    Why. Without it, every new narrow permission requires updating every role that should already have implied it — and someone will miss one, producing a permission that silently is not granted. The prefix match makes new permissions automatically covered.

    Consequence. The check is computed, not mapped. person.admin etc. are real permission rows so they appear in the role editor.

    D-008 — Organizations units are one self-referencing table with configurable types¶

    Status: decided (from your answer) Date: initial design

    Superseded by D-097, outright: the table is gone. Its reasoning that a type is a label and not a permission survives into person_group; the self-referencing hierarchy it was proud of is the exact thing the round deleted.

    Decision. One org_unit table with parent_unit_id self-reference and a configurable org_unit_type. Hierarchy via materialized path plus recursive CTE functions.

    Why. You confirmed sub-units are core. Depth is a data question, not a schema question — a 40-year-old organization has changed its levels. One table means "everyone in this district" is one recursive query rather than a hand-written union.

    Consequence. Nesting rules live in org_unit_type_rule plus a trigger. Units that closed remain queryable forever.

    D-009 — Unit membership links to person, not to membership¶

    Status: decided Date: initial design

    Decision. unit_membership.person_id → person.id, deliberately not membership_id.

    Why. 1990s rosters have a unit and a year but no membership workflow. Linking to membership would make that data unrepresentable and lose the whole historical dataset.

    Cost. Nothing enforces that a person with a unit membership holds an organization membership. Mitigated by application validation plus a nightly check (../data-model/03-membership.md, check 1).

    D-010 — Role assignments and access grants share a scope model and a resolver¶

    Status: decided Date: initial design

    Decision. role_assignment and access_grant are separate tables but share scope_type, the level model, and one can() function. Four authority channels (ownership, guardianship, item grants, roles), each dispatching from the permission's namespace, with an absolute deny check in front of them.

    Amended (see D-031, D-032): the resolver's allow channels are now ordered by locality rather than by channel, and the deny channel is scope-independent.

    Amended again by D-079, and this reaches the sentence above the amendment. "Each dispatching from the permission's namespace" was how the channels were found, and it is gone: dispatch is now subject ≠ actor for guardianship, and system. remains the only namespace with resolver-visible meaning. The four channels themselves are untouched — that part of this decision was durable for six rounds and is the part worth keeping. What the namespace rule turned out to be was a way of skipping the guardianship channel whenever the permission's name happened not to mark it as a guardian act, which is a thing a name cannot do. Note the shape of the failure for future amendments: the channel list was right and the routing over it was wrong, and every document that cited the routing copied the error.

    Why. They are the same idea at two granularities — authority for a period, in a scope, granted by someone. A single resolver prevents the divergence that makes the weaker of two implementations an exploit. Separate tables because their lifetimes, granters, and revocation semantics genuinely differ.

    D-011 — scope_id on access_grant is polymorphic, with no foreign key¶

    Status: assumption ⚠ a real fork — worth a deliberate decision

    Decision. access_grant.scope_type + scope_id with no FK. Validated by grant_scope_type plus nightly orphan checks.

    Why. Most of this system is unspecified (events, documents, and more). Polymorphism makes each new grantable type a config row rather than a schema migration.

    Cost. No referential integrity. Mitigated by: grant_scope_type FK, application-level grant closure on item delete, nightly orphan detection, non-reused BIGINT ids.

    Alternative. A grantable_item(id, item_type) supertable referenced by every grantable entity — full integrity, heavier design, migration per new type. Overrule this if you prefer integrity to flexibility.

    D-012 — Status strings compare by rank, never lexicographically¶

    Status: decided Date: initial design

    Superseded by D-099: the levels are gone, so the bug this guarded is unconstructible. The hazard is not forgotten — the one surviving ordered triple, a guardian's none / view / write, still sorts wrong alphabetically, and data-model/00-conventions.md says so where this entry used to.

    Decision. access_level is a lookup table with an integer rank. All level comparisons use rank.

    Why. 'admin' < 'contribute' alphabetically. A string comparison silently inverts the levels and makes the most powerful level the least. It throws no error and passes most tests. This is the single most dangerous easy mistake in the design.

    D-013 — Explicit deny (revoked) is checked before everything¶

    Status: decided Date: initial design

    Decision. Resolver channel 0. A revoked grant overrides roles, item grants, and ownership. In the guardianship channel, is_granted = false overrides a granted dependent.admin.

    Why. Without an explicit deny level there is no way to express "this person must not see this event" or "this guardian may not see medical records" when a broader grant would otherwise allow it. Court-ordered restrictions must not be overridable by a broader grant.

    D-014 — Roles do not inherit from other roles¶

    Status: decided Date: initial design

    Decision. No role-to-role inheritance. If unit_leader should have assistant_leader permissions, they are granted explicitly.

    Why. Inheritance chains produce authorization answers nobody can predict by reading the configuration. Predictability matters more than configuration economy in an authorization system — the people who must reason about it are volunteers, not engineers.

    Note: unit scope inheritance was a separate axis. It was reversed — see D-031. That reversal does not disturb this decision: role-to-role inheritance remains prohibited for the same reason it always was.

    D-015 — Authority inherits downward through the unit hierarchy ⚠ REVERSED¶

    Status: reversed by D-031 Date: initial design

    Decision (original). A role assigned at a unit covers that unit and all descendants. A district treasurer can act on troops within the district.

    Why (original). Matches how organizations actually work — a district officer has district-wide responsibility.

    Why it is reversed. Your rule: "The organization itself should not be able to itself decide permissions over the nested unit, it must come from the unit itself up. The only exception is the system admin." Downward inheritance makes every unit's authority decidable from above — a role written at the district level silently reaches into troops that never agreed to it. That is exactly the direction you excluded. The replacement is scope_exposure, where the unit grants coverage over itself.

    Consequence, accepted. Organization-wide operational roles (national registrar, national treasurer) no longer work by assigning a role high in the tree. Tracked as the reworked C-1.

    D-016 — Renewal opens a new membership row, not an extended valid_to¶

    Status: decided Date: initial design

    Decision. Shape A. A renewal closes the prior membership and opens a new one, linked by renewed_from_membership_id.

    Why. Extending valid_to destroys the ability to see that someone skipped a year and re-joined — the most commonly asked question about renewals — and makes retroactive corrections ambiguous. You asked for history preserved across decades.

    Cost. More rows; queries must handle a chain. The self-reference makes the chain explicit rather than inferred.

    D-017 — Requests are separate from memberships¶

    Status: decided Date: initial design

    Decision. membership_request is its own table. A rejected request produces no membership row.

    Why. A rejected request must not pollute member listings; a person may apply several times; review data has no meaning on a membership; submitting is self-service while reviewing is a staff capability.

    D-018 — membership_request records the subject and the submitter separately¶

    Status: decided (from your answer) Date: initial design

    Decision. person_id is the person who would become a member (the child). submitted_by_person_id is who submitted it (the parent).

    D-032 — Deny is absolute; locality orders allows only¶

    Status: decided Date: refinement round 2 Amends: D-013

    Decision. Two separate rules that were previously conflated into "local overrides global":

    1. Deny is absolute and scope-independent. An explicit revoked at any scope wins over everything, including a more specific allow, the admin level, ownership, and guardianship. The deny check does not walk ancestors — a deny is matched at the organization scope or at the exact same scope, and that is sufficient to be absolute.

    Why. "The local permission overrides the global one" is true for allows and dangerous for denies.     D-040 — The fee expires yearly; a date-tracked renewal window replaces a grace status¶

    Status: decided (from your answer) Date: refinement round 3 Resolves: A-3, D-3 (grace modelling)

    Decision. Membership activates on payment, and the fee is yearly, expiring at a fixed organizational date (typically January). When it expires:

    1. The membership lapses — the person is not a member and holds no member permissions from that date. There is no third "grace" status in the resolver.
    2. A renewal window — a fixed period such as three months, tracked as dates, not a status — follows the expiry. During it the person may renew without re-applying.
    3. A payment inside the window opens the new membership period at the expiry date, so the membership history shows continuous coverage with no gap and the person is not misclassified as a returning member.
    4. A payment after the window opens a new membership at the payment date, and the gap is real. It still does not require a new application.

    The tension, named. You described the grace period as existing "for them to pay to stay members", and separately confirmed that during it they are "expired now, but they can rejoin without re-applying." Those pull in different directions on one point: whether the person is a member during the window.

    This decision resolves it as: not a member during the window, but the record shows no gap once they pay. The alternative reading — genuinely continuing as a member through the window — would mean a lapse is not detectable until the window closes, and would put a third state into every permission check. If the organization would rather have the softer version, it is a change to membership.renewal_grace_days and the renewal rule, not a rewrite.

    See: ../domain/05-membership-lifecycle.md.

    D-049 — The root may not read into its sub-units; scope_exposure is the only crossing¶

    Status: decided (from your answer) Date: refinement round 4

    Superseded by D-097. The crossing is gone because both of its sides are gone.     D-050 — A renewal inside the window extends the existing root participation row¶

    Status: decided (from your answer) Date: refinement round 4

    Superseded by D-097 and D-098: there is no participation row, so a renewal extends nothing but the membership. The renewal-window semantics D-040 defined are untouched.

    Resolves: D-7

    Decision. When a membership lapses on 1 January and the person pays inside the window, the new membership period is backdated to the expiry date (D-040) and the root-unit participation row is extended to cover the same span. It is not closed and reopened.

    Mechanically, the sweep does not close the root row: it moves valid_to forward to 1 January, and the renewal clears it back to NULL (or sets the new period end), so the row tracks the membership across the boundary without ever being two rows.

    Why. Your answer: "Extend the existing row." The alternative — close at the expiry date, open a new backdated row — is more literal about what happened, but it makes the renewal path diverge from the initial-creation path, and it produces two rows per person per year for the one row the schema most wants to be simple.

    The honest cost, recorded rather than hidden. Extending erases the evidence that a lapse occurred: a person who lapsed and renewed looks, in unit_participation, exactly like a person who never lapsed. The gap exists only if you go and look at the membership rows. This is accepted deliberately, because:

    1. membership remains the authority on payment, and the lapse is fully visible there — the two rows disagree about nothing, they simply answer different questions.
    2. The participation table is a roster history ("who was in this unit when"), not a payment history. Erasing a gap in the roster is the correct thing to do: the child was in the pack across that period, and the question the table exists to answer has one answer, not two.

    Consequence for the participation overlap constraint. ex_unit_participation_no_overlap (03-membership.md §5) is what makes the close-and-reopen alternative awkward, and extending avoids the constraint entirely. The integrity check that verifies the root row mirrors the membership (03-membership.md §7, check 1b) remains valid and unchanged: after a renewal the two agree, and during a lapse-only period — before any payment — the membership has ended while the root row has not yet been swept, which is why the sweep must run and must run before anything reads the roster for authority.

    D-051 — The membership gate is waived by a permission, not only by a role flag¶

    Status: decided (from your answer) Date: refinement round 4

    Reversed entirely by D-100. D-100 moves the gate into the audience expression, and this entry's system.gate_exempt is deleted together with the lockout hazard it documented. The diagnosis that produced it — a membership check performed inside can() is a lockout nobody can see — is still the reason the round kept every one of these tests out of the resolver.

    Resolves: D-6

    Decision. A new permission, system.gate_exempt, waives the membership gate (D-039) for anyone who holds it. It is delivered the way every other permission is: by being placed in a role, which is then assigned to a person at the root or at a unit.

    • It is a system-namespace permission, so it can only arrive through a role_assignment — never through an access_grant. An item-level grant must not be able to lift the gate.
    • It is exempt from the gate itself. Holding it does not depend on membership, or it could not do its job.
    • It is scope-independent: a person who holds it anywhere is waived everywhere. This is what makes it "system-wide" — the gate is a property of the person's membership, so the waiver has to be too.

    Why. Your answer: "Let's create a system-wide permission, that means that their permissions do not end if their membership lapses... The system.gate_exempt is one of the permissions that can be assigned to the permission groups."

    This replaces the earlier framing, in which role.requires_membership was the only switch and the question was therefore which roles to exempt. It is a better fit for the model as it actually works: every organizational role is a permission group, a person may hold several at once (a leader may also hold a role carrying system_admin; a counselor may hold a role carrying event creation and person.view), and a role may be assigned at the root or at a unit. A flag on the role answers "is this role membership-dependent?"; a permission answers "is this person exempt?", which is the question the exemption actually is.

    role.requires_membership stays. It is not superseded — the two compose, and they answer different questions:

    Question Granularity Effect
    role.requires_membership = false Is this role membership-dependent? the role the role grants regardless of membership
    system.gate_exempt Is this person exempt? the person every gated role they hold is honoured

    A role flag is the blunt form: it exempts everyone who holds that role, everywhere. The permission is the precise form: it exempts named people, and can be granted and revoked as an act of its own. The resolver honours a role if either applies.

    Who holds it. system_admin — without it, the 1 January sweep lapses every membership including the administrator's, and the person who would repair the system loses the ability to use it on the day it breaks. That is a lockout, not a policy. Beyond system_admin, which roles carry it is settled in the role review (F-1) — the mechanism is fixed here, the membership of the list is data.

    The evaluation must not go through can(). Reading the permission through the resolver would be circular: can() would have to evaluate the gate in order to learn whether the gate applies, and a lapsed holder of system.gate_exempt would be denied it by the very rule it exists to lift — an unbreakable lockout with no error message. The resolver therefore checks for the permission by direct lookup against live role assignments, outside its own gate condition. This is the one place the resolver reads the role tables without consulting itself, and it is deliberate.

    Consequence. Integrity reports gain a row: who currently holds an exemption, and under which assignment. It is a small list of people who keep authority without paying, and it should be as visible as the system.admin holders already are.

    See: ../data-model/05-authorization.md §3, ../data-model/05 §12, ../appendix/permission-catalog.md §11.

    D-053 — A role is valid always; only its assignment is temporal¶

    Status: decided (from your answer) Date: refinement round 4 Amends: D-052

    Decision. role has no valid_from / valid_to. A role is valid all the time, for as long as the row exists. The only period in the picture is role_assignment.valid_from / valid_to — who held it, and from when to when.

    Why. Your answer: "The roles should be valid all the time, but their assignment to people shouldn't."

    D-052 had just given role a period, on the reasoning that retiring a role is a neat way to abolish one in a single act. That was wrong, and the reason is worth recording because it is not obvious until you push on it: a role is a definition, and a definition does not come into and out of force. "What did unit_leader grant?" has one answer, and it is the same answer for every date. What varies is who held it, which is what role_assignment records.

    The proposed retirement also creates a question with no good answer. If a role has a period and an assignment does not, then an assignment from 2019 rests on a role that is "not in force" — so was that person a leader in 2019? The honest answers are either "yes, and the role's period is irrelevant" (in which case the role's period never did anything) or "who knows" (in which case the design has damaged its own history). Making the role permanently valid avoids the question entirely.

    What this removes. The whole retirement mechanism D-052 introduced:

    Removed Replaced by
    role.valid_from, role.valid_to, ck_role_period, ix_role_current nothing — the columns are gone
    role.retire permission role.unassign, per assignment. A role nobody holds is unused, not retired
    The resolver's check on the role's period (channel 4) nothing. Channel 4 already checks the assignment's period, which was always the load-bearing one
    uq_role_code_current (partial unique, so retired codes could be reused) code TEXT NOT NULL UNIQUE — plain, because codes are never in competition
    Integrity check 17 (roles expiring while held) Reformulated as check 17 (unused roles) — a glance, not a warning

    What this keeps from D-052. Roles are still runtime data: created, edited, assigned and — if never assigned — deleted. is_system still guard-rails deletion. role and role_permission are still audited, because role.edit still changes effective permissions for every holder at once. The BEFORE DELETE trigger stays.

    The consequence worth carrying forward. Because a role never expires, the only thing that ends authority is the assignment ending. That puts the entire weight on role_assignment.valid_to, which is exactly where the design already wanted it — and it is why the open-ended assignment is called the classic access failure (data-model/05 §4). A role-based permission now has no expiry of its own; it is the assignment or nothing.

    D-056 — The legacy import expects a large corpus with legacy member numbers¶

    Status: decided (from your answer) Date: refinement round 4

    Decision. The import is designed for a substantial historical corpus — thousands of records, not hundreds — and the old records carry a legacy member number. That number is imported into person_identifier with scheme = 'legacy' (data-model/01 §7).

    Why. Your answer: "Large, with legacy member numbers."

    This is the favourable case for D-004, and it materially changes what the import has to be:

    If there were no numbers With legacy numbers
    Matching Name + birth date + address, probabilistic, review-heavy Exact key when the number is present; heuristics only for backfilling it
    Review burden Every match needs a human (D-004 assumed this) Only the unmatched remainder does
    Confidence "Probably the same person" "Same number, same person"

    The consequence for the review design. D-004's "no automatic merging, ever" was costed on the assumption that review was the bottleneck and the corpus was small enough to review by hand.     Status: decided (from your answer) Date: refinement round 5

    Why. Your answer, which is the right instinct: "Isn't the draft solved by not giving anyone else permissions, but the organizer?" It is, and it is better than a status enum for a reason worth stating:

    A status column and a permission system that both claim to answer "who may see this?" will eventually disagree — and the one that gets enforced is whoever wrote the last IF.

    With no status column there is nothing to disagree. The questions a draft flag would answer are all answered by grants:

    Question Answer
    "Is this ready to be seen?" Has anyone been granted view?
    "Who can see it before it is announced?" Its organizers, and anyone already granted
    "How do I hide it again?" Revoke the grant — revoked_at set, the row kept

    D-068 — There are no per-resource admin permissions; roles are the bundle¶

    Status: decided (from your answer) — reverses D-007 Date: refinement round 5

    Your answer. Asked whether person.admin should subsume person.merge and person.redact — the standing case against prefix subsumption, since both are irreversible and both are privacy incidents if granted wrongly — you answered: "Only the system should have admin permissions, not the individual items."

    The phrase needed disambiguating, because "individual items" names two different things in this schema: the per-resource permission (person.admin, over the whole resource) and the item-scoped grant (access_grant over one event). You confirmed the first reading.

    Decision. The sixteen <resource>.admin permission codes are deleted — the ten documented ones (person.admin, account.admin, membership.admin, unit_participation.admin, org_unit.admin, position.admin, guardianship.admin, audit.admin, event.admin, audience.admin) and the six sitting in deferred namespaces (document, fee, payment, report, consent, message). So is the resolver's prefix-match branch. What remains:

    • system.admin is the only permission in the system that means everything, and it is reached only through a role assignment (system namespace — never an item grant, never guardianship). Unchanged.
    • "Someone who can do everything about events" is a role the organization composes, bundling the thirteen event.* codes. Not a permission the code invents for them.
    • access_level.admin (rank 40) is untouched. This is a different thing that shares a name, and the collision is the most likely place for a later reader to go wrong. The level answers "how much authority does this grant carry" — view < contribute < manage < admin, used by permission_level to decide whether a contribute-level grant satisfies event.register_self. The permission code answered "does this capability imply that one". The ladder survives; only the wildcard code dies.

    Why this is coherent with the rest of the design rather than an exception to it. D-052 already settled that roles are runtime data and the seed set is not a specification — the organization composes permission groups at runtime. A per-resource admin code is the code composing a permission group on the organization's behalf, in advance, for a bundle nobody asked for. Deleting it makes the two mechanisms agree: the code implements capabilities, the organization groups them. It is the same division D-055 drew when it refused to prune the catalog — a large menu of narrow things, composed by whoever needs them.

    The cost is real, and it is the cost D-007 existed to prevent. Stated in D-007's own words: without the wildcard, every new narrow permission requires updating every role that should already have implied it — and someone will miss one, producing a permission that silently is not granted. That failure mode is back. It is accepted because it fails closed: someone cannot do a thing they were arguably meant to be able to do, and they say so, rather than doing a thing nobody meant them to be able to do. D-007 traded a loud inconvenience for a quiet hazard. The reversal takes the opposite side of the same trade.

    What replaces the protection — since the wildcard is gone, reachability needs a check of its own. Integrity check 18 lists permissions that no role grants, which is the query that surfaces a permission silently orphaned by the absence of a wildcard (numbering follows the existing list in ../data-model/05 §11. It was written as an executable query, and this is it as decided:

    -- 18. ORPHANED PERMISSIONS — granted by no role at all. With no .admin wildcard
--     (D-068), a new permission nobody bundles is silently unusable. This report is
--     the safety net the wildcard used to be.
SELECT p.code, p.resource
  FROM permission p
 WHERE p.is_assignable
   AND NOT EXISTS (SELECT 1 FROM role_permission rp WHERE rp.permission_id = p.id)
 ORDER BY p.resource, p.code;

    The requirement now: every assignable permission that no role bundles is reported, which is the net the .admin wildcard used to be; the check is item 18 of 05-authorization §11, and like the other eighteen it is now something to be verified rather than something that runs.

    What happens to the F-4 question that prompted this. It does not dissolve — it moves, and becomes visible. A role bundling all eleven person.* permissions still reaches person.merge and person.redact, because those are ordinary codes in the bundle. The difference is where the decision lives: previously a resolver rule made the implication, invisible in every role editor and true for every resource whether or not anyone wanted it. Now the implication appears as the contents of a role the organization wrote, reviewable line by line in role_permission, dated, and alarmable. role.edit on that role is already audited for exactly this reason (D-052). The guidance therefore moves from the schema to the seed: a role bundling a resource including its irreversible codes should be named for what it is, and the seed roles in §11 are written so that no seeded role mixes person.merge/person.redact with routine person.edit. That is now expressible as a report rather than a caveat.

    Two survivors, and why neither is an exception. Both look like wildcards and neither is the thing being deleted:

    • dependent.admin stays. It is not a prefix-match artefact — it is a code a staff member chooses and stores, one row in guardianship_permission, granting the full set for one child. A wildcard that must be deliberately written is what this decision endorses, not what it removes. It also has a property no role wildcard can have: an explicit is_granted = false row overrides it, so a court-ordered restriction survives a broad grant. Deleting dependent.admin would make the common restriction easier to express, not harder — listing nineteen narrow rows per child where a court case needs two. The distinction to keep: person.admin implied capabilities nobody wrote down; dependent.admin is a shorthand for capabilities somebody did write down, in a specific row, about a specific child.
    • system.admin stays, for the reasons already in §7 — it is the break-glass capability, concentrating the most dangerous thing in one alarmable holder rather than scattering equivalents. It was never a prefix-match beneficiary; it is checked outright.

    A third thing called "admin", which also stays. dependent.profile.admin, dependent.medical.admin, dependent.consent.admin are not wildcards at all — they are actions meaning "edit" inside a sub-resource, paired against .view. Nothing is implied by them. Three unrelated meanings now share one word in this schema — the access level (rank 40), the deleted resource wildcard, and an edit action — and any of the three may be what a reader means. When one of them comes up in conversation, say which.

    Migration. Deleting role_permission rows for the sixteen codes; no other data moves. Any role that held only person.admin becomes an empty role, which is correct and visible rather than quietly over-privileged — and role.delete still refuses to remove a role that was ever assigned (D-052), so the empty shell survives as evidence of what someone once meant. Re-deriving it means naming the bundle, which is the point.

    Two-way door? No. Re-adding a wildcard later is mechanically cheap and semantically loud — it re-creates the implication silently for resources added after the day you added it. Treat it as a fresh decision, not a revert.

    D-069 — Guardianship ends when a person ends it; the system takes no position on majority¶

    Status: decided (from your answer) — reverses D-024 Date: refinement round 5

    Your answer. Asked what the system does when a guarded child turns 18 — review queue, auto-expire, or nothing — you answered "Nothing at all."

    Decision. No job, no review queue, no computed candidate date, no flag. A guardianship row is ended by a person ending it (guardianship.end), or by import, and the system does not notice birthdays in this connection at all.

    Why this is better than the queue D-024 proposed, and where D-024 went wrong. D-024 reasoned from "fail open rather than silently strip access" and picked the gentler of two automatic behaviours. Both were automatic. The queue was not a refusal to act; it was a deferral of the action, and it smuggled in a claim the system cannot support: that majority is a date the system knows. It is not. D-024's own rationale said thresholds vary by jurisdiction — and then computed a date anyway. A review queue is not a neutral container for a wrong date; it is a worklist of cases staff are told to decide, and the item on it asserts something the organization has not decided.

    The deeper problem with the queue: it inverts who decides. Under D-024 the system raises the question at 18 whether or not anyone wanted it asked, in every case, for every family — including the ones where the adult child asks their parent to keep handling their medical correspondence. The queue's default is that the arrangement is suspect. That is the wrong default for a relationship the organization did not create.

    What "nothing" costs, stated honestly. Nothing is tracked, so "who is still listed as my guardian, and since when?" has no automatic answer. It has a manual one: guardianship carries valid_from/valid_to, so the question is a query on a person's rows and the answer includes the date each was ended. What is lost is a prompt, not a record — which is the same trade the module makes everywhere. See the pattern below.

    This is the latest in a consistent line of refusals, and the reasoning is identical each time. Across five rounds the design has allowed itself exactly two automatic transitions — the yearly fee sweep (D-040) and the event waitlist release (D-066) — and has refused, among others, automatic membership lapse states (D-023), event status (D-064), and recurrence (D-058). Guardianship expiry is the next one refused. The pattern: an automatic transition is cheap to design and expensive to defend, because it acts on every case including the ones it was not designed for. A nightly job that ends guardianships at 18 fails closed and strips a legally valid arrangement overnight; a queue fails open and adds a standing assertion the org never made. The third option — a person who knows the family ends the row — is the only one that can also decide not to.

    Consequence to carry: nothing here weakens the exit path, so the exit path must exist. With no automatic end, guardianship.end is the only door, and it must be reachable by someone. Two things follow, both worth stating because they are now load-bearing in a way they were not when a job existed to help:

    1. The adult child must be able to end it about themselves. They are the subject of the row and currently hold no permission over it — they are not a guardian of themselves. This needs a route, and it is now the module's sharpest open item.
    2. A stale row is invisible by design, so the query, not the job, is the control. A periodic human review is a good idea and is explicitly not a scheduled system behaviour.

    Follow-up raised: E-2 is closed and replaced by E-5 — "how does an adult end a guardianship over themselves?" That question existed before this decision and was masked by a review queue that would have surfaced it. It is now unavoidable.

    D-071 — Nothing forces a role assignment to end; the gate and the report are the control¶

    Status: decided (from your answer) — overrides the recommendation in F-3 Date: refinement round 5

    Your answer. Asked whether valid_to should be mandatory on high-authority role assignments — the classic volunteer who was never removed — you answered "Nothing — rely on the gate."

    The docs had recommended the other way. F-3 said yes, at the application layer, and argued the membership gate made an open-ended assignment more dangerous, not less. You disagree, and the disagreement is worth recording because the recommendation was not obviously wrong.

    Decision. role_assignment.valid_to stays nullable with no application-layer requirement and no per-role policy. The controls are the membership gate (D-039) and a report. No new constraint anywhere.

    Why the recommendation was wrong, in one place. F-3 said the gate makes open-ended assignments more dangerous. It is the other way round: the gate already does what an expiry date would do, for exactly the population an expiry date would target, and it does it without inventing a date nobody chose. A forced valid_to is an guess about when authority should lapse, written by whoever made the assignment — usually inherited from a form default. The gate instead ties expiry to a fact the organization already maintains and renews on purpose: whether this person is a member. When the fee lapses, gated roles stop granting. The expiry date was always going to be a worse approximation of that.

    What the gate does not cover — the honest residue. unit_leader and assistant_leader have requires_membership = false by explicit decision (a volunteer whose own fee lapses still runs the Thursday meeting), so a lapsed leader keeps leading. Also any role held by a non-member, and anything carrying system.gate_exempt. For those, the answer is a periodic human review over open-ended assignments, and D-068 now makes that query sharper, since a role's full reach is visible in role_permission with no wildcard hiding implications in the resolver.

    • the resolver's channels and their order (D-010)
    • three-valued was_present, where NULL means "no register was taken" and not "absent" (D-067)
    • birth_date_precision, because an imported 1990-01-01 often means year 1990
    • tombstone and redaction both survive on person, with the two partial indexes that exist because every ordinary listing excludes both

    D-073 — Guardianship is administered by its own parties, not by staff¶

    Status: decided (from your answer) — closes E-5 Date: refinement round 6

    Your answer. "The guardian has the same rights as the user, so they can modify their own guardians as well as the guardians with the write permissions. There is no need to take this through the management team." and, when asked how far that reaches, "Guardian can be assigned by other guardian."

    Decision. The parties to a guardianship are principals on that row, not third parties holding a grant on it. A guardian may end the arrangement, may add another guardian to the same child, and may change the permission level of the row they are a party to. The adult who is the subject of a guardianship may end it over themselves. None of these routes through staff. A staff member remains a way for it to happen and is never the way.

    This is the founding principle, applied one level down. The rule this system was built on is that authority over a nested thing originates at that thing and cannot be claimed from outside it; the organization itself may not decide permissions over a sub-unit, and only the system administrator is exempt. D-031 applied that to units. A guardianship is a nested thing, and its "unit" is the people in it. A staff role reaching in to decide who is responsible for a child is exactly the move the authorization model refuses everywhere else.

    E-5 closes, and it closes differently from every option on offer. E-5 asked how an adult ends a guardianship over themselves and offered three shapes — support request, ownership channel, request object — all of which assumed the answer must come from somewhere other than the people involved. It does not. Note also that the answer is not the ownership channel: ownership is your own record, and a guardianship row is not the subject's record any more than it is the guardian's. It is a record of a relationship between them, and both parties hold it.

    Mechanically this is a direction, not a fifth channel. The resolver has four channels and D-010 keeps them at four. The guardianship channel already asks "may guardian G act on D's records?"; D-073 gives it a second question, "may a party act on the guardianship row itself?", answered for exactly three acts — end the row, add another guardian, change the permission level. Adding a channel would have been the same capability at the price of touching every document that enumerates them, and enumeration is how the order stays a rule.

    Read D-069 and D-073 as one decision in two halves. D-069 refused to let a birthday end a guardianship and deleted the review queue, on the grounds that a person decides. It left the question of which person, using what open — the exit it assumed had no door. D-073 is the door. Without it D-069 was a refusal with no alternative; with it the pair says something quite coherent: a legal relationship between two people ends when one of those people says so, and the organization's job is to be told, not to permit it.

    The asymmetry, stated plainly, because it is real. A guardian may appoint a guardian. So anyone with authority over a child can give a second person that same authority with no approval from the organization — the ordinary case being a mother adding the father, and the case that is not being everything else. The design accepts this and holds one line instead: the act is attributed. Who added whom, when, from which account, is audited, and the other party is notified. That is a deterrent and an evidence trail, not a prevention.

    Not decided: whether adding a guardian over a minor should notify anyone at the organization beyond the audit log, and whether a subject may refuse a guardian appointed over them. See E-6.

    D-074 — A guardian's rights are none, view, or write. Nothing more granular¶

    Status: decided (from your answer) — supersedes the mechanism of D-020; deletes dependent.* Date: refinement round 6

    Your answer. "Guardian rights should be only 'none', 'view', or 'write', nothing more granular."

    The docs had it the other way round, deliberately. guardianship_permission was a table of per-capability grants — dependent.profile.view, dependent.medical.admin, dependent.consent.admin, dependent.event.register, dependent.fee.pay — and the glossary asserted "Being a guardian grants nothing by itself. Every capability is a separate, revocable, audited row." That was drawn as a consequence of the standing instruction that both read and write permissions be explicit. It went further than that instruction said: explicit and granular are not the same property. Explicit means nothing is implied by identity. That is fully preserved here — a guardianship row with level none grants nothing at all.

    Decision. One value per guardianship row, from exactly three: none, view, write. Not a capability list. A guardian either cannot see the child's records, can see them, or can change them.

    It is the same ladder, not a new one — which is the part that keeps the model honest. The design already ranks authority as revoked(0) < view(10) < contribute(20) < manage(30) < admin(40) and compares by integer, never by string (D-012). The three guardian rights map onto it: none → 0, view → 10, write → 20. Guardian authority is therefore a range of an existing ladder, not a parallel enum, and the resolver compares it with the machinery it already uses for grants. A fourth guardian value would have been the beginning of a second authorization model.

    Amended by D-099, which deleted the ladder this paragraph leans on. The three values and everything they mean stand — the decision was never the numbers — but there is no rank left to map onto. The comparison now runs against a column on the permission: permission.right_kind ∈ read | write, where none covers nothing, view covers the codes marked read, and write covers both (data-model/05-authorization.md §1). That column has exactly one customer, and this entry is who it was added for. The paragraph's real work was never the shared arithmetic: a guardian not being staff is carried by the channel's shape test (D-079) — a check that is not about this child never reaches the guardianship channel, whatever its right level. And the closing warning survives intact, only cheaper to honour: a fourth value would still be the start of a second authorization model, and three values against two kinds is a lookup rather than a scale to keep in step.

    What this deletes. Every dependent.* permission code, including dependent.admin and the three sub-resource .admin codes that D-068 deliberately exempted. The consequence is worth noticing: after D-068 deleted admin as a wildcard and D-074 deletes it as an action, the only things in the entire system still spelled admin are access_level.admin (a rank) and system.admin (the one wildcard permission). The word is no longer ambiguous three ways; it is ambiguous two ways, and the third is recorded as deleted.

    And since D-099 deleted the ladder, it is ambiguous one way. access_level.admin was a rank in a table that no longer exists; system.admin is now the only live permission code in the system whose last segment is not an action, and it is allowed to be one for the two reasons D-104 records: its meaning is defined by the resolver rather than read off the name, and D-068 exempted it explicitly rather than by silence.

    What it gives up, written down rather than discovered later. It is no longer expressible that this guardian may register the child for events but may not read the medical record, or that a grandmother may see the roster but nothing else. Under D-074 she either can see everything about her grandchild or nothing. The rescue is that write is not manage: a guardian at write still cannot do organization-wide things, cannot see a different dependent's records, and cannot reach beyond the records the dependent's own record contains. If the split turns out to be needed in real operation it is a new decision (E-7), and it should not be reintroduced as a permission nobody argued for.

    D-046 survives, simplified. Defaults still differ by how the guardianship came into being — a parent recorded at creation starts at write; a court-appointed guardian and a grandmother-added emergency contact start elsewhere. What differs is now one value instead of a set.

    D-075 — Money arrives from a bank API; a payment is requested by variable symbol and QR code¶

    Status: decided (from your answer) — closes finance questions 3, 5 and 6 Date: refinement round 6

    Your answer. "Collection via gateway is the closest. It will be collected from the bank API and payments will be requested through variable symbol + a QR code."

    This is not the gateway the finance document was braced for. Its question 6 anticipated a card gateway and listed what that drags in: checkout, webhooks, disputes, chargebacks, reconciliation, PCI. What you describe is the bank-account model, and it is a different animal: nobody pays by card through this system. The system issues a payment request carrying a variable symbol; the payer is shown that symbol and a QR code containing it; their own bank moves the money; the bank API reports the incoming transfer with the symbol still attached. The system never touches the payment — it reads a statement.

    Four consequences, in descending order of how much they change the schema.

    1. The variable symbol is the design, so it must be unique forever. It is the only correlation key between "we expect money for this membership" and "money arrived at this account", which makes the payment request — not the payment — the entity the finance module is built around. Uniqueness is not per year, not per membership, not per unit: a symbol issued in 2019 must never resolve to a 2026 obligation, because bank statements are replayed and late payments are the entire reason the renewal window exists.
    2. A symbol is a sequence, never a derivation. Anyone can type eleven digits into a payment form. A symbol derived from a birth date, a membership id or a member number is guessable, and guessing one redirects a stranger's money into a child's financial record — a wrong fee balance, a membership that appears paid, a child recorded as covered who is not. Unguessable is not a privacy preference here; it is the integrity of the ledger.
    3. There are no reversals, so there is almost no status column. Bank transfers do not bounce, are not disputed by the payer's bank and do not expire. payment.status needs nothing resembling pending, failed, declined or disputed. A refund is a second payment in the opposite direction, not a transition of the first. The status enum that question 3 asked about collapses, and refunds — a policy question with no answer for six rounds — mostly answer themselves.
    4. A QR code is a rendering, not data. It encodes the symbol, amount and recipient that already exist. No stored image, no re-generation job, nothing to invalidate.

    The consequence for D-040 is the one that matters operationally. The renewal window opens a new membership period at the expiry date when payment lands inside the window, and D-040's own note said the reliability of that rule depended on payment dates arriving reliably. Until now they arrived when somebody noticed a transfer. They now arrive from the bank. The backdating rule stops being a promise about someone's February and becomes a property of the import.

    What is not decided, and is now the interesting part of the module. Whether event fees get a symbol as well as membership fees; whether a symbol is issued per person, per membership period, or per individual liability (a camp is a separate payable from a fee); and what the amount mismatch means when a payer enters 500 for a 550 request. See F-10.

    See: ../data-model/07-finance.md, D-040.

    D-076 — Money that cannot be matched waits for a person¶

    Status: decided (from your answer) — closes EV-3 and finance question 1's sibling Date: refinement round 6

    Decision. A bank transfer that resolves to no live payment request — unknown symbol, the symbol of a cancelled event, an already-satisfied request, an amount that does not match, more than the request asked for — is recorded as an incoming transaction and enters a queue. The system neither applies it nor returns it.

    The queue's outcomes, all chosen by a human: attach it to a different request; split it across several; record it as a donation with no obligation behind it; or refund it by hand.

    Why not auto-apply by payer identity, which is the tempting answer. Because the case it gets wrong is not the edge case. A parent with two children pays one amount against one symbol is the ordinary shape of family payment in a youth organization, and an identity-based fallback resolves it to whichever child the query reaches first. A fee recorded against the wrong child is simultaneously a finance error, a membership that appears paid when it is not, and — where the fee buys insurance — a coverage record that is untrue. The fallback would be wrong on the common path, which is the one place a fallback is never allowed to be wrong.

    Why not auto-refund. It requires the bank integration to work outbound as well as inbound — a second integration, with its own authorization. And it returns the grandparent's attempt at a camp contribution.

    Where most of the queue's volume will actually come from: cancellation. D-064 made cancellation a recorded fact rather than a state, which means the event survives, the registrations survive, and so does an outstanding payment request against an occasion that is not going to happen. So: cancelling voids the outstanding requests, and money that had already arrived becomes a queue item for a person to refund or carry forward. This is EV-3's answer, which is why EV-3 is closed rather than deferred to finance.

    The pattern, third occurrence. Across six rounds the design has permitted exactly two automatic state changes — the fee sweep (D-040) and the waitlist release (D-066) — and refused every other offer to act on a person's behalf. D-076 is the third refusal, and the first in the opposite direction: the earlier two released a person from something they owed; this one declines to release money from the person it belongs to. Unmatched money is a fact with no subject, and per D-059's discipline the absence gets stored rather than inferred.

    D-077 — Messaging is direct by default, broadcast is an ordinary scoped permission, and the recipient chooses the channel¶

    Status: decided (from your answer) — first decision of the communication module (amended by D-082, which supplied the thing this entry declined and left unprovided: a rule for the private message to a child)

    Date: refinement round 6

    Your answer. "There will be internal messaging through the system. Personnel with 'broadcast' permissions are able to send messages to everyone, other users only to direct persons. The messages get then directed to email, push notifications or IM depending on the user's choices." — and, asked about the unit leader left out by that split, you chose a scoped permission.

    Three decisions in one sentence, and the first is structural.

    1. The system is the medium; email, push and IM are delivery. A message is written once, internally, and then distributed. This is the load-bearing choice, because the alternative — the system as a mail relay — has no record of what anyone was told.
    2. Two sender tiers. Everyone may write direct messages. Broadcast is a permission.
    3. The recipient chooses the channel. The sender chooses who; the recipient chooses how it reaches them.

    Therefore: one message, one recipient row each, and the medium resolved at delivery. A message plus a message_recipient per addressee carrying read state; the channel is selected per recipient against their own contact points. A bounced email is a failed delivery on one channel, not a lost message. person_contact.purpose gains a messaging purpose and each contact point carries its own opt-in, which is the existing contact-point model doing work rather than a new subsystem beside it.

    broadcast is granted at a scope, which is the whole authorization model speaking again. Granted organization-wide it reaches everyone; granted on a unit it reaches that unit's people. No new mechanism — role assignments already carry a scope. A single global broadcast flag would have made a pack leader announcing a 9 a.m. start either the holder of an organization-wide power or the author of twelve identical messages, and the first of those is precisely the arrangement every other part of this design exists to prevent. Note that this lands on scope authority rather than on audiences: who may address a set is authority over that set, and authority over a set originates inside it.

    Age is not a sender concept, and that is a decision, not an omission. The question asked whether staff may address a child directly or only their guardians; the answer replaced it with a sender-tier model that has no age in it. Consistent with D-070, there is no age branch in the resolver. The residue is stated rather than hidden: any account in the system may send a direct message to any other account, including a child's. The rule the communication section had promised — "a rule against contacting minors directly" — is not implemented as a restriction on senders. See MSG-1 for the recommendation, which is to restrict visibility rather than permission: direct messages reaching a minor mirrored to their guardians, so nothing is blocked, nothing is secretly unread, and the resolver still has no age branch.

    Two-way door? The delivery half yes — adding a channel is a new contact purpose. The sender tiers no: once people can message each other, retracting that is a feature removal, and any later safeguarding rule has to be written as surveillance over a channel that already exists.

    D-078 — An exposure extends an assignment, never a direct grant¶

    Status: decided — found by deleting the SQL, not by running it Date: refinement round 6

    Superseded by D-097 with the exposure table itself. Its distinction, that widening an inherited reach is a different act from writing a grant, has no subject after D-099: a grant has exactly one shape, and there is nothing to extend it.

    What happened. Translating the resolver out of SQL for D-072 meant reading each branch for what it decides rather than what it says. The unit-grant tier had two branches, and the second one consulted scope_exposure. It joined the direct grant to se.org_unit_id while also requiring se.org_unit_id = the unit being checked. Both conditions pin the grant to the checked unit — which the first branch had already tested. The branch could never succeed where the first one failed.

    It was not a vulnerability. A branch that can only ever return true where another branch already returned true grants nothing. The damage is to the reader: a tier that appears to widen direct grants through exposures is a tier that will be trusted, reviewed and extended on that basis. It survived every review of the SQL precisely because it reads correctly.

    The rule, now stated. scope_exposure.role_assignment_id points at a specific person's assignment. The unit is agreeing that this person, in this role, for this period may act here — which is what makes the exposure legible as an act of the unit rather than a grant to a whoever-holds. A direct access_grant contains no assignment for an exposure to attach to, and a grant already at the checked unit needs no extension to work there. So the role channel is the table's only consumer, and the unit-grant tier matches exactly.

    Why the tempting repair must be refused. "Exposures don't extend my direct grant — that looks like an oversight, let's add it back" produces a system where a unit that exposed a treasurer role assignment has also, silently, exposed itself to every direct grant held by every person who happens to hold some other assignment there. The repair would widen an exposure to cover people the exposing unit never approved, in the one direction the founding principle forbids. Anyone reaching for it should read this entry first, which is why it is a decision and not a comment.

    What this says about D-072's trade. The deleted SQL contained a bug and the prose cannot contain it, because the prose does not have a dead branch. This is the one case where removing the schema was an unambiguous improvement, and it is worth recording beside the cases where the removal cost something real.

    Two-way door? No, in the sense that matters: adding a second route back is a widening. In every other sense yes — nothing here constrains a future mechanism that names a grant in an exposure row deliberately, which would need a new column and a new argument.

    D-079 — The guardianship channel is entered by shape, not by permission name¶

    Status: decided — consequence of D-074 Date: refinement round 6

    Before. The resolver picked a channel by string: a permission code beginning dependent. went down the guardianship channel, everything else went down the ordinary path. This was elegant, and it had a hole nobody noticed while it was true.

    The hole. A parent correcting their child's address is performing person.address.edit. That code has no dependent. prefix — it is the same code a person uses to correct their own address. So the act did not route through guardianship at all. It resolved against the parent's own roles and item grants, which say nothing about this child, and the answer was deny — correct by accident, for a reason that had nothing to do with the relationship that made the act legitimate. Any future person.* act a guardian needed would have inherited the same dead end, and the fix each time would have been a new dependent.* code, which is how the namespace grew to eighteen.

    Now: the channel is entered when the subject of the act is not the actor. The resolver is already handed both — the actor, and the owner of the thing being touched. Compare them; if they are different people, ask the guardianship question. That question may answer only "yes". If the answer is yes the check is finished and the act is allowed; in every other case the channel falls silent and the resolver carries on to the actor's own roles and grants. It is not the last word, and the paragraph below explains why that had to change as well — the first draft of this decision kept the old finality, and the two halves are inconsistent within one page, which is itself instructive about how a rule outlives the reason it had.

    Three things this buys. (a) Nothing escapes by naming: a permission added next year for a field a guardian must edit is covered the day the field exists, because dispatch reads the shape of the request rather than a list maintained beside it. (b) It is one comparison instead of a prefix match against a namespace that has to be kept in step with the catalog by hand. (c) The rule is stated in the resolver, where a reader looking for "how does a guardian get authority" will find it, rather than in a column's comment.

    What it costs. Dispatch is now invisible in the data. Under the prefix rule you could look at a permission code and know which channel would answer for it; now you have to know whether the check is being made about somebody else, which is a property of the call site, not of the permission. This is the price of every shape-based rule and it is worth paying here: the alternative was a rule that was legible and wrong. The audit side of it is unchanged — an act performed on behalf of a minor is recorded as such regardless of which code was checked (04-relationships §5).

    Where the boundary sits, because subject ≠ actor is far broader than guardianship. A treasurer entering a payment for a child, a leader marking a roster, a registrar correcting a name they imported: all of these are subject≠actor checks, and none of them is a guardian acting on a ward. If the channel answered for all of them, the treasurer would be asked whether they are the child's guardian, told no, and denied an act their role plainly authorises. So the channel speaks only when there is something to ask: a live guardianship row joining this actor to this subject, at this date. No row, no answer, and the resolver falls through to the allow tiers exactly as it always did. There is no age test in that guard, which is deliberate — the guardianship row is the relationship, and adults who file one for themselves (D-073) are covered by the same two words as minors are. An age branch would also contradict D-070 and D-077, both of which insist the resolver has no age in it.

    The consequence is a real weakening of the channel, and it should be read as such. Under the prefix rule the guardianship channel gave the final answer: dependent.medical.view was a guardian-only code, no role held it, so "the guardian's right is view, this is a write" could safely end the check. Now that the channel carries ordinary codes a role might also grant, finality turns into a trap — the parent who is also the event registrar, holding view over their own child, denied the right to do their job. So the guardianship channel now returns allows only: sufficient right → true; insufficient, or none, or no row → silence, and the actor's own roles and grants are still tried. What is not lost:

    • none still grants nothing, which is what D-074 actually promised. It was never a promise to block unrelated authority.
    • A genuine prohibition is still available and still absolute — an explicit deny in channel 0, which runs before everything and does not care about scope. That is where "this person must not touch this child's record" belongs, and it is stronger than what a guardianship level could do.
    • Nothing an actor reaches by falling through is authority the guardianship row was hiding: their role already gave it to them, guardianship row or not.

    What is lost is the ability to say "not even your role". No guardian's view can ever be that sentence again. In a safeguarding system that sentence has to exist, and D-032 already put it in the deny channel rather than distributed across capability levels — so the loss is of a convenient place to write it, not of the mechanism.

    Two-way door? Yes in principle, no in practice — the old dispatch can only be restored by re-inventing the namespace D-074 deleted.

    See: ../data-model/05-authorization.md §10, ../data-model/04-relationships.md §4, ../appendix/permission-catalog.md §9.

    D-081 — Rule names survive the deletion of their mechanisms; a renamed rule must say who enforces it now¶

    Status: decided (editorial ruling, ratified this round) Date: refinement round 6 Follows: D-072, D-080

    What was found. With the DDL gone, roughly sixty sentences still credited a database object with acting: "the trigger in §3 enforces it", "the schema cannot express", "ck_request_rejection_reason requires a reason code", "refused by trigger (§8)". None was false when it was written. Each became a false claim about the present the moment D-072 removed the thing it named, and a reader who trusts the sentence does the one thing this corpus cannot afford — assuming a guarantee exists and not writing it.

    Ruling 1 — the identifiers stay; the agency goes. ck_org_unit_closed, uq_org_unit_single_root, uq_access_grant_live and the rest are kept as names of rules, not as claims about objects:

    Before After
    "ck_org_unit_closed states the invariant explicitly" "A unit cannot be closed without an end date (ck_org_unit_closed is this rule's name)" + which layer carries it
    "the trigger refuses deletion" "Guard 2 is the rule, the no-cascade reference is what refuses it, and event.delete only decides who may ask"

    Deleting the names would be a repository-wide rename touching every cross-reference, and a rule with a stable handle is worth more than a purer vocabulary. The line is agency, not vocabulary: an identifier may survive its table as long as no sentence asks it to do anything.

    Ruling 2 — renaming the mechanism is never the fix. Where a rule loses its enforcement, the sentence must state what is now required and which layer owes it, in the register of data-model/00 §6a. "The trigger guarantees X" and "X is validated in the model" are not adjacent statements; the first is a guarantee on every path and the second is a friendly message on the intended one. Softening one into the other without saying so is how a deleted schema turns into a silently weaker system. Where the honest answer is "no layer enforces this and none can", the text now says that — a convention, not a guard — rather than letting the reader infer it.

    Ruling 3 — a rule that lost both its guard and its report gets a report. Three had neither, which is worse than losing the guard alone, because a missing guard is at least visible to whoever writes the migration:

    Rule Where the guard went Net added
    position.max_holders no constraint can state a count over other rows (F-10 shape 3) 02-organization §9 check 9 — over-limit means bypassed, unlike event capacity, which may be exceeded deliberately
    Registration outside its window Guard 1, inside the writing transaction 08-events §10 check 9 — a row here is evidence about the code, not the data
    fee_obligation, created by the code that places a registration nothing ever enforced it 08-events §10 check 10 — a confirmed place with no bill leaves every row individually correct

    One rule keeps no net, deliberately, with the absence named instead of smoothed over: org_unit.parent_unit_id immutability (D-036). A reparent leaves nothing malformed to count, so it became F-10's fourth shape rather than a check.

    One contradiction of D-080's class, found and settled. §2.1 of data-model/06 said DELETE is outside the audited operations "because nothing in this data model is hard-deleted", while §3's import revert removes the person, membership and unit_participation rows a batch created. Written together they meant a rollback could erase live rows without a trace — the one event someone is most certain to ask about later. Settled in favour of the audit log: a revert writes one audited entry per deleted row, naming the batch, and DELETE stays outside the audited operations only because no other path reaches a business row with a delete.

    The residual that could not be closed. Audit completeness used to be answerable from the database's own catalog — ask which tables carry triggers, compare against the business tables. There is no catalog to ask now: a table is audited because the code writing it remembers to, so the nightly comparison runs between two hand-maintained lists, and both can go stale together and still report zero. The replacement is an assertion over the paths that may write or delete a business row; until that exists this is recorded as a known hole rather than as a solved problem.

    Ruling 4 — the decision log may quote SQL; nothing else may, and a quotation must say where the rule lives now. Five fences survived in this log, and deleting them would be the wrong correction: an entry that says "the exclusion constraint drops membership_type_id" is about that constraint, and rewriting it into prose would quietly revise a record of what was decided in order to keep the vocabulary clean — the same mistake D-080 catalogued, arriving from the opposite direction. So the fences stay, each followed by one italic line naming the requirement as it is now stated, the document that owns it, and the layer that owes it. The header of this log says the same thing once, so that no fence is read as a specification by someone who arrived at it directly. That is the whole distinction: the documentation describes a system; this log records how the description got here, and a record is allowed to quote things it no longer endorses.

    D-082 — A direct message to a minor is mirrored to the minor's guardians¶

    Status: decided (from your answer) — closes MSG-1 Date: refinement round 7 Follows: D-077

    Your answer. Asked which of the two available safeguards you wanted, having been shown that D-077 had declined the sender restriction and left nothing in its place, you chose mirror to guardians.

    The rule. A direct message whose recipient is a minor is delivered also to that minor's guardians, and the sender is told, before sending, that it will be. Nothing is blocked. No permission is involved, and no check in the resolver looks at an age.

    Why this direction and not the other one. The corpus already refused an age branch at check time, for events, in D-070, on the ground that a condition the capability model does not know about is the first rule in a rule engine nobody asked for. Messaging was going to reintroduce exactly that condition by a different door. Mirroring gets the safeguarding property without it: the property nobody was ever arguing for was "an adult cannot reach a child", and the property actually needed was "no private exchange about a child is secretly unread." Those are not the same rule, and only the second one survives contact with a volunteer organization, where a restriction that inconveniences a leader on a Friday evening gets bypassed by Monday — and a routinely-bypassed restriction is worse than none, because it teaches everyone that the rule is decorative.

    Three things "mirror it to the guardians" does not say, settled here rather than in code:

    1. Which guardians — those at view or write. A guardian whose right level is none receives nothing. none is not an oversight; it is the organization having already decided that this party sees nothing about the child, and a safeguarding convenience is not a reason to reverse a recorded decision as a side effect of a message. The consequence is named rather than left to be found: a minor whose guardians are all none is exactly as unwatched as a minor with no guardian row at all, so both are reported together by the existing completeness check in 04-relationships §6. Mirroring must not become a channel through which none quietly stops meaning anything.
    2. Which set, as of when — frozen at send time. The guardianships open at the moment the message is sent are the recipients, recorded into the delivery. A guardianship closed later does not lose its copy; a guardian added later does not acquire old threads. This is the same discipline that makes the audit log answer "what did this role say on that date" rather than "what does it say now" (06-audit §2) — a safeguarding question about a past message has to be answerable against the arrangement that existed then, because the question "did anyone tell the father?" is asked months later, about a family that has since separated.
    3. Broadcast is not mirrored. A scoped broadcast is addressed to a set, recorded, attributable, and not private; mirroring exists precisely for the private case, where "nobody saw this" is a claim nobody can check. Extending it to broadcast would deliver the same content twice to the same guardians and would blur the one distinction the rule depends on.

    What mirroring is explicitly not. Not approval — nobody consents before a message is sent, so the channel stays open and the organization stays out of the middle of ordinary communication. Not delivery confirmation; the mirror inherits the recipient's own channel choice (D-077) and can therefore fail to be read exactly like any other message. And not a record of concern: it is a copy, not a report, and the organization learns of a message only through the ordinary routes.

    The variant rejected, and why it will come back. "Only guardians and unit leaders may message a child." It is the sender rule wearing the visibility rule's clothes: it needs the age branch, it is bypassed the first time it is in the way, and worst of all it tells a child that the adult messaging them has been vetted — a claim the system cannot support, since no background checks are recorded at all (D-043). Recorded here because the proposal is intuitive and will return.

    Impact. One mirroring rule, one notice to the sender, one extended completeness report. No new permission, no resolver branch, no new table. The undesigned module now has a constraint on it before it is designed, which is the point of taking this decision early: a messaging design that ships private delivery to minors with neither restriction nor mirroring would have to be reopened after the fact, when the storage of message bodies and the retention policy are already fixed.

    See: MSG-1, closed, permission-catalog, glossary — Mirroring.

    D-083 — There is no medical record: personal data is one class of data¶

    Status: decided (from your answer) — closes E-7, resolves H-0, retires the health module Date: refinement round 7

    Your answer. "I consider everything apart from name, gender and age a 'medical record'. It is fields in the database, not files. In general, ignore 'court order', guardian has all rights on a child if it's permissions say so. Medical data is not different in any way."

The answer removes the category: there is no privileged subset of the person record, because the whole thing is equally the sensitive thing. Name, gender and age are identity — they are what a person is called and counted as; everything else the system knows is descriptive data of one kind, held in fields, and none of it is a different kind of object from any other.

"Read everything except the diagnoses" was the case the eighteen dependent.* codes were built for; the answer is that the case is not real and the exception is not wanted.     H-0: the medical record is cited by five files and defined by none Resolved by removing the referent, not by building it. Nothing was hiding behind the phrase; the phrase was inherited from deleted permission codes
    "a view guardian already sees them" — the reason the module was deferred It was false (there was nothing to see) and it is now moot: a view guardian sees the person's data, which is the same sentence with a table behind it
    "the medical file, which no event permission reaches" — 08-events' reassurance Corrected, not restated. No file, no reach. See D-085 for who reads what instead

    The court-order case, refused on the merits rather than waved away. The granular model existed for one story: a parent with access to everything about their child except the medical file, by order of a court. That story was the entire justification for a sensitive sub-resource, and it is declined — a guardian's rights are what the guardian's permission says, and no data inside the record changes that. It is worth recording what was traded, because the story is not absurd: the model now cannot express an arrangement a court might order. The trade made is that a system which cannot express it fails visibly — a guardian either has the access or does not, in one place, auditable — whereas a system that can express it has a per-field exception nobody outside a courtroom can configure correctly, and a list of eighteen codes is a list somebody ticks without reading.

    Where protection actually lives now — three places, two of them machinery and the third a sentence somebody has to keep true:

    1. Grants. Whoever holds person.view over that person's scope reads the record. This is why the permission catalog raises person.view rather than inventing a code: a permission that reads everything about a child is not a ⚠, it is in the top tier.
    2. The guardian right level (D-074), applied to the whole record.
    3. The guard on the audit trail (00-conventions §8 item 7) — the trail quotes the whole record, so the permission that opens it is graded accordingly. Erasure reaching it is unchanged and absolute.

    The one thing that must not survive the round: protection keyed by field name. The redactor used to scrub a list of sensitive keys out of logged row images. That list was coherent when there was a sensitive subset; with one class of data it is a list of exceptions to a rule that has no exceptions, and it fails on the first value stored under a column named note — or under a code named allergy, which is worse, because the attribute layer generates such names faster than anybody can list them.

    What replaces it, after one reversal inside this same round. The first answer written down here was that the audit payload therefore carries no descriptive values at all: who changed which code, for whom, when, and that a value existed. That rule is withdrawn, and it was withdrawn by this decision's own logic. Stripping attribute values from the trail while a change of address is logged with its old and new values is a sensitive subset of the person record re-enacted in the logging rules — the privileged corner arriving as a list of table names after it was refused as a list of permission names — and it empties the history that D-085 chose overwrite-in-place in order to have. So the trail holds the values, and what rises instead is the guard: an audit entry about a person is as sensitive as the person data it quotes, which puts audit.view in the catalog's top tier next to person.view. That is a line in a document rather than a mechanism, and it is the weakest link in this design on purpose, so that a reader can see where the protection actually sits (09-attributes.md §6 argues it through, 06-audit-and-import.md §2.2 keeps the withdrawn rule visible). Erasure reaching the payload is unaffected and remains absolute.

    What is genuinely lost. The ability to say "everything except the diagnoses" — to a court, to a doctor, to a future board that wants a narrower access tier. It is lost deliberately. If the case ever arrives in reality the way E-7 hoped it would not, the fix is a second grant scope over a defined set of data, taken as a decision with these documents in front of the reader, and not the return of a code list: one scope, argued once, rather than eighteen flags that encode the same distinction in the names of permissions nobody reads.

    D-084 — Descriptive data is organization-defined at runtime¶

    Status: decided (from your answer) Date: refinement round 7 Follows: D-083

    Your answer. Asked whether the field vocabulary is a fixed typed set, a hybrid, or entirely organization-defined, you chose entirely organization-defined; on typing, typed for rendering, not for law; on curation, values anywhere, codes by permission; on retirement, a retired code keeps its values, redaction erases.

    Decision. Two tables. attribute_definition is the vocabulary the organization maintains: a code, a label, a value type, whether several values may be open at once, and a status of live or retired. person_attribute is a value one person has: the definition it belongs to, the value, who recorded it and when. Nothing in the schema names a fact about a scout.

    Why this is the shape and not the safer-looking one. The alternative — a column per fact — makes every collection habit a release. This organization's list of things it wants to know changes with the program: shoe sizes for a camp season, an insurance number for one country's requirement, a preferred contact language for one intake. A schema where that needs a migration produces the real failure instead of the apparent one: the field does not get added, and the information is collected on paper, photographed, and lost. D-083 removed the argument for a fixed set — a closed typed set is justified by needing to constrain the important fields, and the answer was that no field is more important than another.

    Typing for rendering, not for law. A definition declares text, number, date, yes/no, one-of-a-list, or free text with a unit. The system uses it to draw the right input, to sort a list, and to warn — "that is not a date" — and it does not use it to refuse a save a human insists on. The reason the warning must not be a wall is that the value is not the system's to overrule: 2019 as a year for last_checkup is a truer record than an empty field behind a validation error, and the person typing it knows and the form does not. What this costs is stated plainly in 09-attributes §5: no database type checking, no constraint can reference a value, and no report may assume it understands a code.

    Curation, because a vocabulary is the design. Anyone who may edit a person may record a value against an existing code. Creating a code needs attribute.define, which is a small permission held by few people. An improvised need at 23:00 is recorded as a proposal: the value is written into an uncatalogued code that is visible, unusable-by-default, and waiting for whoever curates the vocabulary to accept, rename, or merge it. The reason is the one failure this design is exposed to more than any other: an open vocabulary left open becomes allergy, Allergy, alergie and allergies (2), after which the layer still stores everything and answers nothing — which is the entirety of what the attribute table was built to do.

    Two rules that keep a runtime vocabulary from decaying immediately:

    • Codes are normalized before comparison — trimmed, case-folded, whitespace-collapsed — and uniqueness is checked against the normalized form. This is not a nicety; it is the difference between four spellings surviving a week and four spellings surviving a decade, and it is a rule the database can still enforce.
    • Retiring a code never deletes values. A retired code disappears from data entry and remains readable, reportable, and revivable. Deleting the label must not delete the fact underneath it — a code discovered to have been badly named is an administrative event, and if it destroys nine years of records it will never be retired, and the vocabulary accretes instead of being curated. Redaction is the opposite case and the only eraser: when a person is anonymised (00-conventions §8), their values go.

    See: data-model/09-attributes.md, D-085, open question F-10 for which of its rules the attribute layer can and cannot express.

    D-087 — Merge chains stay, because reversing a merge is a supported operation¶

    Status: decided (from your answer) Date: refinement round 8 Follows: D-004, D-056

    Your answer. Asked whether the system must be able to reverse a merge that a human approved — framed as the question that decides B-2, since chains make a reversal a replay and flattening makes it a rebuild — you chose chains, and an explicit unmerge.

    Decision. person.merged_into_person_id stays a pointer that is not rewritten forward when the survivor is itself later absorbed. A→B→C remains a chain and resolve_person() keeps walking it (01-identity.md §9). Flattening is now closed off, not merely slower.

    What this decision actually changes is the direction of the argument. These documents have argued for chains because unmerge would otherwise be impossible — an assumption resting on a capability that nothing had asked for. You have asked for the capability, so the reasoning runs the other way now: unmerge is a requirement, and chains are its consequence. That matters for how the rule is defended later, because "flattening is faster" is no longer a trade being weighed against an abstract tidiness — it is a trade against a feature someone named.

    Two rules a permanent chain needs, and neither existed until this entry.

    1. A cycle cannot be created, and the place it cannot be created is the merge, not the read. A merge is refused when the person chosen as survivor resolves — by walking the chain — to the person being absorbed. That includes the one-hop case already ruled out (nobody merges into themselves) and the case that actually happens: absorbing B into A when A has already been absorbed into B. Checking at write time is the whole guard; a read-side step limit would merely decide which of two wrong answers to return.
    2. Chain length is a signal, not an error. Resolution has no hop limit — a bound would silently return a tombstoned id, which is the failure the function exists to prevent. Instead, a chain longer than three hops is reported. Four merges in a row on one line of people does not mean the data is odd, it means the matcher is producing duplicates faster than a human can settle them, which is a statement about the queue and not about the row. 01-identity.md §10 stated this as a breach and is corrected: with chains decided, a survivor that has itself been absorbed is normal, and only the length means anything.

    What was already built, and is confirmed rather than changed. person_merge exists and is append-only with reversed_at/reversed_by/reversal_note, so an unmerge records that a merge was undone instead of erasing the record of the mistake (01-identity.md §8); and the reversal procedure is written in four steps (domain/03-identity-and-legacy.md §6) — tombstone off, rows created before the merge go back, rows created inside the merged window are flagged for a human, and every access_grant from that window is flagged rather than guessed. That asymmetry is the honest core of this entry: a merge can be undone and the merged period cannot be. Whatever those two humans did while they were one row stays one row's history, because the grants exercised in that window were really exercised by somebody who can no longer be identified from the record. Two further things follow and are stated where they belong:

    • Reversal needs no new permission. Unmerging is the same act as merging — an identity correction made by a named human — so it is person.merge, already held by the identity reviewer. A person.unmerge code would grade undoing a mistake as safer than making one.
    • The resolve-on-entry rule now has a check under it. "Every place that accepts a person id from outside must call resolve_person()" is a rule application code can forget, and D-072 removed the database-level ways of catching it; the net is a report for live rows that reference a tombstoned person, which is the only form of this failure that is visible afterwards.

That is why the integrity check below is a requirement rather than a nicety, and why a deny is the row on which access_grant.valid_to earns its keep: everywhere else an open-ended grant that outlived its reason costs a tidy database, and here it costs a child who cannot see their own camp photos. A date is the only remedy that works without somebody remembering to act.

    What it costs, in rows. A role that used to be one grant at manage is now one row per code. The catalog holds 66 codes; a broad office is a couple of dozen rows. That is the price of the question you are now able to ask — "what exactly does this person have?" answered by reading rows — and the price of the one you can no longer ask, which is "what does manage give me on this event?": there is no such word, so there is no such lookup. Integrity check to add: a live grant whose effect is deny and whose grantee, scope and code match no live allow is dead weight and should be reported, because a deny that denies nothing is how a stale restriction survives its reason.

    Two-way door? Cheap in one direction, expensive in the other. Levels can come back as names for sets of codes with no comparison defined — which is what a role already is, so no new mechanism is needed to approximate one. A real ordering coming back means re-importing permission_level, the rank rule, and locality's tie-break, all of which were deleted with their only consumers.

    D-100 — A role is an office and a group is company: two tables of the same shape¶

    Status: decided (from your answer) Date: refinement round 10 Follows: D-097, D-098, D-099

    Reverses: D-039's resolver clause, D-051 entirely, D-033 and the position module, D-009's remaining subject.

    Closes: F-12.

Then, when asked whether roles go too: *"Role and group are technically the same, but not semantically. A role was meant to be for a single person / a small couple of individuals that are visible as the leaders / financial / IT managers of the organization, while the group is a temporary set of members that do e.g. events together." What that buys is the question the old design could not answer cleanly — "what may a treasurer do?" — which is now a query over visible grant rows rather than a walk through a bundle table nobody reads.     2. Positions are deleted. position, position_assignment, is_leadership, max_holders and the appointment workflows go: with no units there is no body to be a leader of, which is the only thing a position recorded and a role does not (D-033's own reasoning for why leadership is a position-assignment fact and not a role fact). An elected leader is now a holder of a role, and the audience rule that used to read unit_leaders — which round 6 had to correct because it was silently matching nobody — is ROLE(leaders) and means what its name says. What is genuinely lost is the elected-versus-appointed distinction as stored data: it survives only as a role the organization invents (elected_council next to appointed_it) or not at all. F-12 is closed and its answer is no: role_holder names one person. The reason the register refused it — a derived holder list cannot answer "who was treasurer in 2023", and an office record that cannot answer that is not an office record — is untouched, and the grantee pair that F-12 contemplated is no longer even tempting, because grants now aim at roles instead of roles being filled by grants.

    3. The gate moves from the resolver into the selector, and this is the round's largest deletion. D-039 made the resolver ask, for every grant, whether the holder currently holds a membership; D-051 then needed system.gate_exempt and person_holds_gate_exempt to let appointed people through anyway, with the documented hazard that a permission check performed through can() there means a lockout with no error message. Now MEMBERS is a selector operand evaluated live on the checked date, and:

    Old mechanism New expression
    The gate applied to a role with requires_membership = true MEMBERS * ROLE(x)
    The gate waived for a whole role ROLE(x) — write it without MEMBERS
    The gate waived for one named person (system.gate_exempt) MEMBERS * ROLE(x) + PERSON(y)

    role.requires_membership, system.gate_exempt and person_holds_gate_exempt are all deleted, the resolver's membership clause is deleted, and the special-case path that had to be carefully kept out of can() goes with it. Ownership and guardianship stay channels and are unaffected — they were never gated. D-071's posture transfers to role_holder: nothing forces a holder row to end, and the control is the report.

    The posture reverses, and the new failure mode is named rather than buried. The gate used to be default-on, so that forgetting it was impossible. It is now opt-in per grant: a grant written as ROLE(TREASURERS) with no MEMBERS authorizes a lapsed member, silently, forever. Three controls, none of which is the resolver:

    • A standing report of live grants naming a ROLE(...) operand whose expression does not contain MEMBERS. An office held by a non-member is the case worth a human eye, and this report is narrow enough to actually be read.
    • Seeded grants and any grant template carry MEMBERS, so the path of least repetition is the safe path.
    • Import completeness. MEMBERS * COUNSELORS is only as correct as the counselor roster: the gate used to fall out of membership alone, so an import that misses 300 counselors silently un-gates them. It fails closed — nothing breaks, which is exactly why nobody notices. The import reconciliation report of D-090 must count people marked as counselors in the corpus against role_holder rows written.

    PERSON(y) is a selector, and this entry is the reason it had to become one. The grammar D-101 first shipped did not include it — LIST and GROUP(x) cover the enumeration cases, and a language with no attribute operands has no obvious place for one person — which left the third row of the table above unparseable in the very entry that wrote it down. It is seeded in selector_type like every other operand, it takes a person, and it passes the materializability test for the plain reason that a set of one is a set. The workaround the membership module reached for before this was repaired — write a second grant whose grantee is that person — stays legal and is arguably clearer for a permanent exception; what was not acceptable is a control that does not parse.

    A consequence of moving the gate that no entry in this round had named: the expiry sweep can lock the organization out of its own system. D-040 lapses memberships on a date, to everyone at once, and whoever runs that sweep is a member too. Under D-039 the collision existed but system.gate_exempt was the purpose-built hole in it, and that mechanism is deleted above. So an administrative office whose grants read MEMBERS * ROLE(...) stops working at the instant the sweep lapses its holder — including the office that would have been asked to fix it. What carries the case now is the second control: the seeded grants for offices that must survive a lapse are written ROLE(...) with no MEMBERS, which turns a flag nobody read into a written expression with an outage attached to getting it wrong. Assumption: the seeded is_system role set contains at least one such office; nothing in the catalog requires it to, and if it does not, 1 January is a support call.

    Why two tables, when you said they are technically the same. Because the difference decides who may edit the membership, and one table would merge those two permissions into one. role.* is the most sensitive code family in the catalog (🔒🔒); writing a group's roster is person_group.member.manage (⚠). One person_group table with a kind column and one membership table gives a single code that both adds a child to the Thursday group and puts the holder into SYSTEM_ADMINS. That is the merge to refuse, and it is the answer to D-080's lesson about two same-shaped tables: these are not two statements of one rule, they are two different grants of power. Same columns, different codes, and ROLE(x) / GROUP(x) distinct in the grant text so the distinction is visible to whoever reads the grant — which is where you asked for it.

    COUNSELORS is seeded, as a role. A permanent, organization-wide population is the opposite of your own definition of a group ("a temporary set of members that do events together"), and the table decides the sensitivity that protects the set every safeguarding convention hangs from. It ships is_system so an editor refuses to delete it. Consistent with D-005: this is a set, and being in it confers nothing until a grant names it — audience membership has never been authority (D-042, restated in D-091). Bare COUNSELORS is legal in an expression, which makes the name namespace load-bearing (D-101).

    Two-way door? The gate is the expensive half. Restoring a default-on membership test means re-adding a resolver clause and re-deciding which permissions it applies to, because a system where every expression is explicit has no record of which grants were meant to be gated. The role/group split is a cheap door in both directions: the tables have the same shape, so merging them is a migration, and the only thing to re-argue is the permission separation this entry records.

    D-101 — An audience is an expression over named sets, stored as a tree¶

    Status: decided (from your answers) Date: refinement round 10 Follows: D-098, D-100

    Amends: D-091 in its third arm. Confirms: D-060, D-011.

    Your words. "A group can be used as a selector in the audience rule (e.g. MEMBERS - GROUP(schuzka2026-1) * COUNSELORS — meaning all counselors that are not part of the group schuzka2026-1)." Asked which of two notations to build on: "Would it be easier for the system if we wrote an evaluator for each person (MEMBER & COUNSELOR | ROLE(TREASURER)) or as a union/difference of groups?" — and then: "I dislike the lack of operand precedence. I would like to be able to use brackets." — and then: "Can we not store it as expressions? Each row has two operands and one operator, and the operands can be either another row or a selector."

    First, the reframe that makes the notation question smaller than it looks. p ∈ (A ∩ B) ∪ C is by definition (p ∈ A ∧ p ∈ B) ∨ p ∈ C. The two notations you were offered are the same function written from two ends, so the choice does not decide what the machine computes; it decides what gets stored and what a writer is allowed to say. The answer is therefore both, split by direction:

    Author in sets. Evaluate per person.

    A check asks about one person, so the resolver compiles the expression down to a predicate and never materializes a set. An implementation that evaluates MEMBERS as a list of ids and then tests for containment pays three thousand rows per request, which is the one way to get this wrong and the reason the requirement is written here rather than left to whoever builds it.

    Why the set form is the source language, in one argument each.

    • It is no weaker. - is complement against EVERYONE, * distributes over +, so every boolean formula has an equal expression here. The predicate form buys zero expressive power.
    • It is the closed one, and that is the whole case. D-060 refused a rule engine, and a per-person boolean language is the door to one: once &, | and ! exist, the next operand somebody wants is AGE >= 15 or FEE_PAID, and there is a parser standing there to accept it. A set language closes it by rule instead of by discipline: an operand must be a named, materializable set of people. An attribute is not a set of people. Guardianship is (GUARDIANS(x) is a set), age is not, and the line falls exactly where D-060 already drew it — eligibility stays capability.
    • The three workloads the corpus already promises. "Who does this grant reach?" must be shown, expanded, in front of a human — D-091 made that a requirement on the screen, not a nicety, and a predicate can only report true, while a set is the answer. "What may a treasurer do?" (D-100) needs the person→set index, and role_holder and person_group_member are it; an expression is unindexable. Caching (F-6) can key on an operand and be reused across every grant, and role_holder changes are the invalidation.
    • It is the schema that exists. An audience's manual arm, its included groups, and everyone / all_members / guardians_of are already named sets; the only genuinely new symbols are * and -. Today's audience has no intersection and no difference at all, which is why your example was not writable in any notation.

    Grammar.

    expr    := term ( '+' term )*
term    := operand ( ( '*' | '-' ) operand )*
operand := EVERYONE | MEMBERS | LIST | PERSON '(' person ')'
         | GUARDIANS [ '(' person ')' ]
         | ATTENDED [ '(' event ')' ]     | PLACED [ '(' event ')' ]
         | CONFIRMED [ '(' event ')' ]    | ON_WAITLIST [ '(' event ')' ]
         | ORGANIZERS [ '(' event ')' ]              argumentless = bound, [D-102]
         | ROLE '(' name ')' | GROUP '(' name ')' | AUDIENCE '(' code ')'
         | name                                      bare; the shared namespace below
         | '(' expr ')'

    MEMBERS names a set the membership module already defines, and does not define it here. It evaluates is_current_member(person) — status active with a period covering the checked date, no grace coalescing, because the renewal window is a date range for rejoining and not a state in which somebody is a member (data-model/03-membership.md §3, domain/06-authorization-model.md §6.1). That is the whole reason the language works: an operand is the name of a set somebody else already provably owns, which is what "materializable" has to mean for this to stay out of rule-engine territory.

    (The AUDIENCE arm is D-103's, added the same round this entry was written, and it is the reason this grammar is marked as amended rather than final: an entry that ships a grammar and then grows an arm is worth seeing to have grown one.)

    Two arms the first draft of this grammar omitted, and both were load-bearing elsewhere in the round. PERSON(x) names one person — a set of one, so it passes the materializability test, and it is how system.gate_exempt's "except Honza" is written inside the expression that granted the rule in the first place, which keeps the exception visible next to the thing it exempts. And bare name, because the round's own control is written MEMBERS * COUNSELORS: an expression that does not parse is not a control. ROLE() and GROUP() remain as explicit qualification, required in the canonical rendering.

    Both arms were still missing from the seeded registry when the registry was written, and that is worth recording rather than fixing quietly. data-model/05-authorization.md §8 was written from the evaluator's arm list, not from this grammar, and an arm list copied from an implementation is exactly the kind of source that loses an arm nobody had implemented yet. The registry carries thirteen rows and PERSON is one of them: takes_argument true, argument_type person, binds_to_item false. Its distinction from LIST is real and is why both survive — PERSON(x) is an argument, so it composes and can be subtracted on its own, while LIST is one set of several people belonging to one audience and subtracting it removes everybody on it. D-103's kitchen example needs both, which is the proof that they are not the same operand wearing two names. The class of defect is F-19, it arrived here in a second registry inside the same round, and D-104 is the answer to it.

    * and - bind tighter than +; * and - bind equally, left to right; brackets override. The rule is arithmetic-shaped so nobody has to learn a table, with one deliberate departure from arithmetic: - does not sit beneath *. The reason is the first expression anybody writes in this language — MEMBERS - GROUP(schuzka2026-1) * COUNSELORS, meant as "all counselors not in that group" — which is what left-to-right gives and is not what *-tighter-than-- gives. Precedence was chosen to match the reading the writer already had, not to be defensible on other grounds.

    The canonical form prints every bracket, always. Not for legibility, so that the paragraph above is never load-bearing when somebody reads a grant two years from now: the stored form of the example is (MEMBERS - GROUP(schuzka2026-1)) * COUNSELORS, the editor rewrites what is typed into that before saving, and an implementer who reaches for arithmetic precedence in their parser builds a different expression than the one the writer meant. This entry's first draft got its own rule wrong — it asserted that the bare form had changed meaning, which is the *-tighter reading this entry then refused — and the correction is worth keeping in place of the claim, because the mistake is exactly the one the always-bracketed canonical form exists to make impossible: two precedence rules can sit in one document, agree with each other in the abstract, and disagree the moment an expression is written without brackets.

    Storage: the tree you described, not a normal form. Each row is a node: operator + left_id + right_id, or a leaf's selector_kind + selector_arg_id. My alternative was to normalize to a union of terms on save; yours is better and the reason is the round's thesis — the normalizer is the code (distribute, dedupe, sort, survive blow-up), and a binary tree needs one evaluator of about fifteen lines and keeps the writer's brackets instead of silently rewriting them. It also makes the depth limit the only complexity bound, since (A + B) * C costs nothing. The rules that come with it:

    Rule Where it is enforced
    Exactly one shape. A node has operator, left_id, right_id and no selector; a leaf has selector_kind and no operator or children. A check on the row — expressible, so it stays a constraint
    One parent, never a DAG. parent_id lives on the child, so a node belongs to exactly one expression. A side table letting two expressions share a node is refused: editing the shared node would silently widen every grant using it, which is D-091's inclusion hazard re-imported Structure, plus a CI check that no such table exists
    Cycles and depth refused when the row is saved — walk the parent chain, refuse a revisit, refuse past selector_depth_limit. Structurally hard to build; refused rather than trusted, for D-091's own reason: a hand-fixed row, a restore from before the guard existed.     selector_arg_id has no foreign key — it points at role, person_group, audience, person or event depending on kind D-011's already-accepted trade-off, with its compensating orphan check
    An operand that does not resolve is the empty set. Fail closed, in every direction, as §Evaluation of data-model/05 already rules for audiences The resolver
    The whole tree is fetched in one indexed read by denormalizing audience_id onto every row, then assembled in memory. The read path never walks a parent chain. Amended by D-103: still one read per audience, but an expression that names another audience needs one per audience in its closure, so the honest claim is "no parent-chain walking", not "one query" A stated implementation requirement

    A naming ruling, written down because the table sits outside the naming conventions and somebody will notice. data-model/00-conventions.md §2 admits two shapes — a junction table named <a>_<b> alphabetically, and a lookup table named for the vocabulary it is — and audience_operand is neither: it is a recursive structure, which the conventions have no rule for because until now the model had none. It is kept for the reason the two existing rules exist: the name should tell a reader what a row means. Operand is the word the grammar itself uses, so the table teaches the language; audience_node was weighed and refused, because it names a graph shape and would leave a reader who has not met the grammar no better off than audience_thing. Worth marking anyway, because it is the reading that gets a migration wrong — singular-for-an-aggregate invites someone to build one row per audience, when the aggregate is the tree and a row is one node of it. The diagram caption and the data model's first line both say rows of one audience's expression tree for that reason. This entry's first draft justified the name by citing a naming decision that turned out not to exist — the rule is a conventions table, not a numbered decision, and a citation invented to settle an argument is the kind of thing this log keeps a record of.

    selector_type is a seeded registry, not an enum. Which operands take an argument, which may bind to the item, and what type their argument is — that was three hard-coded lists (the resolver_key enum written out in prose, the reserved-word list, the "meaningless without a resolver_key" rule). It becomes one seeded table in the shape grant_scope_type already is: code, takes_argument, binds_to_item, argument_type. The parser reads its reserved words from it, the editor builds its dropdown from it, and the write path checks arity against it. The language becomes data. audience.resolver_key and scope_parameter are deleted into it.

    Two sentences this paragraph needed, and did not have. The registry is data, so say what is not thereby open: every selector_type row is seeded and is_system, and the organization may not add one at runtime. "Closed language" and "the language is a table" are contradictory unless the table is read-only to tenants, and the read-only version is the one that keeps D-060's line — an operand is a shipped predicate, not a thing a well-meaning registrar invents at 23:00. One consequence of that rule is a refusal worth naming because it was nearly built: a set of grants is not an operand. GRANTS(<ids>) — "all the people these grants reach", wanted as a way to move a bundle of grants at once — cannot be one, because an operand must resolve to a set of people, and that is what a grantee is; the bulk operation it was wanted for is a screen over the grant list, not a meaning a stored grantee can carry. Refusing it on the type rather than on permissions is also what removes the awkward status such a row would have had: with this rule, every seeded selector is a shipped selector, and there is no third kind. What the deletion of resolver_key does leave unsaid is where a code meets its implementation: the resolver dispatches on code, and a seeded row with no shipped resolver is a deployment bug that shows up as an empty set, fail closed like everything else in the round. Second: this is what makes the age question answerable at all. Attribute operands are refused above, so "13 and over" cannot be typed by a writer; under D-070 the answer stays "open the event to the set whose members are that age" — a group somebody maintains — and an AGED_13_PLUS-style operand becomes legal only as a shipped selector, which is the one route this paragraph allows and the events document was right to guess. Nothing of the kind is seeded at go-live, because one shipped age band is the first step onto a ladder nobody asked for.

    The inclusion arm dies, and composition survives by changing hands. D-091 let a group pull in other groups through audience_include, because a group could otherwise not be composed. Under D-098 a group's membership is its dated rows, and composition now lives in the expression: GROUP(kitchen) + ROLE(troop_staff) composes as much as an edge ever did. What goes with the edge table is a great deal of machinery — the transitive walk, include_depth_limit, the write-time cycle walk over a graph, and integrity check 20's job of asserting that the walk exists — because a tree cannot cycle, so the only acyclicity guard left is the cheap parent-chain one. ~~That sentence is the second-most-durable claim in this entry.~~ D-103, written the same round, lets an operand name another audience, and a forest of trees pointing at each other does cycle: the save-time reachability walk comes back, as does a depth bound counted over the closure. What stays deleted is the edge table and the materialized closure check 20 asserted — the edges are AUDIENCE leaves in the table that already exists. What is genuinely lost: "add the kitchen crew to everything the troop-staff group is used for" is no longer one edit. The answer is that named sets are the composition mechanism now — name the composite once, aim grants at it — which is D-091's outcome reached without a graph nobody could see the shape of.

    audience_member stays, re-roled as the LIST leaf. It is the audience's own dated list of people, reachable in an expression as one operand. Merging it into GROUP(x) was weighed and refused twice over: naming three people in one grant would create a row in the group browser that is not a group anybody talks about, and D-098 already wrote the rule that keeps the two dated-member tables apart (a group's members are true with no grant pointing at them; a selector's additions are meaningless outside the selector). The duplication D-080 would flag is therefore kept on purpose, and the mitigation is the one D-091 already required: the editor shows which mechanism each person arrived through.

    Names are one namespace, and that is a new dependency. Bare COUNSELORS resolves against roles and groups together, since ROLE() and GROUP() no longer have to disambiguate. So: names unique across role and person_group — and audience.code joins them in D-103, so it is three tables and no single constraint spans three of them — which means the write path carries it and an integrity check asserts it exists, per D-081; case, whitespace and separators folded on write; and every selector_type.code is a reserved name, so a group called MEMBERS is refused at the save rather than silently rewriting every gate expression in the system. What is stored is always kind + id, so a rename never rewrites a grant.

    Given up, once. Storing a tree means two expressions with the same meaning are two different row sets, so "you already granted exactly this set on that row" no longer falls out of storage. The route back is a normalized fingerprint computed on save as a derived value used only for a warning — and if the expansion overflows, skip the warning rather than refuse the write: normalization informing a human, not gating one. Registered as an open question rather than promised. Similarly, DNF could have flagged term-matches-nobody syntactically; the tree catches only X - X on a single node, so "this selector reaches nobody" belongs to the editor preview that already has to exist.

    Two-way door? The language is a wide-open door — it is one seeded table plus an evaluator, and an operand can be added by any later decision. Precedence is the closed half: once expressions are stored in canonical fully-bracketed form, changing what binds tighter changes nothing already stored, which is a nice property and the reason the canonical rendering is a requirement rather than a convenience.

    Amends: D-061, D-062, D-065, D-067.

    Your words. "The events are owned by the root unit, so anyone with a permission to create an event can create an event." Then: "I also want to include ATTENDING(<event>) (meaning is registered to an event)", and on the tiers: "let the user pick which they mean — mainly 'registered and confirmed', or 'registered and is confirmed or whitelisted or waiting for confirmation'", and on the argument-less form: "unparameterized form is great, I like that."

    Decision. event.org_unit_id is deleted and there is no owner of an event.     1. Bound operands. Some selectors name a set relative to the item being checked, and write it without an argument:

    Operand On the item checked means Explicit form
    ATTENDED said yes to this event ATTENDED(<event>)
    PLACED said yes and is not waitlisted — the capacity set, the one §5 counts and the index already serves PLACED(<event>)
    CONFIRMED holds a paid place on this event CONFIRMED(<event>)
    ON_WAITLIST is waiting for a place on this event ON_WAITLIST(<event>)
    ORGANIZERS runs this event ORGANIZERS(<event>)
    GUARDIANS are the guardians of the person this item is about GUARDIANS(<person>)

    Every one of these is a seeded is_system row of selector_type, and is_system is not decoration here. D-101 made the registry read-only to an organization, so no tenant action can add an operand; what is_system guards is the platform's own delete path, and it is also the flag that tells a reader this code is vocabulary rather than content. The alternative — seeded but deletable — is a grant breaker with no crime attached: remove ORGANIZERS and every event.answer.view grant in the system silently resolves to nobody while the audit trail goes on reporting them live. ROLE and GROUP are the only kinds an organization populates, and it does so by writing role and person_group rows, not registry rows.

    The argument-less form is the important half, and it exists to kill a specific flaw: ATTENDING(<event 1204>) — attending being this round's starting word for the idea, refused above in favour of four tiers that each name a stored column — written on event 1204 is one grant per event with the event's own id typed into it, so "every participant may see the other participants" is a thing you do 400 times and forget on the 401st. Bound, it is one expression written the same way every time. Two rules make it safe:

    • A bound operand is legal only on an item-scope grant. At the unit there is nothing to bind it to, so it is refused when the grant is saved, with the operand named in the message.
    • A bound operand is legal only on a matching item type. PLACED on a person_group grant is refused because that item is not an event. This is selector_type.argument_type checked against grant_scope_type — which is a reason the registry of D-101 is doing real work and not merely tidying.

    2. ORGANIZERS is what replaces unit authority over an event, and it is not a contradiction of D-062. With the owning unit gone, "the people running this event" has no other expression, and D-061's rule (answers are read by that event's organizers) has to be said somewhere now rather than hard-coded in prose. It is said as a seeded grant: event.answer.view on an event to ORGANIZERS. D-062 and its "an event_organizer row grants nothing" both stand untouched, because an operand is a set, not a grant — the same sentence §8 of the authorization model already repeats twice for unit_leaders and audiences generally. What changed is only that the appointment is now aimed at by grants instead of being special-cased inside the resolver.

    And a seeded grant carrying a bound operand is not one row — a sentence this entry omitted and the events module then had to assume. A grant's scope is the unit or exactly one item, and a bound operand is legal only on an item-scope grant, so there is no row that says "every event's answers go to its organizers": the one row that would say it needs the unit as its scope, which is precisely where the operand is refused. What is seeded is therefore a template, and the event-creation path instantiates it beside the event row. Two consequences, both kept:

    • The import owes one instantiation per event row it writes — this module's share of D-093's shape, and cheap, because it is the same insert the event row already needs.
    • An event whose creation failed between the event row and the grant has nobody who can read its answers. So the two writes are one transaction, and the check is a report — events with no answer-view grant — because "these two rows exist together" is F-10 shape 1 and no layer this project owns can express it.

    What the per-event row buys, and it is not accidental: answers-view is revocable on one event without touching anyone's appointment, which is the kind of thing an organizer asks for the week before a camp.

    3. Four attendance tiers, and the refusal of a fifth. You asked the writer to pick; picking requires that the choices be the stored facts and not four new ideas, so each tier names columns of event_registration and nothing else. PRESENT(<event>) over was_present is refused, and the reason is the failure direction: was_present is NULL until someone takes a register, so an operand built on it would revoke a child's access to their own camp photos because a volunteer forgot to tick a box. That column is a safeguarding signal — three-valued on purpose, per D-067 — and keeping it out of the selector language is what keeps it meaning "a person recorded this" rather than "this is who may see things". WHITELISTED has no stored state to name: the nearest facts are source = staff (an organizer entered them) and promotion off the waitlist. Either it means one of those or it is a new column on event_registration, which is an events decision and not a selector decision, so it stays an open question rather than being implied by a word in a grammar.

    4. The set a grant reaches is now per-item. D-091's requirement that the editor show the expanded people — "the person saving the grant is looking at one row that mentions no person at all" — can no longer be answered from the grant alone: PLACED means different people on different events. So the preview is computed for an item and says so on screen, and the cache key for a bound operand must include the item (F-6 amended). Import consequence: the one-off import owes event rows and event_registration rows (D-090, D-093's shape), and it owes no owner column, which is the import-side saving D-097 already counted. D-094 is deleted rather than reversed: there is no column for an imported event to have.

    Two-way door? Narrow and expensive. Re-introducing ownership means the owner column, the resolver tier that reads it, and every check that the module deleted — but the selectors added here are not in the way, because an ownership grant and a bound operand answer different questions and can coexist. That is the difference between this and D-097: that entry deletes a dimension, this one removes a test and leaves the vocabulary intact.

    See: data-model/08-events.md §2, §8, domain/07-events.md, data-model/05-authorization.md §10.

    D-103 — An audience may name another audience¶

    Status: decided (from your answer) Date: refinement round 10 Follows: D-091, D-098, D-101

    Amends: D-101's grammar, its "a tree cannot cycle" claim, and its one-indexed-read fetch.

    Your words. "What is a LIST? Also it should allow nesting AUDIENCEs." The second sentence is the decision; the first is the reason this entry has to be written at all, and §1 below is its answer.

    1. What LIST is, said plainly¶

    LIST is this audience's own hand-typed list of people — the rows of audience_member, which is the one table in the module that holds persons rather than rules. It is the only operand that is not a rule about people: MEMBERS is a test, ROLE(vedoucí) is an office with dated holders, PLACED is a join against an event, and LIST is the names somebody typed into this one grant.

    It exists so that a grant can carry its own exceptions without creating a thing everybody can see. "Everyone in the kitchen crew, plus Honza, minus the two people who left" is (GROUP(kitchen) + LIST) - PERSON(a) - PERSON(b). The alternative — making Honza a member of GROUP(kitchen) to reach one grant — edits a roster that other grants read, which is D-091's hazard, and it also invents a group nobody talks about, which is the rule D-098 wrote. So LIST is scoped to the one expression that contains it, is invisible in the group browser, and dies with the audience.

    The name is the weak part of this design and the question you asked is the evidence: nothing in LIST says whose list. The registry entry carries the gloss "the people written into this audience", and the editor renders the operand as LIST (this audience). Renaming the code was refused only because the round has already propagated it through four files and the gloss costs nothing; if it keeps causing this question, the replacement is ADDED, which says where the rows came from.

    2. The decision, and the hole it closes in D-101¶

    An operand may name another saved audience: AUDIENCE(<code>). It is an ordinary selector — one row in selector_type, takes_argument = true, argument_type = audience, and it therefore costs one seeded row plus a resolver arm of about the same length as GROUP's.

    The stronger reason is that D-101 did not deliver the answer it claimed to. Having deleted audience_include, it answered "add the kitchen crew to everything the troop-staff rule is used for" with "named sets are the composition mechanism now — name the composite once, aim grants at it." But under D-101's own grammar the only names available were GROUP() and ROLE(), and both name a roster, not a rule: a group's members are its dated rows. The rule you wanted to reuse had no name to point at, so the composite could be named only by copying its rows into a second audience — which is audience_include with the copy step done by hand. Nesting is the half of that answer that was missing: AUDIENCE() is what makes a rule namable.

    It is also the arm that composes the two things the round kept apart. ROLE() names an office, GROUP() names company, ATTENDED() names attendance; only AUDIENCE() names a decision about access, so it is the only arm that can say "the same people that grant may see the fee ledger, plus the accountant".

    3. The three named sets, which are not the same thing¶

    GROUP(x) AUDIENCE(x) LIST
    What it is A dated roster somebody maintains A saved expression, evaluated live Rows on this one audience
    Who may change who is in it person_group.member.manage audience.update on that audience whoever may edit this audience
    Does it exist outside a grant? Yes — D-098: a group's members are true with nothing pointing at them No — it exists to aim a grant No
    "Was she in it on 1 June 2024?" Answerable, from the dated rows Not answerable past the audit window Not answerable
    Sensitive as ⚠ company 🔒🔒 authority 🔒

    That fourth row is the honest cost and it is the D-100 distinction replayed one level down. GROUP(x) is materialized, so it keeps a history you can be asked about; AUDIENCE(x) is a live rule whose past shape survives only in the audit trail, and D-088 expires those payloads after 24 months. So "who could see this child's data in 2024?" is answerable when the grant pointed at a group and is not answerable when it pointed at a nested audience. A rule whose reach cannot be reconstructed is still the right tool for a rule — the roster is the wrong tool for everyone over 13 — but the gap should be closed by the report in §5, not by pretending the question has an answer.

    4. Rules that come with it¶

    Rule Why, and where it is enforced
    A reference names a code, not a name, and only audiences that have one may be referenced. audience.code is optional and unique-where-set; naming stays opt-in, and an unnamed audience is simply not composable. The leaf may not point at a null code — a check reading another table, F-10 shape 3. Audiences were allowed to be anonymous before this round and there is no reason to force a name onto a grant's private addressee list.
    The code joins the shared namespace of D-101 — role, person_group, audience, and every reserved selector_type.code. Still no single constraint spans three tables: the write path carries it and an integrity check asserts the write path exists, per D-081. A name that resolves two ways is a silent grant.
    Bare names do not resolve to audiences. MEMBERS * COUNSELORS stays a role or a group; the audience arm must be written AUDIENCE(veterans). Adding a third table to bare resolution would change what existing stored expressions mean, and the explicit form costs four characters at the one place where being careful is the point.
    Cycles are refused across audiences, at save. See below.
    Depth is bounded over the expanded tree, not the local one — the bound is the same selector_depth_limit, counted after references are followed. A bound measured per-audience is a bound on nothing.
    An audience may not be ended or deleted while a live grant, or a live audience reachable from a live grant, names it. Refused at save; the reverse lookup is a query over audience_operand rows whose selector_kind = 'AUDIENCE'. Without this, "ended" would be a way to silently empty an expression, and under - an empty operand makes the result wider.
    The same refusal extends to person_group — ruled here, in the round after the row above — and it has to be ruled in both directions, which the audience row above does not say loudly enough. Ending a group that something live names is refused; so is writing a grant whose expression contains GROUP(x) onto a group that is already ended, or naming an ended group from an audience. Two causes put a row on the report and only one of them is a broken write path: a rule that constrains ending leaves the second cause untouched, and the hazard is identical either way. The group module found it by writing the opposite as the safe direction: a live grant on an ended group is safe on the allow side and widens a deny on the - side, which is the same asymmetry wearing a different table's clothes. The argument is identical, so the check is: refused at save in both directions, over audience_operand rows whose selector_kind = 'GROUP'.
    ROLE(x) needs no such rule, and the difference is worth naming. An office has no way to be emptied quietly: there is no role.retire, no status, and deletion is already refused while holder rows exist. A group has a lifetime, so ending it is one click that empties a set. A role's members are ended one row at a time, on a screen that shows each person. The hazard is a property of the shape, not of the idea, which is why this row is an exception list rather than a third copy of the check.
    An unresolvable leaf is still the empty set. On the allow side that is quiet and safe; on the deny side EVERYONE - <nothing> denies everybody, which is loud. The loud failure is the one you want. The quiet alternative is discovered in an audit, two years late.
    Naming an audience requires reading it, and grants no read of it to the people it contains. Fail closed, and see what you name is already D-091's requirement.

    One of D-101's sentences is now false and stays struck. "a tree cannot cycle, so the only acyclicity guard left is the cheap parent-chain one" — true of one tree, false of a forest of trees pointing at each other, which is what this decision makes possible. audience_include is not coming back: the edges are the AUDIENCE leaves, so there is no edge table, no transitive walk over rows, and no include_depth_limit; what returns is the write-time reachability walk D-091 already required, over a graph built at save time from rows that already exist. The machinery D-101 counted as deleted stays deleted; only its confidence was wrong.

    5. What this costs, stated as the hazard it is¶

    Editing an audience changes grants you did not make. Add a person to AUDIENCE(veterans) and every grant that names it now reaches them — including grants their owner wrote for a different purpose, and including grants this editor cannot see because they are not theirs. This is not a new failure mode: GROUP(x) has had this property since D-091, and the round accepted it there for the reason it is accepted here, which is that a named set is worth being reusable and a reusable thing has more than one user. The mitigation is D-091's, extended to the second user: saving an edit to a referenced audience shows which grants name it, and at what depth, before it commits, and the same listing is what closes the history gap in §3 as a report rather than as a reconstruction.

    Assumption: the listing is cheap at the sizes this organization runs at, because the edges are indexed rows in the table that already holds every expression. Unverified at any size, and a slow save screen is a real risk if the audit-and-import corpus's row-count estimates are wrong.

    Two-way door? Narrower than D-101's and wider than D-102's. Removing nesting later means finding every stored AUDIENCE leaf — they are one indexed query — and inlining the subtree it pointed at, which changes no grant's meaning on the day it runs and makes every one of them unmaintainable afterwards. So: the door closes quietly rather than loudly, which is the reason the depth bound and the reference listing are requirements rather than suggestions.

    See: D-101 for the language this adds one arm to, data-model/05-authorization.md §8 for the table, and D-091, whose inclusion edge this replaces for the second time.

    D-104 — A permission code's last segment is an action, and a registry that prose contradicts is a fiction¶

    Status: decided — by the assistant at the close of round 10, not from an answer of yours. Reversible, and cheap to reverse today; the day the first grant row exists it becomes a migration, which is the only reason it is written as a decision rather than fixed as a typo. Date: refinement round 10

    Resolves: F-19.

    Follows: D-055, D-068, D-072, D-075, D-081, D-101.

    1. What happened to the QR capability, which is the part worth reading¶

    F-19's third instance was a permission code named two ways in one round: the event door code, written event.qr in one place and event.qr.rotate in another, against a catalog that states its naming patterns as descriptions of the codes it already had.

    It was not resolved by choosing a spelling. The capability is gone. Grepping the closed round finds neither string anywhere in the corpus — not in the catalog, not in the events module, not in the ERD, not in this log. What survives of it is F-19's own description of the dispute.

    What happened, stated plainly: a capability entered this round as prose, was half-designed in the course of arguing about its name, and left as prose — swept away by the same parallel rewriting that introduced it, with no entry in this log involved at either end. Presence is what D-067 and EV-5 left it: somebody holding event.presence.mark records who came, with a clipboard if necessary. The only QR code in this system belongs to a payment, and D-075 already rules that a QR code is a rendering, not data — it encodes three stored facts and is worth keeping no row of.

    So the answer to "did we decide not to have check-in codes?" is no, and that is the finding. Not a typo, not a disagreement about morphology: a thing was possible in prose, argued over as though it were in the model, and removed without ever having been in the model. The registry — the one place a permission legally exists, since D-072 made these documents the specification rather than a description of a schema — never had a row, so nothing refused anything. A reviewer who had asked "which seeded row carries this?" would have ended the argument in one sentence, and nobody asked, because the argument was written in two files that both looked like they were describing something real.

    Closed as follows: there is no QR capability, seeded or deferred, in the events module or anywhere else. If door scanning is ever wanted it arrives as an open question, then as a decision entry naming the permission, the artifact that gets rotated, and who may reprint it — not as a code appearing beside a paragraph about a door.

    2. The naming grammar, promoted from a description to a rule¶

    The catalog described two shapes — <resource>.<action> and <resource>.<subresource>.<action> — and the dispute could not be settled by them because both readings of event.qr fit the description. A description of how existing names happen to look cannot arbitrate a new name; that is why the answer / answers case was easy (the catalog was self-consistent, so naming it the arbiter worked) and the QR case was not. Three rules for a code being added, which is the only moment they cost nothing:

    Rule The test, and what it refuses
    The last segment names the action. Read the code alone and ask what does this let me do? event.grant_access answers it; event.qr does not. A noun-final code states an object, and since D-099 a grant states exactly one thing — a grant of an object would need a second sentence to say what it permits, and a second sentence is where a permission's real scope always hides.
    A middle segment names something the schema stores. answer is event_answer, presence is a column of event_registration, contact, credential, member, participant, request are all rows. qr is nothing — D-075 is explicit that it is a rendering of a symbol, an amount and a recipient. A permission may not be built out of an artifact the database does not keep, because a grant has to be checkable against stored state and there is none. This is the substantive test the QR case needed, and it decides the case without appealing to morphology at all.
    No grade words, and no prefix. admin, all, everything, and any code whose meaning is "every sibling under this prefix" — D-068 deleted sixteen of them and computed the wrong answer for dependent.admin. Restated here as a rule about codes that have not been written yet, which is the only form of that decision that can still prevent anything.

    One exception, named, because a rule with an unnamed exception is a rumour: system.admin. Its last segment is not an action and it stays. It survives because its meaning is defined by the resolver — checked outright, applies_to = unit, never reachable through an item grant — rather than read off its name, and because D-068 exempted it in so many words rather than by omission. It is the only code in this system allowed to be a noun, and the exemption is not a precedent; <resource>.admin is exactly what rule 3 refuses and exactly what was deleted.

    The rules were applied to the registry as it now stands, and found nothing to correct: of the sixty-six live codes in the catalog's tables, sixty-five satisfy both the action test and the stored-state test, and the sixty-sixth is system.admin. That is worth recording precisely because it is a null result — the corpus was already following the rule, the rule was nowhere written, and the QR capability arrived anyway. A convention that is followed and not stated fails exactly once, on the first thing nobody thought to compare.

    3. The report, adopted¶

    F-19's recommended option is adopted: before a round closes, every dotted token in prose is diffed against the seeded registries — permission.code, selector_type.code, grant_scope_type.code, reason_code.code, and the seeded audiences — in both directions, so the report says which tokens name no row and which rows no prose names.

    • It is a report run by hand. This repository has no build step and no CI to hang a check on, so D-081's wording applies exactly: a convention, not a guard. Saying that is part of adopting it, not a caveat appended afterwards.
    • It would have caught all four instances, including the one this round has not yet noticed. The fourth: PERSON( is written into D-100 and D-101 and used in four module pages, while the seeded selector_type registry — copied from the evaluator's arm list instead of from D-101's grammar — carried twelve rows with no PERSON in them. So a control the round wrote for itself, system.gate_exempt as MEMBERS * ROLE(x) + PERSON(y), did not parse, and the pages that noticed resolved it by reading PERSON(y) as LIST, which is the wrong reading: LIST is one set belonging to one audience, so subtracting it removes everybody on it. D-101's registry amendment adds the thirteenth row. Two registries, one round, same defect — which is the strongest argument this entry contains for the report, and it was found by reading, in a file nobody had been asked to check.
    • Allow-listing is the cost and it is not small: illustrative codes, and deleted codes shown struck on purpose, both match no live row. The report is worth running only if its allow-list is re-read rather than frozen, which is the same discipline the struck-text rule already imposes on this log.
    • It runs on the documents, because there is no schema to check against (D-072). That is the condition that makes the whole class possible: the prose is the specification, so prose is free to contradict the registry, and there is no compiler to notice.

    4. What this is worth, and how it fails¶

    Two-way door. Wide for the grammar, which renames nothing today. Already closed for system.admin's exemption, which every round since D-068 has leaned on. And irrelevant for the report, which cannot be violated — only forgotten. That is this decision's failure mode and it is the only one: nothing in the system will ever notice a code drifting from its row, including after this entry, because the enforcement adopted here is a person remembering to run a script.

    What would make it obsolete. An actual implementation, with a seed directory and a test that loads it. Until then the registry and the prose are two copies of one thing (F-10's general shape, in its cheapest instance), and the report is the check that they still agree.
