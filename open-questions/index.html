    Open Questions¶

    Everything still unresolved, each with its schema impact — what changes once you answer. Ordered roughly by how much they block.

    Marked: 🔴 blocking something else · 🟡 important · 🟢 can be deferred.

    Resolved items are not deleted. They are moved to the bottom of this file with a link to the decision that settled them, so the reasoning survives — see § R. Resolved.

    A. Blocking the core design¶

    A-1 ✅ Closed — the unit type vocabulary is not seeded at all¶

    Answered: the sub-unit vocabulary is not a question the specification can answer, so it is not seeded (D-054).

    org_unit_type is runtime data, like role (D-052). The seed contains the root type and nothing else; the organization creates the types it uses. The previous placeholder — pack/group/team, and before it a national/region/district ladder — is gone.

    Why this is a better answer than a correct list would have been. The organization's own vocabulary is not knowable at specification time, and a wrong word in seed data is harder to dislodge than an absent one, because it reads as a specification to whoever implements the system. The shape was always the settled part: one root, arbitrary nesting beneath it (D-035).

    What remains true and worth knowing. Nesting is permissive by default — org_unit_type_rule is seeded with nothing, so any type may sit under any other until the organization states a rule, and a new type is usable the moment it is created. Every rule added later is a constraint deliberately chosen. The words pack, troop and section still appear across these docs as illustration only — read them as "some sub-unit type the organization has defined".

    See: data-model/02 §10, domain/04 §1–2

    A-4 (remainder) 🟢 The organizational calendar¶

    Answered. The fee expires on 1 January (D-047) and the renewal window is 60 days (D-048).

    What is left is not a question but a discipline. Both values live in membership_type as columns — expiry_month, expiry_day, renewal_grace_days — so either can be moved by an UPDATE. The one way to lose that property is a scheduled job or a front end that contains the literal 60 or 1. Worth one line in code review: do these values come from the row?

    See: data-model/03 §1, domain/05 §6

    B. Identity and history — closed¶

    All four are answered, in round 8. What is kept below is the reasoning, because each of these answers bought something and paid for it, and the payment is the half a later editor is tempted to forget.

    B-1 ✅ Closed — thousands of roster rows, numbers present, no payment data¶

    Answered: thousands of rows, one export, 1990s to now, a legacy member number on most of them, no payment data, and free-text columns alongside (D-090).

    Re-described one round later, and read this note before the answer above. The corpus's second half is not a roster: the rows are people with their membership periods at the root, and events with attendance, and they name no units at all. D-092 retires the roster frame and D-093 lifts the ban on imported memberships that the reasoning below had made absolute one round earlier. The corrected shape is in C-5. What survived untouched is everything this item was about — the volume, the legacy number, the absence of money, and the attribute vocabulary arriving from the free-text columns. Its heading is left as written so the links into it keep working: it is closed, on a different description of the file.

    The corpus answers the question the import was going to default. This item's own warning was that membership-vs-participation gets harder with volume, because an inferred open-ended membership makes every 2003 roster a current member with authority today (D-039). That defect never arrives: the import carries no payment data at all, so the exception arm of "participation unless there is payment evidence" has nothing to fire on. Every historical row is a unit_participation; membership rows come only from the current register. The default was correct and is now simply the rule (data-model/06 §6 drops the question accordingly).

    What is unchanged, and was the reason this was worth asking. The legacy number goes to person_identifier with scheme = 'legacy', imported verbatim and never reissued; where it is present the match is exact, and the heuristics in domain/03 §4 are for backfilling it rather than for deciding identity. D-004 is strengthened, not relaxed: at this size the number-bearing rows are the trustworthy set and the rest is a work queue a human settles.

    One consequence this answer created that no earlier document predicted. Under D-084 every leftover free-text column becomes an attribute code, so one file arrives carrying the organization's descriptive vocabulary. Those codes are live on arrival — a curator reviewed the map as one object, which is why the map lives on the batch (data-model/06 §3) — and proposed keeps its meaning of improvised later by a person at a desk. Letting several hundred codes arrive proposed would open the curation queue full and teach everybody that its age signal is noise.

    Still unknown, and still operational. The exact count and the exact year range. Both are inputs the batch carries; neither touches a table. What they do decide is A-4's arithmetic — with attendance and no money, 06 §3.1 is the load-bearing section of the import and the year boundary is what an end date gets inferred from.

    B-2 ✅ Closed — merge chains stay, because unmerge is required¶

    Answered: chains, and an explicit unmerge (D-087).

    The answer ran the argument backwards, which is the interesting part. Chains were chosen because flattening would make unmerge nearly impossible — an assumption resting on a capability nobody had asked for. You asked for it, so now the capability is the requirement and the chain is its consequence. Flattening is closed off, not merely slower, and "flattening is faster" is no longer a trade against tidiness but a trade against a feature someone named.

    What the question's own framing got wrong. It costed the two options in query speed. The real cost of a permanent chain is that it needs rules it did not have: a cycle must be impossible at the merge (a merge is refused when the chosen survivor resolves to the person being absorbed — checked on the way in, never by a read-side hop limit, because a step limit's only achievement is choosing which wrong answer to return), and chain length becomes a signal — resolution has no bound, but a chain over three hops is reported, because four merges on one line of people is a statement about the matcher's queue and not about the row. 01-identity §10 treated "survivor itself tombstoned" as a breach; with chains decided, that is normal, and only the length means anything.

    The asymmetry worth remembering. A merge can be undone; the merged period cannot be. The four reversal steps in domain/03 §6 lift the tombstone and return rows created before the merge, but rows created inside the window — above all the access_grant rows, which are flagged rather than guessed — stay one row's history, because the grants exercised there really were exercised by somebody the record can no longer separate. Unmerging needs no new permission code: undoing an identity correction is the same act as making one, so it is person.merge.

    B-3 ✅ Closed — the accounting skeleton is permanent, the audit trail is short¶

    Answered: the skeleton stays, the trail ages out (D-088).

    The two clocks, which are deliberately opposite. membership, fee_obligation, payment and the anonymised person row: no clock, because that is the organization's own history and the shape this item had already settled ("redact the person, keep the skeleton") is now justified rather than merely unopposed; redaction_log.retained_reason has a real value to hold. audit_log: payloads for 24 months, rows forever — after the window a row is reduced, old_values/new_values emptied, everything else standing, so the trail answers "who changed this, when, and were they allowed to" for the life of the system and stops answering "and to what" after two years.

    What this pays for, and it is not free. D-086 accepts that audit.view exposes whatever the payloads hold; a bounded window is the cheapest control that organization will ever get for that, and it is the strongest thing AT-4 will hear. What it costs is the history that D-085 was justified by. Values live in one overwritten row, the copy of them depends on a write path remembering to log, and the copy now expires — so "what did we believe about this child in 2019" is unanswerable twice over, and the honest description of the trade is no long history, not merely no temporal columns. If a case ever needs the long version the fix is temporal values (D-085 reversed), not a longer trail, since stretching the trail stretches exactly what D-086 graded and D-083 refuses to duplicate.

    Also: the legal review this item asked for is narrower now, not gone. Indefinite retention of named membership and fee rows is a claim that needs a basis, and a decision log cannot grant one; what exists to review is now a concrete policy instead of a blank, and it is recorded as an assumption with a name attached rather than as settled law.

    Residual, non-technical. Confirm the accounting retention period with whoever is liable for the books, and confirm the same 24-month window for access_log (F-8, proposed at the same value).

    B-4 ✅ Closed — one live account; a colliding sign-up files a claim¶

    Answered: refuse, and queue a claim (D-089).

    The rule that enforces it, and it is not a new table. One live account per person stands (01-identity §4); joined to it, an account may not reach active while an unresolved identity_hypothesis names its person. The identity review queue already existed, already records its signals and already has a role for it, so the collision case is a gate on activation plus a hypothesis raised at sign-up — no fourth queue, no new permission (person.merge, already held by identity_reviewer).

    Where the danger actually sat, and the threshold is the whole answer. The tempting version — link automatically once the e-mail verifies — is D-004 under another name, and its failure mode is one human's descriptive data becoming another human's record. The version you chose has its own failure mode, which is a brand-new person blocked by a false positive, so the trigger is a strong match only (exact legacy number, or exact birth date with a normalized name) and the soft scoring band must not raise a hypothesis at all. Two obligations come with it and both are checks rather than intentions: an age check on a hypothesis that is blocking an account, alerting rather than logging, because a stalled identity queue is now a specific child who cannot sign up for a camp; and a refusal that confirms nothing, since a sign-up form that answers "yes, that person exists" is an existence oracle over a roster of children.

    The everyday case is not this case. "I have a new e-mail" was never a second account — account_credential holds many credentials for one account, so it is an addition to the login a person already has. The collision case is a person arriving through a door the system did not know they had.

    C. Organization — closed¶

    Six questions, closed in two rounds. C-2 was resolved long ago and never appeared here: a unit may not be reparented at all, so a unit that moves is a new unit (D-036).

    C-1 ✅ Closed — the root may not read into its sub-units¶

    Answered in round 3, closed here for tidiness: no — scope_exposure is the only crossing, and no reporting channel is built (D-049).

    What was not obvious until it was answered. The question existed on the assumption that the root needed a way around the no-inheritance rule in order to report nationally. It does not, because the root owns the membership registry and the fees — so "how many members in 2019?", "who is currently a member?" and "what fees are outstanding?" are all answered from the root's own tables, with no exposure at all. Only the sub-units' own material — their events, their rosters, their local leadership — requires one.

    The consequence that will be misread as a bug: registrar holds unit_participation.view at organization scope and cannot read a pack roster. Scope is an exact match; it reads the root participation rows, which mirror membership (D-041). See domain/06 §2.1. D-094 gave this the same shape in the other direction: imported events belong to the root, so a unit-scoped "our events" report sees historical camps it did not run — a date filter, not a unit filter, is what makes either list mean what it looks like it means.

    C-3 ✅ Closed — a reused unit number is a new unit¶

    Answered: a new unit, unless somebody records the continuity (D-096).

    The question came back as a question, and that was the answer. Asked whether a number appearing twice across decades is one unit or two, the reply was "what is a unit number?" — which is the right thing to ask, because a code turns out to be a short human label somebody types (T12, 4. oddíl), not an identity, not a name (names are temporal rows in org_unit_name), and not unique: uniqueness is per parent among live rows, which is precisely why a closed unit's number is free again (data-model/02 §3). A label that gets retyped is not a continuity.

    What was decided, and what was refused. One org_unit per unit that existed; continuity is an assertion, written as org_unit_relationship with successor_of, never a match on the label. The opposite default is what "match on code" does if nobody says, and it invents a thirty-year lifespan. What this lost is almost nothing, and the reason is C-5: the corpus names no units at all, so there is no import-time collision to get wrong. This question outlived its urgency by exactly one round, which is worth knowing when reading it.

    See: domain/04 §3, §6

    C-4 ✅ Closed — a group is filled by a rule and a list, and appointing creates nothing¶

    Answered: filling rules on groups, and the two things the model refused to do (D-091).

    The question was about a convenience workflow and the answer was about the group model, which is why it is the largest decision of the round. Asked whether appointing someone to a position should create the matching role assignment, the answer described filling rules: each permission group states who is placed in it on top of the manually added people — "everyone with membership", "a leader role", "anyone", "members of permission group ABC" — with worked examples from a system where a group's population derives from enrolment in a course.

    Three of those four rules already existed (everyone, all_members, unit_leaders), which is the quiet part of the answer: an appointment creates no role assignment, because the derivation belongs on the group's rule rather than copied per appointment, where it would have to be found again and revoked. (Positions are deleted, D-100 — see the round-10 note at the end of this entry.) Two parts were forbidden and are now decided:

    • A group is a rule and a list. audience.kind's builtin-XOR-group split is gone; membership is the union of a rule arm, a manual arm and an inclusion arm.
    • A group may include another group. The one-line ban — "They do not nest" — is withdrawn, and its reason (cycles, unpredictable answers) is answered the way D-087 answered the same reason for merge chains: the cycle is refused when the edge is saved, not defended against in the read path.

    What was deliberately not taken from the answer. In the system described, permissions sit on the group; here a role is still held by one named person, because role_assignment is the office record that answers "who was treasurer in 2023" and a derived holder list cannot. That extension is F-12, not a silent schema change.

    What it costs, and where to look for the bill. A grant's reach is no longer visible in the row that grants it, so the editor must show the expanded set; and "who could read this in 2023" now depends on a recomputation of sets that were never stored, on state that has moved, with the audit payload that also held the answer expired by D-088. ~~F-7 is the route back and is no longer only a performance question.~~ — this sentence stood until round 13 and was the last live claim in this entry pointing at a question that no longer exists. Two things happened to it, and the second is the one that matters. The rebuild arrived (D-111) and F-7 was dissolved rather than answered, because a nightly rebuild of cached answers and a materialized effective-permission table turned out to be one job with two names — and round 14 deleted the rebuild (D-114), which changes nothing here: this paragraph's conclusion rests on the second event, not the first. Then the bill this paragraph was pointing at was cancelled rather than paid: D-110 ruled that the audit record of whom a grant reached is the expression, with the preview logged only as a rendering on a date — so "who could read this in 2023" is a question the system no longer owes anybody an answer to. Recomputing it stays possible and is never promised; the control that stands in place of the lost answer is procedural, the editor printing the resolved set before a shared expression saves.

    Round 10 redrew the line this answer drew, and it still holds — in a different place. D-091's "a group is a rule and a list and other groups, unioned" is no longer how a set is built: an audience is now an expression tree over named sets with + - * and brackets (D-101), and a group is the opposite of a rule — a person_group states its members and nothing derives them (D-098). So the union that D-091 built into one table became an operator in a language, and the hand-kept list that D-091 insisted on survived twice over: as LIST inside an audience, and as the whole content of a group. That was round 10; round 11 deleted one of the two — LIST and audience_member are gone (D-105), so the hand-kept set survives as a group's roster, or inside an expression as PERSON(a) + PERSON(b), which is the second of those two and not a third thing. The two halves of D-091's answer that were refusals — an appointment writes no assignment, a cycle is refused when the edge is saved — both stand, the first confirmed by D-100 and the second widened to references across audiences by D-103. What is now dead wording here is audience.kind, the unit_leaders rule, "level", and the link to §4 of domain/04, which was about positions.

    See: data-model/05 §8, domain/04 — its §4 held the positions this round deleted

    C-5 ✅ Closed — the corpus names no units, and none are assigned¶

    Asked, and answered by correcting the premise: the corpus is people and events, and it says nothing about sub-units (D-092, D-093, D-094).

    This question was not in the register. It appeared when B-1 was read against the unit model: the import matches roster rows to org_unit rows, org_unit.unit_type_id is required, no sub-unit type is seeded (D-054), and the pipeline's only documented behaviour for an unknown unit is a warning that does not block. Something had to create those units, and nothing said what.

    The answer removed the question. The rows are mainly "person with names, birthdate and when they were members of the root unit", "events with attendance". Not much more — do not solve assignment to org units. So:

    • People arrive as a person plus a bounded membership — D-090's absolute ban on imported memberships is narrowed to what it was protecting, never open-ended and never inferred from attendance — and ~~each membership brings its root participation row with it, as 03-membership §5.1 requires~~.     E-6 🟡 A guardian may appoint a guardian¶

    Question. D-072 moved the schema to an ORM. Most of what the deleted DDL asserted an ORM will generate from a model definition. Four shapes it generally cannot, and each appears dozens of times in these documents.

    F-14 ✅ Closed — nothing computes semantic equality of two expressions, and nothing will¶

    Answered: refused, on three grounds, none of them cost.

    1. The stored canonical string is the only identity an expression has. D-105 ruled that the tree is stored exactly as the writer wrote it, and this round's F-22 closes the last route around that: display is free, storage is not, because the write-path checks — the cycle walk, the reserved-name rule, the listing of what names an audience — all reason over the stored form. A fingerprint is a second identity, and a second identity is a second answer to "is this the same audience?", which is precisely the question D-101 gave up in order to keep storage honest.
    2. It is not decidable anyway, and this entry already knew that. With AUDIENCE(code) references, two expressions can fingerprint differently and reach identically because the difference is inside a referenced audience — so the honest design was always "a warning over the expression as written, references treated as opaque atoms". A check that must advertise how much it cannot see is not a control, and D-105's deletion of selector_depth_limit removed even the bounded resolver run that would have made the strong version possible on a deadline.
    3. Nobody is deduplicating audiences, at this system's size. D-112 fixes the population at a few hundred people; the near-duplicate this entry feared "accumulates slowly" is a problem at a scale this corpus will not reach, and the third arm's syntactic fix — storing + children sorted — is now explicitly refused by ground 1. That answers the sentence this entry flagged as unwritten ("whether sorting the children of a commutative operator falls inside what D-105 refused is a sentence nobody has written"): it does not fall inside; it is outside, and it is refused. The stored form is what was typed, including the order.

    What this concedes, since a refusal read as a resolution is the usual damage. Two audiences meaning one thing are still two audiences, and the failure this entry described is untouched: an organization names the stale copy, a grant points at it, and the fix looks like a permission change because it is one. The mitigation is not a fingerprint, it is the listing — which grants name this audience — which D-103 already requires and F-16 now prices; plus the D-109 flag, which lets a redundant audience be hidden rather than reconciled with the copy nobody uses. Two ways to live with the duplicate, and no way to detect it, which is the trade D-101 chose and this entry confirms rather than relitigates.

    What would reopen it. A real organisation reporting that two audiences diverged and a grant followed the wrong one — not two audiences existing. The trigger is an incident, not untidiness, and the entry stays findable under assumption 59, which already says nothing will compute equality.

    Question. D-101 gave up semantic equality to keep storage honest: two audiences are equal when their trees are equal, so MEMBERS + ROLE(x) and ROLE(x) + MEMBERS are two different stored expressions with one meaning, and the canonical fully-bracketed rendering does not fix it because it canonicalizes brackets, not order. Should the system compute a derived fingerprint — canonicalize operands into a sorted multiset per operator, normalize */- where the algebra allows — and warn when a second audience fingerprints the same as a first?

    Why it is 🟢 and why it is still here. Nothing depends on it. Two identical sets cost one extra row and one extra evaluation, and the confusion is cosmetic until someone edits one copy. But D-101 explicitly registered this as a question rather than a promise, and the failure mode it prevents is a slow one: an organization accumulates near-duplicate audiences, a grant names the stale one, and the fix is indistinguishable from a permission change — which is audited, alarmed, and requires explaining to somebody.

    The part that should not be oversold. The fingerprint is not decidable in general once AUDIENCE(code) references exist (D-103): two expressions can fingerprint differently and reach identically because the difference is inside a referenced audience, and expanding the closure to compare them is a resolver run, not a save-time check.     What round 11 did to it, and it was in both directions at once. The option that made the duplicate syntactically equal, storing + children sorted, is meanwhile in tension with the same round's ruling that the tree is stored exactly as the writer wrote it, with no rebalancing: sorting the children of a commutative operator is not rebalancing, but it is the same temptation in a milder uniform, and whether it falls inside what D-105 refused is a sentence nobody has written — which is now a thing that has to be said before it can be done. The colour stays 🟢: nothing depends on the answer, and a duplicate still costs one extra row and one extra evaluation. What changed is how often it is paid, not what it costs.

    Positions. Warn on equal fingerprints (catches the common case, false-positives on deliberately identical sets like two events' ORGANIZERS); compute nothing and let the which grants name this audience listing (F-16) do the work of showing redundancy; or normalize at write so + children are always stored sorted, which makes the common duplicate syntactically equal and needs no new machinery — at the cost of storing an order the language says does not matter.

    Schema impact. One derived column on audience, or nothing, and it must never be a unique constraint: a warning that became a constraint would refuse two audiences that legitimately reach the same people, and D-101's reason for giving up equality is precisely that the two are not the same question.

    Needed. Not before implementation. Revisit when the first organization has enough audiences that someone asks why two of them behave the same.

    F-16 ✅ Closed — listing the grants that name an audience is a scan over a small table, at the stated size¶

    Answered by D-112: D-103's assumption is true, now on stated grounds rather than on hope. Listing the grants that name an audience is "a scan over a small table with a handful of referencing rows each", at a few hundred people and a few dozen registrants per event, a big camp on the order of two hundred. Pagination is a UI nicety, not a requirement. So both D-103 protections that hang off this query — refusing to end a referenced audience a live grant reaches, and showing which grants name it, and at what depth before such an edit saves — stand as written, and the fallback this entry kept polished (weaken the D-103 rule, in the open, as a decision entry) is not needed.

    What it cost, and one caller that quietly disappeared. No schema, no decision entry, and — worth recording, because this entry's whole argument was that the walk had gained callers — F-6 has just removed one of them. Round 12's worry was that cache invalidation across the reference closure might be too expensive to run on every edit ("an invalidation that is too slow to run is not a slow feature, it is a stale allow"). ~~D-111 deletes that caller: a nightly full rebuild does the walk itself, in batch, and the incremental version is never implemented.~~ Round 14 removes the rebuild too, and hands the caller back in a smaller shape (D-114): the only thing now invalidated through the closure is a compilation, and because a compilation is finite and enumerable over the audience tree, "an edit to a shared audience invalidates everything" is "it invalidates the compilations that embed it" — a bounded walk, over the same closure, using the walk the save path already performs. So the caller count is two, not one: the cycle check on save, which is mandatory and was always mandatory, and compilation invalidation, which is optional in the sense that a compilation can simply be dropped and re-made. What changed about being fast is the consequence of being slow, and it got much smaller: a slow walk now delays an edit instead of leaving a stale allow standing, because nothing an expression reaches is cached as an answer any more. At this size both are cheap, and only one of them has to be correct.

    The reasoning stays, because it is the part that transfers. Everything below about the reverse-edge walk — that the index serving "what is in this tree" does not serve "what points here", and that the plausible answer "a selector_arg_id index" is the kind of answer that stops being true the first time an OR over selector_kind and selector_arg_id walks past it — is still how the query has to be thought about, and still unwritten. D-112 makes it affordable; it does not make it correct. These documents still contain no SQL (D-072), so what is settled is the cost, not the plan, and a future implementation that reads this entry as "already solved" will write the slow version of a query that is only fast because the table is small.

    What reopens it. The D-112 trigger — a few thousand people, or a thousand registrants on one event — with this entry second in that list, after the preview. Note what reopening costs here and nowhere else: the fallback is not a slower screen but a weaker D-103 rule, which is a decision entry, because the property being traded is the one that keeps a retired set from widening access.

    Question. D-103 makes two safety rules depend on one query: an audience may not be ended or deleted while a live grant — or a live audience reachable from one — names it, and saving an edit to a referenced audience must show which grants name it, and at what depth. The decision entry states its premise as an assumption: that finding the referrers is cheap. Nothing has measured it, and the whole of D-103's protection is built on it.

    Why the answer is not obviously yes. audience_operand denormalizes audience_id so that "what nodes are in this audience's tree" is indexed — that is the cheap direction. The protection needs the opposite direction: which other audiences contain a leaf pointing here, then transitively upward, then the grants aimed at each of those. That is a reverse-edge walk over a tree table, and the index that makes the forward walk fast does not serve it.     Why it matters more than a UI query. Because under - an empty operand makes the result wider, not narrower: an audience that stops resolving does not quietly stop granting, it can start granting.     Positions. Add the reverse index and state it as an invariant to verify (cheap, and it is a row in §11 of data-model/05 rather than a design change); ~~cap the listing by depth so the walk is bounded by selector_depth_limit, which D-101 already enforces and which makes the worst case finite by construction~~ — this position is void, and it was the cheapest of the three: the parameter and the save-time bound behind it are both deleted (D-105), so there is no number for a listing to inherit, and the walk is finite only because the closure is acyclic and is discovered by walking it; or drop the "and at what depth" half of the requirement, which removes the transitive walk and keeps the single-hop refusal.

    What round 11 did to it: this measurement gained callers rather than changing shape. Adding a name to an audience used to be an insert into audience_member; it is now a save of the whole expression (D-105), so every hand-typed exception added to an audience that references another one runs the editor's referrer walk — the listing is priced per name added, which is a different traffic pattern from once, when somebody edits a rule, and it arrives next to the two-writers problem D-105 names in the same breath. The same walk also became, in the same round, the only structural guard the save path has at all: the cycle check across audiences is a reachability walk over the closure, and with the depth bound gone it is the only thing standing between a saved expression and one that never terminates. One measurement therefore now answers two questions — is D-103's protection cheap enough to be obeyed, and does saving a wide audience cost anything an editor can feel — and the second is a question nobody had to ask last round. Still 🟡, for its original reason: the fallback is already written down as a decision entry (weaken the D-103 rule, in the open), so the exposure is a guard people route around rather than a design with no answer.

    Needed. Before an editor offers to name an audience. If the answer is "not cheap", the fallback is not a slower screen but a weaker D-103 rule, which is a decision entry, not an implementation detail — and it should be taken in the open, because the property being traded is the one that keeps a deleted set from widening access.

    Impact. If the walk is slow at real sizes, either the guard is skipped under time pressure or the feature people use is the one that bypasses it. Both are worse than the measurement.

    F-17 ✅ Closed — the expression is the record, so a nested audience's past is recomputed and never promised¶

    Answered by D-110, which removed the premise rather than filling the gap. "Whom did this grant reach in May?" is answered, if at all, by evaluating the words against the data of May, and these documents do not promise the answer. The audit record of a grant's reach is the expression; the preview is logged as a rendering on a date, not as a statement of members. None of the three positions below is adopted — not acceptance-by-declaration, not materialized dated expansions, and notably not the audience_revision row this entry recommended, because D-110 refuses exactly what made it attractive: the audit trail records the edit, not the meaning that existed before it, so a history of inner expressions is not being kept and a table for it would be a promise these documents have just declined to make.

    Why the question lost its force rather than its argument. Two things changed the ground under it. First D-109: if nothing a rule names is deleted, the words stay evaluable long after their reason is gone — a retired office still resolves, a deprecated group still resolves, a name stays reserved — so a past-date recomputation is usually computable rather than usually impossible. Second D-110's own refusal of the roster: the tempting fix was always "keep the list", and the list is the table this corpus has deleted twice. What is left is honestly bounded, which is the most any answer here was ever going to be.

    The part that is conceded rather than solved, written down so nobody finds it sideways. Editing a shared audience changes what every grant that names it has meant all along, because those grants hold a word and not a copy — an edit to a shared audience is therefore a retrospective edit to every rule that names it — and a re-evaluation for a past date uses today's inner expression. This is why a past-date answer can be wrong rather than merely missing, which is worse and is the reason the entry was 🟡. What D-103 already provides is the control, and it is the only one there will be: the editor prints the resolved set before an edit to a shared expression saves, so the person editing sees, at least once, the thing they are changing backwards in time. What is not kept is a history of inner expressions. D-103 accepted this as the price of reuse; D-110 makes it an explicit consequence for the audit question instead of an implication.

    The one asymmetry that survives, and it is the real residue. A group still answers "was she in it on 1 June 2024?" from dated rows, and an audience still does not. D-110 settles what an audience records, not what it can reconstruct, and the guidance this entry already gave stays the guidance: a set you must be able to reconstruct across time is a group, not an audience — which is now advice backed by a ruling about the record rather than by a gap in the storage.

    What reopens it. An incident, not a gap. Specifically: a question asked during an actual safeguarding or dispute review that a recomputation could not answer, because that is the moment the promise these documents just declined starts costing something, and D-110's honest boundary ("possible, never promised") is the sentence that will be quoted at somebody. A second trigger is the D-112 size trigger, since a recomputation over years of data is cheap at a few hundred people and may not be at a few thousand.

    Question. "Whom did this grant reach on 1 June 2024?" is answerable for a group — its roster rows are dated — and unanswerable for an audience, whose expression is evaluated live. D-103 makes that sharper: with AUDIENCE(code) a rule can now contain another rule, so the set reached in 2024 depended on the shape of an expression that nothing has stored a copy of, edited ever since. The one place the old shape existed is the audit trail, and its payloads expire after 24 months (D-088). So past a two-year window, a nested audience's past reach is not reconstructable at all — not imprecise, unavailable. Is that acceptable, or is this the case that finally justifies F-7's materialized table?

    Why this is the strongest version of F-7's argument, and why it is stated separately. ~~F-7 is framed as performance and answered "start with cache-only"~~, which is right on its own terms. (Two corrections from later rounds, both against this sentence rather than this entry: F-7 was dissolved in round 13 and never answered, and D-114 has since deleted the cache-only arm the recommendation preferred — so there is no longer a first arm to start with, and a materialized table would arrive on its own merits at D-112's trigger. The question raised below is untouched by that, and is the harder one.) This question is not about speed: it is that the audit trail's short half and the question's long half do not overlap. A safeguarding question ("who could see this child's record while X was treasurer?") is asked years later, of a system whose expressions are recomputed from state that has moved, over a set — referenced audiences — that nobody versioned. D-103's own note that the listing matters "more than it looks" is the same observation one hop away.

    The uncomfortable symmetry, which round 11 made sharper. D-098 kept person_group_member and audience_member as two dated sets of people on purpose, and refused to unify them, because a group states its members and an audience computes them — and that refusal is exactly what made one of them answerable across time and the other not. D-105 deleted the second of those two tables, so the pair these documents have to live with is now a group's dated roster against a PERSON(x) leaf that carries no date at all. The hand-written set, which used to be the half of an audience that could answer "was she in it in 2024?", moved to the unanswerable side along with the rest of the expression: same asymmetry, one table narrower, and worse in one specific way — a set somebody keeps by hand was the cheap instance of the reconstructable answer, and there is no hand-kept set left inside an audience that can give it. Any answer here still pushes toward making an audience a dated snapshot series, which is what D-101 refused to store and D-098 refused to merge; what changed is that the pressure now arrives from the plainest audiences in the system rather than from the nested ones this entry was written about.

    Positions. Accept it, and write it down — these documents state plainly that an audience has no reconstructable reach beyond the audit window, and that a set you need to be able to reconstruct is a group (cheap, honest, and consistent with D-098's "a group states its members; a selector picks them"; this is the default these documents currently assume). Materialize dated expansions for audiences a live grant names — F-7's option, arriving with a sweep that must not fail silently, since a silent refresh failure is an access bug nothing detects. Version the expression instead of the result — an audience_revision row per edit, small because it is a tree of ids, which answers "what did the rule say" but not "whom did it reach", and is a much cheaper promise to keep.

    What round 11 did to it: it widened the hole and raised the value of one answer. D-105 did not dodge the history question — with audience_member deleted, "who was on this audience in 2026?" joins the questions that are a recomputation over audit payloads, the payloads expire after 24 months (D-088), and so the question stops being answerable in 2028: the same hole, one table wider, accepted rather than papered over. What moved is the worth of the third position. audience_revision used to answer "what did the rule say?" and to stop there, because the hand-typed people lived outside the rule in a table of their own. A name somebody typed is now part of the rule, so versioning the expression versions the names with it: for a hand-written set — and for exactly that part of any audience — a revision row now answers the reached-set question outright, dated by edit rather than by validity, which is the as-of/audit-time distinction the glossary insists on rather than a new one. It still answers nothing for GROUP(x), ROLE(x) or a referenced audience, all of which move under an expression without being written in it. A narrower promise than the entry implied, and a real one. The colour stays 🟡: this is the same question with more evidence behind one option, and still no question implementation waits on.

    Recommendation. The third, plus the first. Storing the expression per edit is nearly free, it is the question a reviewer actually asks, and it keeps the answer honest about what it is; the reached set stays a group's job and these documents should say so out loud rather than leaving a reader to discover the gap during an incident. The second only if a real question demands it, and then decided together with F-7 rather than as a history feature, because a maintenance sweep that can fail silently is the same liability either way.

    Schema impact. One append-only table (audience_revision, or a dated copy of audience_operand); or materialized expansion rows and the sweep that keeps them true; or nothing, and a sentence in domain/06 and the glossary fixing what an audience does not promise. Note the tension with D-101's design note that an audience's history is not stored — whichever way this goes, that note has to be checked against it.

    Needed. Before someone asks the question during an incident, which is when the answer gets written as an emergency migration.

    F-22 ✅ Closed — the editor may fold and flatten for display; the stored canonical string never changes¶

    Answered, as an editor decision with one hard limit on it. The first position below is the answer. The editor may fold a sum of same-kind leaves onto one line and render PERSON(a) + PERSON(b) + PERSON(c) as a list rather than as thirty-nine pairs of brackets; it may do the same for any sum of like operands. What it may not do is change the stored canonical string. The rendering is a rendering, and these documents now say so in one place: display is free, storage is not.

    Why the limit is load-bearing and not aesthetic. D-105's ruling that the tree is stored exactly as its author wrote it is not a nostalgia rule, and this round's F-14 is the reason it cannot be bent for comfort: the stored form is the only identity an expression has, and the write-path checks — the cycle walk over the reference closure, the reserved-name rule, the listing of which grants name an audience — all reason over that. An editor that stored its own tidier spelling would be rewriting the expression it was handed, which is the one thing D-105 named as making a stored grant mean something nobody wrote. So the flattening happens on the way to the screen and never on the way to the row, and a reviewer who needs the exact stored text — during an incident, or a diff, or an audit export — can still be shown it, because nothing overwrote it. This is the same ruling F-14 reached from the other side: sorting + children so duplicates collapse is refused for being a storage change, and this entry refuses the identical temptation for being legible instead of being tidy, which is the more persuasive version of the same error.

    What is not decided, and stays open inside a closed entry. Nothing here sets a size at which a writer is told to reach for a person_group, and the second position — refuse above a size — stays refused for the reason this entry already gave: an editor that blocks the safe action teaches the unsafe one, and here the unsafe one is inventing a group that other grants will read, which is the exact widening D-105 spent its entry arguing against. D-105 named the destination (a set big enough to be unreadable is a person_group) and no round has set a trigger, and none needs to: the flattened rendering removes the pressure that would have made a trigger necessary, and the judgement is left where it was always going to be left, with the writer.

    EV-6 🟡 WHITELISTED — the word people reach for, with no stored state to name¶

    Question. D-102 named four attendance tiers a grant may bind to and refused a fifth (PRESENT, refused because was_present is NULL until somebody marks it). WHITELISTED keeps coming up in the same sentence and there is nowhere in the model for it to read from: no flag on event_registration, no roster on event besides organizers, no column anywhere that says this person was let in. Should the language refuse the word, or should the model give it state?

    The half that is already answered, and should be said before anything is built. "These named people may register for this event" needs no new anything: it is an allow grant on the event naming event.register_self, aimed at an audience whose expression is the hand-typed PERSON(a) + PERSON(b) or names a GROUP — one row per sentence, revocable, audited, and dated by the grant rather than by the names, since the dated rows those names used to live in are deleted (D-099, D-102, and D-105 for the deletion; F-20 settles which of the two spellings a given sentence wants, and this entry does not). That is the D-102 answer to the sentence, and it is better than a flag because a flag cannot be aimed at a group, cannot expire, and cannot be refused by a deny. Anyone adding is_whitelisted is reimplementing grants badly.

    The half that is not answered. There is a different sentence that sounds identical and is not about permission: "she was invited, ahead of the public opening, and she has not answered yet." That is a fact about a person's standing on one event, and the model cannot state it. Worse, the tiers actively misreport it: PLACED is the capacity set, so an invited person who registers onto a full event is ON_WAITLIST — the model says waiting where the organizer's head says has a place, we made room — and D-065 records an organizer exceeding capacity by report, not by state. So the overrun is real, visible in a report, and invisible to any selector, which means a grant aimed at "the people we actually have room for" and a grant aimed at "the people we invited" are the same four tiers stretched over two different questions.

    Positions. - Refuse the word — say plainly, where the tiers are listed, that there is no WHITELISTED and that the sentence it wants is a grant. Consistent with D-102's refusal of PRESENT, costs nothing, and leaves the invited-but-unanswered person described the way unanswered already is: by the absence of a row (D-059). This is the default these documents hold today. - Give it state — a boolean or small status on event_registration, which makes it a fifth tier and forces the tier algebra to be restated: is an invited person PLACED by right, or only once capacity lets them through? Whatever is chosen, PLACED's definition — the set the capacity let through, the one the index already serves — stops being one predicate, and that is the cost, not the new column. - Make it a group — the invitation list is a person_group (D-098), named, dated, and separately answerable across time. This is cheap and it is almost right: it says who was invited, which is the fact people actually ask for later, and it is answerable on 1 June 2024 in a way an audience never is. It is wrong for the per-event case, because it makes an invitation a thing with its own lifetime.

    Needed. Not before implementation, and not before someone asks — but the word should be refused in writing now, in the same paragraph that refuses PRESENT, because "no WHITELISTED" is a sentence that has to exist somewhere before the first person implements it as a column. The PRESENT refusal is the precedent to copy: it was refused for a representable reason (nothing is stored until a person marks it), and this one needs its reason stated rather than inherited.

    Impact. Refusing costs a paragraph. The column costs a restated PLACED, a re-derived index, and a report that now has two ways to be full.

    AT-1 🟡 Should an event question bind to an attribute code?¶

    Raised by D-085, which made the event form the fallback rather than the ceiling.

    The situation. A returning camper types their allergy into every event form, every season, and the answer lives in event_answer.value for that event only. Meanwhile the organization may already hold the same fact as an attribute on the person, with a name, a value_type, and a recorded author. Nothing connects them.

    Why this is a question and not an obvious improvement. Prefilling an answer from the record makes the record the thing a leader relies on, and the record is: whatever was typed, by whoever, possibly two years ago, with no obligation on anyone to update it. Today's arrangement is worse data and better epistemics — the form asks now, about this event, and the answer is dated today. Bind the two and an out-of-date attribute becomes a wrong answer that looks authoritative, which is the one failure mode a health fact has that makes it dangerous.

    Recommendation. Prefill as a suggestion the registrant confirms or corrects on the way in, and write the confirmed value back to the attribute with today's date and this person as its author. Then the form stays the authority for the event, the record gets refreshed by the act of using it, and nobody ever relies on a two-year-old entry without a human having just looked at it. The variant to reject is reading the attribute directly into the organizer's view without the registrant's confirmation pass — that is the same convenience with the safety removed.

    Impact. One binding on the question definition, one write-back rule, and a rule about which is authoritative when they disagree. No new permission.

    See: D-061 (as amended), data-model/08 §7.

    AT-2 🟡 Who curates the vocabulary, and how long may a proposal sit?¶

    Raised by D-084, which made attribute.define a permission instead of a release.

    An open vocabulary is only as good as somebody tending it, and "somebody" is currently nobody in particular. Two halves:

    • Who holds attribute.define. The starting role set (permission-catalog §11) is the place this gets answered, and the honest answer is that a volunteer organization has one or two people who will do this and not a committee. Too narrow and the proposal queue is a bottleneck that teaches people to file facts into notes instead; too wide and it is not a curation.
    • How long a proposal may sit before it is promoted, merged or discarded. The check exists (09-attributes §8 checks 1 and 2) and the number does not. A quarter is a defensible default: long enough that a seasonal field is not judged off a single use, short enough that a proposal is answered inside the season that produced it.

    Recommendation. One named role, a stated age limit on proposals, and a standing decision that an expired proposal's values stay — the curation is about the name, never about deleting what was recorded.

    Impact. Configuration and one role, no schema change. The thing it prevents is the slow failure: a vocabulary nobody curates stops being queryable and the layer keeps storing everything, which looks like success for years.

    AT-4 🟡 Is one permission enough to guard a trail that holds person data?¶

    Raised by the reversal recorded in D-083, which decided the audit trail does hold a person's descriptive values — because D-085 made that trail the only history such values have, and stripping them would have made the history empty while quietly grading health-shaped fields above a change of address. What protects the copy is then one thing: audit.view, graded ⚠⚠ beside person.view (permission-catalog §8). Three positions exist and none is recorded as taken:

    • Per-entry filtering in the history view: show an audit row's values only where the reader could also see the live field.     • Split the permission: the trail's shape (who changed which table, when) apart from its payloads. Honest about what an auditor usually needs, and it is the option that reintroduces a sensitive subset through the back of the catalog — which is why the documents do not recommend it.

The rule the communication section had promised — "a rule against contacting minors directly" — is therefore not implemented, and it is worth being blunt that this is the most consequential unanswered question in the file.

    Why restricting senders is the wrong fix here. An age branch in the resolver is what D-070 refused for events, on the grounds that a condition evaluated at check time which the capability model does not know about becomes the first rule in a rule engine nobody wants. It would also be the kind of restriction that gets loosened the first time it inconveniences a leader, and a permission that is routinely bypassed on a messaging system is worse than none, because it makes the bypass normal.

    Recommendation — restrict visibility, not permission. Mirror direct messages reaching a minor to that minor's guardians, and make the mirroring visible to the sender. Then:

    • nothing is blocked, so the resolver still has no age branch;
    • nothing is secretly unread, which is the actual safeguarding property;
    • it is built on the guardianship rows the organization already maintains, so it needs no new authority concept;
    • and it degrades honestly — a child with no guardian on record gets no mirroring, which is the same safeguarding gap check 4 in data-model/04 §6 already alerts on, arriving through a second channel.

    The variant to reject. "Only guardians and unit leaders may message a child." That is the restriction wearing the visibility recommendation's clothes: it is a sender rule, it needs the age branch, and it silently tells a child that the adult messaging them has been vetted — which the model does not establish, and the organization records no background checks (D-043).

    Answered (round 6): the recommendation is adopted, as D-082 — mirror to guardians, tell the sender, block nothing. Three details were settled with it, because "mirror it to the guardians" does not by itself say who the guardians are to this message:

    • Which guardians. Those whose right level is view or write. A guardian at none receives nothing: none is the organization having already decided that this party sees nothing about the child, and a safeguarding rule is not a licence to undo a recorded decision by side effect. A minor whose guardians are all none is therefore reported with the minors who have no guardian at all — otherwise the exclusion would be a way to make a child silently unwatched.
    • Which set, as of when. The guardianships open at the moment the message is sent, frozen into the delivery. A guardianship closed afterwards does not lose its mirror, and a guardian added later does not acquire old threads — same discipline as 06-audit §2, which keeps the trail answering "what was true then".
    • Broadcast is not mirrored. A scoped broadcast is already addressed to a set, recorded, and attributable; mirroring exists for the private case, which is the one that can be invisible.

    What mirroring is not. Not approval, not a gate, and not evidence anyone read it. It buys the one property the safeguarding argument actually needs — no private conversation about a child is secretly unread — without putting an age into the resolver.

    See: D-082, permission-catalog's message row, glossary — Mirroring.
