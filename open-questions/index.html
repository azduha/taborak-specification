    Open Questions¶

    Everything still unresolved, each with its schema impact — what changes once you answer. Ordered roughly by how much they block.

    Marked: 🔴 blocking something else · 🟡 important · 🟢 can be deferred.

    Resolved items are not deleted. They are moved to the bottom of this file with a link to the decision that settled them, so the reasoning survives — see § R. Resolved.

    A. Blocking the core design¶

    A-1 ✅ Closed — the unit type vocabulary is not seeded at all¶

    Answered: the sub-unit vocabulary is not a question the specification can answer, so it is not seeded (D-054).

    org_unit_type is runtime data, like role (D-052). The seed contains the root type and nothing else; the organization creates the types it uses. The previous placeholder — pack/group/team, and before it a national/region/district ladder — is gone.

    Why this is a better answer than a correct list would have been. The organization's own vocabulary is not knowable at specification time, and a wrong word in seed data is harder to dislodge than an absent one, because it reads as a specification to whoever implements the system. The shape was always the settled part: one root, arbitrary nesting beneath it (D-035).

    What remains true and worth knowing. Nesting is permissive by default — org_unit_type_rule is seeded with nothing, so any type may sit under any other until the organization states a rule, and a new type is usable the moment it is created. Every rule added later is a constraint deliberately chosen. The words pack, troop and section still appear across these docs as illustration only — read them as "some sub-unit type the organization has defined".

    See: data-model/02 §10, domain/04 §1–2

    A-4 (remainder) 🟢 The organizational calendar¶

    Answered. The fee expires on 1 January (D-047) and the renewal window is 60 days (D-048).

    What is left is not a question but a discipline. Both values live in membership_type as columns — expiry_month, expiry_day, renewal_grace_days — so either can be moved by an UPDATE. The one way to lose that property is a scheduled job or a front end that contains the literal 60 or 1. Worth one line in code review: do these values come from the row?

    See: data-model/03 §1, domain/05 §6

    B. Identity and history — closed¶

    All four are answered, in round 8. What is kept below is the reasoning, because each of these answers bought something and paid for it, and the payment is the half a later editor is tempted to forget.

    B-1 ✅ Closed — thousands of roster rows, numbers present, no payment data¶

    Answered: thousands of rows, one export, 1990s to now, a legacy member number on most of them, no payment data, and free-text columns alongside (D-090).

    Re-described one round later, and read this note before the answer above. The corpus's second half is not a roster: the rows are people with their membership periods at the root, and events with attendance, and they name no units at all. D-092 retires the roster frame and D-093 lifts the ban on imported memberships that the reasoning below had made absolute one round earlier. The corrected shape is in C-5. What survived untouched is everything this item was about — the volume, the legacy number, the absence of money, and the attribute vocabulary arriving from the free-text columns. Its heading is left as written so the links into it keep working: it is closed, on a different description of the file.

    The corpus answers the question the import was going to default. This item's own warning was that membership-vs-participation gets harder with volume, because an inferred open-ended membership makes every 2003 roster a current member with authority today (D-039). That defect never arrives: the import carries no payment data at all, so the exception arm of "participation unless there is payment evidence" has nothing to fire on. Every historical row is a unit_participation; membership rows come only from the current register. The default was correct and is now simply the rule (data-model/06 §6 drops the question accordingly).

    What is unchanged, and was the reason this was worth asking. The legacy number goes to person_identifier with scheme = 'legacy', imported verbatim and never reissued; where it is present the match is exact, and the heuristics in domain/03 §4 are for backfilling it rather than for deciding identity. D-004 is strengthened, not relaxed: at this size the number-bearing rows are the trustworthy set and the rest is a work queue a human settles.

    One consequence this answer created that no earlier document predicted. Under D-084 every leftover free-text column becomes an attribute code, so one file arrives carrying the organization's descriptive vocabulary. Those codes are live on arrival — a curator reviewed the map as one object, which is why the map lives on the batch (data-model/06 §3) — and proposed keeps its meaning of improvised later by a person at a desk. Letting several hundred codes arrive proposed would open the curation queue full and teach everybody that its age signal is noise.

    Still unknown, and still operational. The exact count and the exact year range. Both are inputs the batch carries; neither touches a table. What they do decide is A-4's arithmetic — with attendance and no money, 06 §3.1 is the load-bearing section of the import and the year boundary is what an end date gets inferred from.

    B-2 ✅ Closed — merge chains stay, because unmerge is required¶

    Answered: chains, and an explicit unmerge (D-087).

    The answer ran the argument backwards, which is the interesting part. Chains were chosen because flattening would make unmerge nearly impossible — an assumption resting on a capability nobody had asked for. You asked for it, so now the capability is the requirement and the chain is its consequence. Flattening is closed off, not merely slower, and "flattening is faster" is no longer a trade against tidiness but a trade against a feature someone named.

    What the question's own framing got wrong. It costed the two options in query speed. The real cost of a permanent chain is that it needs rules it did not have: a cycle must be impossible at the merge (a merge is refused when the chosen survivor resolves to the person being absorbed — checked on the way in, never by a read-side hop limit, because a step limit's only achievement is choosing which wrong answer to return), and chain length becomes a signal — resolution has no bound, but a chain over three hops is reported, because four merges on one line of people is a statement about the matcher's queue and not about the row. 01-identity §10 treated "survivor itself tombstoned" as a breach; with chains decided, that is normal, and only the length means anything.

    The asymmetry worth remembering. A merge can be undone; the merged period cannot be. The four reversal steps in domain/03 §6 lift the tombstone and return rows created before the merge, but rows created inside the window — above all the access_grant rows, which are flagged rather than guessed — stay one row's history, because the grants exercised there really were exercised by somebody the record can no longer separate. Unmerging needs no new permission code: undoing an identity correction is the same act as making one, so it is person.merge.

    B-3 ✅ Closed — the accounting skeleton is permanent, the audit trail is short¶

    Answered: the skeleton stays, the trail ages out (D-088).

    The two clocks, which are deliberately opposite. membership, fee_obligation, payment and the anonymised person row: no clock, because that is the organization's own history and the shape this item had already settled ("redact the person, keep the skeleton") is now justified rather than merely unopposed; redaction_log.retained_reason has a real value to hold. audit_log: payloads for 24 months, rows forever — after the window a row is reduced, old_values/new_values emptied, everything else standing, so the trail answers "who changed this, when, and were they allowed to" for the life of the system and stops answering "and to what" after two years.

    What this pays for, and it is not free. D-086 accepts that audit.view exposes whatever the payloads hold; a bounded window is the cheapest control that organization will ever get for that, and it is the strongest thing AT-4 will hear. What it costs is the history that D-085 was justified by. Values live in one overwritten row, the copy of them depends on a write path remembering to log, and the copy now expires — so "what did we believe about this child in 2019" is unanswerable twice over, and the honest description of the trade is no long history, not merely no temporal columns. If a case ever needs the long version the fix is temporal values (D-085 reversed), not a longer trail, since stretching the trail stretches exactly what D-086 graded and D-083 refuses to duplicate.

    Also: the legal review this item asked for is narrower now, not gone. Indefinite retention of named membership and fee rows is a claim that needs a basis, and a decision log cannot grant one; what exists to review is now a concrete policy instead of a blank, and it is recorded as an assumption with a name attached rather than as settled law.

    Residual, non-technical. Confirm the accounting retention period with whoever is liable for the books, and confirm the same 24-month window for access_log (F-8, proposed at the same value).

    B-4 ✅ Closed — one live account; a colliding sign-up files a claim¶

    Answered: refuse, and queue a claim (D-089).

    The rule that enforces it, and it is not a new table. One live account per person stands (01-identity §4); joined to it, an account may not reach active while an unresolved identity_hypothesis names its person. The identity review queue already existed, already records its signals and already has a role for it, so the collision case is a gate on activation plus a hypothesis raised at sign-up — no fourth queue, no new permission (person.merge, already held by identity_reviewer).

    Where the danger actually sat, and the threshold is the whole answer. The tempting version — link automatically once the e-mail verifies — is D-004 under another name, and its failure mode is one human's descriptive data becoming another human's record. The version you chose has its own failure mode, which is a brand-new person blocked by a false positive, so the trigger is a strong match only (exact legacy number, or exact birth date with a normalized name) and the soft scoring band must not raise a hypothesis at all. Two obligations come with it and both are checks rather than intentions: an age check on a hypothesis that is blocking an account, alerting rather than logging, because a stalled identity queue is now a specific child who cannot sign up for a camp; and a refusal that confirms nothing, since a sign-up form that answers "yes, that person exists" is an existence oracle over a roster of children.

    The everyday case is not this case. "I have a new e-mail" was never a second account — account_credential holds many credentials for one account, so it is an addition to the login a person already has. The collision case is a person arriving through a door the system did not know they had.

    C. Organization — closed¶

    Six questions, closed in two rounds. C-2 was resolved long ago and never appeared here: a unit may not be reparented at all, so a unit that moves is a new unit (D-036).

    C-1 ✅ Closed — the root may not read into its sub-units¶

    Answered in round 3, closed here for tidiness: no — scope_exposure is the only crossing, and no reporting channel is built (D-049).

    What was not obvious until it was answered. The question existed on the assumption that the root needed a way around the no-inheritance rule in order to report nationally. It does not, because the root owns the membership registry and the fees — so "how many members in 2019?", "who is currently a member?" and "what fees are outstanding?" are all answered from the root's own tables, with no exposure at all. Only the sub-units' own material — their events, their rosters, their local leadership — requires one.

    The consequence that will be misread as a bug: registrar holds unit_participation.view at organization scope and cannot read a pack roster. Scope is an exact match; it reads the root participation rows, which mirror membership (D-041). See domain/06 §2.4. D-094 gave this the same shape in the other direction: imported events belong to the root, so a unit-scoped "our events" report sees historical camps it did not run — a date filter, not a unit filter, is what makes either list mean what it looks like it means.

    C-3 ✅ Closed — a reused unit number is a new unit¶

    Answered: a new unit, unless somebody records the continuity (D-096).

    The question came back as a question, and that was the answer. Asked whether a number appearing twice across decades is one unit or two, the reply was "what is a unit number?" — which is the right thing to ask, because a code turns out to be a short human label somebody types (T12, 4. oddíl), not an identity, not a name (names are temporal rows in org_unit_name), and not unique: uniqueness is per parent among live rows, which is precisely why a closed unit's number is free again (data-model/02 §3). A label that gets retyped is not a continuity.

    What was decided, and what was refused. One org_unit per unit that existed; continuity is an assertion, written as org_unit_relationship with successor_of, never a match on the label. The opposite default is what "match on code" does if nobody says, and it invents a thirty-year lifespan. What this lost is almost nothing, and the reason is C-5: the corpus names no units at all, so there is no import-time collision to get wrong. This question outlived its urgency by exactly one round, which is worth knowing when reading it.

    See: domain/04 §3, §6

    C-4 ✅ Closed — a group is filled by a rule and a list, and appointing creates nothing¶

    Answered: filling rules on groups, and the two things the model refused to do (D-091).

    The question was about a convenience workflow and the answer was about the group model, which is why it is the largest decision of the round. Asked whether appointing someone to a position should create the matching role assignment, the answer described filling rules: each permission group states who is placed in it on top of the manually added people — "everyone with membership", "a leader role", "anyone", "members of permission group ABC" — with worked examples from a system where a group's population derives from enrolment in a course.

    Three of those four rules already existed (everyone, all_members, unit_leaders), which is the quiet part of the answer: an appointment creates no role assignment, because the derivation belongs on the group's rule rather than copied per appointment, where it would have to be found again and revoked. (Positions are deleted, D-100 — see the round-10 note at the end of this entry.) Two parts were forbidden and are now decided:

    • A group is a rule and a list. audience.kind's builtin-XOR-group split is gone; membership is the union of a rule arm, a manual arm and an inclusion arm.
    • A group may include another group. The one-line ban — "They do not nest" — is withdrawn, and its reason (cycles, unpredictable answers) is answered the way D-087 answered the same reason for merge chains: the cycle is refused when the edge is saved, not defended against in the read path.

    What was deliberately not taken from the answer. In the system described, permissions sit on the group; here a role is still held by one named person, because role_assignment is the office record that answers "who was treasurer in 2023" and a derived holder list cannot. That extension is F-12, not a silent schema change.

    What it costs, and where to look for the bill. A grant's reach is no longer visible in the row that grants it, so the editor must show the expanded set; and "who could read this in 2023" now depends on a recomputation of sets that were never stored, on state that has moved, with the audit payload that also held the answer expired by D-088. F-7 is the route back and is no longer only a performance question.

    Round 10 redrew the line this answer drew, and it still holds — in a different place. D-091's "a group is a rule and a list and other groups, unioned" is no longer how a set is built: an audience is now an expression tree over named sets with + - * and brackets (D-101), and a group is the opposite of a rule — a person_group states its members and nothing derives them (D-098). So the union that D-091 built into one table became an operator in a language, and the hand-kept list that D-091 insisted on survived twice over: as LIST inside an audience, and as the whole content of a group. The two halves of D-091's answer that were refusals — an appointment writes no assignment, a cycle is refused when the edge is saved — both stand, the first confirmed by D-100 and the second widened to references across audiences by D-103. What is now dead wording here is audience.kind, the unit_leaders rule, "level", and the link to §4 of domain/04, which was about positions.

    See: data-model/05 §8, domain/04 — its §4 held the positions this round deleted

    C-5 ✅ Closed — the corpus names no units, and none are assigned¶

    Asked, and answered by correcting the premise: the corpus is people and events, and it says nothing about sub-units (D-092, D-093, D-094).

    This question was not in the register. It appeared when B-1 was read against the unit model: the import matches roster rows to org_unit rows, org_unit.unit_type_id is required, no sub-unit type is seeded (D-054), and the pipeline's only documented behaviour for an unknown unit is a warning that does not block. Something had to create those units, and nothing said what.

    The answer removed the question. The rows are mainly "person with names, birthdate and when they were members of the root unit", "events with attendance". Not much more — do not solve assignment to org units. So:

    • People arrive as a person plus a bounded membership — D-090's absolute ban on imported memberships is narrowed to what it was protecting, never open-ended and never inferred from attendance — and ~~each membership brings its root participation row with it, as 03-membership §5.1 requires~~. That obligation is gone (D-097); what survives of the sentence is the part that was load-bearing for the import: an imported membership is bounded at both ends, always. No fee_obligation is created: the corpus has no money, and an obligation per historical year would arrive as debt.
    • Events arrive ~~owned by the root, which satisfies D-058's exactly-one-unit with a rule instead of a judgement~~ — withdrawn by D-102, which deleted event.org_unit_id and with it the question of who an imported event belongs to; the import writes an event row and registrations, and owes one answer-view grant per event row instead (F-10 shape 1). Attendance becomes registrations — with not_attending written for nobody, because an export lists who came and silence is not a refusal (D-059).
    • Units are not imported, not created, and not matched. The parser keeps its parsed_unit_code for the day an export surprises someone; nothing reads it.

    The consequence to keep in sight: the historical record contains no sub-units. "Who was in pack X in 2011?" has no answer on day one — not a wrong one, none — and the first answer it has will be typed in by hand. Nothing in the model is missing; the source cannot say it. This is also the round to note that B-1's closure now rests on a different description of the corpus than the one recorded in it, which is why B-1 carries a pointer rather than an edit to its own wording.

    See: domain/03 §7, data-model/06 §3.1

    C-6 ✅ Closed — units carry no restrictions; joining one is somebody else's act¶

    Answered: no restrictions on units, and no self-assignment anywhere (D-095).

    Asked whether a unit type marked allows_minors = false should refuse a minor's position as it refuses their participation, the answer refused the premise from both sides: a unit does not have any restrictions — however, persons can't assign themselves; they will be assigned to the unit by the counselors — and on entry, into the root unit there is a fee; into the sub-units there is no fee, it is entirely managed by the organization, including adding more members.

    Two entry paths, one gate each. The root: you pay, and the membership flow is the only self-service entry in the system. A sub-unit: somebody else writes the row, through unit_participation.manage held at that unit, with no self-scoped variant and none to be added; the same for position assignment. No fee anywhere below the root, and no model wants one.

    What was deleted, and what that leaves. org_unit_type.allows_minors goes, with the check it drove and the seed's allows_minors = false on the root type — a flag documented as a safeguard and enforced on one of two write paths is a receipt, not a safeguard. D-081's requirement is answered with a change of kind: the rule "do not place a child where nobody supervises them" is now enforced by who may write the row — an audited write by a named adult — rather than by a boolean on a type. It is a stronger control for the wrong-person case and it is silent on the which-units-are-for-children question, which the system can no longer answer at all; with D-043 recording no background checks either, that is the whole of the organization module's safeguarding story, stated where it can be argued with.

    See: domain/04 §1, §4, data-model/02 §1

    F-6 🟡 The permission cache lifetime, and what invalidates it¶

    Retitled, because round 10 moved the weight of this question. It used to be "how long may an answer be reused", with the invalidation list settled underneath it; the list is now the hard half and the TTL is a number nobody can pick until the list is.

    Question, in two parts. (a) What TTL is acceptable on a resolved (person, permission, item) answer? (b) What events invalidate a cached answer, and how wide is each one's fan-out?

    Why the key changed shape. The answer used to be a function of a person and a permission, with a scope that was either the organization or a unit somewhere in a tree. D-102 made the reached set depend on the item itself — a bound operand like PLACED or ORGANIZERS means the same grant says something different about every event it is written on — so the item must be in the key, not merely the scope type. Two consequences worth stating before anyone builds this: an item-scope grant can no longer be answered by one cached row per person, and a per-item preview is a per-item cache entry (F-15).

    Why the invalidation list grew a transitive edge. D-103 lets an audience name another, so a cached answer now depends on every audience its expression references, transitively — not only the ones a grant names directly. Editing volunteers must invalidate anything whose closure reaches volunteers, three levels up if something is three levels up. The walk that computes that closure is the same reachability walk the save path already performs to refuse cycles, which is the convenient reading; whether it is cheap enough to run on every edit is exactly what F-16 asks, and nothing has measured it. An invalidation that is too slow to run is not a slow feature, it is a stale allow.

    What invalidates what, as of round 10.

    Write Invalidates
    access_grant insert, update, revoke that grantee × that permission × that scope (and the unit, for the dead-weight-deny report's sake)
    audience_operand — the tree, not just the rows every answer whose expression reaches this audience, transitively (D-103)
    audience_member (the LIST leaf) the same set, as above
    role_holder everyone holding that office × each permission granted to ROLE(x)
    person_group_member everyone in that group × each permission granted to GROUP(x) — and anything naming an audience that references the group
    membership open/close, and the 1 January sweep by person, not by scope, and only where an expression contains MEMBERS — the sweep is no longer the universal invalidator it was while the gate existed
    event_registration insert, waitlist move, is_confirmed every cached answer on that event for the four attendance tiers, which are computed rather than stored
    person merge or unmerge both directions, by person id, since sets are keyed on person
    ~~a unit's parent changing~~, ~~a scope_exposure write~~ retired — the hierarchy and scope_exposure are deleted (D-097), and with them the two widest fan-outs the list used to have

    What is genuinely still a question. The TTL, and one shape of invalidation that has no good answer yet: a deny added late must be seen immediately, because the decision rule is "allowed iff some live allow applies and no live deny applies" (D-099) — a stale cache holding an allow is a permission the organization has since withdrawn, and the withdrawal is the part with the safeguarding story behind it. An asymmetric TTL — short or zero for denies, longer for allows — is the obvious answer and nobody has written it down as a decision.

    Impact. The shorter the TTL, the smaller the window in which a withdrawn grant still works, and the more load on a resolver that is now doing tree walks over operand nodes and following audience references. The per-person invalidation by the sweep is settled (data-model/05 §10, and its cache section); what is not settled is whether the transitive audience edge can be invalidated incrementally at all, which is what makes this 🟡 rather than 🟢.

    F-8 🟢 Retention policy for access_log¶

    Question. How long do the login and authorization-decision rows live?

    This entry used to answer itself, in the wrong direction. It said: partition monthly, archive to cold storage, never deletion. That is right about the rows and wrong about everything else, and the mistake is the same one D-088 made salient for audit_log: a retention policy stated as one number silently decides what the row contains, which is the part with the person data in it.

    Proposed — and it is a proposal awaiting you, not a position these documents hold: access_log takes the same window as audit_log's payloads, 24 months, with rows kept and their contents emptied on the same schedule, because a trail of who was allowed to see what that outlives the trail of what was actually changed answers the interesting half of an incident and not the other half. Monthly partitioning survives as the mechanism; it is how the window gets applied cheaply, and it was recommended long before anybody decided on a window.

    Why the question is structurally weaker here than it is for audit_log. 05-authorization §9 keeps the contents of a read out of this table to begin with — it records that a permission was exercised, not what was on the screen — so there is no payload-expiry argument and no long-history loss to weigh. What remains is the ordinary tension: a security review wants the login trail back to the start of the system, and a privacy review wants a record of somebody's late-night browsing to stop existing eventually.     F-10 🟡 Which invariants the ORM cannot express, and who writes those¶

    Question. D-072 moved the schema to an ORM. Most of what the deleted DDL asserted an ORM will generate from a model definition. Four shapes it generally cannot, and each appears dozens of times in these documents.

    The four are not equally bad, and round 10 moved them in opposite directions, which is the reason this entry changed colour. Shapes 1, 2 and 3 gained instances — the round that deleted the hierarchy spent itself inventing new temporal tables and a new expression language. Shape 4 lost its only instance, and shape 4 was the entire reason this question was red.

    1. No two open rows overlap — the temporal invariant under memberships, guardianships, grants, and — new — person_group_member (D-098) and role_holder (D-100). On PostgreSQL this needs an exclusion constraint over a range built from two columns. The two new ones are stricter than the idiom is usually generated: both state "may not overlap, counted over all rows and not only the open ones", which is the opposite of the partial-index habit this shape normally pairs with. An ORM that generates the familiar "one open row per key" version silently permits the overlapping closed row that a group member's history is full of, and the imported corpus guarantees one.
    2. Unique, but only among rows satisfying a condition — "one open request per person and type", "one primary contact among open rows", and new: audience.code unique where set (D-103), because naming an audience is optional and most audiences are a grant's private addressee list. These need a partial unique index; a plain unique constraint over the same columns is a different and wrong rule, forbidding the second NULL that history requires — and here it would forbid every unnamed audience, which is most of them. Gone: "one live exposure per unit and assignment", with scope_exposure (D-097).
    3. Anything whose answer comes from another table or from the resolver — this is where round 10 worked, and it now has five instances where it had three:
    4. Gone: the holder limit (max_holders, deleted with positions, D-100), the nesting rules and the exposure direction (both D-097). Naming them keeps the count honest.
    5. Kept: per-scheme identifier uniqueness (D-080 item 1 is this class), and one current value per (person, definition), whose condition lives in attribute_definition.allow_multiple — a uniqueness rule some definitions want and others forbid (data-model/09-attributes.md §3). It stays the cleanest example in the list: the same two columns are unique for one definition and repeatable for the next, so no partial index can be written without knowing which definitions exist at runtime.
    6. New — requiredness conditioned on another table: an audience_operand leaf must carry selector_arg_id exactly when its selector's takes_argument is true, and must leave it null exactly when the operand binds to the item (D-102). The condition is a value in selector_type, three tables away from the row it constrains, so NOT NULL cannot state it and the arity check has to.
    7. New — a check that reads another table: an AUDIENCE(...) leaf may not point at an audience whose code is null (D-103; §11 check 12 of data-model/05). Nothing about the operand row tells you this; only the row it references does. The same class carries the name namespace, now spanning role, person_group and audience.code with every selector_type.code reserved against it — no single constraint spans three tables and a fourth table's values, so the write path carries it and check 12 only asserts that the write path exists.
    8. New, and the mirror image of the rest: two rows that must coexist. Creating an event obliges an instantiated event.answer.view grant aimed at ORGANIZERS (D-102) — one row in one table requiring a row in another, in one transaction, with nothing in either schema stating the debt. A constraint can forbid a missing child or an orphan parent; it cannot make an INSERT in event write a row in access_grant. The backstop is the events with no answer-view grant report, and an organizer whose event arrived without its grant is a person with a title and no permissions — which reads as a bug report, not a constraint violation. The legacy import owes one per event row, so the first occurrence of this is expected in bulk, not at the margins.
    9. A column that may not change once it is set — its only named instance is gone: org_unit.parent_unit_id (D-036) was deleted by D-097, so this shape is currently empty. That is a fact about the corpus, not a proof, and the two candidates left are worth naming because they were previously hiding behind the dead one: permission.code — the catalog's own words are "adding one is free, renaming one is a migration", and nothing in a schema enforces a migration — and audience.code once something names it, since AUDIENCE(code) resolves through that column and a rename rewrites every expression that reached it, which is exactly what rule 5 of the name namespace promises does not happen for names.

    What made this shape different from 1–3 was that there is no report, and that is the half worth re-examining rather than inheriting. A reparent left no offending row: every row stayed individually valid while the meaning of a subtree's history moved under it, and the path the damage would show up in was itself derived and would simply be recomputed to match. audience.code has a report — which grants name this audience, and at what depth — and D-103 requires the editor to show it before saving an edit. So shape 4 is no longer the shape with no evidence, provided that listing is cheap: see F-16. permission.code needs the same query over a different table and nobody has written either. This entry is 🟡 rather than 🔴 on exactly that condition, and 🟡 is a bet, not a measurement.

    Why this is a question and not a task. The fallback an ORM offers for all four is validation in the model layer, and data-model/00 §6a explains why that is not the same guarantee: an import, a data fix, and a second client all bypass it. The legacy import is the specific case that makes this urgent rather than theoretical — the corpus arrives through exactly the path that model-layer validation does not cover, and an overlapping membership written by the importer is nearly impossible to diagnose afterwards, because the two rows look like two memberships and only one of them was ever real. Round 10 gave the import two more of these: consecutive dated periods for the same person in whatever table ends up holding them (shape 1), and one answer-view grant per event row it creates (shape 3) — a debt the importer owes in bulk, whose first failures will therefore also arrive in bulk. Add the third new graph rule to shape 3's list while the section is open: a cycle across audiences is refused at save by a reachability walk over the reference closure (D-103), which is a rule about a graph spanning two tables and is the least constraint-shaped thing in the model.

    Needed. A decision per shape — hand-written migration, database check, or application check plus report — before the first migration is generated, not discovered during one. The recommendation in data-model/00 §6a is that shapes 1 and 2 are hand-written migrations, and that this is the condition on which using an ORM is safe rather than an argument against using one. Shape 3 needs one more thing than a decision: its checks are the only enforcement the selector language has, so the arity and null-argument checks have to be written before the first expression is saved, and the §11 list in data-model/05 — renumbered for round 10, several checks having lost their subjects — is a review instruction rather than a test.

    Impact if unanswered. Not a crash. A system whose constraints are quietly absent, whose integrity checks (every "Invariants to verify" section) then start reporting rows, and whose first report is read as a data-quality problem rather than as the missing guarantee arriving on schedule.

    See: data-model/00 §6a, appendix/erd.md's inventory, which marks every temporal entity.

    F-11 🟢 Does the identity reviewer need to read the person record to settle a claim?¶

    Question. D-089 routes a colliding sign-up to identity_reviewer and resolves it with person.merge. The seed role holds person.merge, import.view and import.apply — and not person.view. So a reviewer decides "is this the same child?" from match signals, names and dates, without opening either record.

    Why this is a question now and was not one before. Merging already needed a human, but the alternative to merging was doing nothing: a wrong call left two rows side by side, visible in the nightly duplicate report, correctable next quarter. The activation gate changed the stakes. A reviewer who rejects a hypothesis lets an account go live; one who confirms it joins two lives, including a login, into one row. Both directions now have a person waiting on the far side of the answer, which is a different job from tidying a queue, and a job the permission set does not obviously cover.

    Positions. - Leave it — the signals are the decision, and a reviewer who needs to read both records is a reviewer who is about to merge on a hunch anyway. Cheapest, and consistent with "identity is what the match says, adjudicated by a person". - Grant person.view to identity_reviewer — settles it, and quietly makes an identity role one of the roles that can read a child's whole record, which is a bigger thing than the role's name suggests and is exactly what the catalog's top tier is reserved for. - A narrower read the catalog does not have yet — the resolver code that would expose only the two candidate rows and their signals, which would be a new code and therefore a decision entry, not an edit to this file. It is not proposed here, and would need arguing.

    Recommendation. Leave it, and watch the queue rather than the design. If reviewers start resolving hypotheses at a suspiciously high confirmation rate without asking for context, that is the sign the signals are not enough — and the honest response is a person.view grant discussed as a top-tier membership, not a new code invented at a desk.

    Needed. Nothing before implementation. Revisit when the first real import has produced a real queue.

    F-12 ✅ Closed — may a role be held by a rule, as an audience is?¶

    Answered: no, and the split is the design (D-100). The first of the three options below is the decision. A role is an office held by a named person for a period and it confers nothing; a group is company, a dated set of people with no authority of its own; and what reaches a set of people with a permission is a grant, which has had a grantee pair since D-042. Round 10 did not defend that boundary so much as make it cleaner than the question assumed: it renamed role_assignment to role_holder, deleted role_permission, deleted positions, and deleted the membership gate — so "everyone with a current membership holds role X" is now not a missing feature of the office table but a sentence about who the grants reach, written MEMBERS * ROLE(x) where it is wanted.

    Why the answer is no, in the decision's own terms. role_holder is the office record: it is what a report reads to answer "who was treasurer in 2023", and a holder list derived from live state cannot answer that, because there is nothing to date. D-100 keeps the two tables specifically because they answer different questions and because merging them would put 🔒🔒 role.assign in one table with ⚠ person_group.member.manage in another — the same objection this entry raised, accepted, and then sharpened. The office record stays the one human-readable answer in the permission model, which is also the resolution of assumption 51.

    What closed the other two options. Both began by putting a grantee pair on the office table. With role_permission gone there is nothing left for a rule-held office to carry, so the second arm's materialization sweep would be recording membership in a thing that grants nothing — at which point it is a group, which already exists, is already dated, and does not pretend to be an office. The third arm's cost was never worth having: it deletes the office record's guarantee to buy a row the group table already gives you. F-7 stays open and stays the right place for the materializing question; it is no longer coupled to this one.

    What the question was, kept because the reasoning recurs. Raised by D-091, which refused to decide it: the answer that produced D-091 described permission groups — a set of people with filling rules, carrying permissions — and that was expressible here for anything an access_grant could target, but not for a role, which named one person, one role, one scope, one period with no grantee pair like the one D-042 put on access_grant. ~~"everyone with a current membership holds role X" cannot be written~~ was true of the old table and is false of the language: what cannot be written, still, is a rule-held office — which is the thing that was asked for and refused.

    F-13 🟡 Should a role grant without MEMBERS be a lint warning, or only a report?¶

    Question. D-100 moved the membership test out of the resolver and into the expression, and reversed the posture while doing it: the gate used to be default-on with named carve-outs, and now every sentence about membership is written by hand. Three controls were accepted in place of the deleted mechanism — a standing report, the promise that seeded grants carry MEMBERS, and an import-time counselor count. None of the three inspects a hand-written grant at the moment it is saved. So: when somebody writes ROLE(treasurer) where they meant MEMBERS * ROLE(treasurer), should the editor warn at save, or is the standing report the whole control?

    Why it is a question and not a lint rule. The two forms are both legal and one is not always wrong — that is the entire point of the decision, since ROLE(counselors) without MEMBERS is how an appointed counselor keeps serving through a lapsed year. A warning therefore fires on the intended case as often as on the mistake, which is the classic way a warning dies. Against that: the mistake is invisible in the row (a grant with a missing operand looks exactly like a grant that was finished) and its symptom is a person with an office and no powers, discovered by the person least able to diagnose it.

    Positions. - Report only — what D-100 says today. Cheapest, no false positives, and the failure is at least aggregate-visible: a report listing role grants whose expression contains no MEMBERS term is a list somebody can read down once a period. - Warning at save, not a refusal — the editor already parses the expression to store the tree, so the test is one node lookup, and the save still succeeds. The cost is a prompt on the legitimate case, which D-100's own example shows is not rare. - Require an explicit choice — the editor asks "must this holder be a current member?" and writes the MEMBERS term or a comment field. Honest, and it is designing a new column out of a question nobody asked yet.

    Recommendation. The report, plus one narrow save-time warning: fire only when the expression names ROLE(x) for a role whose is_system is true and contains no MEMBERS term — the seeded offices are exactly the ones where the omission is nearly always an oversight, and is_system is the only signal in the schema that distinguishes "the organization's own vocabulary" from "a role somebody invented this afternoon". A convention, not a guard, in D-081's wording: nothing stops a client from writing the grant anyway.

    Schema impact. None for the report or the warning — both read access_grant joined to the audience_operand subtree. The third arm is a column. No seeded row changes.

    Needed. Before the grant editor ships, because "we warn on nothing" and "we warn on this" are different products and the second is cheaper to add first.

    F-14 🟢 Is semantic equality of two expressions worth a fingerprint?¶

    Question. D-101 gave up semantic equality to keep storage honest: two audiences are equal when their trees are equal, so MEMBERS + ROLE(x) and ROLE(x) + MEMBERS are two different stored expressions with one meaning, and the canonical fully-bracketed rendering does not fix it because it canonicalizes brackets, not order. Should the system compute a derived fingerprint — canonicalize operands into a sorted multiset per operator, normalize */- where the algebra allows — and warn when a second audience fingerprints the same as a first?

    Why it is 🟢 and why it is still here. Nothing depends on it. Two identical sets cost one extra row and one extra evaluation, and the confusion is cosmetic until someone edits one copy. But D-101 explicitly registered this as a question rather than a promise, and the failure mode it prevents is a slow one: an organization accumulates near-duplicate audiences, a grant names the stale one, and the fix is indistinguishable from a permission change — which is audited, alarmed, and requires explaining to somebody.

    The part that should not be oversold. The fingerprint is not decidable in general once AUDIENCE(code) references exist (D-103): two expressions can fingerprint differently and reach identically because the difference is inside a referenced audience, and expanding the closure to compare them is a resolver run, not a save-time check. So the honest design is a warning over the expression as written, with references treated as opaque atoms — which catches operand reordering and misses everything nested, and must say so in the UI rather than implying an equivalence proof.

    Positions. Warn on equal fingerprints (catches the common case, false-positives on deliberately identical sets like two events' ORGANIZERS); compute nothing and let the which grants name this audience listing (F-16) do the work of showing redundancy; or normalize at write so + children are always stored sorted, which makes the common duplicate syntactically equal and needs no new machinery — at the cost of storing an order the language says does not matter.

    Schema impact. One derived column on audience, or nothing, and it must never be a unique constraint: a warning that became a constraint would refuse two audiences that legitimately reach the same people, and D-101's reason for giving up equality is precisely that the two are not the same question.

    Needed. Not before implementation. Revisit when the first organization has enough audiences that someone asks why two of them behave the same.

    F-15 🟡 What does the per-item audience preview cost at real event sizes?¶

    Question. Before D-102 the question "whom does this grant reach?" had one answer per grant. Now a bound operand makes the reached set a function of the item, so an editor that wants to show whom this reaches must compute it per item: for a camp, the audience's tree evaluated against that camp's registrations, waitlist, confirmations and organizer roster. At what size does that stop being an interaction and start being a job?

    Why this arrived with round 10 and not before. The preview used to be one expansion of a rule against a set of people. D-102 made ATTENDED, PLACED, CONFIRMED, ON_WAITLIST and ORGANIZERS read the item's own tables, and D-103 made each AUDIENCE(code) node a nested evaluation rather than a row fetch — so one preview can now touch four registrations tables and re-evaluate a tree per referenced audience, and the number of people it expands to is the size of an event roster. F-7 asked whether answers should be materialized for enforcement; this is the same cost centre for preview, where staleness is a UI lie rather than an access bug — which is the softer failure and the more tempting one to ship.

    What is assumed and not measured. That expanding a few hundred people at a screen is fine, and that the tree walk is cheap because it is small. Neither has been measured against a corpus of thousands of roster rows (B-1) and an event with a real registration list, and the case that hurts is the nested audience three levels deep, evaluated once per item in a list of items.

    Positions. Preview lazily, per item, on demand, and never for a list of items (the honest default: a count, not a name list, until somebody opens one). Cache the expansion per (audience, item) with the key shape F-6 settles. Or refuse previews above a threshold and show "too many to list; export instead", which is cheap, honest, and the kind of answer a spec is allowed to give before it has a number.

    Schema impact. None for the lazy form. A cache is not a table, but the key must include the item (D-102) and the dependency set must include every referenced audience transitively (D-103), so F-6 and this are one decision about keys taken twice if they are not decided together.

    Needed. A measurement before the editor ships, because "show the set" is a promise the resolver has to keep on a UI thread. Assumption in the meantime: previews are per-item and lazy, and no screen expands a set for more than one item at a time.

    F-16 🟡 Is the listing of grants naming an audience as cheap as D-103 assumes?¶

    Question. D-103 makes two safety rules depend on one query: an audience may not be ended or deleted while a live grant — or a live audience reachable from one — names it, and saving an edit to a referenced audience must show which grants name it, and at what depth. The decision entry states its premise as an assumption: that finding the referrers is cheap. Nothing has measured it, and the whole of D-103's protection is built on it.

    Why the answer is not obviously yes. audience_operand denormalizes audience_id so that "what nodes are in this audience's tree" is indexed — that is the cheap direction. The protection needs the opposite direction: which other audiences contain a leaf pointing here, then transitively upward, then the grants aimed at each of those. That is a reverse-edge walk over a tree table, and the index that makes the forward walk fast does not serve it. A selector_arg_id index probably answers it — one lookup per level — which is exactly the kind of answer that looks certain until the first OR over selector_kind and selector_arg_id stops using it.

    Why it matters more than a UI query. Because under - an empty operand makes the result wider, not narrower: an audience that stops resolving does not quietly stop granting, it can start granting. That is why the listing is not a nicety on top of the deletion rule but the only way an editor can tell a person what they are about to widen. A protection you cannot see is a protection you will route around — and the route is right there, because naming an audience is optional, so an editor that blocks the safe action teaches people to inline the subexpression instead, which removes the reference the safety rule needed.

    Positions. Add the reverse index and state it as an invariant to verify (cheap, and it is a row in §11 of data-model/05 rather than a design change); cap the listing by depth so the walk is bounded by selector_depth_limit, which D-101 already enforces and which makes the worst case finite by construction; or drop the "and at what depth" half of the requirement, which removes the transitive walk and keeps the single-hop refusal.

    Needed. Before an editor offers to name an audience. If the answer is "not cheap", the fallback is not a slower screen but a weaker D-103 rule, which is a decision entry, not an implementation detail — and it should be taken in the open, because the property being traded is the one that keeps a deleted set from widening access.

    Impact. If the walk is slow at real sizes, either the guard is skipped under time pressure or the feature people use is the one that bypasses it. Both are worse than the measurement.

    F-17 🟡 A nested audience has no reconstructable past. Is that the case for materializing?¶

    Question. "Whom did this grant reach on 1 June 2024?" is answerable for a group — its roster rows are dated — and unanswerable for an audience, whose expression is evaluated live. D-103 makes that sharper: with AUDIENCE(code) a rule can now contain another rule, so the set reached in 2024 depended on the shape of an expression that nothing has stored a copy of, edited ever since. The one place the old shape existed is the audit trail, and its payloads expire after 24 months (D-088). So past a two-year window, a nested audience's past reach is not reconstructable at all — not imprecise, unavailable. Is that acceptable, or is this the case that finally justifies F-7's materialized table?

    Why this is the strongest version of F-7's argument, and why it is stated separately. F-7 is framed as performance and answered "start with cache-only", which is right on its own terms. This question is not about speed: it is that the audit trail's short half and the question's long half do not overlap. A safeguarding question ("who could see this child's record while X was treasurer?") is asked years later, of a system whose expressions are recomputed from state that has moved, over a set — referenced audiences — that nobody versioned. D-103's own note that the listing matters "more than it looks" is the same observation one hop away.

    The uncomfortable symmetry. D-098 kept person_group_member and audience_member as two dated sets of people on purpose, and refused to unify them, because a group states its members and an audience computes them. That refusal is exactly what makes one of them answerable across time and the other not. Any answer here pushes toward making an audience a dated snapshot series, which is the thing D-101 refused to store and D-098 refused to merge.

    Positions. Accept it, and write it down — these documents state plainly that an audience has no reconstructable reach beyond the audit window, and that a set you need to be able to reconstruct is a group (cheap, honest, and consistent with D-098's "a group states its members; a selector picks them"; this is the default these documents currently assume). Materialize dated expansions for audiences a live grant names — F-7's option, arriving with a sweep that must not fail silently, since a silent refresh failure is an access bug nothing detects. Version the expression instead of the result — an audience_revision row per edit, small because it is a tree of ids, which answers "what did the rule say" but not "whom did it reach", and is a much cheaper promise to keep.

    Recommendation. The third, plus the first. Storing the expression per edit is nearly free, it is the question a reviewer actually asks, and it keeps the answer honest about what it is; the reached set stays a group's job and these documents should say so out loud rather than leaving a reader to discover the gap during an incident. The second only if a real question demands it, and then decided together with F-7 rather than as a history feature, because a maintenance sweep that can fail silently is the same liability either way.

    Schema impact. One append-only table (audience_revision, or a dated copy of audience_operand); or materialized expansion rows and the sweep that keeps them true; or nothing, and a sentence in domain/06 and the glossary fixing what an audience does not promise. Note the tension with D-101's design note that an audience's history is not stored — whichever way this goes, that note has to be checked against it.

    Needed. Before someone asks the question during an incident, which is when the answer gets written as an emergency migration.

    F-18 🟢 Does a role record elected versus appointed, and what does an election write?¶

    Raised as a loss by D-100, not as a feature request. position carried is_leadership, min_age, max_holders and a position_assignment row, and the corpus's organization keeps an elected committee. Those columns are deleted, so the model now has one kind of office and cannot distinguish "elected for a two-year term by a vote" from "appointed by whoever holds role.assign". role_holder has valid_from, valid_to, granted_by and note, which is nearly enough to describe an election — and granted_by names the person who wrote the row, which for an election is a secretary, not a mandate.

    Question. Does a role say elected or appointed; and if so, what does an election write — one role_holder row whose note says who voted, a document attached to the row, or a row in a table that does not exist yet?

    Why it might be nothing. An election is an event in the world that the system records, not a process it runs: there is no ballot, no candidate table and no quorum rule anywhere in these documents, and D-043 settled that this system does not hold background checks either — it is not the registry of everything true about a volunteer. note, valid_from, valid_to plus a document answer "we voted and here is the minutes", and is_system keeps the seeded offices distinct from the organization's invented ones. A convention, not a guard: nothing will ever refuse to appoint someone to an office the bylaws reserve for an election.

    Why it might be something. Two things the deleted tables answered by construction now have no answer at all: the vacancy question (max_holders made "two chairpersons is one too many" a check) and the term-limit question (role.max_term_months is a per-role cap, not an electoral rule — a two-year term renewable once is a different claim from "may hold for at most 24 months"). Both recur in a Scout-like body with annual meetings, and both will arrive as one-off questions.

    Positions. Nothing — note and a document (cheapest, defensible, and consistent with the round's direction); a boolean on role that says only how the office is filled, which answers the bylaws question and writes nothing new; or an election/appointment record, which is a new module and therefore a decision entry with an actual argument in it, not a column added here.

    Schema impact. Either zero, one boolean on role, or a table plus its permission codes plus its audit behaviour. The boolean is not free either: it invites a check ("may a non-elected holder be written for an elected office?") which D-100's posture — opt-in, review by report — would refuse to enforce, and a column nobody enforces is a column that lies after the first exception.

    Needed. Not before implementation. Before the first AGM, which is when somebody asks whether the system can show that the current chair was elected.

    EV-2 🟡 Retention of event_answer¶

    The question, restated once so it stays answerable. It used to read "a dietary answer citing a medical condition is health data, and health data has a retention obligation" — and D-083 removed the second half of that sentence's subject: there is no class of health data with its own obligation, only personal data, of which a dietary answer is one instance.     Why it is not trivial. D-061 made an event form the route by which a camp leader learns a child has a nut allergy. That is a deliberate widening, and it puts health-adjacent data in a table whose protections are weaker than the health record's — and in round 6 that gap widened twice over: there is no longer a dependent.medical.* code marking which data is the sensitive kind (E-7), and the audience entitled to read an answer is whoever runs that event, a set sized by whoever creates it. The retention policy is the remaining half of that trade.

    Needed. Legal input, of the same kind B-3's indefinite retention still needs. The technical question — where does it live, who may read it — is answered; whether it must be deleted, kept, or archived is not.

    Changed in round 7, in a way that strengthens the case rather than settling it. D-083 made every fact about a person one class of data held on the person, so an event answer naming an allergy is now the same kind of fact stored in two places by two different rules — one on the person, where it is audited, curable and erased with the person; one in an event's table, readable by whoever runs that event, with no retention policy. The retention question and AT-1 are the same question from two directions: an answer worth keeping is an attribute that was collected at the wrong address, and an answer not worth keeping should be deleted on a schedule rather than surviving because nobody wrote a policy. Until one of the two is decided, the weakest-protected copy of a health fact is the one that is freshest.

    EV-6 🟡 WHITELISTED — the word people reach for, with no stored state to name¶

    Question. D-102 named four attendance tiers a grant may bind to and refused a fifth (PRESENT, refused because was_present is NULL until somebody marks it). WHITELISTED keeps coming up in the same sentence and there is nowhere in the model for it to read from: no flag on event_registration, no roster on event besides organizers, no column anywhere that says this person was let in. Should the language refuse the word, or should the model give it state?

    The half that is already answered, and should be said before anything is built. "These named people may register for this event" needs no new anything: it is an allow grant on the event naming event.register_self, aimed at a LIST or a GROUP — one row per sentence, dated, revocable, audited (D-099, D-102). That is the D-102 answer to the sentence, and it is better than a flag because a flag cannot be aimed at a group, cannot expire, and cannot be refused by a deny. Anyone adding is_whitelisted is reimplementing grants badly.

    The half that is not answered. There is a different sentence that sounds identical and is not about permission: "she was invited, ahead of the public opening, and she has not answered yet." That is a fact about a person's standing on one event, and the model cannot state it. Worse, the tiers actively misreport it: PLACED is the capacity set, so an invited person who registers onto a full event is ON_WAITLIST — the model says waiting where the organizer's head says has a place, we made room — and D-065 records an organizer exceeding capacity by report, not by state. So the overrun is real, visible in a report, and invisible to any selector, which means a grant aimed at "the people we actually have room for" and a grant aimed at "the people we invited" are the same four tiers stretched over two different questions.

    Positions. - Refuse the word — say plainly, where the tiers are listed, that there is no WHITELISTED and that the sentence it wants is a grant. Consistent with D-102's refusal of PRESENT, costs nothing, and leaves the invited-but-unanswered person described the way unanswered already is: by the absence of a row (D-059). This is the default these documents hold today. - Give it state — a boolean or small status on event_registration, which makes it a fifth tier and forces the tier algebra to be restated: is an invited person PLACED by right, or only once capacity lets them through? Whatever is chosen, PLACED's definition — the set the capacity let through, the one the index already serves — stops being one predicate, and that is the cost, not the new column. - Make it a group — the invitation list is a person_group (D-098), named, dated, and separately answerable across time. This is cheap and it is almost right: it says who was invited, which is the fact people actually ask for later, and it is answerable on 1 June 2024 in a way an audience never is. It is wrong for the per-event case, because it makes an invitation a thing with its own lifetime.

    Needed. Not before implementation, and not before someone asks — but the word should be refused in writing now, in the same paragraph that refuses PRESENT, because "no WHITELISTED" is a sentence that has to exist somewhere before the first person implements it as a column. The PRESENT refusal is the precedent to copy: it was refused for a representable reason (nothing is stored until a person marks it), and this one needs its reason stated rather than inherited.

    Impact. Refusing costs a paragraph. The column costs a restated PLACED, a re-derived index, and a report that now has two ways to be full.

    AT-1 🟡 Should an event question bind to an attribute code?¶

    Raised by D-085, which made the event form the fallback rather than the ceiling.

    The situation. A returning camper types their allergy into every event form, every season, and the answer lives in event_answer.value for that event only. Meanwhile the organization may already hold the same fact as an attribute on the person, with a name, a value_type, and a recorded author. Nothing connects them.

    Why this is a question and not an obvious improvement. Prefilling an answer from the record makes the record the thing a leader relies on, and the record is: whatever was typed, by whoever, possibly two years ago, with no obligation on anyone to update it. Today's arrangement is worse data and better epistemics — the form asks now, about this event, and the answer is dated today. Bind the two and an out-of-date attribute becomes a wrong answer that looks authoritative, which is the one failure mode a health fact has that makes it dangerous.

    Recommendation. Prefill as a suggestion the registrant confirms or corrects on the way in, and write the confirmed value back to the attribute with today's date and this person as its author. Then the form stays the authority for the event, the record gets refreshed by the act of using it, and nobody ever relies on a two-year-old entry without a human having just looked at it. The variant to reject is reading the attribute directly into the organizer's view without the registrant's confirmation pass — that is the same convenience with the safety removed.

    Impact. One binding on the question definition, one write-back rule, and a rule about which is authoritative when they disagree. No new permission.

    See: D-061 (as amended), data-model/08 §7.

    AT-2 🟡 Who curates the vocabulary, and how long may a proposal sit?¶

    Raised by D-084, which made attribute.define a permission instead of a release.

    An open vocabulary is only as good as somebody tending it, and "somebody" is currently nobody in particular. Two halves:

    • Who holds attribute.define. The starting role set (permission-catalog §11) is the place this gets answered, and the honest answer is that a volunteer organization has one or two people who will do this and not a committee. Too narrow and the proposal queue is a bottleneck that teaches people to file facts into notes instead; too wide and it is not a curation.
    • How long a proposal may sit before it is promoted, merged or discarded. The check exists (09-attributes §8 checks 1 and 2) and the number does not. A quarter is a defensible default: long enough that a seasonal field is not judged off a single use, short enough that a proposal is answered inside the season that produced it.

    Recommendation. One named role, a stated age limit on proposals, and a standing decision that an expired proposal's values stay — the curation is about the name, never about deleting what was recorded.

    Impact. Configuration and one role, no schema change. The thing it prevents is the slow failure: a vocabulary nobody curates stops being queryable and the layer keeps storing everything, which looks like success for years.

    AT-4 🟡 Is one permission enough to guard a trail that holds person data?¶

    Raised by the reversal recorded in D-083, which decided the audit trail does hold a person's descriptive values — because D-085 made that trail the only history such values have, and stripping them would have made the history empty while quietly grading health-shaped fields above a change of address. What protects the copy is then one thing: audit.view, graded ⚠⚠ beside person.view (permission-catalog §8). Three positions exist and none is recorded as taken:

    • The guard is enough (current documents). One permission, marked honestly, and a rule that whoever holds it is reading person data. Simple, and it makes the auditor role — which has audit.view and not person.view — a reader of the entire person record (permission-catalog §11 note 3).
    • Per-entry filtering in the history view: show an audit row's values only where the reader could also see the live field. Consistent with everything §9 of data-model/05-authorization.md says about channels, and it was considered and left unimplemented, because it means running the resolver per audit row against rows that may no longer exist — a grant withdrawn last year is exactly the case a history is read for.
    • Split the permission: the trail's shape (who changed which table, when) apart from its payloads. Honest about what an auditor usually needs, and it is the option that reintroduces a sensitive subset through the back of the catalog — which is why the documents do not recommend it.

    The cost of not answering is asymmetric in the uncomfortable direction: the first position is already implemented by default, so leaving the question open is choosing it, and the choice is made invisible — nobody signs off on "volunteers with audit.view can read children's medical history" because there is no moment at which anybody has to say it.

    MSG-1 ✅ Closed — a direct message to a minor is mirrored to their guardians¶

    Raised by D-077, which declined the restriction rather than forgetting it.

    The situation. Messaging has two sender tiers — direct, which everyone may do, and broadcast, which is a permission. Neither tier mentions age. So any person with an account may send a private message to any child with an account, and nothing in the model prevents it, records it as unusual, or tells anyone. This is not a gap created by oversight: the question asked whether staff may address a child or only their guardians, and the answer replaced it with a model in which age is not a sender concept at all. The rule the communication section had promised — "a rule against contacting minors directly" — is therefore not implemented, and it is worth being blunt that this is the most consequential unanswered question in the file.

    Why restricting senders is the wrong fix here. An age branch in the resolver is what D-070 refused for events, on the grounds that a condition evaluated at check time which the capability model does not know about becomes the first rule in a rule engine nobody wants. It would also be the kind of restriction that gets loosened the first time it inconveniences a leader, and a permission that is routinely bypassed on a messaging system is worse than none, because it makes the bypass normal.

    Recommendation — restrict visibility, not permission. Mirror direct messages reaching a minor to that minor's guardians, and make the mirroring visible to the sender. Then:

    • nothing is blocked, so the resolver still has no age branch;
    • nothing is secretly unread, which is the actual safeguarding property;
    • it is built on the guardianship rows the organization already maintains, so it needs no new authority concept;
    • and it degrades honestly — a child with no guardian on record gets no mirroring, which is the same safeguarding gap check 4 in data-model/04 §6 already alerts on, arriving through a second channel.

    The variant to reject. "Only guardians and unit leaders may message a child." That is the restriction wearing the visibility recommendation's clothes: it is a sender rule, it needs the age branch, and it silently tells a child that the adult messaging them has been vetted — which the model does not establish, and the organization records no background checks (D-043).

    Answered (round 6): the recommendation is adopted, as D-082 — mirror to guardians, tell the sender, block nothing. Three details were settled with it, because "mirror it to the guardians" does not by itself say who the guardians are to this message:

    • Which guardians. Those whose right level is view or write. A guardian at none receives nothing: none is the organization having already decided that this party sees nothing about the child, and a safeguarding rule is not a licence to undo a recorded decision by side effect. A minor whose guardians are all none is therefore reported with the minors who have no guardian at all — otherwise the exclusion would be a way to make a child silently unwatched.
    • Which set, as of when. The guardianships open at the moment the message is sent, frozen into the delivery. A guardianship closed afterwards does not lose its mirror, and a guardian added later does not acquire old threads — same discipline as 06-audit §2, which keeps the trail answering "what was true then".
    • Broadcast is not mirrored. A scoped broadcast is already addressed to a set, recorded, and attributable; mirroring exists for the private case, which is the one that can be invisible.

    What mirroring is not. Not approval, not a gate, and not evidence anyone read it. It buys the one property the safeguarding argument actually needs — no private conversation about a child is secretly unread — without putting an age into the resolver.

    See: D-082, permission-catalog's message row, glossary — Mirroring.
