    Open Questions¶

    Everything still unresolved, each with its schema impact — what changes once you answer. Ordered roughly by how much they block.

    Marked: 🔴 blocking something else · 🟡 important · 🟢 can be deferred.

    Resolved items are not deleted. They are moved to the bottom of this file with a link to the decision that settled them, so the reasoning survives — see § R. Resolved.

    A. Blocking the core design¶

    A-1 ✅ Closed — the unit type vocabulary is not seeded at all¶

    Answered: the sub-unit vocabulary is not a question the specification can answer, so it is not seeded (D-054).

    org_unit_type is runtime data, like role (D-052). The seed contains the root type and nothing else; the organization creates the types it uses. The previous placeholder — pack/group/team, and before it a national/region/district ladder — is gone.

    Why this is a better answer than a correct list would have been. The organization's own vocabulary is not knowable at specification time, and a wrong word in seed data is harder to dislodge than an absent one, because it reads as a specification to whoever implements the system. The shape was always the settled part: one root, arbitrary nesting beneath it (D-035).

    What remains true and worth knowing. Nesting is permissive by default — org_unit_type_rule is seeded with nothing, so any type may sit under any other until the organization states a rule, and a new type is usable the moment it is created. Every rule added later is a constraint deliberately chosen. The words pack, troop and section still appear across these docs as illustration only — read them as "some sub-unit type the organization has defined".

    See: data-model/02 §10, domain/04 §1–2

    A-4 (remainder) 🟢 The organizational calendar¶

    Answered. The fee expires on 1 January (D-047) and the renewal window is 60 days (D-048).

    What is left is not a question but a discipline. Both values live in membership_type as columns — expiry_month, expiry_day, renewal_grace_days — so either can be moved by an UPDATE. The one way to lose that property is a scheduled job or a front end that contains the literal 60 or 1. Worth one line in code review: do these values come from the row?

    See: data-model/03 §1, domain/05 §6

    B. Identity and history¶

    B-1 (remainder) 🟢 The legacy corpus is large and number-bearing¶

    Answered: large, and the old records carry a legacy member number (D-056).

    That changes what the import has to be. The number goes into person_identifier with scheme = 'legacy', and where it is present the match is exact rather than probabilistic — same number, same person. The heuristics in domain/03 §4 are then for backfilling the number on rows that lack it, not for deciding identity from scratch.

    The consequence for D-004. The "no automatic merging, ever" rule was costed on a small corpus where review was the bottleneck. At thousands of rows that changes shape: the number-bearing rows are the trustworthy set and the rest is a work queue. The rule is unchanged — the human still decides every match — but the number does the work the human would have done, so the rule becomes far cheaper to obey. This is a strengthening, not a relaxation.

    What must hold. The legacy number is imported verbatim and never reissued. The (scheme, value) index is what enforces it. A second numbering era can coexist, because person_identifier carries a scheme and a period.

    What gets harder, not easier: membership vs. participation. Volume and numbers fix identity; they say nothing about what a historical row means. At this scale a 1998 roster almost certainly records which unit someone attended, not whether their fee was paid — so the import must decide per row which of the two it becomes (D-041). The safe default matters more at thousands of rows than at hundreds, because the failure compounds: participation unless there is payment evidence, since an inferred open-ended membership would make every 2003 roster member a current member today through the gate (D-039).

    Still needed (operational, not design). The record count, the format, and the year range. Those are inputs the import batch carries; they do not change the schema.

    B-2 🟡 Merge chains: allowed or flattened?¶

    Question. If A is merged into B, and later B into C, does A point at B (a chain) or is A repointed at C (flattened)?

    Current design. Chains. resolve_person() follows them recursively.

    Impact. Flattening is faster to query but rewrites pointers and makes unmerge nearly impossible. Chains need resolve_person() called everywhere an external id enters the system — a rule application code can forget.

    B-3 🟡 Erasure: the policy, not the mechanism¶

    Question. What must be redacted, what must be retained, for how long? Does the organization have a legal obligation to keep membership records after an erasure request?

    Resolved already. The shape is settled: redact the person, keep the financial and membership skeleton — the person row is anonymised in place and the membership, fee_obligation and payment rows survive intact, because the organization's own accounting and "was this person a member on that date" questions outlive the person's participation.

    Still open. The retention periods and the legal basis. redaction_log.retained_reason is a placeholder for that judgement.

    Needed. Legal review. Not a technical question.

    See: data-model/06 §4

    B-4 🟢 Can a person hold two live accounts?¶

    Recommendation. No. Enforced by the partial unique index already in the schema.

    Impact. If yes, the index is dropped and identity attribution weakens.

    C. Organization¶

    C-1 🟢 May the root see what happens in its sub-units?¶

    Answered: no — scope_exposure is the only crossing, and no reporting channel is built (D-049).

    What was not obvious until it was answered. The question existed on the assumption that the root needed a way around the no-inheritance rule in order to report nationally. It does not, because the root owns the membership registry and the fees — so "how many members in 2019?", "who is currently a member?" and "what fees are outstanding?" are all answered from the root's own tables, with no exposure at all. Only the sub-units' own material — their events, their rosters, their local leadership — requires one.

    The consequence that will be misread as a bug: registrar holds unit_participation.view at organization scope and cannot read a pack roster. Scope is an exact match; it reads the root participation rows, which mirror membership (D-041). See domain/06 §2.4.

    C-3 🟢 Units with the same number across decades¶

    Question. When a troop closes and a new troop with the same number starts ten years later, is it the same unit or a new one?

    Impact. An organizational judgement, not a technical one — but it must be recorded, or it will be re-litigated every time someone asks about the 80s troop with that number.

    See: domain/04 §3

    C-4 🟢 Does appointing someone to a position auto-create a role assignment?¶

    Current design. Separate. position.is_leadership lets a workflow offer both.

    Impact. Purely a workflow question; the schema is unaffected.

    D. Membership¶

    D-6 — closed, by making the question the organization's to answer¶

    Answered: the mechanism (D-051). The membership gate is waived by a person-level permission, system.gate_exempt, in addition to the role-level flag. system_admin holds it — without it the 1 January sweep locks the administrator out of the system on the day it needs repair.

    And "which other roles carry it" is no longer a question for this document. Roles are runtime data: the organization creates them, edits what they grant, assigns them, and deletes the unused ones (data-model/05 §3). Marking a role as carrying system.gate_exempt is therefore a configuration act the organization performs, not a fact the specification can state. The seed set in appendix/permission-catalog.md §11 shows the shape; it is a starting point to edit, and it explicitly declines to answer this.

    What is not delegatable, and is therefore all this document has to get right: that system.gate_exempt is a system-namespace permission, so it can only ever arrive through a role and never through an item grant. That structural guarantee — an access_grant cannot lift the membership gate — is the part a configuration screen must not be able to weaken.

    Tracked here only for visibility: check 7b in data-model/05 §11 reports who currently holds the exemption, so the organization can see the list it has configured.

    D-7 🟢 What does the root-unit participation row do at renewal?¶

    Answered: it is extended, not closed and reopened (D-050).

    The yearly sweep moves the root row's valid_to forward to the expiry date rather than closing it, and a renewal inside the window stretches that one row over the new period. The join between the two is person and date (new_m.valid_from = up.valid_to), not a membership FK — the participation table has none, deliberately.

    The accepted cost, recorded rather than hidden. This erases the visual evidence of the lapse: a person who lapsed and renewed looks, in unit_participation, exactly like a person who never lapsed. Accepted because membership remains the authority on payment and the lapse is fully visible there, while the participation table answers a roster question — and for "who was in this pack when" a child who was present across the period has one answer, not two.

    See: data-model/03 §5.1

    D-8 🟢 Should unit_participation reference the membership?¶

    Question. A nullable membership_id on unit_participation would give referential integrity between "paid up" and "takes part", at the cost of being unenforceable for imported historical rows, where no membership exists to point at.

    Impact. Integrity vs. import coverage. The current design chose person-based linkage for exactly that reason.

    See: data-model/03 §5

    D-9 ✅ Closed — household is removed entirely¶

    Answered: drop it (D-057). household, household_member, fee_obligation.household_id, its CHECK arm, ix_obligation_household and integrity check 7 are all gone.

    Why removal rather than a derived view. D-037 had already taken the load-bearing half — the fee is flat and per person, so there is no family price. The two survivors were both served by tables that must exist anyway: a billing address is a person_contact row where contact_type = 'postal' AND purpose = 'billing', and "who lived at this address in 2003?" is a query over that table's own valid_from/valid_to history. The household table was duplicating the address under a second key, and the copy had already gone stale — its postal_address was documented as denormalised from the contact row, with nothing keeping it true.

    The safeguarding property is untouched, and this is the point to check first. Shared address never granted access: a child's records are reachable only through a guardianship row, whatever the household arrangement beside it. Removing a table that granted nothing cannot grant anything. D-019 stays in the log, marked superseded, because "why does living together not imply access?" will be asked again.

    The one thing genuinely lost. A household was a group with a name and its own lifetime; two people at one address are now related by a query, not a row. There is nowhere to hang "the Novák family" as a first-class thing. Accepted because nothing used it. If family-level communication or a family discount is ever wanted, the grouping comes back as a group with a period — not a fake person.

    One knock-on worth knowing. Finance question 2 (family/sibling discounts) is now more open, not less: a per-family discount needs the grouping designed again before it can be priced. A per-person discount is unaffected.

    See: data-model/04 §3

    E. Guardianship¶

    E-2 ✅ Closed — the system takes no position on majority¶

    Answered: nothing at all. No job, no review queue, no computed candidate date (D-069, reversing D-024). A guardianship is ended by a person ending it.

    What was wrong with the review queue the docs had recommended: it was still automatic, and it computed a date the system has no authority to assert. Deferring a decision is not the same as declining to make one.

    This closes E-2 and immediately opens E-5 below. With no automatic end and no queue, the only exit is guardianship.end — and the adult who is the subject of the row holds no permission over it.

    E-5 ✅ Closed — the parties administer their own row¶

    Answered: the guardian and the subject both act on the row themselves; there is no management-team route (D-073).

    All three of the shapes above were wrong in the same direction. Support request, ownership channel, and request object each assumed the answer had to come from somewhere other than the people in the relationship. It does not. A guardianship is a relationship between two people, both of them are principals on the row, and either may end it. A guardian may add another guardian. No staff approval, and no workflow invented for the purpose.

    It is not the ownership channel, which is why option (2) was the right answer for the wrong reason. Ownership is your own record; a guardianship row belongs to neither party alone. The guardianship channel simply gained a direction — from "may guardian G act on D's records?" to also "may a party act on this row?" — and the resolver still has four channels.

    The gap this closes was real, and it is now closed at the only place it could be. D-069 removed both the automatic end and the queue, leaving guardianship.end as the sole exit and the subject unable to reach it. That was a door with no handle on the inside.

    Two things this opens, both below.

    E-6 🟡 A guardian may appoint a guardian¶

    Raised by closing E-5. D-073 lets a guardian add another guardian, so anyone with authority over a child can hand that same authority to a second person with no approval from the organization. The ordinary case is a mother adding the father. The design does not prevent the non-ordinary case; it attributes it — who added whom, when, from which account, audited, with the other party notified.

    The open question is whether attribution is enough, and specifically whether adding a guardian over a minor should also notify somebody at the organization beyond the audit log. A child gaining a second legal stranger with write over their records is not the same kind of event as an adult adding a co-parent.

    Recommendation. Notify a safeguarding contact on guardianship.assign where the subject is a minor, and nothing else. Notification is visibility, not approval, so the parties still do not need the organization's permission — which is the whole point of D-073.

    Impact. One notification rule. No schema change.

    E-7 ✅ Closed — one level cannot separate the medical record from the profile, and nobody wanted to¶

    Raised by D-074, which deleted the eighteen dependent.* codes that existed for this case.

    What could not be said. "This guardian may register the child for events but may not read the medical record." "Read-only, except not the health data." "The grandmother may see the roster and nothing else." A guardian either sees everything about the child or nothing. The case the old namespace was built around — a court order restricting one parent's medical access while their other access continues — was inexpressible.

    Why it was accepted anyway. Three values a volunteer treasurer can hold in their head, versus eighteen whose differences nobody outside a court uses. And the alternative had a failure mode of its own: a granular list that administrators ticked without reading is not more protective than a coarse one, it only looks more precise.

    Answered (round 7), and the answer was not the one the question expected. The question assumed a medical record worth separating. Asked directly, you answered: "ignore 'court order', guardian has all rights on a child if it's permissions say so. Medical data is not different in any way." Recorded as D-083.

    So this closes as a dissolved question, not an answered one. "Everything except the medical record" is not a sentence the organization wants to say, which means the missing granularity was never a gap — it was the absence of a feature nobody asked for. There is now no inside and outside to the person record, because there is no separate record: everything the system knows about a person other than name, gender and age is one class of data, reached by person.view and governed by the guardian right level whole.

    What the closure trades away, in one sentence and on purpose: a system that cannot express "everything except the diagnoses" cannot express an arrangement a court might order, and will express it instead as a guardian who either has the record or does not. If the case arrives in reality, the route back is one new grant scope over a defined set of data, argued once as a decision entry — not a namespace of eighteen codes, which is what was deleted and why this question existed.

    Impact. None left open. One value, three choices, over the whole record.

    See: D-083, data-model/09-attributes.md, glossary — Descriptive data.

    E-3 🟢 Guardian acting for an adult child¶

    Question. Can a parent register their adult child for an event, with the child's consent?

    Recommendation. An explicit consent-based delegation, not a guardianship — the legal basis differs and access_grant.is_delegated already supports it.

    Note. Now that grants can target audiences (D-042), the event-wide version of this question — "register everyone in this group" — is answered without touching guardianship at all. What remains is the individual case.

    E-4 🟢 Guardianship lifetime vs. the membership gate¶

    Question. Guardianship is exempt from the membership gate (D-039), so a lapsed parent keeps their guardian's right over their child's records. Confirm that is intended rather than a side effect: it means an unpaid parent and a paid one are indistinguishable inside the guardianship channel.

    Impact. None structurally. It is worth stating explicitly because it is the one place the gate is deliberately absent, and "why can this person still see that?" should have a written answer.

    F. Authorization¶

    F-1 ✅ Closed — the catalog stays comprehensive and granular¶

    Answered: keep the catalog large and granular; more permissions arrive with the unbuilt modules (D-055).

    It is a menu, not a checklist. Administrators assign people only the permissions they actually need, and that is only possible if the capabilities exist as separate rows to assign. The parts of the question that remain — the exact contents — are tracked in appendix/permission-catalog.md §12 and will move as events, documents, communication and reporting land.

    Note the asymmetry with roles, because it looks like an inconsistency and is not. Roles are runtime data the organization invents (D-052); permissions are capabilities the code implements. You cannot assign a power that is not expressible in the schema, so a comprehensive catalog costs only rows. A comprehensive role list, by contrast, would be a specification pretending to be data.

    The sharp edge. Granularity only buys least-privilege if the grants are narrow, and D-007 means any new permission in a namespace is retroactively held by everyone with that namespace's .admin, with no assignment written. That is intended — and it is the reason role.edit is marked 🔒🔒.

    F-3 ✅ Closed — nothing forces an assignment to end¶

    Answered: nothing — rely on the gate. No NOT NULL, no application-layer requirement, no per-role policy (D-071). The docs had recommended yes, at the application layer; that recommendation is withdrawn.

    Why the recommendation was wrong. It claimed the membership gate makes an open-ended assignment more dangerous. It makes it less: the gate already expires authority for exactly the population an expiry date would target, and ties expiry to a fact the organization maintains on purpose rather than to a date somebody typed.

    The residue, which is the whole control now. unit_leader and assistant_leader have requires_membership = false by decision, so a lapsed leader keeps leading; the same for any role held by a non-member or carrying system.gate_exempt. For those, a periodic human review over open-ended assignments is not a nice-to-have, it is the entire defence — D-053 put all the weight on role_assignment.valid_to and this decision declined to add a guard rail there. Read the two decisions as one pair.

    See: data-model/05 §4

    F-4 ✅ Closed — the question was answered by deleting the premise¶

    Answered obliquely and decisively. Asked whether person.admin should subsume person.merge/person.redact, the answer was "Only the system should have admin permissions, not the individual items" — which removed the subsumer rather than choosing between the two options offered (D-068, reversing D-007).

    The question moved rather than dissolved. A role bundling all person.* codes still reaches person.merge and person.redact. What changed is where that is decided: it used to be a resolver rule, invisible in every role editor and true for every resource whether or not anyone wanted it. Now it is the contents of a role somebody wrote — visible in role_permission, dated, alarmable, and audited on change.

    What carries the guidance now is the seed table, not the schema: no seeded role mixes person.merge/person.redact with routine person.edit, and identity_reviewer is the one that deliberately holds person.merge. A role that does bundle a resource including its irreversible codes should be named for it.

    See: appendix/permission-catalog.md §11

    F-4a ✅ Closed — the catalog is the only list now¶

    Surfaced by D-068, not created by it. When the two were reconciled during that work, 22 documented permissions had no INSERT row — including unit_participation.view, which five of the catalog's own seed roles assign, and person.redact, one of the two codes D-068 exists to protect. A further 12 were the event.* set, catalogued when events were designed and never seeded. All 34 are now fixed; both sides list 91 codes and the diff is empty.

    Why nobody noticed, which is the part worth keeping. D-068 made a harmless inconsistency into a live one. Under the prefix-match wildcard, a role holding unit_participation.admin reached unit_participation.view whether or not a permission row existed — the catalog could advertise a capability the database could not name, and nothing noticed, because the wildcard papered over the gap and only the permission editor showed it. The cushion was itself the bug's hiding place.

    What is open is the discipline, not the data. There is no SQL check for this — one side is a Markdown file. Integrity check 18 reads the table, so it can find a permission no role grants; it cannot find a permission the catalog promises and the seed never contained. The reconciliation is scripted in data-model/05 §12, and it is a review rule, not a test.

    The actual question: should the catalog be generated from permission rather than maintained beside it? That is the only change that makes the two incapable of disagreeing. Against it: the catalog's value is its prose — the sensitivity marks, the rationale notes, the §5a and §8a argumentation — none of which belongs in a table. A middle path is to keep the prose in Markdown and generate the code tables from the database, so only the commentary can drift.

    Impact. If left manual, this recurs on every module added, and D-055's decision to keep growing the catalog guarantees modules get added.

    ✅ Closed — answered by deleting one of the two lists. Asked whether to generate the catalog from the seed, the answer was "delete the schema, I will use ORM anyway" (D-072), which removed the seed blocks, the DDL and the 19 integrity checks from the documentation altogether.

    The generation question dissolved rather than being settled, and the difference matters for what is still true. Nothing is generated, because there is no longer a table to generate from. The catalog is now the only list that exists — which answers the drift problem completely and removes, at the same time, the executable form of every rule the DDL had been carrying. That trade is D-072's to make and its entry records what it costs: integrity check 18, the orphaned-permission check that was the safety net for the deleted wildcard, is now a prose instruction rather than a query. A check nobody runs is a convention.

    What remains genuinely open is the thing the check was guarding. With no seed and no wildcard, a capability in the catalog that no role bundles is unusable and silent. It is now caught by review of the catalog, and there is no automated backstop at all.

    F-5 🟢 Which built-in audiences are needed?¶

    Question. everyone and all_members are seeded, plus parameterised unit:<id>:participants and unit:<id>:leaders (D-042). Which others are real — "the guardians of this child", "the leaders of the parent unit", "adults only", "everyone in this section and everything under it"?

    Impact. Each is one audience row plus one branch in person_in_audience(). Cheap to add, cheap to remove. But the parameterised ones raise a second question: are unit:42:participants rows seeded per instance on demand, or created when first granted? The first is a migration that must be re-run as units are created; the second needs a create-on-demand path that bypasses the usual admin permission.

    F-6 🟢 The permission cache lifetime under the membership gate¶

    Question. D-039 means the resolver's answer changes when a membership lapses — including at the yearly sweep, which touches everyone at once. What TTL is acceptable?

    Impact. The shorter the TTL, the smaller the window in which a lapsed member still has access, and the more load on the resolver. The sweep must invalidate by person, not by scope (data-model/05 §10), and that is settled — this is only about the steady-state TTL.

    F-7 🟢 Cache vs materialized effective_permission table¶

    Recommendation. Start with cache-only. Materializing is a denormalization requiring transactional maintenance, and a silent refresh failure is an access bug nothing detects.

    Impact. Performance only; revisit if measurement demands it. The membership gate makes materializing harder, not easier — every membership transition would have to rewrite rows.

    F-8 🟢 Retention policy for access_log¶

    Legal input required. Recommend monthly partitioning from the start, with archival to cold storage and never deletion.

    F-9 🟢 Should membership_type stay a table with one row?¶

    Question. D-037 kept membership_type as a table with a single seeded member row, on the principle that vocabularies are rows and not enums — at the cost of an FK that always holds one value.

    Impact. A deliberate trade, not an oversight. Worth confirming it is the trade you want, since it is the one place the design pays a structural cost for a hypothetical future.

    See: data-model/03 §1

    F-10 🔴 Which invariants the ORM cannot express, and who writes those¶

    Question. D-072 moved the schema to an ORM. Most of what the deleted DDL asserted an ORM will generate from a model definition. Three shapes it generally cannot, and each appears dozens of times in these documents:

    The list below is four shapes, and they are not equally bad. Shapes 1–3 have a known answer even if nobody has chosen it yet; shape 4 does not have one, and is why this question is red.

    1. No two open rows overlap — the temporal invariant under memberships, participations, assignments, guardianships, grants and exposures. On PostgreSQL this needs an exclusion constraint over a range built from two columns.
    2. Unique, but only among rows satisfying a condition — "one open request per person and type", "one primary contact among open rows", "one live exposure per unit and assignment". These need a partial unique index; a plain unique constraint over the same columns is a different and wrong rule, forbidding the second closed row that history requires.
    3. Anything whose answer comes from another table or from the resolver — the holder limit, the nesting rules, the exposure direction, per-scheme identifier uniqueness (D-080 item 1 is this class), and since round 7 one current value per (person, definition), whose condition lives in attribute_definition.allow_multiple — a uniqueness rule that some definitions want and others forbid (data-model/09-attributes.md §3). It is the cleanest example in the list, because the rule is not even conditional on the row's own data: the same two columns are unique for one definition and repeatable for the next, so a partial unique index cannot be written without knowing which definitions exist at runtime. No declarative constraint can state these; they need a check inside the writing transaction plus a report.
    4. A column that may not change once it is set — org_unit.parent_unit_id (D-036). This is not a PostgreSQL limitation that an ORM happens to inherit; no declarative constraint in any database states it, which is why it survived into the hand-written migrations even when the DDL was still in these documents. It is a rule about a transition between two states of a row, and a constraint sees states.

    What makes it different from 1–3 is that there is no report. The nightly checks catch shape 1 and 2 by finding a pair of rows that should not coexist, and shape 3 by recomputing an answer and comparing. A reparent leaves no offending row: every row in the database stays individually valid and satisfies every constraint, while the meaning of the subtree's entire history moves under them. Nothing can be compared afterwards, because there is no second statement of the intended hierarchy to compare against — and the path the damage would show up in is itself derived and would simply be recomputed to match. So the guard is the whole enforcement, and it must sit in the write path (data-model/02 §4), with an automated test that attempts the update and expects a refusal. A test is not a substitute for the guard; it is the only remaining evidence that the guard was intended to stay.

    Why this is a question and not a task. The fallback an ORM offers for all three is validation in the model layer, and data-model/00 §6a explains why that is not the same guarantee: an import, a data fix, and a second client all bypass it. The legacy import is the specific case that makes this urgent rather than theoretical — the corpus arrives through exactly the path that model-layer validation does not cover, and an overlapping membership written by the importer is nearly impossible to diagnose afterwards, because the two rows look like two memberships and only one of them was ever real.

    Needed. A decision per shape — hand-written migration, database check, or application check plus report — before the first migration is generated, not discovered during one. The recommendation in data-model/00 §6a is that shapes 1 and 2 are hand-written migrations, and that this is the condition on which using an ORM is safe rather than an argument against using one.

    Impact if unanswered. Not a crash. A system whose constraints are quietly absent, whose integrity checks (every "Invariants to verify" section) then start reporting rows, and whose first report is read as a data-quality problem rather than as the missing guarantee arriving on schedule.

    See: data-model/00 §6a, appendix/erd.md's inventory, which marks every temporal entity.

    G. Events — designed, with three things left open¶

    The module is written: domain/07-events.md and data-model/08-events.md. Fifteen questions have been answered (D-058 … D-067, plus EV-1 and EV-5 in a later round); what remains below is what those answers did not settle. None of it blocks implementation.

    EV-1 ✅ Closed — there is no age ceiling; the grant is the rule¶

    Answered: leave it. No min_age/max_age on event, and no age test anywhere in the path that places a registration (D-070).

    The residual risk is accepted, not eliminated, and it is worth restating so nobody "closes" it later without knowing: an event opened to all_members can be registered for by a nine-year-old and nothing objects. What makes it survivable is attribution (source = 'staff'), a roster query one join away from birth dates, and the fact that the age-bounded case is already handled by opening an event to the right unit.

    If it ever needs closing, the shape is a built-in audience, not a column on the row — all_members is a rule the resolver evaluates, so members_aged_13_plus can be one too. That keeps every answer to "who may register" inside access_grant, which is the property D-060 bought and D-070 defended.

    EV-2 🟡 Retention of event_answer¶

    The question, restated once so it stays answerable. It used to read "a dietary answer citing a medical condition is health data, and health data has a retention obligation" — and D-083 removed the second half of that sentence's subject: there is no class of health data with its own obligation, only personal data, of which a dietary answer is one instance. The question survives, and it is now the ordinary version of a question this system has not answered anywhere: event answers end with the event, "end" is not a defined policy, and a fact recorded on a form is the same kind of fact as the same sentence recorded as a person_attribute (data-model/09-attributes.md), which raises the sharper form of the question — should an answer about a child be deleted on a schedule at all, when the same information held as an attribute is kept until someone retires it? The paragraph at the end of this item is where that doubling is worked out; what changed here is only that the question can no longer be filed under a category of data that no longer exists.

    Why it is not trivial. D-061 made an event form the route by which a camp leader learns a child has a nut allergy. That is a deliberate widening, and it puts health-adjacent data in a table whose protections are weaker than the health record's — and in round 6 that gap widened twice over: there is no longer a dependent.medical.* code marking which data is the sensitive kind (E-7), and the audience entitled to read an answer is whoever runs that event, a set sized by whoever creates it. The retention policy is the remaining half of that trade.

    Needed. Legal input, like B-3. The technical question — where does it live, who may read it — is answered; whether it must be deleted, kept, or archived is not.

    Changed in round 7, in a way that strengthens the case rather than settling it. D-083 made every fact about a person one class of data held on the person, so an event answer naming an allergy is now the same kind of fact stored in two places by two different rules — one on the person, where it is audited, curable and erased with the person; one in an event's table, readable by whoever runs that event, with no retention policy. The retention question and AT-1 are the same question from two directions: an answer worth keeping is an attribute that was collected at the wrong address, and an answer not worth keeping should be deleted on a schedule rather than surviving because nobody wrote a policy. Until one of the two is decided, the weakest-protected copy of a health fact is the one that is freshest.

    EV-3 ✅ Closed — cancelling voids the request, and paid money queues¶

    Answered by D-076, in the finance module rather than here. The recommendation was right and the mechanism arrived before the policy did:

    • Cancelling an event voids its outstanding payment requests, recording why (finance model §2b).
    • Money already received becomes a queue item for a person to refund or carry forward. Not auto-refunded — that needs an outbound bank integration and would return a grandparent's mistaken camp fee.

    Why the recommendation held. It said neither, automatically, because an automatic release would be a second automatic transition in a module with exactly one (D-066). That argument was strong enough to survive contact with the payment design unchanged. Voiding an outstanding request is not that second transition — a request nobody has paid against has no state to preserve and nobody is disadvantaged by its withdrawal, which is exactly the property the waitlist release had and this does not.

    What actually moved. The question assumed cancellation was the interesting case and payment an afterthought parked in finance. It is the reverse: cancellation is where most of the unmatched queue's volume comes from, because a cancelled event keeps its registrations (D-064) and therefore its money obligations, unless something explicitly voids them.

    Impact. Answered; the queue itself lives in the finance module.

    EV-4 🟢 was_present as a safeguarding record¶

    The question. Presence is the record of who was actually in the organization's care (D-067). Does it need its own retention, or its own permission?

    Why it might. It is the record that answers "was this child at camp on the day of the incident" — the question insurance and any safeguarding review will ask. That is a heavier thing than "who said they were coming", and it currently shares both a table and a permission with the registration.

    Why it might not. It is meaningless without the registration it belongs to, and splitting it would put two rows in two places describing one fact.

    Impact. Splitting it is a table; keeping it is nothing. The argument for splitting is permissions — a volunteer who takes the register at camp is not the same trust as one who may alter the roster. See EV-5, which is the same tension.

    EV-5 ✅ Closed — it split, and the new permission sits a level lower¶

    Resolved in favour of the split: event.presence.mark, at contribute.

    The reasoning recommended the split and the recommendation stood. Marking the register at a camp door is not the same trust as deleting a child from the roster, and one permission forced organizations to hand the clipboard-holder both. Note where the new permission landed: contribute, not manage — so the volunteer taking the register is somebody who could already register themselves, which is the right bar for the job and plainly the wrong bar for altering who is coming. Same shape as membership.lapse versus membership.terminate (D-022): one routine, one consequential.

    Thirteen event.* codes now exist; event.admin is not one of them (D-068).

    See: appendix/permission-catalog.md §8a

    Ga. Personal attributes — designed, with four things left open¶

    The module exists: domain/08-person-data.md and data-model/09-attributes.md, decided by D-083, D-084 and D-085. It arrived instead of the health-records module, because the question "what is a health record here" answered itself a size larger: everything about a person except name, gender and age is one class of data, defined by the organization at runtime, with no privileged subset.

    AT-1 🟡 Should an event question bind to an attribute code?¶

    Raised by D-085, which made the event form the fallback rather than the ceiling.

    The situation. A returning camper types their allergy into every event form, every season, and the answer lives in event_answer.value for that event only. Meanwhile the organization may already hold the same fact as an attribute on the person, with a name, a value_type, and a recorded author. Nothing connects them.

    Why this is a question and not an obvious improvement. Prefilling an answer from the record makes the record the thing a leader relies on, and the record is: whatever was typed, by whoever, possibly two years ago, with no obligation on anyone to update it. Today's arrangement is worse data and better epistemics — the form asks now, about this event, and the answer is dated today. Bind the two and an out-of-date attribute becomes a wrong answer that looks authoritative, which is the one failure mode a health fact has that makes it dangerous.

    Recommendation. Prefill as a suggestion the registrant confirms or corrects on the way in, and write the confirmed value back to the attribute with today's date and this person as its author. Then the form stays the authority for the event, the record gets refreshed by the act of using it, and nobody ever relies on a two-year-old entry without a human having just looked at it. The variant to reject is reading the attribute directly into the organizer's view without the registrant's confirmation pass — that is the same convenience with the safety removed.

    Impact. One binding on the question definition, one write-back rule, and a rule about which is authoritative when they disagree. No new permission.

    See: D-061 (as amended), data-model/08 §7.

    AT-2 🟡 Who curates the vocabulary, and how long may a proposal sit?¶

    Raised by D-084, which made attribute.define a permission instead of a release.

    An open vocabulary is only as good as somebody tending it, and "somebody" is currently nobody in particular. Two halves:

    • Who holds attribute.define. The starting role set (permission-catalog §11) is the place this gets answered, and the honest answer is that a volunteer organization has one or two people who will do this and not a committee. Too narrow and the proposal queue is a bottleneck that teaches people to file facts into notes instead; too wide and it is not a curation.
    • How long a proposal may sit before it is promoted, merged or discarded. The check exists (09-attributes §8 checks 1 and 2) and the number does not. A quarter is a defensible default: long enough that a seasonal field is not judged off a single use, short enough that a proposal is answered inside the season that produced it.

    Recommendation. One named role, a stated age limit on proposals, and a standing decision that an expired proposal's values stay — the curation is about the name, never about deleting what was recorded.

    Impact. Configuration and one role, no schema change. The thing it prevents is the slow failure: a vocabulary nobody curates stops being queryable and the layer keeps storing everything, which looks like success for years.

    AT-3 🟢 Do attribute labels need translation?¶

    Inherited from the multi-language row in §H, and sharper here than anywhere else because the vocabulary is runtime data: if a code's label is Czech-only, a Slovak-speaking volunteer cannot pick the field at all. Whether the answer is a translation column on attribute_definition, a separate label-per-language table, or "the organization is single-language, stop asking" is unrecorded. The cost of not answering is asymmetric — a label table added later is a migration; a body of codes accumulated with one label each is a data-cleaning project.

    AT-4 🟡 Is one permission enough to guard a trail that holds person data?¶

    Raised by the reversal recorded in D-083, which decided the audit trail does hold a person's descriptive values — because D-085 made that trail the only history such values have, and stripping them would have made the history empty while quietly grading health-shaped fields above a change of address. What protects the copy is then one thing: audit.view, graded ⚠⚠ beside person.view (permission-catalog §8). Three positions exist and none is recorded as taken:

    • The guard is enough (current documents). One permission, marked honestly, and a rule that whoever holds it is reading person data. Simple, and it makes the auditor role — which has audit.view and not person.view — a reader of the entire person record (permission-catalog §11 note 3).
    • Per-entry filtering in the history view: show an audit row's values only where the reader could also see the live field. Consistent with everything §9 of data-model/05-authorization.md says about channels, and it was considered and left unimplemented, because it means running the resolver per audit row against rows that may no longer exist — a grant withdrawn last year is exactly the case a history is read for.
    • Split the permission: the trail's shape (who changed which table, when) apart from its payloads. Honest about what an auditor usually needs, and it is the option that reintroduces a sensitive subset through the back of the catalog — which is why the documents do not recommend it.

    The cost of not answering is asymmetric in the uncomfortable direction: the first position is already implemented by default, so leaving the question open is choosing it, and the choice is made invisible — nobody signs off on "volunteers with audit.view can read children's medical history" because there is no moment at which anybody has to say it.

    MSG-1 ✅ Closed — a direct message to a minor is mirrored to their guardians¶

    Raised by D-077, which declined the restriction rather than forgetting it.

    The situation. Messaging has two sender tiers — direct, which everyone may do, and broadcast, which is a permission. Neither tier mentions age. So any person with an account may send a private message to any child with an account, and nothing in the model prevents it, records it as unusual, or tells anyone. This is not a gap created by oversight: the question asked whether staff may address a child or only their guardians, and the answer replaced it with a model in which age is not a sender concept at all. The rule the communication section had promised — "a rule against contacting minors directly" — is therefore not implemented, and it is worth being blunt that this is the most consequential unanswered question in the file.

    Why restricting senders is the wrong fix here. An age branch in the resolver is what D-070 refused for events, on the grounds that a condition evaluated at check time which the capability model does not know about becomes the first rule in a rule engine nobody wants. It would also be the kind of restriction that gets loosened the first time it inconveniences a leader, and a permission that is routinely bypassed on a messaging system is worse than none, because it makes the bypass normal.

    Recommendation — restrict visibility, not permission. Mirror direct messages reaching a minor to that minor's guardians, and make the mirroring visible to the sender. Then:

    • nothing is blocked, so the resolver still has no age branch;
    • nothing is secretly unread, which is the actual safeguarding property;
    • it is built on the guardianship rows the organization already maintains, so it needs no new authority concept;
    • and it degrades honestly — a child with no guardian on record gets no mirroring, which is the same safeguarding gap check 4 in data-model/04 §6 already alerts on, arriving through a second channel.

    The variant to reject. "Only guardians and unit leaders may message a child." That is the restriction wearing the visibility recommendation's clothes: it is a sender rule, it needs the age branch, and it silently tells a child that the adult messaging them has been vetted — which the model does not establish, and the organization records no background checks (D-043).

    Answered (round 6): the recommendation is adopted, as D-082 — mirror to guardians, tell the sender, block nothing. Three details were settled with it, because "mirror it to the guardians" does not by itself say who the guardians are to this message:

    • Which guardians. Those whose right level is view or write. A guardian at none receives nothing: none is the organization having already decided that this party sees nothing about the child, and a safeguarding rule is not a licence to undo a recorded decision by side effect. A minor whose guardians are all none is therefore reported with the minors who have no guardian at all — otherwise the exclusion would be a way to make a child silently unwatched.
    • Which set, as of when. The guardianships open at the moment the message is sent, frozen into the delivery. A guardianship closed afterwards does not lose its mirror, and a guardian added later does not acquire old threads — same discipline as 06-audit §2, which keeps the trail answering "what was true then".
    • Broadcast is not mirrored. A scoped broadcast is already addressed to a set, recorded, and attributable; mirroring exists for the private case, which is the one that can be invisible.

    What mirroring is not. Not approval, not a gate, and not evidence anyone read it. It buys the one property the safeguarding argument actually needs — no private conversation about a child is secretly unread — without putting an age into the resolver.

    See: D-082, permission-catalog's message row, glossary — Mirroring.

    How to answer¶

    The blocking set is now empty. Four rounds have cleared every question that was holding the schema still, so nothing here has to be answered before implementation could start.

    What remains is genuinely deferrable, and the most useful next ones are:

    1. F-5 — which built-in audiences are needed, and whether parameterised ones are seeded per instance or created on demand
    2. F-3 — should high-authority role assignments require a valid_to?

    Everything else can be answered as we go. The schema is built so that most answers change data rather than structure — which is why the four above are worth a moment and the rest are not.
