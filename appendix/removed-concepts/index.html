    Removed Concepts¶

    A lookup for names that are not in the model. Every spec page states the design as it is now and carries no history, so this is the one page where a dead name is written down — with what it was, why it went, and the decision that took it. The argument is in the decision log; the row here is only an index to it.

    Read it when a word from an older draft, another system, or a conversation does not appear anywhere in these pages. The organization may still use the word — a removal from the model is not a removal from its vocabulary.

    Name What it was Why it went Use instead Decision
    audience_include, include_depth_limit a stored edge putting one permission group inside another, and the cap on how deep those edges could nest arms became operands and + composes inside one grant, so membership of a set is now written where it is used GROUP(x) + GROUP(y), or name the composite once as a saved audience D-101
    audience_member the audience's own hand-typed list of people, with per-person dates and an adder a hand-written set is a sum of PERSON() leaves like any other set, and the list was a second roster the permission system owned PERSON(a) + PERSON(b); for anything dated and shared, a person_group D-105
    everyone, all_members the two audiences the platform shipped: one whose whole expression was EVERYONE, one whose whole expression was MEMBERS, each named so a grant could point at it, each marked not editable by a screen a name over a one-operand expression is worth a row only if somebody is going to name it, and naming is one row a person writes when they have a reason; the editor refusals that guarded them guarded a category that does not need a flag — an expression is not a member list, and there is no audience_member table to add somebody to the operand written directly in the grant's expression: EVERYONE, MEMBERS; a named audience is one someone writes, and AUDIENCE(x) is what makes a name worth having D-153
    dependent.*, guardianship_permission eighteen per-capability codes on a guardian: a read and an act spelling over each of eight resources — profile, contact, membership, event, fee, medical, achievement, document — plus dependent.admin over the lot, each its own row one right per guardianship row, compared against permission.right_kind; the granular split was declined, not left unbuilt right_level ∈ none / view / write on guardianship D-074
    background_check, person.background_check.*, and with them the identity_hypothesis.proposed_by value background_match the system's record of whether an adult had been checked, and the name the nightly batch matcher's row went by while that record existed outside the system's remit: it records the appointment, not the vetting behind it nothing in the model; the organization keeps that outside D-043
    can_event() a wrapper around can() that called it twice and added an event-shaped clause: the holder of a unit-level event permission reached every event nothing owns an event, so there was no unit authority to extend; the exception was the whole content of the wrapper plain can(), with ORGANIZERS naming the people connected to the event D-102
    effective_permission the honest name for a table of answers — one row per person and code saying what they may do, rebuilt nightly, proposed as the answer to "who could read this in 2023?" it is permission_cache under its own name: a row mapping a person to an answer is what invariant 19 forbids a check resolves on the live rows; what F-7 names as what to build again if the scale trigger is ever reached D-114
    event.qr, event.qr.rotate a check-in capability argued about by name across a whole round, under two readings of its last segment, with no catalog row, no migration and no evaluator arm behind either the catalog and the registry are the record: a name carried only by prose is not a feature, and a registry that prose contradicts is a fiction nothing — the name was never grantable; whether a person turned up is event_registration.was_present D-104
    the shipped event.answer.view → ORGANIZERS grant row, and the template read of it — the code is live and unrenamed, only the row that arrived with the platform is gone the one grant row saying an event's organizers may read its registrants' answers — shipped as a row, later re-read as a template the event-creation path instantiates beside each event, since a bound operand cannot sit on a unit-scope grant one hand-written grant per event is a list somebody keeps in step with the catalog by remembering; the authority an item's people need is derivable from the codes that admit that item the act that creates an event writes twelve item-scope allows beside the event row, in the same transaction — every event.* code except event.create (applies_to = unit), each aimed at an audience whose expression is ORGANIZERS D-151
    GUARDIANS, GUARDIANS(p), guardians_of a named set of the same people, then an operand naming the guardians of the person an item is about guardianship is a channel entered by the shape of a request and carrying a right_level, not a set a grant aims at the channel answers for a guardian; a kept set of contact adults is a GROUP(x) D-113
    household a table grouping people at one address, and a basis for access through it a shared address never granted anything, and the group was a fact the organization could not maintain an address is a person_contact of type postal; two people at one address are related by a query D-057
    is_member, member_type, is_child, current_member_category() flags on the person row saying what kind of human this row was, and the function asking which category a member was in right now personhood is not a type, membership is ageless, and one person can be a member twice with a gap between membership rows, and is_current_member() on the date asked about; is_minor(person, as_of) reads the person D-001, D-038
    permission.is_system, role.is_system, selector_type.is_system, audience.is_system a per-row boolean telling an editor that this row was shipped by the platform and must not be edited or deleted three of the four tables have no screen that writes them and no code that adds a row, and grant_scope_type — just as uneditable — never carried the flag, which is the tell: it was a sentence about the table, stored on every row of it. On role the flag protected exactly one row, and there is no shipped office the sentence lives in the paragraph about the table: "written only by migrations", organization-read-only. What still refuses a delete of a held office is the foreign key from role_holder, which was always the half that also refused an import, a manual fix and a second client D-152
    LIST the audience's own typed set, moving as one unit under + LIST and - LIST the same people are written PERSON(a) + PERSON(b), and one spelling of a set is enough PERSON() leaves; the exemption belongs in the grant that carries the rule D-105
    locality, "the nearest scope wins" a tie-break ordering allows by how specific their scope was a grant answers one code yes or no, so there is nothing to order; what survived is that a deny is absolute allow iff some live allow applies and no live deny applies D-099
    access_level, permission_level, level_satisfies(), revoked < view < contribute < manage a rank saying how much authority a grant carried, compared against a permission's rank a grant allows or denies exactly one code; roles and audiences are the bundle a broad office gets one access_grant row per code, plus the seeded starting grant set D-099
    <thing>.admin codes a code per resource implying every sibling capability on it one implied wildcard in a system of one-code grants would swallow the audit trail system.admin, and a grant list for everything else D-068
    medical.*, the medical record, event_medical_note a class of personal data with its own storage and its own permissions, and one table of it holding medical facts about one person at one event personal data is one class; sensitivity is graded by what a grant exposes, not by which table it reads the attribute layer, and person.view read with that cost in mind D-083
    the membership gate, role.requires_membership, system.gate_exempt, person_holds_gate_exempt a resolver clause honouring an office only while its holder was a paid-up member, the per-office switch waiving it, and the waiver list with its reader function the test is now an operand the grant's writer puts in, so the posture is opt-in per grant MEMBERS * ROLE(x); the exemption is + PERSON(y) in the same grant D-100
    org_unit, org_unit_type, org_unit_name, org_unit_relationship nodes of a nested unit hierarchy: types, renamed names, and split/merger/succession edges the corpus names no units and a unit restricted nothing, so the structure carried no information — and a group is named by one column, so renaming one loses the old name, which is the cost D-097 recorded the unit is a scope, never a row; groups are the sets of people D-097
    org_unit_type.allows_minors a flag on a unit type refusing a child's placement a boolean refused only the placements somebody had thought about; the safety is in who may write the row person_group.member.manage, held by a named adult D-095
    org_unit_id on an event, event_organizer special cases the unit an event belonged to, and the roles that reached it through that link nothing owns an event; the people connected to it are named by selectors that bind to it ORGANIZERS, and a grant scoped to the event D-102
    permission_cache stored answers to permission checks, keyed per person, plus the staleness policy keeping them true no row may map a person to an answer; a check resolves, a request memoizes, and only a compilation is cached a cached compilation (an expression root plus ruleset_version, holding no person and no item), the request memo, and can_many(person, codes[]) / which_of(people[], code, item) D-114
    position, position_assignment, is_leadership, max_holders, min_age, position.requires_membership, appointment_reference a slot in a body that a person filled for a period, with occupancy rules — one of them requiring the filler to be a paid-up member, and a column citing the document that appointed them with one unit there is no body to be a leader of — the one fact a position held that an office does not role_holder: an office, a person, a period D-100
    requested_unit_id the unit an applicant asked to join on a membership request which set a new member lands in is a write on that set, not a preference on the request the request ends at the unit; a roster is a later act D-098
    resolver_key, scope_parameter the rule arm of a permission group: a stored template that computed members a rule is an expression now, and an expression is stored as a tree of named operands the selector registry, and audience_operand rows D-101
    role_assignment, role_permission, role.scope_required the period a person held a role within a scope, the codes attached to that role, and the column saying an office's assignments had to name a scope an office confers nothing by being held; the codes an office carries are the live grants naming ROLE(x), and each of those rows names its own scope role_holder, and grants aimed at ROLE(x) D-100
    the seeded role set — the counselors row, and the system_admin office the catalog sketched as shipping offices the platform wrote so a new installation had somewhere to put people, with a holder column empty on arrival and no grant naming them an office confers nothing by being held, so a shipped office was a name nobody had a reason to name and a row no screen could delete — and the checklist of what to grant belongs in the catalog, where a person reads it, not in rows a migration wrote day one is one account and one ordinary access_grant row giving it system.admin at the unit, and every office after it is written with role.create and aimed at by grants; counselors stays as the corpus's worked example of an office, which is what every expression naming it always was D-150, D-154
    scope_exposure, scope.expose, scope.exposure.review, scope_exposure_covers_assignment() the only crossing between a covering unit and a covered one, written by the covered unit there is one unit, so there is no outside to be stopped from; the safeguarding property it bought is recorded as lost in domain/04 §1 a grant at the unit, or on one item D-097
    requires_scope on permission a column fixing the level at which that permission could be granted at all — organization or org_unit both values named bodies this schema no longer has, and the ladder it slotted permissions into is gone as well; no decision entry names this column in either its deleted or its kept list nothing: the scope is said on the grant, never on the permission, and any code may be granted at the unit or on one item its applies_to allows — (no decision names it; the ruling that made it impossible is D-097)
    selector_depth_limit a configuration parameter capping how deep an audience's expression tree could nest, refused at save over the expanded tree the argument that justified a bound was a stored column that no longer exists, and the property it underwrote — that a check costs a bounded amount — was given up on purpose: an expansion is bounded only by acyclicity nothing: the save-time cycle walks are the only structural guard, and a tree is stored with the shape its writer gave it D-105
    successor_of an edge saying that one body continued another after a split, merger or rename the bodies it joined no longer exist, and groups keep no group-to-group edges a new row, plus a person's note where continuity matters D-096
    unit_ancestors(), unit_descendants() the walks up and down the unit tree there is no tree, and a check about a function that does not exist is not a guard the check matches scope exactly: the unit, or the item D-097

    unit:<id>:participants, unit_participants the audience naming one unit's participants — written as an id string, and the set the worked example of an age-gated camp opened itself to there is one unit and it is a scope with no rows under it, so a unit's participants were never a set to name: they are the members MEMBERS D-097
    unit_participation, with its is_primary, role_in_unit, data_confidence and its join_reason_code / leave_reason_code vocabulary (transfer, promotion, reorganisation, unit_closed) the period a person took part in one sub-unit, the root row every membership owed, and the reason vocabulary and display labels those rows carried no sub-units; membership is one query and a group roster is another, and the reason a row was written is in the audit trail that already names who wrote it membership for the membership, person_group_member for the roster, audit_log for why a row moved D-097
    the root participation row a renewal extended, the integrity check 1b that watched the pairing, and import_staging.applied_participation_id the second row holding the same period as every membership, the report that found the writers who skipped pairing them, and the staging column whose only job was to say that a membership had written half of that pair one of the two rows is deleted, so the pairing is not a rule running without a guard but a redundancy removed; membership cannot disagree with a copy of itself membership alone — and a renewal inside the window still backdates the period there D-097, D-050
    unit_membership the name that table carried before D-041 renamed it to participation the name asserted a second species of membership, which raised whether the fee was owed twice; the thing it named is now deleted outright membership for the membership, person_group_member for belonging to a group D-041
    requirement_code, membership_request_requirement, and its seeded items guardian_consent, background_check, medical_form, references, previous_unit_transfer, photo_consent the checklist a membership request had to satisfy before it could be accepted, one row per item, seeded with six of them nothing gates a request but identity and payment, and keeping the mechanism as empty infrastructure was offered and not taken the request as it stands — a person, a submitted timestamp, a reviewer, a decision, a payment D-044
    membership_type.category, min_age, max_age, requires_background_check, requires_references, requires_guardian_consent, allows_concurrent, grace_period_days, fee_schedule_id, ck_membership_type_ages the columns on a membership type saying which kind of person it was for, who was eligible, what a request had to carry, whether two memberships could overlap, how long the grace ran, and what it cost one type with a flat fee makes every one of them inert, and each put an eligibility rule on what is only a vocabulary row ages are facts about the person; nothing gates a request but identity and payment; the grace is renewal_grace_days, a window read from the row; the fee attaches to the fee_obligation D-037, D-038, D-040, D-044

    The codes that left the catalog¶

    A code is a stable identifier, so one leaving the catalog silently is a migration nobody decided. The tables in the catalog hold only codes that can be granted today; these were granted, and here is where their act is performed now.

    Code The act Where the act is now Decision
    ~~org_unit.view~~ the list of units, and the "which units exist" report Nowhere. The unit is a scope, not a row: there is no list to read D-097
    ~~org_unit.create~~ creating a unit Nowhere, and nothing needs creating — the unit arrives as a code in grant_scope_type, not as data D-097
    ~~org_unit.edit~~, ~~org_unit.rename~~ renaming what a body is called person_group.edit, and it is cheap: a grant and an expression store kind + id, never a name, so a rename rewrites nothing D-097, D-101
    ~~org_unit.restructure~~ splitting, merging and succeeding a unit Nowhere, and the loss is stated once in D-097: a group that splits is an old group that ended and two that began, with no edge between them unless somebody writes one D-097
    ~~org_unit.close~~ ending a unit person_group.end — which ends a set, and is graded accordingly D-097
    ~~position.view~~, ~~position.assign~~ seeing a body's slots; appointing somebody into one role.view and role.assign (catalog §7). An elected leader is a holder of a role, and the audience rule that used to read unit_leaders is ROLE(leaders) D-100
    ~~unit_participation.view~~, ~~unit_participation.manage~~ seeing and writing one sub-unit's participants membership.view for the organization (one query, no depth), person_group.view and person_group.member.manage for a group. D-095's discipline transfers intact: never self-scoped, the write is somebody else's act, the report is the control D-097, D-098
    ~~membership.transfer~~ moving a member between units person_group.member.manage — close one dated row, open another — and it does not touch the membership at all. Obsolete twice over: D-041 moved unit belonging into a participation row, and D-097 deleted that D-041, D-097
    ~~guardianship.permission.grant~~ granting a guardian individual capability codes there was no namespace to grant from: a guardian's rights are one value with three choices guardianship.change_right

    Two habits this page is meant to prevent. Naming a removed thing in a spec page, which is what put the history back into the pages this appendix exists to keep clean; and re-adding one quietly, which is why every row ends in a decision — a concept comes back by a decision entry, or it does not come back.

    Decisions behind this page: D-001, D-037, D-038, D-040, D-041, D-043, D-044, D-050, D-057, D-063, D-068, D-074, D-083, D-095, D-096, D-097, D-098, D-099, D-100, D-101, D-102, D-104, D-105, D-113, D-114, D-150, D-151, D-152, D-153, D-154.
