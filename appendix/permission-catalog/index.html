    Appendix — Permission Catalog¶

    Every permission code, its namespace, and the grant that carries it.

    This is the proposed catalog, seeded in ../data-model/05-authorization.md.

    Round 10 rewrote this page. D-097 deleted the unit hierarchy, D-099 the level ladder, D-100 positions, role_permission and the membership gate, D-101 the audience's rule/list/inclusion arms, and D-102 event ownership. Thirteen codes here lost their subject, and five arrived for the two new tables. What changed shape is not only the list: a code is no longer paired with a level, so a row in this catalog is a capability and nothing more. Whoever grants it says how far it reaches, for how long, and to whom — in one row, whose grantee is an expression (§1). And §1's two naming shapes are rules now, not descriptions of the rows below: the last segment names the action, a middle segment names something the schema stores, no grade words and no prefix — with system.admin named as the single exception (D-104).

    Deliberately comprehensive and granular, and staying that way (D-055). This is a menu, not a checklist. Administrators assign people only the permissions they actually need; that is only possible if the capabilities exist as separate rows to assign. Further permissions arrive with the modules not yet specified — documents and communication. Events were on that list and are no longer: §8a carries their thirteen codes (§10).

    This is the opposite disposition from roles, and the asymmetry is deliberate. Roles are runtime data the organization invents (D-052); permissions are capabilities the code implements. You cannot assign a power the data model cannot express, so a comprehensive permission catalog costs only rows — while a comprehensive role list would be a specification pretending to be data.

    Codes are still stable identifiers: adding one is free, renaming one is a migration (§1). What is not yet settled is the exact contents — tracked in §12.

    1. Conventions¶

    Code shape¶

    <resource>.<action>               e.g.  person.edit
<resource>.<subresource>.<action> e.g.  event.answer.view

    resource is always the first segment and matches permission.resource. Codes are stable identifiers — the display_name may change, the code may not. Renaming a code is a breaking change requiring a migration that rewrites every access_grant row naming it. Before D-100 the same migration also rewrote role_permission rows; that table is deleted, and a grant is now the only place a code is written down — which makes the rule smaller, not weaker.

    Those two shapes are rules for adding a code, and since D-104 they are written here as rules rather than as a description of what is already in the tables below. As a description they arbitrated nothing: both readings of one disputed name fitted them exactly, and that dispute ended with the capability deleted rather than either spelling chosen (§12). Three rules, and the moment they cost nothing is the moment a code is added:

    1. The last segment names the action. Read the code on its own and ask what does this let me do? event.grant_access answers it; a noun-final code states an object instead. Since D-099 a grant permits exactly one thing, so a grant of an object would need a second sentence to say what it permits — and a second sentence is where a permission's real scope always hides.
    2. A middle segment names something the schema stores. answer is event_answer, presence is a column of event_registration, and contact, credential, member, participant and request are rows. A permission may not be built out of an artifact the database does not keep, because a grant has to be checkable against stored state and there is none to check against: the payment's QR code is exactly that artifact, and D-075 already ruled it a rendering of three stored facts rather than data. No code in this catalog spells qr, and none may (§12).
    3. No grade words, and no prefix. Not admin, all or everything, and not any code whose meaning is "every sibling under this prefix" — D-068 deleted sixteen of them and computed the wrong answer for the one it chose to exempt, dependent.admin — which D-074 then deleted too, for having no set left to stand for (the table further below). D-104 restates that decision as a rule about codes that have not been written yet, which is the only form of it that can still prevent anything.

    One exception, named because a rule with an unnamed exception is a rumour: system.admin. Its last segment is not an action, and it stays. It survives because its meaning is defined by the resolver — checked outright, applies_to = unit, never reachable through an item grant (§7) — rather than read off its name, and because D-068 exempted it in so many words rather than by omission. It is the only code in this system allowed to be a noun, and the exemption sets no precedent: <resource>.admin is precisely what rule 3 refuses and precisely what was deleted.

    The three rules were run against the sixty-six live codes in the tables below and corrected nothing — sixty-five satisfy both tests, and the sixty-sixth is system.admin. That null result is the reason this section changed voice rather than its contents: a convention that is followed and not stated fails exactly once, on the first thing nobody thought to compare, and the thing this round failed on had never existed anywhere but in prose (§12). Nothing in the schema will ever notice a code drifting from its row — the check D-104 adopts is a person remembering to run a report over the seeded registries in both directions, which this repository can only ever do by hand (F-19).

    What a grant is, and what it used to carry¶

    A grant is five things: a grantee (a person or an audience expression) + a scope (the unit, or exactly one item) + one permission code + effect ∈ allow, deny + a period. The answer it feeds:

    allowed when some live allow applies and no live deny applies. (D-099)

    That is the whole of the precedence rule, and this catalog carries no column beside a code because of it. What the level column used to promise, and what covers it now:

    ~~access_level used to~~ Now
    ~~bundle several codes under one word — "manage on this event"~~ One grant row per code. A bundle is a role or an audience, which is what D-068 already said: roles are the bundle
    ~~grade one act at two strengths — view against edit~~ Two codes, plus permission.right_kind ∈ read \| write saying which side each sits on
    ~~decide whether a grant was enough for the code being checked~~ Nothing to decide. A grant names exactly one code, and the answer is yes or no
    ~~order two grants that both apply — locality, D-032~~ Nothing to order: two allows that apply produce one answer. Deny is absolute, and that half of D-032 survives untouched
    ~~carry revoked as the bottom rung~~ effect = deny on a grant row, and it is still asked first

    Withdrawn by D-099. The rank integer it rested on went with it (D-012), and so did permission_level, the table that mapped levels onto codes: the famous bug it guarded — 'admin' < 'contribute' comparing alphabetically and inverting the model — cannot occur in a system with no levels, which is a better fix than the guard. The question that dies with the column is "what does manage give me on this event?": there is no such word, so there is no such lookup. The question it buys is "what exactly does this person have?", answered by reading grant rows.

    Two columns moved onto permission itself, and only one of them is comfortable.

    • right_kind ∈ read | write survives only so that D-074's guardianship channel has something to compare a permission against now that the ladder is gone: none covers nothing, view covers read codes, write covers both. Nothing else in the system compares it. It is a column whose only job is one other mechanism, and saying so is cheaper than discovering it later (§6).
    • applies_to ∈ unit | unit_and_item is where a code may be granted at all, and it is checked when the grant is saved, not at check time: an item scope is refused for codes like event.create (an event cannot be created twice, so a creation permission attached to a thing that already exists answers no question) and membership.terminate (a membership is a fact about a person at the unit, not something an event owns). The example D-099 gives for the second half is membership.manage, and this catalog has never carried a code of that name — §12 records that rather than minting it. The system namespace is unit-only the same way, which is who enforces now for the old rule that system.admin can never arrive through an item grant (D-081).

    Scope is two things, not a ladder. A grant at the unit — the organization, of which there is one, and which is a scope and never a row (D-097) — reaches every item of every type. A grant on one item reaches that item and nothing else. There is no tier between them and no relation on the item to test: no owner, no parent, no covering body.

    A grantee is an expression¶

    Wherever this catalog writes a grantee, it is a legal expression in the selector language of D-101: the leaves EVERYONE, MEMBERS, GUARDIANS[(person)], PERSON(person), ROLE(name), GROUP(name), AUDIENCE(name), the two age sets OLDER(n) and YOUNGER(n), and the five event-bound sets ATTENDED, PLACED, CONFIRMED, ON_WAITLIST, ORGANIZERS — each writable with its argument spelled, or bound to the item being checked (D-102) — combined with + union, - difference, * intersection, and brackets. Those three operators are unchanged: round 12 added two operands and no operator (D-107), so (MEMBERS * OLDER(18)) - YOUNGER(6) — brackets printed as always, since * and - bind equally and the stored form never relies on a reader who memorized it — is an ordinary expression of the grammar that already existed, and nothing in this file's grant rows, in audience_operand, or in §11's tables is shaped differently for it. There is no comparison operator in the language — no >=, no <, no bare AGE — and after this round that, not any claim about what counts as a set, is the clause keeping eligibility rule engines out (D-060, as amended by D-107). A hand-written set of people is not a leaf and has no table: it is a sum, PERSON(a) + PERSON(b), because the leaf that used to hold one and the table behind it are both deleted (D-105).

    Those fourteen leaves are the registry, not a sample of it. They are the seeded selector_type rows: the eleven that D-101 copied from the evaluator's arm list and that survived it, plus PERSON, which arrived as the thirteenth to repair a waiver expression that did not parse — the episode D-104 settles — minus LIST, which left in the round after (D-105), plus OLDER(n) and YOUNGER(n), which arrive this round and are the first operands whose argument is a number rather than a row of some table (D-107). So the count has been twelve, thirteen, twelve and now fourteen, and it is still not a contradiction: the second number counted an arrival, the third a departure, the fourth two arrivals more, and only the last is a fact about today. This corpus already ruled that an ordinal and a count are different facts — "the thirteenth to arrive" and "one of the twelve that remain" were both true of PERSON at the same time — and round 12 is the round where one of them moved twice, so the rule now has a worked example rather than an assertion: the ordinals are durable and the counts are not. Every number in that sentence except the last is a true sentence about history and will stay true forever; the last one is a sentence about the seeded rows as of this round and is the only one the next round has to re-check.

    Two of these leaves move with the calendar, and that is new. OLDER(n) and YOUNGER(n) read person.birth_date as of the date the check is made, so a person joins or leaves one of those sets with no write of any kind, one person at a time, at midnight — and a check asked about a past date answers for that past date, which is a question no snapshot design could answer. Nothing is stored, so there is nothing to invalidate (F-6): no table changes when a person turns eighteen, so there is no row to expire and no cache of membership to keep — which is exactly the property age bands would not have had, and why bands are not in this design. The editor's preview is a workbench and never was a record; the record is the audit row written at the moment of the write, which states whom the grant reached on that date and is honestly what it says it is (§12).

    A leaf outside that registry does not parse, and that sentence is now the whole of what keeps a rule engine out: an operand must be a named operand — a row — and AGE >= 18 is not a row and cannot become one while the language has nowhere to put >=. The test this corpus gave for the same rule, from ../domain/06-authorization-model.md §6, is quoted here so that this file's rule is not read as resting on it again: ~~"an attribute is not a set of people; guardianship is (GUARDIANS(x) is a set), age is not, and the line falls exactly where D-060 already drew it."~~ That test is withdrawn, and it was never holding anything up: OLDER(18) is the set of people who are eighteen or older on the date being checked, exactly as MEMBERS is the set of people who pass is_current_member and GUARDIANS(x) is the set of people who hold a row — every operand in the registry is a test with a set behind it, and reading one column is not a different kind of thing from joining one table — and MEMBERS would have failed the old test too, since nothing in this system stores the member list. D-060's decision stands; its sentence does not (D-107). The refusals below are operands people ask for that the registry does not carry.

    Every expression below is printed in the canonical stored form, which brackets every bracket, always. * and - bind tighter than +; * and - bind equally, left to right; and the stored string never relies on a reader who memorized that (../domain/06-authorization-model.md §6.2). So event.answer.view on an event is aimed at ORGANIZERS, an open camp is opened by MEMBERS, a gated office is MEMBERS * ROLE(treasurers), and the exemption for one named person is (MEMBERS * ROLE(treasurers)) + PERSON(jan) — a second grant aimed at a person is the other way to write the same thing, and keeps the exception off the expression everyone else reads.

    Three refusals belong next to the language, because each is a temptation this catalog creates, and a reader could now mistake the first two for type errors. They are not, and never were (D-107): a selector is allowed to be a hard-coded computation in the resolver, because MEMBERS is one today, and an operand may read a column against a date, because OLDER(n) does. Nothing is kept out of the registry for what it is — the word that sounded like it did, ~~"not materializable"~~, is retired with the test it belonged to — so every refusal standing here is an argument about consequences, which is what all three have always been.

    • PRESENT(<event>) is not seeded, on the argument that always carried it. was_present is NULL until somebody takes a register, so an operand over it would revoke a child's access to their own camp photos — a leader's access to their own camp — because a volunteer forgot to tick a box. Presence stays a three-valued safeguarding signal (D-067), and nowhere in this file is it a set anyone may be granted over. The language would not stop anybody writing it now, and that is exactly why the consequence has to be the thing that says no.
    • WHITELISTED is not seeded because there is nothing stored to evaluate (F-20): no type system is objecting — there is no type system left to object — but an operand with no argument, nothing bound to the checked item and no column behind it is a word pointing at a state this system does not keep. F-20 stays open as a question about whether the feature is wanted.
    • A bare name is one namespace across roles and groups (D-101), which makes §11's office names a load-bearing vocabulary, and makes every selector code a reserved name: an office called MEMBERS is refused when it is saved. Two more reserved names arrive with this round — an office, a group or an audience called OLDER or YOUNGER is refused on the same rule, and it is the parser rather than a review that saves a reader from OLDER(18) meaning an office with that name.

    There is no wildcard, except system.admin¶

    Every capability in this catalog is narrow and explicit. A check for X.y is satisfied by an exact grant of X.y — or by system.admin, which is checked outright and is the only permission in the system that means everything.

    A check for 'X.y' is satisfied by: an exact grant of 'X.y', OR 'system.admin'.

    There are no per-resource admin permissions. The earlier convention that every resource should expose an <resource>.admin subsuming its narrower codes — a prefix match computed in the resolver — was reversed by D-068, which also deleted the resolver branch that implemented it.

    "Someone who can do everything about events" is a role, not a permission — the organization composes it from the thirteen event.* codes. That is the division D-052 already drew: the code implements capabilities, the organization groups them. A per-resource admin was the code guessing at a bundle on the organization's behalf. Since D-100 the composition is literal: a role confers nothing, so the bundle is thirteen live grants whose expression names ROLE(x) — thirteen rows you can read, which is what D-068 was reaching for.

    The cost, because it is real. A new narrow permission is not automatically covered by the offices that should imply it; someone must write the grant row. Integrity check 18 is the safety net the wildcard used to be — it lists permissions no live grant names, which is what a missed bundle looks like now that no role carries a permission list of its own. It fails closed: a capability goes unheld and somebody says so, rather than a capability going unmeant and nobody saying so.

    Two things named "admin", which are not the same thing¶

    The word used to be ambiguous three ways. Three rounds of deletion left one, and the others are recorded as deleted rather than quietly dropped:

    Shape What it is Status
    ~~access_level.admin (rank 40)~~ A grant level — how much authority a grant carries, in view < contribute < manage < admin. Used by permission_level to decide whether a given grant satisfies a given permission. Deleted — the whole ladder, top rung included, by D-099. This row read "real, untouched" until round 10, which is what "untouched" was worth
    system.admin The one wildcard permission: everything, carried by a grant at the unit and never on an item (applies_to = unit) Real, and the one named exception — the only code in this system allowed to end in a noun. Exempted by name in words by D-068, and named as an exception by D-104, because its meaning is defined by the resolver rather than read off the name. Not a precedent (§1)
    <resource>.admin A wildcard permission code implying every sibling on that resource Deleted — all sixteen, by D-068, and refused in advance for codes not yet written by D-104: a grade word, and a prefix read as a permission
    dependent.medical.admin, dependent.admin An action meaning "edit", paired against .view inside a sub-resource; plus a shorthand for the whole set Deleted — by D-074, which reduced a guardian's rights to none / view / write

    D-068 exempted dependent.admin on purpose, and D-074 withdrew the exemption. The reason D-068 kept it was sound at the time: it was not a prefix match inferred by code but a value a person deliberately stored on one row about one child. What changed is not the reasoning about wildcards but the thing it was a value of — there is no longer a set of guardian capabilities for a shorthand to stand for. Read the two decisions together before reinstating anything that spells admin.

    Namespaces¶

    Namespace Resolved against Channel
    (absent) access_grant — aimed at a person or at an audience — and ownership 1, 3
    system access_grant at the unit only — applies_to = unit, so never on an item 1

    The channel numbers are the three in ../domain/06-authorization-model.md §1: grants, guardianship, ownership. There used to be a fourth row in this table and a fourth channel above it — role_assignment, the channel a system permission could only be reached through. Withdrawn by D-100: role_assignment is role_holder, a role confers nothing, and every code in this catalog — system.admin included — arrives through the one grant channel now. Who enforces that a system code stays out of item grants: applies_to, checked on save (D-081), not the absence of a channel.

    There is no dependent namespace (D-074); §9 explains what replaced it, and what was lost with it.

    That leaves the guardianship channel with no prefix to dispatch on, which has to be answered rather than left implied. It used to route on dependent., and the reason for routing by prefix was that no caller should decide which channel applies — otherwise the same authorization rule gets implemented twice, once correctly. It now routes on a fact about the request instead of a fact about the name: the channel is consulted whenever the person the action is about differs from the person performing it. That is stronger than the prefix rule, not weaker — under the old rule a guardian asking to change their child's address with a person.contact.edit code would not have routed through guardianship at all, because the code did not carry the right prefix. Nobody chooses a channel; the shape of the request selects it.

    The guardianship.* codes are additionally satisfiable by being a party to the row, and not only by a grant (D-073).

    system permissions remain non-grantable on an item: system.admin must never be delegable to a single event, a group, or an office. What enforces it is no longer the shape of the channel that could carry it but a column on the code itself.

    Sensitivity marker¶

    The Sens. column flags permissions that need extra care:

    Mark Meaning
    ⚠ Granting it exposes personal data
    ⚠⚠ Granting it exposes children's personal data — or the same about an adult, where the code reads a whole person record rather than one field of it. Since D-083 there is no separate health data class to name: the mark grades what a grant exposes, not which field the code points at
    🔒 Granting it confers authority over the permission system itself
    🔒🔒 The escalating half of that family: granting it changes what other people can do, not merely what the holder can do. role.* is marked this way in D-100, which names it "the most sensitive code family in the catalog"
    ⛔ Granting it can end someone's membership or standing

    These marks should drive UI warnings and the alerting in ../data-model/05-authorization.md. A mark grades what a grant exposes, not the table a code names (D-086), and the two new families are placed by that rule: person_group.member.manage takes ⚠ because a roster is a list of people, and role.* keeps 🔒🔒 because writing a holder row writes who may hold everything else.

    2. People and identity¶

    Code Namespace Sens. Grants
    person.view — ⚠⚠ See person records — all of them, including every descriptive value
    person.create — Add a person record
    person.edit — ⚠ Change person details, including descriptive values
    person.contact.view — ⚠ See contact points
    person.contact.edit — ⚠ Change contact points
    person.merge — 🔒 Confirm identity matches and merge people — and reverse a merge, and resolve a sign-up collision; there is no separate code for any of the three
    person.redact — 🔒 Perform a GDPR-style erasure
    attribute.define — Curate the vocabulary of descriptive data — create, rename, merge or retire a code

    person.merge and person.redact are separated from person.edit deliberately: both have privacy consequences far beyond editing a record. This paragraph used to justify the separation by calling both irreversible in practice, and D-087 has withdrawn that premise for one of them — a merge can be reversed, and reversing it is a required operation. What survives the correction is the half the separation actually rests on: the merged window cannot be reversed, so the union of two people's permissions is real from the moment the merge commits, whatever is discovered afterwards. The separation stands on the narrower reason.

    Three operations, and not one new code. Round 8 introduced two capabilities and, each time, checked whether the catalog needed a row for it (D-087, D-089):

    • Unmerge — reversing a merge a human approved: person.merge. Undoing an identity correction is the same act as making one, done by a named human, through the same queue, over the same rows. A person.unmerge code would grade undoing a mistake as safer than making one. Such a row stood in §2 until round 8 and is removed here; no seed role held it, so no role loses anything, and it is recorded rather than quietly deleted because a reader of an older draft will look for it.
    • Resolving a sign-up collision — working the claim a colliding registration files: person.merge. Resolving it is confirming or rejecting an identity_hypothesis, which is what person.merge already means (../domain/03-identity-and-legacy.md §4).
    • Linking a colliding sign-up to the person it matched: nothing, deliberately. There is no account.link and no account_claim table (§3). An automatic link once the e-mail verifies is D-004 under another name, and its failure mode is one human's descriptive data becoming another human's record.

    The check itself is the point: this file is the only list of grantable codes, so a code minted while propagating a decision is a migration nobody decided.

    Before D-068, the way to keep them apart was to carve them out of person.admin's prefix match — a special case in the resolver that was invisible in every role editor. Now there is no wildcard to carve out of, and the question moves somewhere reviewable: an office bundling all of person.* reaches them, and you can see it — since D-100 deleted role_permission, the bundle is the live grant rows naming ROLE(x), one row per code, dated and attributable. The guidance that replaces the special case is in §11 — no seeded office mixes person.merge or person.redact with routine person.edit, and one that does should be named for what it is. This is now a report a person can read, not a caveat about a resolver rule.

    person.background_check.* is gone (D-043). The organization has no background checks handled by this system, so there is nothing to view and nothing to record. If that changes, the permission pair and a dated record with an expires_at are the natural shape — and it would belong here, next to person.*, because a clearance is a fact about a person and not about their membership.

    Descriptive data: two old codes and one new one¶

    Everything the system knows about a person other than their name, their gender and their age is one class of data, in fields the organization defines while it runs (../domain/08-person-data.md, ../data-model/09-attributes.md, D-083, D-084). The catalog's whole involvement in that is one row added and none removed:

    • Read: person.view. Write: person.edit. That is the entire access story. No read or write code was added for descriptive data, because there is nothing left for one to gate — a code that separated, say, the allergy list from the rest of the record would reinstate the privileged subset D-083 refused on the merits. There is therefore no health.* or medical.* namespace and no per-field access rule, deliberately: category on a definition groups a form and grants nothing. If a narrower tier is ever genuinely needed, the route is a decision entry about a second grant scope over a defined set of data, not a code with a suggestive name.
    • attribute.define is the new one, and it is the narrow one (D-084): it creates, renames, merges and retires a code — deciding what the organization collects, which is what makes the data queryable. Recording a value against a code that does not exist needs no such permission: it saves as a proposed definition and waits in the curation queue. The mark column stays empty for it because it reads nobody's data — the vocabulary is rows about codes, and the values underneath it are reached through person.view like anything else.
    • person.view moved from ⚠ to ⚠⚠, and the reason is the same decision: the marker grades what a grant exposes, and this one now exposes everything known about a child — an allergy list, an insurance number, a note about who the child actually lives with — through a single code that used to be graded as ordinary personal data from when the record was smaller than the person.

    person.redact reaches the layer too, and in the opposite direction from retiring a code: retiring one keeps the values, redacting a person erases theirs — in the audit trail as well as in the row, since a trail that still reads out an erased value has preserved it rather than missed it (../data-model/09-attributes.md §6).

    3. Accounts¶

    Code Namespace Sens. Grants
    account.view — ⚠ See account records
    account.create — Create an account for someone
    account.suspend — ⚠ Suspend an account
    account.close — ⚠ Close an account
    account.credential.reset — 🔒 Issue a credential reset

    account.suspend is not membership.suspend. Suspending a login does not remove someone from the organization; the two are separate lifecycles and separate permissions.

    Nothing in this namespace links an account to a person it already belongs to, and the absence is decided, not overlooked. A sign-up that strong-matches an existing person raises an identity_hypothesis and brings nothing into the world that a human has not approved — nothing merged, nothing linked, nothing activated; the account sits at pending_verification until a reviewer decides, and deciding is person.merge (§2, D-089). So there is no account.link code and no claim object for one to act on: the second live account those would manage is exactly what the rule forbids, and the case they would have been asked to solve most often is already handled underneath permissions — account_credential holds many credentials for one account, so a member with a new e-mail address is adding a credential to the login they have, not acquiring a second one.

    audit.view is graded ⚠⚠, and the reason is a property of the trail rather than of any field it touches. audit_log carries the before and after images of what changed, which makes it a second copy of the person record — descriptive values included, on the same terms as a person_contact or a note change. There is no exclusion list doing that work, and there must not be one: a rule naming the person fields whose values may not be logged is a privileged subset of the record, which is precisely what D-083 refused — and it would hollow out D-085, whose entire justification for overwriting a value in place is that the trail holds the sequence. So reading the trail over a scope is reading person data over that scope, and reading more than person.view shows: the current row is the organization's present belief, the trail is every belief it has held. What protects the trail is therefore the guard on it — scope, this mark, and who is granted it — exactly as the guard on person.view protects the record. The grading rule this applies — the mark follows what a grant exposes, not the table a code names — is D-086, taken during propagation rather than from an answer, and reversible on one line.

    The contents expire, which bounds this exposure without fixing it. A row lives for the life of the system; its old_values/new_values are emptied 24 months after they were written, by a scheduled job this corpus calls payload reduction — a third operation on the trail, distinct from redaction (a person's erasure, immediate and absolute, whatever the age of the row) and from an import revert (D-088). So "the trail is every belief it has held" is, since round 8, true only of the values less than two years old; about anything older the trail answers who touched this row, when, and were they allowed to and not and to what. For the risk this note is actually about — a grant graded wrongly, or simply held by the wrong person — that is a control worth having: it does not make the exposure impossible, it puts a horizon under it, which for an organization of this size is the realistic form the same protection takes. AT-4 stays open, because a window on the payload is an argument about how long a bad grant can do harm, not an answer to whether one permission should guard the trail.

    Payload reduction needs no code here, and saying so is the check that it was considered. Nobody performs it interactively: it is scheduled, and the guard on it is a check that alerts when a row past the window still carries a payload (../data-model/06-audit-and-import.md §2.2). A permission for it would imply a person choosing not to run it.

    The excluded-keys list survives, with a smaller and honest job. Values that must never be logged at all belong on it: credential secrets, tokens, session material. Personal data does not, because personal data is protected by who may read the table, not by a list of its names.

    Erasure reaches the payload. A redaction that rewrote the business tables while the erased values stayed readable in the trail is a failed redaction, not a partial one (../data-model/06-audit-and-import.md §2, ../data-model/09-attributes.md §6).

    audit.export sits at ⚠⚠ for a reason unrelated to what it reads. An export carries the payload outside every mechanism this catalog governs: scope stops at the file, revoking the grant does not recall the copy, and a later redaction cannot reach it. It is graded by where the data goes, not by what the code is allowed to see.

    Whether one permission is enough of a guard for all that is itself open — tracked as AT-4 (../open-questions.md). The grading above is what is settled: the trail is read with the guard of person data, whichever permission or combination of permissions that guard turns out to be.

One permission covering both forces the organization to hand the clipboard-holder the ability to delete a child from the camp roster. Splitting it costs two rows and makes the ordinary delegation ordinary. What the split was graded with is gone — the note used to add "and note the level: presence is contribute, the same bar as being able to register", and there is no bar to compare now (D-099). The split is worth more than the level was: the distinction the level made softly — this volunteer is not roster leadership — is now written as the only thing a grant can say, one code, and granting event.presence.mark on an event cannot smuggle in event.manage_participants the way contribute once sat underneath manage. It follows the shape of membership.lapse versus membership.terminate (D-022) — one routine, one consequential — and it is free to add because the catalog is a menu, not a fixed set (D-055). It was previously an open question (EV-5); it is resolved there as a split, and the split outlived the ladder it was graded on.

    event.register_self is the whole of D-060. Opening an event to the membership is one row: an access_grant scoped to that event, of event.register_self, aimed at MEMBERS. One row is the point — nobody is enumerated, so nobody is left out when the roster changes, and nothing has to be re-run when someone joins. It used to be one row at contribute, and the level was doing a second job there that nobody assigned it: it made the eligibility grant the same size as the presence task. With the level gone the row says one thing, which is the smaller claim and the one that survives review.

    An age-restricted camp is a narrower expression instead — MEMBERS * GROUP(camp_2026_junior) aimed at the same one code, or the same subtraction pattern read the other way. There is no age rule on the event and there will not be one — an open event with an age ceiling is accepted as a risk, on the grounds that a registration-time condition the capability model does not know about is the first rule-engine rule (D-070). If it ever needs closing, the shape is a new selector in the selector_type registry, not a column (../domain/07-events.md §4) — and note that GROUP(...) is a set somebody maintains, so "who is eligible" stays a roster with a person's name on every row rather than a predicate the resolver evaluates.

    event.cancel is separated from event.edit deliberately. Cancelling is the most consequential thing anyone does to an event: it affects every registrant, it usually involves money, and it is a decision rather than an edit. It does not notify anyone — that is the communication module's job, and conflating the two makes "who cancelled this, and when?" harder to answer than it should be.

    event.delete is on this list and nothing else has an equivalent, because events are the one thing in this data model that can be deleted. (The comparison used to be with org_unit, which had no delete permission and had six codes of its own; §5.) A draft event with no registrations is a mistake to be cleaned up; anything else is cancelled, not deleted (D-064). No event with even one registration row may be deleted — Guard 2 in ../data-model/08-events.md §8 is the rule, and cancelling is what to do instead. The obligation is not the permission's to carry: event.delete decides who may ask, and only a migration-level constraint — event_registration.event_id referencing event.id with no cascade — refuses the same delete when it arrives from an import or a hand-written fix instead of a screen. Enforcing this in the model layer alone would leave the record of who was coming deletable by everything except the intended route.

    event.answer.view is where D-061 lives, and since round 10 it lives there as a grant. The sentence "answers are read by that event's organizers" used to be hard-coded prose beside the resolver, reached through the event's owning unit. event.org_unit_id is deleted, so the sentence is now said where permissions are said: a seeded grant of event.answer.view, scoped to the event, aimed at ORGANIZERS (D-102). Because a bound operand is legal only on an item-scope grant, this cannot be one row for every event: what ships is a template, and D-102 now says plainly that the event-creation path instantiates it beside the event row, in the same transaction as the event, and that the import owes one instantiation per event it writes (../data-model/08-events.md §8). What remains open is only the safety net: an event whose two writes were not one transaction has no organizer who can read its answers, and "these two rows exist together" is a report — events with no answer-view grant — that no layer of this project can express as a constraint (F-10). The rule itself is unchanged: whoever runs an event reads that event's answers with no additional gate, because holding an office grants nothing (§7) and leadership is not guardianship — guardianship authority belongs to the guardians (§9). That is a deliberate widening and it is recorded as one. The catalog's registered spelling is event.answer.view, singular — the arbiter for a spelling the round briefly had two of, and the reason §12 says a code is a row and prose is only prose (§12, F-19).

    Its premise has since been narrowed, and not by reversing it (D-085). D-061 was written when an event form was the only route by which a camp leader learned a child has a nut allergy, because nothing else was readable. Descriptive data now exists (../domain/08-person-data.md) and a leader holding person.view over that unit reads a recorded allergy there, so the form is the fallback for a fact the organization has not recorded, not the ceiling on what an organizer may know. What survives unchanged is the decision itself, and the discipline below it.

    This code is graded ⚠⚠, and it is the second time in this round that the marker followed the content rather than the category. It sat at ⚠ beside a paragraph conceding that the answers under it can be clinical, which is the same mismatch audit.view had one section above: a payload that is children's personal data, graded as though it were logistics. D-083 refuses a class of data more delicate than the rest, so either an adrenaline-pen answer is person data — it is — or the grading on the audit trail was wrong. The raise narrows nothing: D-061 stands, an event's organizers read that event's answers with no additional gate, and all that changed is what a reviewer should notice before ticking the box for the grant that reaches thirty volunteers — and since D-102 there is a box to tick: the seeded grant above, rather than a clause in a resolver nobody can read.

    Which leaves the discipline exactly where it was, and says so plainly: the rule that only preference-level detail belongs on a form is guidance on the form's label and nothing more. No layer enforces it and no layer can: nothing distinguishes "vegetarian" from "carries an adrenaline pen" to a database (../data-model/08-events.md §7). It rests entirely on whoever writes the form — a convention, not a guard, and D-072's own sentence is the right way to read that.

    11. Roles — proposed seed set¶

    A starting point, not a specification. The heading is kept because its slug is cited from the decision log and from four other pages, not because the words still fit: this section used to list roles with their permissions attached to them, and a role has no contents now. ~~Scope required · Req. · Waives gate · Key permissions~~ — role_permission is deleted, with role.scope_required and role.requires_membership beside it (D-100), so the codes an office carries are the live grants whose expression names it: one row per code, each with its own scope and its own period. Roles stay runtime data — the organization creates them, names them, writes and closes their holders, and deletes the unused ones (§7). What is no longer runtime data is reach, which is administered through access_grant.create and access_grant.revoke and is therefore reviewed in access_grant, not in a role editor (§7).

    The gate moved into the expression¶

    ~~Req.~~ was role.requires_membership: whether the office stopped conferring anything the moment its holder's fee lapsed (D-039). ~~Waives gate~~ was the separate, person-level permission system.gate_exempt (D-051), and the two columns answered different questions and were never alternatives: the flag exempted everyone holding an office, everywhere, while the permission exempted one named person across every office they held. Both columns, both mechanisms and the resolver clause that implemented them are deleted by D-100. MEMBERS is an operand now, evaluated live on the checked date, and whether an office survives its holder's lapse is a property of the expression written on the grant:

    Old mechanism New expression What the writer is saying
    The gate applied to an office with requires_membership = true MEMBERS * ROLE(x) this office is for people who are members right now
    The gate waived for a whole office ROLE(x) written without MEMBERS; a lapse in the fee ledger does not stop this office
    The gate waived for one named person (system.gate_exempt) (MEMBERS * ROLE(x)) + PERSON(y) one person is the exception, and the exception is visible to everyone who reads the grant

    A second grant aimed at PERSON(y) is the other way to write the third row, leaving the gated expression alone; D-100 keeps both legal and calls the second arguably clearer for a permanent exception, because it keeps the exception off the expression everyone else reads. What is gone is the permission — not the ability.

    The posture reversed, so name the new failure instead of burying it. The gate used to be default-on, which made forgetting it impossible and waiving it a deliberate act. It is now opt-in per grant: an expression written ROLE(treasurers) with no MEMBERS authorizes a lapsed member, silently, for as long as the grant lives. Three controls, none of which is the resolver:

    • A standing report of live grants that name a ROLE(…) operand and contain no MEMBERS. An office held by a non-member is the case worth a human eye, and this report is narrow enough to actually be read — system_admin, leaders and auditor are on it here, and all three are on it because someone chose them, which is the whole point.
    • Seeded grants and any grant template carry MEMBERS, so the path of least repetition is the safe path. In this seed that control has nothing to work on: the seed's one grant must not carry MEMBERS, and it is the only one, so every office grant anyone ever writes will have been written by hand — the safe path is not the short one. Recorded in §12.
    • Import completeness. The counselor office is only as correct as the roster behind it, and the gate used to fall out of membership alone; the duty is stated above, and it fails closed.

    One value in the old table was never a preference, and it is the one to copy carefully. system_admin was marked Waives gate = yes because on 1 January the expiry sweep of D-040 lapses every membership in the organization including the administrator's, and without the exemption the person who would repair the system loses the ability to use it on the day it breaks. That is a property of the system, not a policy choice, and it is carried now by writing that one row ROLE(system_admin), with no MEMBERS — which turns a flag nobody read into an expression with an outage attached to getting it wrong. The loud mistake is the opposite one: writing MEMBERS * ROLE(system_admin) "for consistency" reproduces the lockout, silently, with no error message — D-051's documented hazard outlives the mechanism that produced it. Whether any office in the shipped seed is written this way is a different question, and the answer is no: the seed contains no office grants at all (What the seed ships, §12).

The code is deleted (§4), and the oddity it defended — a scope that matched only the root's own rows and refused to read into a pack's roster, because crossing into a sub-unit took a scope_exposure (D-049, D-041) — has no subject after D-097: there is one scope, so there is nothing for it to fail to reach, and membership.view answers who is in the organization? on its own. Leadership is not guardianship, so no office hands anyone a guardian's right over a child — not the right to act for that child, and not the row that decides what the family may see. That is also why §2 now grades that code ⚠⚠: the safeguarding review moved from "is there a code we kept out of offices?" to "which grants were given this one?", which is a question the catalog can actually answer. Do not re-derive the old rule as a list of codes to keep out of offices — the rule is about the channel, and there is no code left to quarantine.
    4. system_admin, leaders and auditor are the three example offices written without MEMBERS, and the last two are the successors to the old Req. = no. The rule the old column followed was one sentence — staff-like offices working on the organization's own records require a membership; volunteer-facing offices do not — and it survives as a writing habit, because a resolver clause does not survive otherwise. The failure it prevents is specific: the volunteer whose own fee is unpaid still runs the Thursday meeting, and must not lose their roster the night it lapses. ~~The corresponding position.requires_membership stays true, so the unpaid volunteer shows up on a chase-up report.~~ Positions are deleted (D-100), so the noticing moved: that volunteer's office now appears on the standing report of grants that name a ROLE(…) operand and carry no MEMBERS, which is how the organization notices, and the resolver is still not how it punishes. See ../domain/06-authorization-model.md §4.
    5. identity_reviewer decides identity questions about children without a read over the person record. The office carries three rows — person.merge, import.view, import.apply — and person.view is not among them: the reviewer works from the candidate pair, the match_signals recorded against it, and the names and dates those signals compare. That is deliberate as it stands — the question being decided is whether two rows are one human, and the descriptive values underneath are not evidence about that — and it is the same shape as auditor reading the trail without holding person.view. What round 8 changed is the pressure on it. This is now also the office a blocked sign-up lands on: an account held out of active by an unresolved hypothesis, with an age check alerting because the stalled item is a person who cannot log in (D-089). If reviewers begin asking for context they cannot see, that is the finding to act on, and the two honest answers are a scoped, dated person.view on this office, or a review screen that shows more of the signals. Reaching instead for an organization-wide person.view would put the catalog's largest ⚠⚠ read in the office with the most write authority over identity. Tracked as F-11, where none of the three positions is yet recorded as taken.
    6. No office in this set holds person_group.member.manage, and that is a hole rather than a neutral omission — the sentence used to be about unit_participation.manage, and the code is deleted. What D-095 decided has not moved: joining a set is somebody else's act, the write is never self-scoped, and this code is now the only thing standing between a person and a group's roster (§5a). As written, leaders may see a roster and cannot write one. The gap is wider than it was, not narrower, because the answer behind D-095 was "they will be assigned to the unit by the counselors" — and the counselor office is seeded with no grants at all (What the seed ships), so on the shipped seed nobody at all may write a roster. It is recorded here instead of added to the table on purpose: which volunteer office may put a child on a group's roster is the organization's decision, and an appendix that quietly hands it to leaders would be making a safeguarding choice on someone else's behalf (§12).
    7. attribute.define is held by nothing here, and an office is the wrong shape for the answer. open-questions AT-2 points at this section as the place the question gets answered, and the honest answer for a volunteer organization is one or two people rather than an office: a grant aimed at PERSON(x) (§1) is the form that fits, with a date on it, and an office would only be a way of making one person's job look like a policy. What is not the answer is leaving it unheld while proposals keep arriving through ordinary data entry (§12).
    8. An office name is now load-bearing in a way it never was, because names are one namespace. A bare name in an expression resolves against role and person_group together, so an office called leaders and a group called leaders cannot both exist, and the collision is caught on the write path rather than by a constraint (there is no constraint spanning two tables) (D-101, D-081). Every selector_type.code is reserved on top of that, so an office called MEMBERS is refused when it is saved rather than silently rewriting every expression in the system. audience_admin is therefore a name with a second duty: as well as saying who may edit audiences (§5a), it occupies a name no group may take — and note that it grants nothing over person_group at all, so whoever manages audiences and whoever manages groups may be, and here are, different people.

    12. Open issues¶

    • The catalog's disposition is settled; its contents are not. It stays comprehensive and granular (D-055), so there is no longer a "prune this down" review to do. What remains is additive: each unbuilt module brings its own permissions as it is specified, and unused rows cost nothing.
    • Which offices' grants carry MEMBERS is now a decision with no default recorded anywhere. ~~Both were attributes of roles, and roles are runtime data the organization administers, so the values shown were reasoned defaults~~ (D-039, D-051 — both mechanisms deleted by D-100). The answer is now written into a grant's expression, and what the specification still owes is the thing D-100 nominates as the only control: a standing report of live grants naming a ROLE(…) operand whose expression contains no MEMBERS — who runs it, how often, and what makes a row on it a finding rather than a fact. §11 puts three offices on it on purpose, which is not the same as having the report. Tracked as F-13, which asks the sharper half of the same question: a warning at save time, or a report afterwards — and a report is the weaker answer precisely because a lockout is silent.
    • Nothing bounds what a holder of access_grant.create may write, and the catalog no longer pretends otherwise. ~~A grant could not carry a level above the writer's own~~ — that was permission_level's second job, and the table is deleted by D-099. So anyone with access_grant.create can grant system.admin to anyone, including themselves, and the only remaining guard is applies_to = unit, which stops the shape of the grant and not the act (§1, §7). Every earlier answer to "who can grant what" is gone with it: the ceiling was the one thing the deleted ladder was still doing, and nothing replaced it. Whether the answer is a second code for granting the system. namespace, a two-person rule, or "the audit trail and a small organization's judgment" is open, and it is the sharpest hole round 10 left in this file.
    • event.grant_access may now be an orphan, and it is one the round created. Its whole purpose was to demand a level over an event that the general grant path could not express; with the level gone, what distinguishes it from access_grant.create is the scope alone (§8a). Either it is a scoped front door onto the same table — in which case the catalog should say so and the two codes' relationship should be an invariant — or it is a code with no remaining subject, which is the class of bug D-068 made visible. It is left in the catalog, marked, rather than deleted here: deleting a code because one mechanism died is the events module's call, not an appendix's.
    • A deny that matches no allow is invisible, and D-099 asks for a report nobody has written. The new integrity report is "a live deny matching no live allow is dead weight" (§9 restates it). It is not the same question as integrity check 18's — that one asks which permissions no grant names, this one asks which grants do nothing — and it is easy to under-build: a deny aimed at a set that currently resolves nobody looks identical to a deny that is working. Open only as a report with no owner; the semantics are settled.
    • A leaf that names nothing is still the empty set, and it is now also a line on a page. Nothing about resolution moved: EVERYONE - PERSON(x) with a dead x still subtracts nobody and therefore still denies everybody, and nothing is refused at save because a leaf is broken (D-106). What arrived is the report — an audience carrying a leaf that does not resolve is listed, for the audience's owner, in a second column of the page F-21 already asks for — and it is the thing that separates the two rows this bullet is about: a deny over a set that is genuinely empty, and a deny whose operand has quietly stopped resolving. The direction is the fact worth carrying, not a volume: a failed operand on the + or * side narrows the set, and a failed operand on the - side widens it, so - is not the noisy operator, it is the only one whose failed operand can grant — and a check that "fails closed" on that side is fail-closed and lockout-everybody in the same step. And one thing is not a failure at all: a person with no birth date is not a broken OLDER(18). The operand resolves perfectly well, to the set of people who are that age on the date being checked, and that person is simply not in it, exactly as a person with no membership row is not in MEMBERS. A missing value on the person being asked about never reaches the report, which is the distinction the page has to preserve or it pages about every incomplete import in the legacy corpus. The page is a query with an owner, not a guard (D-081's phrase, applied to it by D-106): no save depends on it, and the catalog mints no code for reading it.
    • audience.manage is one code over an expression, and the largest act it covers is still unmarked. ~~D-091's inclusion arm~~ is gone, and composition is the expression now (D-101): the arm that used to need its own code is an ordinary + beside a leaf, and the leaf that should worry everyone is EVERYONE. What the round took away is an option, not a safeguard: the code's former second half — editing a LIST's names apart from the rule — lost its operand when D-105 deleted the list, so may tick names on this audience without may rewrite the rule is no longer a shape any code could cover even if one were written; if the need is ever real it is a new question about the editor, not an argument that the deletion was wrong. The shape of the concern is unchanged and one edit shorter: whoever can edit one expression can widen every live grant aimed at it, including by writing EVERYONE, which is legal, reachable, and resolves to non-members and the public — and the reach is now transitive, because D-103 lets one audience be named inside another, so editing a widely-named audience widens every grant aimed at every audience that names it. Either composition is documented as plainly inside audience.manage — accepting exactly that consequence — or it gets a code of its own; no code was invented here to fill the gap. The interim control is the editor showing the expanded set and the affected grants before the save, which is a user-interface requirement carried in ../domain/06-authorization-model.md §6.2, not a permission.
    • Nothing bounds what a permission check costs, and that was a property of this system until this round. The bound lived in audience.selector_depth_limit and was refused at the save, which is where the sentence "a check costs a bounded amount" came from; D-105 deleted the column, the bound and the save-time depth refusal together, and kept the two cycle walks — inside the tree, and across audiences through every AUDIENCE(x) leaf — as the only structural guard there is. An expansion that never terminates is still refused, because acyclicity is the one thing the deletion did not relax; what a terminating expansion costs is bounded by nothing. What replaced the property is a standing report of the widest and deepest audiences and their per-check cost, which is a convention, not a guard (D-081) — D-105 counts it as the third control of that shape this module stands on, beside §11's no-MEMBERS report and D-104's by-hand registry report. Nobody is named to read it, no number makes an audience too wide, and nobody has ruled who may ever add a cap back — that is F-21, and until it is ruled, bounded cost is an open finding here, not a property. The catalog mints nothing against it: no code governs expansion, and none could — whoever can write EVERYONE into an expression already holds audience.manage (§5a).
    • A grant's reach now moves with the calendar, and there is no write to mark the moment. OLDER(n) and YOUNGER(n) are ordinary named operands composed by the same three operators as every other (§1), and they are the first whose membership changes with no write at all (D-107): a person turns eighteen, joins the set, and no row was touched — no table changes, so there is no row to expire and no cache of membership to keep, which is exactly why age bands are not in this design. F-6's model was that a write invalidates a decision, and this is the first exception to it; the recorded answer is not a new invalidation path but the observation that a cached decision is already keyed to a date and already expires. One thing follows that is open, and one that is closed, and keeping them apart is the whole point. Open: nothing bounds what such a check costs — the bound this system had was a depth bound and D-105 deleted it, so an age-bearing expression is one more set to expand and it is bounded by nothing; that is F-21, whose shape this round did not change and whose width it did, and the catalog mints nothing against it: no code, no column, no number, no threshold. Closed, and deliberately not a finding here: whom a derived set reached. The preview a writer looked at is a workbench, never a record; the record is the audit row written at the moment of the write, which says whom the grant reached on that date and is correct for the date it was written — a prediction about the future, and honest about being one. Ask the model the same question about a date in the past and it does not read that row back, it computes the answer live from a birth date and a date, which is the property D-107 bought rather than a hole it left. The premise this rests on is the organization's own — the people writing the rules WILL know what they are doing — and it is written down in D-107 with its two limits, because a claim about the authors buys nothing about the people a rule reaches and nothing about the write that is never recorded.
