    Appendix — Entity Relationship Diagrams¶

    This appendix describes relationships — what points at what, how many, and whether the link is temporal. Field-level definitions live in the data-model documents, each in the one that owns the entity, and are deliberately not repeated here.

    Diagrams of the schema in ../data-model/00-conventions.md. Split by subject area so each stays readable; the areas connect through person, which appears in all of them.

    Notation: → is a foreign key pointing at the referenced table. ⇒ is a polymorphic reference (no database-level foreign key). Temporal tables are marked [T].

    PERSON_ATTRIBUTE }o--o| ATTRIBUTE_OPTION : selects

    Key point: these three tables are the whole of what the system knows about a person beyond name, gender and age. There is no health table beside them and no privileged corner inside them: D-083 removed the category and D-084 put an organization-maintained vocabulary in its place. Reading is person.view, writing is person.edit, and only the vocabulary needs a code of its own (attribute.define). Fields and rules: ../data-model/09-attributes.md.

    None of the three is [T], and the no beside them in §7 is a decision, not an omission. A person_attribute row is the current belief, overwritten in place, and audit_log holds the sequence of beliefs, values included for as long as the payload window lasts — 24 months, after which the row is reduced and the values are gone (D-088) — which is why the trail is guarded as person data is (the permission catalog §8). This corpus gives periods to things that are true over an interval — a membership, an address, an office held, a guardian's authority — and a descriptive value is not one of those: it is a statement made now about whatever it is about, with a timestamp on the assertion. A valid_from here would ask a volunteer when an allergy began, which is a question the organization is not competent to record and has no rule that could use (D-085). The cost is named rather than left out: the history of a value lives in the one control D-081 calls the corpus's weakest, and §7 lists it as the accepted risk. It is also a deliberate departure from guardianship two sections below, which keeps its current value and its history in business tables — because authority is asked "what was it on that date?" as a routine part of answering whether an act was permitted, and an allergy list is not.

    The two vocabulary tables are non-temporal for a smaller reason of their own: a code leaves service by status, not by a period, so a value recorded against a retired option keeps meaning what it meant on the day it was chosen. Retiring therefore never touches a fact — only redacting a person erases one (../domain/08-person-data.md).

    2. Organization¶

    There is no organization-structure diagram, because there is no organization structure. There is one unit, it is the organization, and it is a scope and not a row: grant_scope_type carries a code unit with is_item_scoped = false, and a grant written at it has no scope_id (D-097). What this section drew until round 10 was a hierarchy of bodies with a vocabulary of types, rename history, lineage edges, rosters and offices. Every one of those tables is deleted, not moved; the ledger of what each took with it is ../data-model/02-organization.md §5. What is left for this section to draw is the group — a set of people, not a body.

    erDiagram
    PERSON_GROUP {
        uuid id PK
        uuid public_id
        string name
        string description
        date valid_from
        date valid_to
    }
    PERSON_GROUP_MEMBER {
        uuid group_id FK
        uuid person_id FK
        date valid_from
        date valid_to
        uuid added_by FK
        string note
    }
    PERSON ||--o{ PERSON_GROUP_MEMBER : "is in"
    PERSON_GROUP ||--o{ PERSON_GROUP_MEMBER : has

    Key point: a group is a named set of people with a lifetime, and that is the whole of it — no parent, no type, no code, no path, no nesting rule, no rename history, no split or merger edge, no leadership, no roles, no fee (D-098). The member row is dated, so the roster answers "who was in schuzka2026-1 on 14 March 2026" from its own rows rather than from the audit trail, whose payloads expire after 24 months (D-088). No two rows for one person and one group overlap, counted over all rows and half-open, so a person who left in 2020 and came back in 2024 is two rows and never one row edited in place.

    Membership of a group confers nothing. A set is not a grant; a group member is reached only because some grant's expression says GROUP(x) (D-005). The group is an item in grant_scope_type, so a grant may be written on one — that edge is in §5a, not here, because access_grant owns it and not this module. The box is deliberately alone beside its roster: name is unique across role and person_group together, but no constraint spans two tables, so that is a write-path rule and not a drawn edge (D-101).

    Gone from this diagram, one line each, so that a reader hunting for a box finds the decision:

    • ~~org_unit~~, ~~org_unit_type~~, ~~org_unit_type_rule~~, ~~org_unit_name~~, ~~org_unit_relationship~~ — all deleted by D-097, with path, depth, the unit vocabulary, the nesting checks, the rename history and the lineage edges. There is no unit table anywhere in this appendix. The unit appears once, as the unit row of grant_scope_type (§5a) — a lookup row naming a scope, not a body.
    • ~~unit_participation~~ — deleted by D-097. person_group_member is the roster that outlived it and membership (§3) is membership of the unit; the import owes participation rows to nothing.
    • ~~position~~, ~~position_assignment~~ — deleted by D-100: with one unit there is no body to be a leader of. is_leadership and max_holders went with them; the office survives as role + role_holder (§5a).
    • ~~org_unit_type.allows_minors~~ — the flag was deleted by D-095 and the table that carried it by D-097. Do not place a child where nobody is responsible is now person_group.member.manage held by a named adult, and the system can no longer say which groups are for children — that loss is D-095's, restated in D-098.
    • ~~scope_exposure~~ — deleted by D-097 with the direction-of-authority check and the nightly alert that was its only detector. §5 says what was lost with it.

    See ../data-model/02-organization.md and ../domain/04-organization-structure.md; the scope itself is ../domain/06-authorization-model.md §2.

    Four points that matter:

    • membership_request has two person references: person_id (the child, who would become a member) and submitted_by_person_id (the parent, who applied). Collapsing them makes the audit trail false.
    • A request asks for membership of the unit and names nothing else. requested_unit_id is deleted with the units (D-097, D-098), and there is therefore no edge from this diagram to any body: which group a new member lands in is a write on the group — one person_group_member row, §2 — and not a preference on the request. The ~~unit this request was aimed at~~ is withdrawn, not moved; the want behind the column is served by the free-text notes the row already carries.
    • Belonging lives in two shapes now, and neither is a membership. person_group_member (§2) is a group's dated roster and is keyed on person, never on membership — the argument unit_participation made and D-098 carried over: an imported roster or a 1998 camper has no membership row to point at, and inferring an open-ended one would sweep that person into MEMBERS today. The table that held it, ~~unit_participation~~, is deleted by D-097, along with the root participation row every membership used to owe. Field rules: ../data-model/03-membership.md.
    • membership_type exists with exactly one row, and category, min_age, max_age and requires_background_check are all gone. Membership is ageless (D-038); age is read from person.birth_date where it matters, which is guardianship — positions carried the last stored eligibility rule and D-100 deleted it, so age is nobody's check and membership never was one.

    Key points:

    • One table grants. access_grant is the only place authority is written, plus the one table over a single person, guardianship_permission (§4, step 4 above). role_holder, person_group_member and every operand of an audience decide only whom a grant reaches — being in a set is worth exactly what the grant aimed at that set says (D-005, restated for roles by D-100). ~~role_assignment and access_grant are the same idea at two granularities, sharing scope_type, the level model and the resolver~~ — withdrawn by D-100 and D-099: role_holder has no scope columns, no level and no resolver channel, and what the two now share is only the temporal shape every dated row has.
    • There is no wildcard permission. A check for X.y needs an exact grant of X.y, or system.admin. The old <resource>.admin prefix match was removed with its sixteen codes (D-068, reversing D-007); "can do everything about events" is a role some grants name, each grant naming one of the thirteen event.* codes. ~~Note access_level.admin (rank 40) is a grant level and survives — same word, different mechanism~~ — there is no grant level now (D-099), so the collision the sentence existed to warn about cannot occur: admin is only ever the code system.admin.
    • Deny is absolute, and this round quietly upgraded it. D-013 said revoked beats deny, which left an escape hatch — a stale denial could be outranked by a newer act, and revoking it was a decision somebody could take late. Deleting the ranking deleted the hatch: a live deny now beats every live allow with no tie-break, and the only thing that removes one is a person ending its period. That is why valid_to earns its keep on a deny row and why a live deny matching no live allow is a reported shape rather than a harmless row — a deny that denies nothing is how a stale restriction outlives its reason (D-099).
    • The membership gate is deleted, and the posture reversed from default-on to opt-in. ~~The gate sits on the role tier and nowhere else (D-039): no current membership → the role grants nothing, unless the role opts out~~, and ~~system.gate_exempt waives it for one named person (D-051)~~. Withdrawn by D-100: MEMBERS is an operand evaluated live on the checked date, so MEMBERS * ROLE(x) gates and ROLE(x) alone does not, and the "except Honza" case is written inside the same expression. The new failure mode is a grant written ROLE(x) with no MEMBERS, authorizing a lapsed member silently and forever, failing closed-looking so nobody notices — the control is a standing report of exactly that shape, plus seeded grants that always carry MEMBERS. Ownership and guardianship were never gated and are untouched.
    • The guardianship channel is entered by shape, not by permission name (D-079): the check is about someone other than the actor, and the channel answers with allows only. A sufficient right_level returns true; no row, none, or too low a level returns nothing at all and the actor's own grants are tried. A prohibition is therefore a deny grant, never a low level. What the channel compares a permission against is now permission.right_kind — a column D-099 added and names as having exactly one customer, this channel.
    • There is no downward crossing, because there is no down. ~~Authority never inherits downward; a sub-unit's authority reaches outward only through a scope_exposure row, written by the sub-unit granting coverage over itself~~ — deleted by D-097, taking the direction-of-authority check, the scope.expose code and the nightly alert that was that check's only detector. D-031 was not weakened, it was deprived of its subject: with one unit there is no "outside it" to be stopped from. What is genuinely lost and reproduced nowhere is the safeguarding property — access to a body's children had to be granted by that body, by people who recruited the leader and can be asked. What remains is a permission held by a named adult, an audit trail whose payloads expire after two years, and a report of who holds the write, minus the part where the adult was somebody the body chose. A grant at the unit therefore reaches every item of every type, and system.admin with it.
    • A grantee may be an audience. access_grant.person_id and audience_id are mutually exclusive — never both, never neither. An audience is now an expression over named sets (D-101), so the old sentence "built-in audiences are rules evaluated at check time; named groups are stored lists carrying the stale-group problem knowingly" no longer describes three arms: every operand is evaluated live and nothing is stored as a roster — D-105 deleted LIST and its table, so a hand-written set is PERSON(a) + PERSON(b) in the expression — and the composition D-091 wanted is an operand instead of an edge. Author in sets, evaluate per person — a check compiles to a predicate and never materializes a set, and an operand that does not resolve is the empty set: fail closed in every direction.
    • Nothing owns an event (D-102). event.org_unit_id is deleted, so the people connected to an event are named by operands that bind to it — ORGANIZERS, PLACED, CONFIRMED, ATTENDED, ON_WAITLIST — each a set the item itself defines. An operand is a set, not a grant, which is why D-062 ("an event_organizer row grants nothing") stands untouched while the resolver stopped special-casing it. The consequence worth remembering: a bound operand is illegal at the unit, so "every event's answers go to its organizers" is a template the event-creation path instantiates beside the event row, one per event, in one transaction — and an event whose creation died between the two rows has nobody who can read its answers, which is what the events with no answer-view grant report is for.
    • scope_id is polymorphic (no FK) so a new grantable item type is a config row, not a migration. Accepted cost, with mandatory mitigations. D-101 extended the same trade-off, and the same four mitigations, to audience_operand.selector_arg_id.

    See ../data-model/05-authorization.md and ../domain/06-authorization-model.md.

    Key point: access_grant is a pentagon of references and grants exactly one thing — a grantee (person or audience), a scope, one permission, an effect, a period (D-099). Uniqueness follows the shape: at most one live allow per grantee, scope and permission, with denies deliberately outside the rule so a deny can sit beside an allow on the same item — that pair is the only way to say "this person has the unit's events, except this one".

    No line leaves scope_id, and that is the diagram telling the truth. The edge that exists runs to grant_scope_type, the seeded registry (unit — the only row with is_item_scoped = false, event, person_group, role, document deferred) which is what states which table the unresolved id belongs to. The id itself is ⇒ polymorphic: no foreign key, validated by the registry plus a nightly orphan scan per type (D-011, §8). A unit grant carries no scope_id at all, which is the entire schema-level content of "the unit is a scope, not a row".

    A role is not a permission bundle. role_permission is deleted by D-100: the codes an office carries are the live grant rows whose audience names ROLE(x), so "what may a treasurer do?" is a query over rows a screen can show. role_holder is a dated holder row — person, role, period, who granted it, note — and names one person, never a rule (F-12 is closed with the answer no, because an office that cannot answer "who was treasurer in 2023" is not an office record). role itself has no period: it is a definition, valid always, and the period lives on the holder row (D-053). The second arrow into person is granted_by, and it is drawn to a person because the column records who appointed — a fact carried on the appointment, readable five years later by whoever has to ask. The act of appointing is what audit_log holds, with its actor taken from the request context rather than from the row (../data-model/06-audit-and-import.md §2); the two are not one column's job, and every other actor column here (access_grant.granted_by, person_group_member.added_by) points the same way for the same reason — the third of the three, audience_member.added_by, is gone with its table, and what it used to answer per name is answered now only by who last saved the expression and by audit_log (D-105).

    Names are one namespace. role.code, person_group.name and a set audience.code are unique together, case- and separator-folded, and every selector_type.code is reserved — so a group called MEMBERS is refused at the save rather than discovered later as an expression whose meaning moved. No constraint spans three tables, so the write path carries the rule and an integrity check asserts the write path still does (D-101, D-103, D-081). What is stored is always kind + id, so a rename never rewrites a grant.

    Five of these lines are ⇒ in the notation above, and not one of them is a foreign key. A leaf's selector_arg_id is one integer column pointing at role, person_group, audience, person or event depending on selector_kind — the same polymorphism, the same four mandatory mitigations and the same nightly orphan scan that access_grant.scope_id already accepted (D-011, carried over by D-101). Drawing it as five real edges would be the lie; drawing it as no edges at all would hide the fan. The registry is what resolves the ambiguity, and it is a real edge: selector_type says whether the code takes an argument, whether the argument-less form binds to the item being checked, and what type the argument is — the parser reads its reserved words from that table, the editor builds its dropdown from it, and the save path checks arity against it (D-101). It is seeded, every row is_system, and organization-read-only: "the language becomes data" has never meant the language is extensible at runtime, and a seeded code with no shipped evaluator arm is a deployment bug that surfaces as an empty set — which is why the registry holds no row waiting to be implemented.

    No leaf resolves to anything but people, and that is why there is no GRANTS(…). An operand resolves to a set of people, because a set of people is what a grantee is; a set of grants is a filter over the grant list, and "these twenty rows, now also for that office" is something an editor does while finding the rows to act on, not something a stored grantee could ever be evaluated against. The bulk operation stays an affordance over the list, and the registry refuses the kind rather than leaving it unimplemented (D-101).

    One row is one node or one leaf, never both. A node carries operator (+ union, * intersection, - difference) with left_id and right_id, which are not interchangeable because - is not commutative; a leaf carries selector_kind and, where the registry says so, selector_arg_id. parent_id lives on the child, so a node belongs to exactly one expression and a sharing table is refused — editing a shared node would silently widen every grant using it. audience_id is denormalized onto every row so the read path fetches one audience's rows in one indexed read and assembles the tree in memory; it never walks a parent chain (D-101).

    AUDIENCE(code) is the leaf that points back into this diagram (D-103): it names another saved audience by its code, which is why code exists and is optional, and why an unnamed audience is simply not composable. The AUDIENCE leaves are the reference edges — there is no audience_include table, so "does this cycle", "how deep", "which grants name this audience" and "may I end it" are all one indexed query over selector_kind = 'AUDIENCE' rows. One sentence of D-101 is false and stays struck: ~~a tree cannot cycle, so the only acyclicity guard left is the cheap parent-chain one~~ — true of one tree, false of a forest of trees pointing at each other, so the save-time reachability walk is back — inside the tree, and across audiences through every AUDIENCE(x) leaf — and D-105 deleted selector_depth_limit and left those two cycle walks as the only structural guard there is. It walks for cycles and nothing else: the tree is stored exactly as the writer wrote it, with no depth bound and no rebalancing, and the standing report of the widest and deepest audiences is a convention, not a guard (D-081). The protection that keeps the dangerous case out is that an audience named by a live grant may not be ended or deleted while that grant lives: under -, an emptied operand makes the answer wider.

    audience_member is deleted, and LIST with it (D-105). A hand-written set of people is now written where every other set is written — in the expression, as PERSON(a) + PERSON(b) — and what the table carried that the tree does not is written as lost, not as managed: no per-person dates (a person is in the audience or not; a June-to-August exception is a second grant with its own period, which is what D-099's shape is for), and no who added this person beyond who last saved the tree. The reason it was never merged into GROUP(x) survives the table unchanged: a group's members are the organization's record and are true with no grant pointing at them, while a name written into an expression is meaningless outside the expression it completes (D-098). Naming people inside a grant must not make them group members: (GROUP(kitchen) + LIST) - PERSON(a) becomes (GROUP(kitchen) + PERSON(honza)) - PERSON(a) — same meaning, one fewer kind of thing — and merging the two would still make the permission table the system's roster.

    PERSON(x) is drawn as the person argument edge, and it was the thirteenth seeded selector_type row added — with LIST deleted, it is one of the twelve that remain. It got there late and by an odd route: D-101's grammar and D-100's exemption table both wrote PERSON(y) from the start, the registry was written from the evaluator's arm list instead, and the two disagreed for a whole round without any check noticing (D-104). GUARDIANS(x) takes a person argument either way, so the storage was never the disputed part — selector_arg_id may hold a person id per D-011 — which is why this appendix drew the edge while the language was still being argued about. What the row adds over that storage fact is one fact of meaning: an expression may name a single human who is on nobody's roster — and since a hand-written set is a sum of these (D-105), the edge is load-bearing: every hand-named person in the system is now a selector_arg_id with deliberately no foreign key, so a merge or a redaction must repoint every leaf that names the absorbed person, and the nightly orphan scan is the backstop rather than the mechanism. PERSON, GUARDIANS, ROLE, GROUP and AUDIENCE are the five codes whose argument names a person, an office, a group or another audience. The fifth drawn edge, to event, belongs to the item-bound codes — ORGANIZERS, PLACED, CONFIRMED, ATTENDED, ON_WAITLIST — whose argument is optional exactly because the item being checked usually supplies it (D-102).

    See ../data-model/05-authorization.md §8 and ../domain/06-authorization-model.md §6.

    Note the two membership rows have the same type. They differ only in period and end reason — this person was a member twice, and was a child and then an adult throughout. The old diagram called them child and adult; that was the framing the ageless decision replaced (D-038).

    Where the first row came from is not drawn, and the answer moved twice this round. A 1990s roster row states a period of membership, and since D-093 one reviewed batch may turn that stated period into membership #1 itself: both ends dated, data_confidence low, the batch id on it, no fee_obligation and a balance that stays absent rather than zero, because the corpus carries no money in it (D-090). Two shapes remain forbidden, and they are the two the ban was ever really about: an open-ended imported membership, and one inferred from an attendance row. A closed period gates nothing in the present; an open one hands authority to whoever signs up under that name tomorrow. What the pipeline no longer produces at all is the second row of this diagram's previous version: the participation rows it owed beside every membership went with the unit hierarchy (D-097), so a people batch writes the membership and nothing else, and the group rows are written by somebody who knows the group exists (../domain/03-identity-and-legacy.md §7).

    Questions this shape supports, all of which fail against a design with person.is_member:

    • Was this person a member on 1998-06-01?
    • How many years of membership, excluding the gap?
    • Which groups was he in during 2003? — person_group_member answers it, because those rows are dated rather than derived from a rule that could change its mind.
    • Who held the office of treasurers in 2023? — the same shape of answer, one role_holder row, which is the reason F-12 was closed with the answer no.
    • Would that grant have reached him on that date? — holder row, expression and grant are all evaluated as of the same at, and none of the three may be stored as a materialized list (D-101).
    • How old were they when they joined the second time? — answered from person.birth_date, which the membership rows never copy.
    • Who are the returning members — more than one membership with a gap between?

    Every one of them is answered as of a date, and an as-of date must be applied to every join in the answer, not only to the first one — a period joined without it leaks the present into the past. That is what the [T] marking on the tables above exists to make visible.

    7. Table inventory¶

    One entry per entity: what it is, what it references, how many may exist, and whether it is temporal. ⇒ marks a polymorphic reference with no foreign key. Entries that exist only to join two other entities say so. An entity that no longer exists keeps its row, struck, in the block a reader would have looked for it in, with the decision that deleted it — and its Points at and How many cells are empty, because there is nothing left to point at and no rule left to count.

    Reference vocabularies — reason_code, grant_scope_type, selector_type, identifier_scheme, permission. Each is named by a value held elsewhere rather than pointing at anything, and each exists so that a vocabulary is data the organization can see rather than a list inside the application. Two of this list's former members are gone: access_level (D-099) and org_unit_type (D-097), and selector_type arrived in the same round, which is the whole of the change here. attribute_definition is the same kind of thing in spirit and a different shape in fact — it has a curation lifecycle, a child table, and rows pointing back at it — so it is inventoried above rather than here.

    event carries no [T] — it has no valid_from / valid_to, because an event is a dated occasion rather than a period-tracked record. Its lifecycle is starts_at / ends_at / cancelled_at, and it has no status column at all (D-064). event_registration likewise stores no period: a person is attending, or they are not, and "unanswered" is the absence of a row (D-059).

    Removed since the first draft, listed so the inventory stays honest: requirement_code and membership_request_requirement (nothing gates a request — D-044); unit_membership (renamed unit_participation by D-041 — and deleted with it by D-097, so the rename was itself undone); every background-check structure (D-043); every medical structure, event_medical_note included, because personal data is one class of data and no table of it is (D-083); the whole unit and position family, with scope_exposure (D-097, D-100); the level ladder and its per-scope requirements (D-099); the role's permission bundle and its assignment table (D-100); the group-inclusion edge (D-101); and audience_member with the LIST operand and its seed row (D-105), the only row the selector registry has ever lost, in its one round of existence. Recorded here too, because it is the kind of entry this list exists for: event.qr, a check-in capability that never had a row in this appendix or anywhere else — it entered a round as prose, was argued about by name, and left as prose (D-104).

    [T] = temporal, carries valid_from / valid_to. A no says it does not; where the reason for not is a decision about someone's data rather than the nature of the table, the row says so — which in this inventory is person_attribute, and nowhere else.

    8. Foreign key summary¶

    Columns with no FK, and why:

    Column Why no FK
    access_grant.scope_id Polymorphic by design. Validated by grant_scope_type + orphan checks. It is absent exactly when the scope type is unit, and that absence is the schema-level form of "the unit is a scope, not a row" (D-097).
    audience_operand.selector_arg_id The second one, and newer: one integer pointing at a role, a person_group, an audience, a person or an event depending on selector_kind, resolved by selector_type.argument_type and caught by the same nightly orphan scan. D-101 carried D-011's trade-off across deliberately, mitigations included — the registry is the only thing that says which table an id belongs to, so an unmapped kind is the empty set, not an error.
    access_log.scope_id Same shape as the grant's; absent for a check at the unit.
    access_log.authorization_ref_id Points at one of two tables, access_grant or guardianship_permission. It named role_assignment as a third until D-100 deleted that table; a historical row whose channel reads role keeps the word and loses the reference, which is the honest state of a value whose table is gone.
    access_log.entity_id Polymorphic target of the audited action.
    field_conflict.entity_id Polymorphic; recorded alongside entity_table.
    audit_log.record_id Polymorphic; recorded alongside table_name.

    access_grant.scope_id is no longer the only reference-less key, and this appendix said it was for nine rounds. That sentence is worth keeping where it can be found, because the class is what matters and not the count: an id with no constraint behind it needs a registry that says which table it belongs to, a save-path check against that registry, an orphan scan the scheduler owns, and an explicit rule that failure resolves to the empty set. Two columns now carry that debt and both carry the same four mitigations. ../data-model/00-conventions.md §9 still calls access_grant.scope_id "the one reference-less key"; the events module is where the newer row is written, and that page has not caught up.

    access_grant has no grantee column — that is the one mutual-exclusion case rather than a missing-FK case: exactly one of person_id / audience_id is set, never both, never neither. Both columns are nullable, so nothing but the rule says whom a grant means; a grant naming neither is meaningless and one naming both is ambiguous about whom in the audience it speaks for. audience_operand carries the same shape of rule one table down — operator with left_id/right_id, or selector_kind with selector_arg_id where the registry says the code takes an argument — and for the same reason: a row satisfying neither is a node in no tree, and an expression containing one resolves to nobody.

    Every other column ending in _id has a real foreign key with ON DELETE RESTRICT, with one exception: event_organizer.event_id is the single ON DELETE CASCADE in the design — an appointment is nothing once the occasion it appointed somebody to is gone, and the guards in ../data-model/08-events.md §8 are what make that delete safe to allow at all. Everything else that merely looks like a child restricts: a registration, an answer, a member row, a holder row, a grant. The general rule is still ../data-model/00-conventions.md §9 — nothing cascades in front of a 40-year trail — and this row is the exception that page does not yet list.
