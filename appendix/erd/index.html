    Appendix — Entity Relationship Diagrams¶

    This appendix describes relationships — what points at what, how many, and whether the link is temporal. Field-level definitions live in the data-model documents, each in the one that owns the entity, and are deliberately not repeated here.

    The schema these diagrams draw is governed by ../data-model/00-conventions.md. The appendix is split by subject area so each part stays readable; the areas connect through person, which appears in all of them.

    Notation: → is a foreign key pointing at the referenced table. ⇒ is a polymorphic reference (no database-level foreign key). Temporal tables are marked [T].

    Section numbers are shared across the three parts and never renumbered, because other pages cite them by number and their anchors are built from them: erd.md holds §1–§4, the diagrams of the people — identity and attributes, the unit's groups and offices, membership, guardianship; erd-a-authorization.md holds §5–§5b, the whole authorization answer, its tables and the audience expression tree; erd-b-inventory.md holds §6–§8, the temporal pattern, the table inventory and the foreign key summary.

    Key point: everything hangs off person, and person itself holds only identity. No status, no role, no membership — everything else the organization records about the human is the descriptive layer drawn next. See ../data-model/01-identity.md.

    1a. Personal attributes — everything that is not a name, a gender or an age¶

    erDiagram
    ATTRIBUTE_DEFINITION {

        string value_unit

        boolean allow_multiple
        string status
        string proposed_by
        datetime proposed_at
        datetime retired_at
    }
    ATTRIBUTE_OPTION {
        string definition_code FK
        string code
        string label
        integer sort_order
        string status
    }
    PERSON_ATTRIBUTE {
        uuid person_id FK
        string attribute_definition_code FK
        string value_option_code FK
        string value
        string recorded_note
        string source
        datetime created_at
    }
    PERSON ||--o{ PERSON_ATTRIBUTE : has
    ATTRIBUTE_DEFINITION ||--o{ ATTRIBUTE_OPTION : offers
    ATTRIBUTE_DEFINITION ||--o{ PERSON_ATTRIBUTE : defines
    PERSON_ATTRIBUTE }o--o| ATTRIBUTE_OPTION : selects

    Key point: these three tables are the whole of what the system knows about a person beyond name, gender and age. There is no health table beside them and no privileged corner inside them: personal data is one class of data, graded by what a grant exposes rather than by which table it reads (D-083), and what the organization collects is named by a vocabulary the organization maintains itself (D-084). Reading is person.view, writing is person.edit, and only the vocabulary needs a code of its own (attribute.define). Fields and rules: ../data-model/09-attributes.md.

    None of the three is [T], and the no beside them in §7 is a decision, not an omission. A person_attribute row is the current belief, overwritten in place, and audit_log holds the sequence of beliefs, values included for as long as the payload window lasts — 24 months, after which the row is reduced and the values are gone (D-088) — which is why the trail is guarded as person data is (the permission catalog §8). This corpus gives periods to things that are true over an interval — a membership, an address, an office held, a guardian's authority — and a descriptive value is not one of those: it is a statement made now about whatever it is about, with a timestamp on the assertion. A valid_from here would ask a volunteer when an allergy began, which is a question the organization is not competent to record and has no rule that could use (D-085). The cost is named rather than left out: the history of a value lives in the one control D-081 calls the corpus's weakest, and §7 lists it as the accepted risk. It is also a deliberate departure from guardianship two sections below, which keeps its current value and its history in business tables — because authority is asked "what was it on that date?" as a routine part of answering whether an act was permitted, and an allergy list is not.

    The two vocabulary tables are non-temporal for a smaller reason of their own: a code leaves service by status, not by a period, so a value recorded against a retired option keeps meaning what it meant on the day it was chosen. Retiring therefore never touches a fact — only redacting a person erases one (../domain/08-person-data.md).

    2. Organization¶

    There is no organization-structure diagram, because there is no organization structure. There is one unit, it is the organization, and it is a scope and not a row: grant_scope_type carries a code unit with is_item_scoped = false, and a grant written at it has no scope_id (D-097). What this section draws is the one set-shaped thing the module holds: the group — a set of people, not a body — beside the roster that belongs to it.

    erDiagram
    PERSON_GROUP {
        uuid id PK
        uuid public_id
        string name
        string description
        date valid_from
        date valid_to
    }
    PERSON_GROUP_MEMBER {
        uuid group_id FK
        uuid person_id FK
        date valid_from
        date valid_to
        uuid added_by FK
        string note
    }
    PERSON ||--o{ PERSON_GROUP_MEMBER : "is in"
    PERSON_GROUP ||--o{ PERSON_GROUP_MEMBER : has

    Key point: a group is a named set of people with a lifetime, and that is the whole of it — no parent, no type, no code, no path, no nesting rule, no rename history, no split or merger edge, no leadership, no roles, no fee (D-098). The member row is dated, so the roster answers "who was in schuzka2026-1 on 14 March 2026" from its own rows rather than from the audit trail, whose payloads expire after 24 months (D-088). No two rows for one person and one group overlap, counted over all rows and half-open, so a person who left in 2020 and came back in 2024 is two rows and never one row edited in place.

    Membership of a group confers nothing. A set is not a grant; a group member is reached only because some grant's expression says GROUP(x) (D-005). The group is an item in grant_scope_type, so a grant may be written on one — that edge is in §5a, not here, because access_grant owns it and not this module. The box is deliberately alone beside its roster: name is unique across role and person_group together, but no constraint spans two tables, so that is a write-path rule and not a drawn edge (D-101).

    There is no unit table in any diagram in this appendix. The unit appears once, as the unit row of grant_scope_type (§5a) — a lookup row naming a scope, not a body, and there is nothing nested under it (D-097). What a reader might expect a unit to do is done by these instead: belonging to the unit is membership (§3), belonging to a set of people is person_group_member (above), an elected leader is a role_holder row, and do not place a child where nobody is responsible is person_group.member.manage held by a named adult, because nothing on a group says who it is for (D-095, D-100, D-098).

    See ../data-model/02-organization.md and ../domain/04-organization-structure.md; the scope itself is ../domain/06-authorization-model.md §2.

    3. Membership¶

    erDiagram
    MEMBERSHIP_TYPE {
        string code PK
        integer duration_months
        integer expiry_month
        integer expiry_day
        integer renewal_grace_days
    }
    MEMBERSHIP {
        uuid person_id FK
        string membership_type_id FK
        string status
        datetime valid_from
        datetime valid_to
        uuid renewed_from_membership_id FK
        decimal outstanding_balance
    }
    MEMBERSHIP_REQUEST {
        uuid person_id FK
        uuid submitted_by_person_id FK
        string status
        uuid membership_id FK
        uuid previous_membership_id FK
    }
    PERSON ||--o{ MEMBERSHIP : has
    MEMBERSHIP_TYPE ||--o{ MEMBERSHIP : defines
    MEMBERSHIP ||--o{ MEMBERSHIP : renews
    PERSON ||--o{ MEMBERSHIP_REQUEST : subject
    PERSON ||--o{ MEMBERSHIP_REQUEST : submits
    MEMBERSHIP_REQUEST }o--o| MEMBERSHIP : produces
    MEMBERSHIP ||--o{ MEMBERSHIP_REQUEST : precedes

    Four points that matter:

    • membership_request has two person references: person_id (the child, who would become a member) and submitted_by_person_id (the parent, who applied). Collapsing them makes the audit trail false.
    • A request asks for membership of the unit and names no body. No edge leaves this diagram for a group: which group a new member lands in is a write on the group — one person_group_member row, §2 — and not a preference on the application (D-097, D-098). Where an applicant would have said which group they had in mind, the row has the free-text notes it already carries.
    • Belonging lives in two shapes, and neither is a membership. person_group_member (§2) is a group's dated roster and is keyed on person, never on membership: an imported roster row or a 1998 camper has no membership row to point at, and inferring an open-ended one would sweep that person into MEMBERS today (D-098). A membership is membership of the unit, and it owes no second row to anything. Field rules: ../data-model/03-membership.md.
    • membership_type exists, with exactly one row, kept as a table so the vocabulary can grow, and it carries fee and renewal parameters. Why the row exists at all: membership is ageless (D-038), and age is read from person.birth_date where it matters — which is guardianship, entered by the shape of a request — so age is nobody's eligibility check and a membership type never was one.

    PERSON ||--o{ GUARDIANSHIP : dependent
    GUARDIANSHIP ||--o{ GUARDIANSHIP_PERMISSION : records
    PERSON ||--o{ GUARDIANSHIP_PERMISSION : changes

    Key point: guardianship is a general graph — one guardian → many dependents, many guardians → one dependent, and a person may be both. Authority is per guardianship row, and since D-074 that row carries one value — none, view or write — so a parent may write one child's records and only read another's. See ../data-model/04-relationships.md.
