    Data Model — Membership¶

    membership_type, membership, and membership_request.

    Belonging to the organization is a membership; belonging to a group is person_group_member, specified in the groups module. Nothing is in between: there is no per-unit participation row, because the unit is a scope and not a table (D-097). §5 is the pointer left where that table used to be specified, and where the write obligation it carried now sits on groups.

    Domain rationale: ../domain/05-membership-lifecycle.md.

    1. membership_type — one row, kept as a table¶

    Fields

    Field Kind Notes
    code text, required 'member' — and nothing else, for now.
    name text, required
    description text, optional
    duration_months integer, required, defaults to 12 12: the fee is yearly. Kept as a column rather than a constant so a type with a different term could be added as a row, with no migration.
    expiry_month, expiry_day integers, required, both defaulting to 1 When the fee expires (D-047): 1 January. The organizational year runs with the calendar, so "a member this year" means what a reader expects, and the sweep, the campaign and the reports all land on a boundary nobody has to look up. These are columns, not a constant in a scheduled job, for the reason given for the renewal window below: the date is a parameter the organization may move, and moving it must not require a code change. Every lapse date, the yearly sweep and the renewal worklist derive from these two values.
    renewal_grace_days integer, required, defaults to 60 The renewal window after valid_to, during which a payment restores the membership without re-applying and backdates the new period to the expiry date. Dates, not a status: the person is expired throughout (D-040). 60 days (D-048). Read it from here; never hardcode 60 in a job or a front end (D-048). The requirement attached to that answer was precisely that the value stays tunable.
    is_self_registerable boolean, required, defaults to true
    requires_approval boolean, required, defaults to true
    sort_order integer rank, required, defaults to 0
    valid_from, valid_to period (from/to, open-ended allowed); both ends optional
    created_at timestamp, audit time

    Rules

    • code is unique over all rows.
    • expiry_month is between 1 and 12; expiry_day is between 1 and 31.
    • Where both ends of the period are set, valid_to is later than valid_from. Either end may be absent, and no comparison is attempted when one is.

    Why this table still exists with one row¶

    There is exactly one membership (D-037). Everyone who is a member holds membership_type = 'member', the fee is flat and per person, and being a counselor or a leader is a role, never a type (D-100).

    The table survives rather than collapsing into a constant for two reasons:

    1. Consistency with the design's own principle. Vocabularies are rows, not enums — the same argument that keeps the seeded registries as tables (grant_scope_type, selector_type). A second kind of membership (a supporting or honorary one) would then be a data change.
    2. A place for the organizational calendar to live. The term, the expiry date and the renewal window are genuinely type-dependent parameters even when there is one type — and they are the parameters most likely to be tuned. Putting them in a row rather than in code is what makes "it should not be hard to modify" (D-048) true by construction rather than by discipline.

    The cost is honest and small: an FK that currently always holds one value. Recorded here rather than hidden.

    What is deliberately not on this table¶

    The type says nothing about who may join, and nothing about what they pay. No age floor, ceiling, or automatic age-out: membership is ageless and age is a fact about the person (D-038). No requirement a request can be held up by: nothing gates a request but identity and payment (D-044), and the system records no background checks at all (D-043). No flag saying whether two memberships may overlap — the person-scoped overlap constraint of §3 decides that, and decides it the same way for every type. No fee reference: the fee is flat and per person, so a schedule attaches to the obligation instead (07-finance.md §2). And the grace is a window read from renewal_grace_days, never a status a member enters (D-040).

    Why: a vocabulary row that also carries eligibility rules is a second place the admission policy can drift out of agreement with itself — D-037. The names of the columns that carried those rules are indexed in removed-concepts.md.

    2. membership_request¶

    Fields

    Field Kind Notes
    id surrogate id Internal only.
    public_id uuid, required, generated The identifier used outside the system; unique.
    person_id reference to person, required The subject: the person who would become a member. For a minor's application this is the child, not the parent.
    submitted_by_person_id reference to person, optional Who actually submitted it. Equals person_id for self-application; differs when a guardian (or staff) applies on behalf. This is the act-on-behalf record.
    requested_membership_type_id reference to membership_type, required
    status text, required, defaults to draft One of draft, submitted, under_review, approved, rejected, withdrawn, expired.
    submitted_at timestamp, optional
    decided_at timestamp, optional
    decided_by reference to person, optional
    rejection_reason text, optional Free text, written by whoever rejects (D-128)
    rejection_note text, optional
    membership_id reference to membership, optional Set on approval. The reference is added only once membership exists (§3): this is the design's circular pair, broken with an optional column and not a deferred constraint, which is what 00 §9 requires (D-129).
    previous_membership_id reference to membership, optional Links a renewal or re-application to the prior membership. This is how a returning member's chain is expressed.
    expires_at timestamp, optional An unreviewed request eventually goes stale. Needed so the review queue does not accumulate abandoned drafts forever.
    notes text, optional
    source text, optional self, guardian, staff or import.
    created_at, created_by, updated_at, updated_by timestamp, audit time; reference to person The standard audit columns.

    Rules

    • A request in approved or rejected has both decided_at and decided_by. There is no decision without a decider and a time.
    • Any request that is not draft has a submitted_at.
    • An approved request points at a membership. The one allowance is a request decided at a time still in the future, which is how the request and the membership are inserted in two steps inside one transaction; the link is not optional once that transaction is over.
    • At most one open request per person per membership type. Open means draft, submitted or under_review. Decided requests — approved, rejected, withdrawn, expired — are outside the rule, which is what lets a person apply again after being turned down.

    Indexes

    • On person_id with submitted_at descending: one person's applications, newest first.
    • A partial index over the review queue only — rows in submitted or under_review, which is the whole queue and nothing else.
    • On submitted_by_person_id, covering only the rows where that optional column is actually set.

    person_id vs submitted_by_person_id is the most important pair in this table. The subject is the child; the submitter is the parent. Collapsing them into one column — which is what most systems do — makes it impossible to answer "who applied for this child?" and falsely attributes the parent's action to the child. See ../domain/02-actors.md.

    Why requests are a separate table from memberships. A rejected request produces no membership and must not pollute member listings; a person may submit several over time; and review data (who decided, why) has no meaning on a membership. See ../domain/05-membership-lifecycle.md.

    A request asks for membership of the organization, and names no body beneath it (D-098) — because there is no body beneath it to name (D-097). The want behind a which group? field is real: a reviewer would like to know where the applicant expects to turn up. It is served by the free-text notes the row already has, which is what such a field always was — a sentence addressed to whoever reads the request, carrying no authority. Placing the person is a separate act and a separate row — one person_group_member row, written by a person holding person_group.member.manage — and an approved request with no group beside it is a complete, ordinary outcome. Which group a new member lands in is a write on the group, not a preference on the request.

    A rejection requires a reason (ck_request_rejection_reason is the rule's name): no rejected request may be written without one. Two columns of the same row, so a migration can state it directly as a check on the row — and it belongs there rather than only in the model layer, because the two paths that most need catching, an import and a hand-corrected row, never reach a model-layer guard. "Why was this application turned down?" is asked months later, sometimes by the family. A rejection with no recorded reason is an answerable question made unanswerable.

    previous_membership_id is what makes the returning-member chain explicit rather than inferred from date arithmetic.

    3. membership¶

    Fields

    Field Kind Notes
    id surrogate id Internal only.
    public_id uuid, required, generated The identifier used outside the system; unique.
    person_id reference to person, required
    membership_type_id reference to membership_type, required
    status text, required One of pending_payment, active, suspended, lapsed, terminated, completed. No default — the state is always chosen deliberately.
    valid_from date, required
    valid_to date, optional NULL = open / current. Never NULL on an imported row — both ends are what makes an imported membership safe, and check 1 of 06-audit-and-import.md §5 counts the rows that broke it (D-093).
    joined_via_request_id reference to membership_request, optional
    renewed_from_membership_id self-reference to membership (the previous one), optional Forms the renewal chain. See domain/05 §6.
    outstanding_balance money amount, optional Denormalised from fee_obligation/payment. 07-finance.md §3 recommends dropping this column in favour of v_fee_obligation_balance — a wrong balance suspends the wrong child. Kept here only until that decision is taken. NULL on every imported row, and since D-093 put memberships back into the import that is load-bearing rather than incidental: the export carries no payment data, and a zero would be a claim — settled — that the export does not support. There is no fee_obligation underneath these rows either, which is what makes the NULL unambiguous rather than merely uncomputed (07-finance.md §2, D-090).
    termination_reason text, optional Free text, written by whoever terminates (D-128)
    termination_note text, optional
    ended_by reference to person, optional
    ended_at timestamp, optional
    data_confidence text, required, defaults to high One of high, medium, low.
    import_batch_id reference to the import batch, optional Set on imported rows.
    notes text, optional
    created_at, created_by, updated_at, updated_by timestamp, audit time; reference to person The standard audit columns.

    Rules

    • Where both ends of the period are set, valid_to is later than valid_from.
    • A terminated membership has both a termination_reason and an ended_at.
    • A membership may not be renewed from itself: renewed_from_membership_id never points at its own row.
    • THE critical rule — one person, one membership, full stop. Two rows for the same person may not cover the same date while either of them is pending_payment, active or suspended. Periods are half-open, so one ending on a day and another beginning on that day do not collide. Statuses outside those three are outside the rule entirely, and the rule reaches every person regardless of membership type — the type is not part of it, and that omission is deliberate, as the next section explains.

    Indexes

    • ix_membership_current — per person, over rows that are open and active. The membership gate reads through this, and it is the index a far-future sentinel date would defeat — see Why valid_to IS NULL and not a sentinel below.
    • On valid_to over active rows that have one. This drives the renewal worklist: who expires soon, who is in their renewal window.
    • On (status, valid_to) over active and pending_payment rows — the states anyone is actually queried in.
    • On person_id with valid_from descending, and a period index per person: one person's membership history, and the range scan the overlap rule and every point-in-time question use.

    One person, one open membership¶

    The uniqueness rule is scoped to the person, not to the type (D-037): with one membership type, the case an honorary member who is also an active member cannot arise, so "one person, one open membership" is an enforceable invariant rather than a convention. It is conditional uniqueness — one open row per person — which is the shape 00-conventions.md §6a says a migration must emit by hand: a unique constraint over all rows is a different rule and the wrong one, because it forbids the second closed membership that the person's history requires.

    This is what makes is_current_member() a question about one row, one status, one date rather than one that has to reconcile concurrent memberships. It is worth saying who reads it: MEMBERS is evaluated live on the checked date, and it evaluates to exactly this predicate (§6, D-100). The constraint is what makes that evaluation cheap and unambiguous.

    renewed_from_membership_id and the renewal window¶

    When a person pays inside the renewal window (D-040), the new membership's valid_from is set to the previous row's valid_to, not to the payment date. Two consequences worth stating:

    • The history shows continuous coverage — no gap, no spurious "returning member".
    • The person is nevertheless expired during the window (D-040). The two facts are compatible because the window is a date range, not a status: they were not a member while it was open, and the record of that period is filled in retrospectively once they pay. Nothing needs backdating in the audit sense, because the new row's as-of start is the expiry date and its audit time is the payment date — the two-times distinction in 00-conventions.md.

    A payment after the window opens the new membership at the payment date, and the gap is real.

    The exclusion constraint and status transitions¶

    The overlap rule covers only pending_payment, active, suspended. A terminated/lapsed/completed row is excluded, so a new membership can be created with a valid_from inside an old one's period without violating the constraint. This is deliberate — a returning member's new membership may legitimately overlap the tail of a lapsed one if the dates were entered imprecisely. Historical imports rely on this.

    Consequence: the constraint does not prevent two active memberships with overlapping periods if one was inserted while in another status and then transitioned. A status update re-evaluates the constraint (PostgreSQL does check exclusion constraints on UPDATE), so this is safe — but the transition from lapsed back to active can therefore fail with a constraint violation. That is correct behaviour: it means the person has two overlapping claims to membership and someone must resolve it. Handle it as a business error, not a crash.

    Which layer carries all of that: the migration. A status transition that re-checks the overlap is only a violation if the constraint is in the database, and no ORM emits an exclusion over a period assembled from valid_from and valid_to scoped to three statuses — the migration writes it, as 00-conventions.md §6a requires. The same check performed in the model layer returns a friendlier message a moment earlier and guarantees nothing: a batch that imports the legacy people export writes memberships by the thousand (D-090, D-093), and a hand-corrected row never passes through the model layer either. Both meet the constraint in the database; neither would ever meet a model-layer check.

    Why valid_to IS NULL and not a sentinel¶

    Repeated from the conventions because it is the mistake most likely to be made here. A '9999-12-31' sentinel breaks IS NULL checks, makes daterange spans enormous, and defeats the ix_membership_current partial index. Use NULL.

    renewed_from_membership_id¶

    Renewal opens a new row (Shape A in ../domain/05-membership-lifecycle.md). The self-reference makes the chain explicit:

    membership 501  member  1990-09-01 → 1991-06-30   completed
     ↑ renewed_from
membership 502  member  1991-09-01 → 1992-06-30   completed
     ↑ renewed_from
membership 503  member  1992-09-01 → 1993-06-30   completed
    (The type is member on every row — there is only one type, and the person's age is not part of it: §1, D-037, D-038.)

    "Why does this person have 15 membership rows?" is then answerable by following the chain rather than by reasoning about dates. And a gap — a missing link — is visible as data.

    Current-membership queries¶

    Five questions the membership table has to answer, each with the exact rule that decides it. The wording of each is load-bearing; the differences between them are the design.

    • Is this person a member right now? is_current_member(person) — true when they have a membership whose status is active and whose period covers today: valid_from on or before today, valid_to absent or after today. No grace coalescing: a lapsed membership is lapsed, and the renewal window (domain/05 §6) is a date range for rejoining, not a state in which the person is a member. This predicate is what the MEMBERS selector evaluates on the checked date (§6) — the resolver asks the expression instead of asking this of a person directly, which changes the predicate's callers and not its meaning.
    • Was this person a member on a given past date? was_member_on(person, date) — true when a membership of theirs covers that date, on the same half-open terms, and its status is anything except pending_payment. Note the asymmetry with the question above: now demands active, then admits every terminal status, because how a membership ended does not change that it existed.
    • When does the organizational year containing a date expire? membership_expiry_date(as_of) — expiry_month and expiry_day read off the member row, applied to the year of as_of. Always derived from those two columns and never from a constant (D-047).
    • May this person renew without re-applying? in_renewal_window(person, as_of) — true when they have a membership of theirs that has ended (valid_to set) with valid_to on or before as_of, and valid_to plus that type's renewal_grace_days still after as_of; in other words the window is [expiry, expiry + grace), half-open like every other period here. No status is consulted — this is arithmetic on dates alone. D-040: expired, but inside the window. This is the distinction a grace_period_days membership status would have blurred: they are not a member, and they may rejoin cheaply. 60 days, read from the row (D-048). Not a member during the window: this answers "may they rejoin cheaply?", never "do they have access?".
    • How long has this person been a member? membership_years(person) — the sum of the lengths of their memberships, with today standing in for an open valid_to and any pending_payment row left out, expressed in years of 365.25 days.

    membership_years sums the periods rather than subtracting the first join date from today. The difference is the 14-year gap in the returning-member case, and getting it wrong mislabels a returning member as having 36 years of service.

    Age is never asked of a membership. The question is this person currently a child or an adult? has no answer on this table, because membership is ageless (D-038); it is a fact about the person, and the views ask it there:

    Is this person a minor? is_minor(person, as_of) — true when person.birth_date is recorded and as_of falls before their eighteenth birthday. A person with no recorded birth date is not a minor by this test; nothing guesses one. A fact about the person, never about their membership.

    This matters for guardianship and safeguarding, which are where age legitimately bears — not for whether someone may be a member.

    4. What a membership request must contain¶

    Identity and the fee — nothing to verify (D-044). A request is a person, a submitted timestamp, a reviewer, a decision and a payment. The membership_request table in §2 is complete as it stands, and no checklist table sits beside it.

    Guardian consent is not a membership requirement. It belongs to the guardianship layer, where it is a relationship fact rather than an item on a form — 04-relationships.md.

    If a requirement ever appears — a form, an interview, a document — it arrives as a table added deliberately, with the requirement that made it necessary recorded as a decision.

    Why: the general-purpose mechanism was deleted rather than kept as empty infrastructure, so a future requirement is a decision rather than a reuse of a shelf that is no longer there — D-044.

    5. unit_participation — deleted by D-097¶

    Deleted by D-097. There is one unit, it is the organization, and it is a scope rather than a row — so there is no body below it to belong to, and no table to record belonging in. Everything the table carried goes with it: the sub-unit rosters, the root participation row every membership owed, the transfers between units, the display label and primary flag those rows carried, the vocabulary of reasons a row was opened or closed, and the confidence value an import stamped on them. removed-concepts.md indexes their names.

    What the reasoning was, and what survives the table. Belonging below the organization is participation, not a species of membership (D-041). An earlier name for that table had asserted otherwise, and the distinction settled the questions the name raised — which membership was which, and whether a fee was owed twice. The distinction is alive one level down: membership of a group confers nothing and owes nothing, because participation is not authority and being stored in a tidier table does not quietly promote it (D-098, restating D-005). The key says the same thing: person_group_member is keyed on person_id, never membership_id, because a person may belong somewhere with no membership behind them, and a row about 1998 must not become unrepresentable because the record of 1998 status is thin or absent.

    Where each question goes now (D-098) — two shapes, and no depth parameter on either:

    Question Read
    Who is in the organization on date D? membership — one query over the period and status of §3
    Who is in group G on date D? person_group_member — a point-in-time read over the dated rows, 02-organization.md §1

    What the pair used to buy was one query shape for both rows of that table, and that is what is given up. What is given back is the redundancy: two tables kept in step only by an obligation on every writer, and a report watching for the writers who forgot.

    The write obligation is retired, and so is the check that watched it¶

    No write owes a second row to anything (D-097). The rule this section carried was that no write may change a membership's period, or open or close one, without making the matching change to that person's root-unit participation row in the same transaction — two rows holding one fact — and integrity check 1b was the report that found whoever skipped it. Nothing enforces either of them now, because there is nothing left to enforce: the second row is deleted, so this is not a rule running without a guard but a redundancy removed, and membership is the single record and cannot disagree with a copy of itself. Obligation and check retire together rather than being restated somewhere else, which is what D-081 asks for: said plainly, not left as a silence.

    Why this is written down instead of quietly dropped: the pairing was reversed twice inside three rounds — a correction, the reversal of that correction, then the deletion of the arm both readings were arguing about — and what every one of them got right is the framing rather than the conclusion. The obligation was never about one batch: import, renewal, extension and hand-corrected row each owed the paired write exactly as much, and the answer moved twice only because nobody had read the input file (D-092, D-093). Read the input before saying what an import owes.

    A renewal opens a row that starts where the old one ended. The sweep sets the expiring row's valid_to to the expiry date, and a payment inside the window opens the new membership with valid_from set to exactly that date (§3, and ../domain/05-membership-lifecycle.md §6), so the record reads as continuous coverage while the person was expired throughout the window. The deleted root row bought its version of that look by being extended rather than closed and reopened (D-050); what was accepted along with it is worth stating once, because it is the same answer today — a roster answers who was in this body when, and a child who was there across a lapse has exactly one answer to that, while membership remains the authority on payment. With the second row gone, both answers come from membership alone.

    Moving between groups closes one row and opens another¶

    Moving a person from one group to another is two writes — closing one person_group_member row and opening another — never an edit of the group on the existing row (D-098). Close-and-open is what preserves "where was this child in 2003?"; an in-place update destroys it, and the whole temporal design exists to answer that question. Nothing about the person's membership, their fee, or their standing as a member changes, because moving was never a membership event.

    Who enforces it now. The close-and-open pair is the write path's, behind person_group.member.manage, audited and naming who wrote the row; the invariant underneath it — no two rows for one person and one group overlap, counted over all rows and not only the open ones, half-open so a row ending on a day and one beginning that day do not collide — is shape 1, which a hand-written migration emits and the ORM will not. A person who left in 2020 and came back in 2024 is therefore two rows, never one row edited in place: the edit destroys the answer to "were they in the group in 2019?". The groups module owns both, and this document does not re-specify them — 02-organization.md §1–§2 and ../domain/04-organization-structure.md.

    What was given up, named as a loss. A group that splits is an old group that ended and two that began, with no edge between them unless somebody writes one: org_unit_relationship's split_from / merged_into / successor_of are deleted, so restructuring has stopped being a recorded event (D-097's third loss). The bulk reorganisation transfer goes with it — close and open across every member of a body, as one named procedure with a dry run, carrying a reason saying why. There is no reorganisation to perform in one statement now, and the lineage it recorded is a thing a person would have to write down on purpose. The roster's own columns went too: a vocabulary of reasons for opening and closing a row, a primary-group flag saying which of a person's groups to show first, a display label, and an import-confidence value with nothing left to import into — the corpus names no groups either, so every group member row is typed by a person, which is also the only way one can be true (D-092). D-098 gives up the lot, on the instruction that a group needs no special features; their names are indexed in removed-concepts.md.

    6. Membership and the authorization system¶

    The resolver does not ask whether you are a member. The grant does (D-100). This is the single largest coupling between these two modules, so it is stated in full rather than in a footnote. MEMBERS is a selector operand, evaluated live on the checked date, and the question must this person be a current member to hold this? is answered by whether the expression says so:

    What the writer means What the writer writes
    This office is for members only MEMBERS * ROLE(x)
    This office is for whoever holds it, member or not ROLE(x)
    …and this one named person too MEMBERS * ROLE(x) + PERSON(y)

    Who enforces the rule: whoever writes the grant, by putting MEMBERS in the expression or leaving it out — and the expression is a row that can be read. A waiver for one person is + PERSON(y) in the same grant, which PERSON being a seeded selector makes ordinary (data-model/05 §8); where the exemption should outlive the office and carry its own dates, it is a second grant aimed at the person instead (D-105).

    Guardianship and ownership were never gated. A parent's authority comes from a legal relationship, so an unpaid fee must not stop a parent acting for their child; and a lapse must not lock a person out of the very screen they renew on. Both are channels, and a channel is not something a grant gates. The third case — appointed counselors and local leaders the organization needs present regardless of their own fee status — is the only one that was ever a waiver of a gate, and it is now simply the second row of that table: write the office without MEMBERS.

    The posture is opt-in, so the new failure is named rather than buried. The gate used to be default-on, so forgetting it was impossible; now a grant written ROLE(TREASURERS) with no MEMBERS authorizes a lapsed member, silently, forever. Three controls, none of which is the resolver:

    • A standing report of live grants naming a ROLE(...) operand whose expression does not contain MEMBERS — check 1 of §7. An office held by a non-member is the case worth a human eye, and the report is narrow enough to actually be read.
    • Seeded grants and any grant template carry MEMBERS, so the path of least repetition is the safe path.
    • Import completeness. MEMBERS * COUNSELORS is only as correct as the counselor roster: the gate used to fall out of membership alone, so an import that misses 300 counselors silently un-gates them. It fails closed — nothing breaks, which is exactly why nobody notices — and the import reconciliation report of D-090 must count people marked as counselors in the corpus against role_holder rows written.

    What still costs, unchanged by the move:

    • A membership transition invalidates nothing, because nothing is stored to invalidate. A check resolves against the live rows and MEMBERS is evaluated on the checked date, so a lapse or a termination is visible the moment it is written; there is no answer kept anywhere that could go stale, and the yearly expiry sweep keeps every other thing it had to do (D-114, §11's invariant 19).

    Why this is spelled out instead of left unsaid: the coupling this page once demanded here was real, the cache policy written three rounds later left membership off its list, and membership.terminate is exactly the ⛔ action a concerned guardian waits for. An invariant with nowhere to be violated closes that class of miss better than a louder requirement — which is what D-114 records. - A lapse silently removes access — from exactly those grants whose expression names MEMBERS, and from none of the others. "Why can't I see this?" now has an answer that is a date and a line of grant text.

    The "leaver with access" report is two reports. D-071's posture transfers intact to role_holder: nothing forces a holder row to end, and the control is the report. Checks 1 and 2 of §7 are that control — one for grants that gate nothing, one for offices held by people who are not members.

    Dormant authority is a real hazard. A membership that lapses and is renewed a year later resurrects every still-open role_holder row the person accumulated in the interim, including ones a human had quietly decided not to reinstate — and where the grant behind that role was written without MEMBERS, it was not dormant at all in the meantime, it was live. Closing the holder row at the same time as the membership is the honest fix; the reports find the ones that were missed. A role holder row should not outlive the membership that justified it.

    A role is held at the unit and nowhere else. role_holder carries no scope columns, because D-097 left one scope; there is no body to hold an office of. The table, the ROLE(x) selector and the codes an office carries belong to 05-authorization.md §3 role and §4 role_holder.

    7. Integrity checks¶

    Invariants to verify. Six checks, numbered from 1. The retired numbers are listed after them, so that a citation of an old number — the decision log cites several — lands on an explanation rather than on a gap.

    • 1. Live grants that gate nothing. Counts live grants whose audience expression names a ROLE(...) operand and does not contain MEMBERS — D-100's standing report, restated here because this is the module whose data it reads. Enforced by no layer, and no layer can: whether an office is written with MEMBERS is a choice made in the grant text, so the controls are this report, plus seeded grants and any template carrying MEMBERS so the common path is the gated one (§6). A non-zero count is not a fault — it is the list of offices worth a human eye, and it is narrow enough to actually be read.
    • 2. Non-members holding an office. Counts open role_holder rows whose holder is_current_member() says is not a member (§3). Enforced by nothing, deliberately: D-071's posture transfers to role_holder, so no constraint and no sweep ends a holder row and this report is the control. Read it with check 1, which says whether that role's grants are gated: on a gated role this is dormant authority that springs back to life at the next renewal, and on an ungated one it is access that is live today (§6).
    • 3. Approved requests that never produced a membership. Counts requests that are approved, carry no membership_id, and were decided more than seven days ago. Non-zero is an approval that went nowhere. Enforced by the §2 requirement that an approved request points at a membership once the deciding transaction is over — a deferred reference rather than a suggestion, and one a migration can state on the row.
    • 4. Memberships expiring soon. Counts active memberships ending within the next 90 days — the renewal campaign worklist (domain/05 §6), not a fault. Run by whoever runs the campaign; nothing here guards it, because there is nothing to guard.
    • 5. Renewal chains with a broken link. Counts memberships whose renewed_from_membership_id names a row that does not exist. Non-zero means the chain is followed into nothing. Enforced by the ordinary foreign key on that column, which any migration emits; the check survives as the assertion that the key is there, which is the form 00-conventions.md §6a prescribes for a constraint this project's ORM does not generate on its own.
    • 6. Renewals inside the window whose new period does not start at the previous expiry date. Counts renewals whose valid_from differs from the previous membership's valid_to and begins less than 91 days after it. The renewal rule (D-040) backdates the new period, so a mismatch means either a genuine post-window rejoin or a bug. Enforced by nothing: both answers are legal data, so only a report separates them, and only a reader decides which one it is looking at.

    Checks 1 and 2 are read together, and neither alone is the control — one is a report about grant text and the other a report about people, and the risk only appears across both: an office held by somebody who is not a member is dormant authority when its grants say MEMBERS, and live access today when they do not (§6).

    Check 4 is operational (a worklist for the renewal campaign). The rest are data-quality checks for cases no constraint rejects at the write.

    Two checks this module deliberately does not hold. The one D-099 asks for — a live deny whose grantee, scope and code match no live allow, and so denies nothing — is a report over grants, not over memberships, and belongs to 05d-invariants-and-seed.md §11. The no-overlap invariant over person_group_member belongs to the groups module, 02-organization.md §6. Naming both here is to stop either being written twice and drifting.

    8. Seed data¶

    The organization starts with a single membership type — member, named and described in plain words, open for a person to register themselves for, and left to requires_approval at its default of true. The term and the calendar parameters on that row are §1's, not constants anywhere else.

    One row, and that is the whole vocabulary (D-037). The fee is flat and per person, so there is nothing to vary by type; being a counselor or a leader is a role, not a type (D-100); and membership is ageless, so there are no age limits to seed (D-038).

    Nothing else is seeded here. The counselors role that D-100 seeds — shipped is_system, so an editor refuses to delete it — is a row of the authorization module (05d-invariants-and-seed.md §12) and not of this one, and it is a set that confers nothing until a grant names it: no more than a membership type has ever conferred.

    All three are settled, and all three are §1's columns — 12 months, 1 January, 60 days (D-047, D-048). None is a placeholder: the term is what the yearly lapse sweep (07-finance.md §4) and the period a renewal opens both read, and a term of the wrong length produces a membership that ends on a date nobody chose. None of the four is a constant, so tuning any of them is an UPDATE, not a release — which is the whole difference between a settled value and a hard-coded one.

    The one rule about these four values: read them from the row. A scheduled job, a front end or a report that contains the literal 60 or 1 has quietly reverted a parameter to a constant, and the organization will discover it the first time it changes its mind.

    No requirement is seeded, because no requirement exists (D-044): consent of any kind lives in the guardianship layer where it is a relationship fact, background checks are not recorded at all (D-043), and a reference, a form or a photograph has never been a condition of joining.

    9. Open issues¶

    • Whether 60 days is the right renewal window for an organization whose renewal campaign is a handful of people. The mechanism is settled and the value is a column read from the row (§1, §8); only a year of real lapses answers the value.
    • Whether outstanding_balance should exist as a denormalised column or be computed (§3) — depends on the finance design in 07-finance.md.
    • Which offices are written without MEMBERS. The membership gate left the resolver for the grant text (§6, D-100), so somebody has to decide, per office, that a lapsed member may still hold it — and nothing in the model records who decided it or why, only whether the expression contains the word. The standing report of §7 check 1 is the control over the outcome, not over the choice. Assumption: this is left to whoever writes the grant, which is the honest reading of D-100 rather than a ruling in it.
    • Whether a group is ever allowed to state an age rule of its own. A group carries no eligibility and D-098 refuses it one, so nothing says children only about a group today; the answer is a report over person_group_member and is_minor(), which is a question about the data rather than a rule in the model. Left as a question for ../open-questions.md rather than answered here.

    Settled, and stated where the rule lives rather than here. Whether a person may hold several open memberships, when a membership activates, whether permissions follow membership state, the age questions, the grace period and the requirement mechanism are settled and stated — in §1, §3, §4 and §6. Whether the legacy import may create a membership is D-093 and 06a §3.1. Two of those answers have a consequence worth keeping in view, because both are easy to undo: the roster is keyed on a person and never on a membership, so belonging survives where no membership record survives (§5), and a renewal inside the window opens its row at the previous expiry date, which is what makes a lapse invisible in the coverage and still visible in the money (§3).
