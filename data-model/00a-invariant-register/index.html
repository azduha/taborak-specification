    Data Model — 00a. Who enforces each invariant¶

    One row for every rule this schema states, saying what carries it, what would notice a breach, and what a breach looks like. Written so that the answer to "is that rule guarded?" is one lookup instead of twenty pages.

    ← 00-conventions | 01-identity

    This page does not restate any rule. It links to the page that owns each one, because a restated rule is a second copy of it, and the defect this corpus keeps hitting is a copy that drifted — the story the catalog's §12 tells about a seeded table copied from an evaluator's arm list, and the reason D-127 diffs documents against their own registries rather than against a list. What is here is the three facts a rule's own page is allowed to leave implicit — which layer carries it, which report would see a breach, and what a breach looks like — and the register is where a blank in those two columns is visible instead of being a sentence on page 412 that nobody re-reads.

    The four shapes, and the layer each is assigned (D-130):

    Shape What it is The layer that carries it Why not another layer
    1 No two rows overlap in time A hand-written PostgreSQL exclusion constraint, emitted by a migration The ORM cannot generate one, and an application check is bypassed by the import, the bulk edit and the fix at 2am (00 §6's rule 3)
    2 Unique, but only among rows meeting a condition A partial unique index, emitted by a migration The unconditioned constraint is a different and usually wrong rule — it forbids the second closed row, which history requires
    3 The answer reads another table, a resolver, or a graph The write path, inside the transaction that writes No constraint spans two tables. The layer named in this register is always the write path; what varies is whether a report was named beneath it
    4 A value that may never change once set Nothing automatic. The rule, the referrer listing, and the review There is no offending row to catch — only a rewritten history — and 00 §10's rule against rewriting a historical row's meaning is the prose that stands behind it

    How to read the two right-hand columns. Backstop names the report that would list a breach, by the page and number where that report is written. none in bold is not an omission of this page and not a slur on the rule: it means the corpus names no such report anywhere, which is the finding. Five rows are in that state and all five are shape-3 rows, whose only enforcement is a line of code. The five are not one kind of blank, and the kinds are worth naming because they fail differently. Two are rulings: D-133 decided that a rule about an ended key gets no report, and D-143 decided the same about a delegation outliving the permission behind it — in both cases the absence was chosen, and said on the page that owns the rule rather than only here. One is a promise with an address: D-130's identifier row names the section the report will be added to, so that none is dated rather than permanent. Two are blanks this page is not allowed to fill by inventing a check nobody asked for. The count came down from eleven — seven after round 19, five after round 20 — and none of the six losses was a re-reading. Two pages were given the check sections they lacked (D-135). Two rows here turned out to describe a rule no page states at all, so they are gone rather than repaired (D-133, D-144) — which is the half of this page's history it should be embarrassed by. And one none was simply false in the other direction: the displayed-name row said no report existed while the report had been sitting in 01b §10 since the page that owns the check was written (D-142). That is the reason this column is worth the trouble it costs: a citation can be checked and a claim of absence cannot, so a blank is as much a claim about the corpus as a link is, and it can be wrong while looking humble. Breach is what the bad data looks like afterwards, because a shape-1 breach and a shape-2 breach both read as "two rows" and only one of them is a duplicate.

    Nine numbered checks, on three pages, are assertions about the code rather than reports over data — the six TIME-BOMB checks of 05d §11 (15, 16, 17, 18, 19 and 22), 02 §6 check 4, and 08a §10 checks 1 and 9. They are cited below as save-refusal, never as a report: they verify that a guard still exists, never that the data is clean. Filing one as a backstop would overstate coverage in exactly the direction that matters.

    1. No two rows overlap in time¶

    Four rules. All four are a hand-written exclusion constraint over a range built from valid_from and valid_to, half-open, so that a row ending 2010-06-30 and one starting 2010-06-30 do not collide.

    A report beneath a real constraint is a courtesy, not a control — the constraint cannot be breached quietly — so a none in this table or the next is only a finding where the layer is the write path.

    The rule Stated in Key it excludes on Rows it counts Backstop Breach
    A person is in a group once at a time 02 §2 (person_group_id, person_id) all rows, open and closed — there is no status to scope it by 02 §6 check 1 Two member rows for one person in one group, one of them a history row nobody can tell was ever superseded
    A person holds one membership at a time 03 §3 (person_id), predicate: either row is pending_payment, active or lapsed three statuses only 03 §7 Two live memberships, so MEMBERS counts the person twice
    A person holds an office once 05 §4 (person_id, role_id) all rows 05d §11 Two holder rows, so authority survives the row that was meant to end it
    A guardian is a guardian of a child once 04 §1 (guardian_person_id, dependent_person_id) all rows, and past ones are expected and unlimited 04 §6 — added by D-130, which is what closing F-10 owed this row Two guardianship rows for one pair with different right_level, so whose word the child's record takes is a query-order accident

    The predicate is part of the constraint, not a comment on it. membership counts three statuses and guardianship counts none, and a migration that copies the first constraint and edits the table names produces a rule that refuses a lapsed row beside a new one — which history requires. This is the same mistake 00 §6a records as already having been made once, in an index.

    Two rules that read like this shape and are not: person_identifier (scheme, value) and person_attribute (person_id, attribute_definition_id). Both conditions live in another table — identifier_scheme.is_unique and attribute_definition.allow_multiple — which makes them shape 3, and 00 §6a tells the story of the index that got this wrong once by ignoring a flag. Uniqueness stated over all rows — permission.code, role.code, payment_request.variable_symbol, the public_id columns, the one-row-per-pair rules on registrations and answers — is a plain unique constraint and is not listed here at all.

    3. The answer reads another table, a resolver, or a graph¶

    Forty-seven rules, counted off the table below rather than carried down from the last round that touched it — this sentence said forty-one while the register's own summary elsewhere in the corpus said forty-five, and both were describing one table. In this shape the layer is always the write path — no constraint spans two tables — so the layer column is gone from this table and only two columns remain. The report column is the one worth reading: none means a rule that holds until somebody edits the write path and nothing downstream ever says so.

The register keeps those rows precisely so that "we checked" and "we chose not to" are different words in the same column.

    4. A value that may never change once set¶

    This shape is not empty. It was described as empty on the strength of one deleted instance; four live ones were already in these pages, and the test that separates them from a column nobody would think to rename is the same test that made the two named candidates worth naming: a rename rewrites what references it, and nothing leaves a row in the wrong state for a report to find. Eight rows are below and seven of them are members, counted off the table rather than carried down: the audience row is the eighth and is the correction, not a member. The seventh arrived in round 20 without anyone looking for it — a decision about event forms made a vocabulary code referenced, and the shape grew by whatever the corpus references, which is the one property of this shape that does not need a checker.

    The value Stated in What references it What carries the rule
    A member row's group_id and person_id 02 §2 the row's own meaning the close-and-open pair, which is the write path; never an edit of the row
    A bank transaction, every column 07 §2a reconciliation against money already matched "immutable once imported", and a re-import or a new row instead
    person.merged_into_person_id 01b every walk that resolves who a person is now — chains are expected and walked the rule against rewriting a historical row's meaning
    A permission's code 05 §2 every access_grant row — and, since D-150, that is the entire list: the second referrer used to be the seeded roles, which named codes by value in a file no review ever opened stated twice and enforced nowhere; now a rule with a referrer listing behind it (D-131) — the list shrank and the conclusion did not
    A selector's code 05a §8 every stored expression, through selector_kind the same rule; this is the instance the register was looking for and the candidate list did not carry
    A key's code 05e §14 grants, audit rows, and the report of who called the same rule (D-131)
    A definition's code 09 §2 event_question.bound_attribute_code from round 20 on — the first table that ever named a vocabulary code by value the same rule, arrived at by D-131's own test rather than by looking for it: a merge may carry the bound questions, a rename would silently re-answer every form asked under the old name (D-131, D-139)
    An audience's code 05a §8 nothing, after the save — AUDIENCE(x) resolves once, into selector_arg_id not immutable, and this row is the correction: a rename rewrites no grant, which is what §5 of the name namespace promises out loud and what the candidate list F-10 carried had forgotten

    What the register cannot say¶

    • It cannot say whether a write path still contains its rule. Every shape-3 row above rests on code this repository does not contain. Where a numbered check exists for such a rule, it is a save-refusal: it re-asks whether the guard is there, and it is the only thing standing between a removed line of code and a silent rule.
    • It cannot reach a rule stated only once, in prose, on the page it governs. That is what the inventory behind this page was for, and what it found in the way of absences is in the open questions, each one naming the page it is missing from.
    • It cannot rank the nones. It used to be able to say at least where they clustered, and the answer was two pages: 07-finance.md and 06a-import.md had no "Invariants to verify" section, so every rule they stated was unassigned by construction rather than by oversight. That structural excuse is gone (D-135) and both pages now carry their own list, which leaves this column holding only rules that were read in the round that found them and left unguarded on purpose or on the table's own limits. Ranking those is still not something a register can do without inventing a severity, which is the thing it refuses to do.
    • It is not a substitute for the constraint. A row here saying migration is not the migration. 00 §6a is the rule about what must be emitted below the application; this page is the evidence that the rule was applied to every row and told where it was not.
