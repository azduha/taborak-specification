    Data Model — Authorization: invariants, day one, open issues¶

    The invariants a correct implementation must hold, the rows the platform ships with, and what is still open on this part of the model.

    Section numbers are shared across the six parts and never renumbered, because other pages cite them by number and their anchors are built from them: 05-authorization.md holds §1–§7, 05a §8 (the audience table, the grammar, the selector registry), 05b §8 continued (the tree and what each operand costs), 05c §9–§10 (access_log and the resolver), and 05d §11–§13 (invariants, seed data, open issues), and 05e §14–§17 (a key, and what it may hold).

    11. Invariants to verify¶

    Each entry states what it counts and what a non-zero result would mean. They are verified by something, in whichever way the implementation chooses. The numbering has no holes and does not move: other pages cite these checks by number, so a check whose subject is gone keeps its number and says in one line what stands in its place.

    No check reads a column this schema does not have. requires_scope, permission_level, scope_exposure and system.gate_exempt are not columns of anything described here, and no entry below counts them.

    Some entries assert behaviour rather than program text, because there is no stored resolver text left to read and behaviour is the strongest form still available — D-081 requires saying so: a prohibition nobody runs is a convention, not a guard.

    A report whose first run is empty, or is everything, is not a finding. Three entries below report correctly on a system that has just been set up and look, from the number alone, like a failure: check 9 returns exactly one holder on a system nobody has configured yet, and that holder is the installation's own day-one grant (D-150), check 13 returns the entire permission catalog because nothing is granted to anybody at the unit yet, and the import reconciliation of D-090 counts nothing to reconcile because the office whose roster it checks is one the organization has not written (D-154). All three are the system's age showing, and each says so beside its own expectation. This paragraph is prose and no check was written for it, which is deliberate: "was this report read with the system's age in mind" is not a query, and a check that could only be answered by a human reading a number would be a report of a report (D-131's lesson about what a check is allowed to be).

    Invariants to verify

    • 1. Live grants for a person who has been merged away. An open access_grant whose person has been merged into somebody else. A row means authority is still attached to a tombstone; it should have been closed or moved at merge time.
    • 2. Orphaned item grants, and orphaned selector arguments. Per scope type, generated from grant_scope_type: a grant whose scope_id names no row in the item table it points at — and the same scan over audience_operand.selector_arg_id, which is polymorphic for the same reason and takes the same mitigation. A row is exactly the risk the polymorphic columns accept (§6, D-011, extended to operands by D-101), and this is that trade's compensating control. An orphaned operand is normally the quiet half: it resolves to the empty set, so the grant is inert rather than dangerous, and inert authority is the failure nobody notices.

    selector_arg_id also points at audience (D-103), and an orphaned AUDIENCE leaf is not necessarily quiet: quietness is a property of the leaf's position, not of the leaf. Reached through + or * it removes people; reached through - it adds everyone the missing audience was excluding. Run one scan with two outputs, splitting on whether the orphan sits under an odd number of - right-hand positions, and route the wide half to check 7's second report rather than to this one's — an orphaned ROLE leaf belongs with inert authority and an orphaned AUDIENCE leaf belongs with the grants that got wider. The operator is what decides the direction of a failure (§8's evaluation rules).

    This scan is a backstop, not the mechanism. Every hand-named person in the system is a leaf in this column with no key behind it, so a person merge and a redaction are required to repoint those leaves in all five argument kinds that name an entity (§8, A hand-named person is now a keyless reference). The scan cannot stand in for that requirement, for two reasons. It runs the following morning, and an expression resolves wrong from the moment of the merge. And it only fires when the absorbed person's row is actually removed — if the merge leaves the row in place, as any design that keeps its history will, the leaf still names an existing id, this check reports nothing, and the grant quietly keeps a person who no longer signs in. On the allow side that is inert — the failure narrows the set and stops there; under - the same failure widens it, and EVERYONE - PERSON(x) with an un-repointed x denies everybody. Why the halves are reported apart: they do not differ in volume, they differ in which direction a wrong answer moves access, and only one of those directions can grant (D-106). - 3. A grant at a scope its code forbids. An open grant whose scope_id is present while the permission's applies_to is unit — or any grant of a system. permission whose applies_to is not unit, which is the shape §12 says it fixes and nothing else. Zero expected, and a row means the save-time check was skipped, not that a constraint was disabled — no constraint spans those two tables. This is the report that stands in for a database rule, which makes it the kind of row to find the day it appears rather than weeks later: nothing about it will come and find a person on its own. - 4. A bound operand where it cannot bind. An audience_operand whose selector has binds_to_item = true and which sits in an audience aimed at a unit-scope grant, or whose selector_type.argument_type differs from the item type of every grant aimed at that audience. Zero expected for the same reason as 3: refused on save, unenforced by any constraint, and a row means the write path was bypassed. PLACED aimed at a group, or ORGANIZERS aimed at nothing, should be unsaveable, and this check catches the build in which they are not. - 5. A deny that denies nothing. A live deny whose grantee, scope and code match no live allow anywhere. Probably intended as a removal rather than as a restriction; verify the intent. D-099 requires this one by name: a deny that denies nothing is how a stale restriction survives its reason, and the resolver will never tell anyone it is dead, because a deny never needs to. - 6. A grant naming an office with no MEMBERS. A live grant whose audience expression contains a ROLE(...) operand and no MEMBERS operand anywhere in the tree (D-100's standing report). A row is not an error — writing an office without the gate is a legitimate act and is exactly how an appointed officer keeps serving while their own fee is unpaid — but it is the case worth a human eye, because it authorizes a lapsed member silently and forever. The report is deliberately narrow: it has to be short enough to actually be read. - 7. A grant aimed at an audience that reaches nobody — or everybody. A live access_grant naming an audience whose expression contains no operand that can hold a person — a sum of PERSON(x) leaves naming people who have been merged away, a GROUP(x) whose group has ended, an operand whose selector_arg_id is orphaned, an AUDIENCE(x) leaf whose target has ended or gone (§8, and D-103), a tree that cannot be assembled. The grant join is what makes this check worth running: an empty audience on its own is a work in progress, but an empty audience a live grant points at is a permission configured, visible in an editor as granted, and reaching nobody — and it is the inert authority an administrator cannot see from the grant screen.

    Run the same scan for the mirror-image case and report it separately, because it is the more dangerous of the two: an empty operand reached through - makes the expression wider, so EVERYONE - AUDIENCE(x) with x gone reaches everybody — an allow that meant to exclude now includes, and a deny that meant to exclude now falls on everyone. Why these are two reports and not one: a widening is not a noise, it is a direction, and a wide failure is only better than a narrow one when somebody is reading (D-106). The permissions page's tab (F-21) therefore carries a second column naming which leaf failed, not merely that one did, aimed at the audience's owner — a listing with somebody's name beside the row. So the control here is report, twice over, and not a refusal: nothing stops an audience whose leaf is broken from being saved (D-107). MEMBERS - AUDIENCE(x) is the narrow version and it is the easier one to miss: the exclusion is the grant's whole point and its target is gone, which reads on screen as a grant that still names the audience it excludes. The save-time refusal (an audience named by anything live cannot be ended or deleted) is the primary control; this check is the one that fires when the refusal was bypassed by a restore or a manual delete, and unlike the empty side it is read the day it is non-empty rather than on a weekly list — a widening waits there to be found, it does not announce itself (D-164). - 8. A grant whose expression contains EVERYONE. Live, and naming EVERYONE anywhere in the tree. Not a violation: it is what a public page is for, and holding EVERYONE directly is legal. It is on the list because a language with union in it lets one edit widen a grant to every person with no account and no membership, and the person who made the edit is the only control (§8, What audiences do not do). - 9. Holders of system.admin, and whether they can sign in. Everyone with a live allow of it, however they came by it — through a personal grant or through an expression naming an office. This should be a very short list, and it is the list to open whenever anyone says the holders have changed. A key never appears on it and cannot: that grant is refused when it is saved and counted by check 20, so a list containing only people is also the evidence that the refusal held. The second column is what turns the list into a warning: for each holder, is account.status active and is their credential live — account_credential.valid_to unset or still in the future, not revoked (01a §5). An empty second column is the report's real output: a world in which somebody could hold the capability and nobody can reach a screen is the state D-126's procedure exists for, and that procedure keeps the one name it names — the column is read by whoever works the queue and answered by the recovery person written into the procedure, which is a procedure needing a name rather than an alert, and nothing in this design sends it to anyone (D-126, D-164). On a first run this report is one row long, it has already reported its holder, and both are correct: the one grant the installation writes is a holder of system.admin, so the report's first output is the installation itself (D-150). Nothing about an event widens this list: the bundle an event creation writes is item-scoped, and system.admin is applies_to = unit, so it cannot be handed out on an item at all (§2, §12). And a row can only reach this list from a person who already holds what they handed out — the save-time ceiling refuses a grant naming a permission its writer does not hold (05 §6), which is what makes it bearable that this report is read rather than sent (D-163). - 10. Expression trees that are not trees. Any of: a node with a selector, or a leaf with an operator; a node with one child; a row whose audience_id differs from its parent's; a row whose parent_id names no row; an audience with zero or several root rows. Zero expected, and every shape here means the write path let a tree be assembled one row at a time. §8's first rule is the one check a migration can state; the rest of the list cannot be, which is exactly why it is here. Nesting relaxes none of it: AUDIENCE(x) is a leaf pointing at another audience's root, never at one of its interior rows, so a tree still has one parent per node and one audience per tree — and a row whose parent_id crosses an audience boundary is this check firing, not a feature. - 11. A delegation that cannot expire. A live access_grant with is_delegated true and no valid_to. The row rule forbids it and no constraint enforces it. There is no source grant for the check to point at — delegation_of is not a column of this schema (§4) — so the delegation's own expiry is the only guard against it outliving its reason. - 12. Two names that are one name, and a reference that points at an unnamed thing. Three shapes, one namespace: 1. A role.code equal to a person_group.name after case, whitespace and separator folding — a group has no code column (02 §1 says so), and this section promises at its head that no check reads a column the schema does not have; 2. either of those equal to a selector_type.code, or any of the three equal to an audience.code — audience shares the namespace, because AUDIENCE(<code>) resolves through that table (D-103); 3. an AUDIENCE leaf whose selector_arg_id names an audience whose code is absent — legal on every column of both rows and unsayable as a constraint, because the check reads a third table (shape 3).

    Zero expected; no single constraint spans three tables, and no constraint at all covers the reserved-word half or the null-code half, so the write path carries all of it and this check asserts the write path exists. A row here is not untidy: a group called MEMBERS would silently rewrite the meaning of every expression in the system, and an audience sharing an office's code is the same accident one arm over — the kind of a name decides which set a bare expression meant. - 13. Orphaned permissions. An assignable permission that no live grant names, at any scope. With no wildcard, a permission nothing bundles grants nobody, so the question is asked of the grant rows themselves and of nothing else (D-068). Expected on day one: everything but system.admin, and that is not a finding. Nothing is seeded into a grant, so a first run reports the whole catalog back at the person reading it, which is the most useful thing this check ever prints — it is the list of capabilities that exist and have not been given to anybody, and §12 calls it the checklist. A row means something different once the organization has been writing grants for a year: either a permission nobody has bundled into an office yet — fine on a roadmap, wrong in production — or a module was added and its grants were not. Note what it cannot see: a permission granted to an office but not to the office that arguably should have it. That residual is the accepted cost of D-068 and nothing closes it; it is a human reading the catalog against the grants, and that is the one report here that gets less useful the longer nobody reads it. - 14. Offices nobody holds, and holder rows pointing at an office that is gone. The first is expected and is not an error: a role nobody holds is either one about to be used or one stopped using and not deleted, and there is no third possibility, because a role has no period (D-053) and cannot be switched off, only held or not held. Delete the mistakes, keep the ones on the roadmap. The second should be zero — the delete guard on role enforces it, and the check exists because a restored dump or a manually disabled guard bypasses it, and the loss is unrecoverable. - 15. TIME-BOMB: an expression must be refused at the write, never survived at the read. It asserts a guarantee rather than a set of rows. Four halves keep their numbers; the last is the one that fails silently, and half 2 is retired rather than active. 1. A cycle must be unsayable, over both walks. Saving is refused for both shapes — a node whose parent chain revisits a row inside one tree, and an AUDIENCE leaf whose target audience reaches back to the audience being saved, at any distance (D-103). A forest of audiences naming each other is not a tree, so "a tree cannot cycle" is not a proof of safety and the cross-audience walk is not optional. Both are tested as a test that tries, not one that counts, because after the fact there are none to count. Zero is the expected result every time this runs, and a non-zero result is not bad data but a missing guard. 2. Retired, and it asserts nothing: there is no save-time size rule to test. selector_depth_limit is not a parameter of this system (D-105), so an assertion here would test nothing — a build that gets an enormous expression is a green build. The number stays in the list because other pages cite these halves by number. What is true of size is that neither shape is bounded: height is unlimited, and an expression's cost is proportional to the number of audiences it reaches, so a wide flat sum of + AUDIENCE(...) leaves costs a fetch per leaf per check. What stands there is the standing report of the widest and deepest audiences and their cost per check (§8, The cost of composition) — no CI job, no refused save, nothing that fails if the report is not read, which is D-081's case: a rule's name outliving its mechanism. F-21 is the open question about who reads it. Half 3 is therefore the whole structural story: acyclicity at save, and nothing else. 3. No sharing table may exist, and the read path must grow neither a depth cap nor a cycle check. The tree's one-parent rule is worth nothing if a side table lets two expressions share a node — editing the shared node would silently widen every grant using it, which is D-091's inclusion hazard re-imported. AUDIENCE is not that table and must not become it: it points at an audience's whole expression, never at an interior node. A forest met at read time is survivable-looking, so whoever meets one reaches for a hop counter, and the cap becomes the thing that decides who a grant reaches — which is why the read path depends on the write guard rather than backing it up. With no bound anywhere, a hop counter looks like the obvious way to make a check cheap (D-105), and this refusal is the only structural one left, so the temptation is the design's real exposure. A build that passes half 1 and fails this one is a build where the write guard has been removed and papered over — the shape nesting makes easy to reach, because a read path that can follow an audience is a read path that wants a counter. 4. A referenced audience may not be emptied from the other end. Saving must refuse to end or delete an audience while a live grant, or a live audience reachable from a live grant, names it (§8, Rules). It is a save-path refusal like the others and it belongs to this assertion for the same reason: the data after the fact is perfectly well-formed — an ended audience and a leaf naming it are both legal rows — and the damage is that every expression doing X - <that one> silently got wider. Of the four halves this is the one most likely to be implemented as a warning, because a delete that pops a confirmation dialog feels like sufficient care and a refuse feels like an obstacle. It is the one where a warning is not enough.

    Why this is a CI assertion and not a report: three of the four guards are walks over rows rather than comparisons within one row, which means they live in application code and no migration can emit them (shape 3). A guard that lives in code is deleted by a refactor and the data looks fine afterwards, and nothing greps for it at build time (D-072). - 16. TIME-BOMB: no permission path may materialize a set. The requirement is that operand_holds decides membership for one person and never loads a set of ids to test containment in. An operand is a named set — a row of selector_type, which is the only test the language has. One thing wants it as an expanded set: the editor's preview, which shows the set to a human and is not a permission path (D-114). In the resolver an operand is a predicate, and D-101 writes the distinction down precisely because an implementation is one lazy join away from getting it the other way and paying three thousand rows per check. Materializability is not the test for what an operand may be (D-107): OLDER(18) is precisely as materializable, and precisely as unmaterialized, as MEMBERS — a birth date read at the checked date and a membership row read at the checked date are both answers computed per person, and neither is allowed to become a list of ids. This is a requirement about how the code computes, which no migration can state and no reviewer will notice missing until the first slow day.

    Nesting is where this assertion earns its keep, so assert on a nested expression specifically. A flat ROLE(x) is awkward to write as a set load and natural to write as a predicate; an inner AUDIENCE(veterans) inside an outer expression reads like a job for "fetch the inner set once and reuse it", which is the tempting optimization, is correct as an answer, and is the thing that makes a check slow at exactly the depth the expression happens to have — and there is no depth above it: an expression is as deep as somebody typed (D-105). A test exercising only single-level expressions passes on an implementation that materializes at every nesting level. Assert that the recursion takes a person and returns a boolean, and that no path between two audiences hands over a collection. - 17. TIME-BOMB: .admin prefix matching, and any ordering comparison, must stay deleted. Two parts, both prose: there is no SQL left in which a build could grep for either (D-072). First, no step of the resolver may build a permission code by concatenating a resource with .admin, and no permission may have admin as its action except exactly one: system.admin. The allow-list is that single code and the check is an equality, not a set membership (D-074), because an allow-list is where a wildcard comes back to life. Zero rows expected. Second: no comparison of access_level ranks, no required_level lookup, and no "at least contribute" anywhere. There are no levels to compare (D-099), so the bug D-012 existed to catch — 'admin' < 'contribute' read alphabetically — cannot occur, which is a better fix than the guard. The one ordering this model still performs is right_kind containment in the guardianship channel, so a build where a second ordering has appeared has not reintroduced a bug; it has started reintroducing the ladder. - 18. TIME-BOMB: deprecated and hidden must never change an answer, and disabled must change one and say whose. Three states stand where deletion stood (D-109), and they are only safe if two of them are inert. Assert both halves, because each fails alone. Inertness: resolve every live expression, then flip a selector_type, role, person_group or audience row to deprecated and then to hidden, and the resolved sets must be identical — a rule that quietly stops granting because somebody tidied a list is the precise failure this design exists to make impossible, and an implementation gets it wrong by having the editor filter non-active rows out of a list it also uses to evaluate. Effect: flipping the same row to disabled must empty exactly the leaves that name it, in every expression, and the write must record the rules it touched, resolved before and after. Third assertion: the flag is read live by the resolver, never compiled into a predicate — flipping a row to disabled changes the next check, not the next rebuild (D-114). A deprecated row that stops granting is therefore a bug in one function, and a disabled row that does not is visible in the same place. Nothing else in §11 can see this one, because the flag is a legitimate value in a legitimate column and every row is well-formed on its own. - 19. TIME-BOMB: no row, table or field anywhere may map a caller — or a caller and a code, or a caller and an item — to a permission answer. A caller is a person or a registered key, and the widening is deliberate rather than a tidy-up: as written over persons only, a table keyed by api_key_id and permission_code holding a boolean would not have been forbidden by this invariant (D-123), and "the integration's permissions" is the most natural table in this system to write — it reads like configuration, not like a cache. This is the reason a permission cache cannot come back later as an optimization (D-114). Assert it the way a schema review asserts things: no column pairing a caller with a boolean that could only have come from a check, no table whose key contains person_id or api_key_id together with permission_code or a selector_kind / selector_arg_id or an item, and no computed_at sitting beside an answer. api_key.last_used_at is named here and cleared, but it is not a fourth shape: a timestamp of when something happened answers no permission question and nothing reads it to decide one, while api_key.last_checked_permission would be exactly the row this check exists to catch, and is the name a review should search for. Three shapes survive the sweep and each is legal for a reason worth repeating: ruleset_version, an integer about a ruleset that names no person and keys a compilation; D-110's record of whom a grant reached, deliberately stale because it is a historical record — a rule naming a person who has since left must still read as it read then, and nothing reads it to decide whether to allow something now; and the audit payloads, which record that a check happened and expire on their own schedule (D-088). The first is a value in a column; the second and third are records of an event. There is no fourth, and what the check looks for is a row that is a current answer. This is enforced structurally, which is both its strength and its limit: the schema has nowhere to put an answer, so an implementation cannot persist one by forgetting not to — it would have to add a table, which is an act. In D-081's vocabulary the residue is a named convention, not a guard: nothing stops a team from adding a permission_cache table again in a year, under load, at 2 a.m., because it is the obvious move and this invariant is a paragraph. Read D-114 before writing that migration.

    • 20. A refused code granted to a key. A live grant naming api_key_id whose permission is system.admin or one of the four api_key.* codes (D-122). This check is the entire net, and saying so is the point: the refused set is an equality against five named codes, permission and access_grant share no column, and so no database rule can span them — unlike check 3, which reads one column of the permission row and can therefore always see the shape it counts. A row here means the save path was skipped, not that a constraint was disabled. The refused set is written out code by code and never derived, for the reason check 17 states for .admin: an allow-list is where a wildcard comes back to life.
    • 21. A grant naming a key that cannot be used. A live, unrevoked grant naming an api_key row that is revoked or past its valid_to. The grant is inert — an expired secret cannot authenticate, so nothing is being reached — and that is precisely why the check exists: dead weight of this kind reads as an active integration to the next person reviewing who can do what, which is the same failure check 5 reports for a deny that denies nothing and check 13 for a code nothing grants. Closing the grant is a person's act with a reason, and §14's revocation triple is where the reason is written.

    • 22. TIME-BOMB: nothing may read a key's own columns to decide an answer. An assertion, not a report: no code path reaches for last_used_at, owner_person_id or created_by when it resolves a permission, and no check consults the person who installed an integration at all (D-120, D-123). The reason this needs its own numbered assertion is that every one of those columns is right there on the row the check has already loaded, which makes creator-derived authority the cheapest wrong turn available: a suspended account, a lapsed membership or a deny written against whoever installed a key would otherwise change what the key may do, and D-005's "a permission is never derived from an identity" forbids exactly that — including when the identity belongs to somebody else. 15 and 16 are CI assertions too, and this belongs beside them for the same reason: a prohibition nobody runs is a convention, not a guard.

    • 23. The four reference-less keys nothing else reads, and the fifth that is deliberately left unread. One count per column over field_conflict.entity_id, access_log.scope_id, access_log.authorization_ref_id and access_log.entity_id: a row where the column is set and no row exists in the table named beside it — entity_table, entity_type, scope_type, authorization_channel — or, where a registry names the table, in that table. A set id that resolves nowhere means the row was written wrongly at the moment it was written; there is no constraint here for a bypassed save path to have bypassed. Only a set column counts. An absent scope_id is a check at the unit and an absent authorization_ref_id is no grant involved (00-conventions §7a), and the document kind is deferred, so there is no table there for any scan to walk. Check 2 holds the two keys on the granting side, what the polymorphic trade costs, and the split that decides which orphan is the dangerous one; nothing this check counts grants anything, so a row here has never changed who may do what — it has left a question in the trail with nothing to answer it, which is why this one is a listing to read and nothing more, there being nothing in the design that would send it (D-164).

    Which absences are legal, and where the pages stop short of saying so. Two paths in this design remove a business row outright, and neither can take a trail row with it: 05c §9 permits only the erasure and the reduction to change a row of that trail, permits them to touch only the state columns, and calls every other field on it immutable. The import's revert removes the event_registration, event, membership and person rows a batch created (06a §3, Reversibility), and the erasure deletes the person's person_attribute rows (00-conventions §4, 06b §4). So the exception is a rule about the target table plus a demand for evidence, never a list of tolerated ids: an absence is legal exactly when the table the row names is one of those five and the trail shows the removal — a revert writes one audit entry per row it deleted, naming the batch, and an erasure writes one redaction_log row naming person_attribute in redacted_tables. Everything else is a defect, including a row inside those five tables with no removal recorded against it — and revert's pre-flight is stated as a check for references (06a §3) and never as one that reads a column with no foreign key in front of it, which is what makes an absence under these three columns an expected outcome rather than a surprise.

    Erasure on its own accounts for none of them: what it deletes is attribute rows, plus the expression leaves naming the person where it removes one rather than rewriting it, while an erased person's scope_id names a scope — an event, a group or an office, and nothing at all where the check was at the unit — and their authorization_ref_id names an access_grant or a guardianship_permission row, none of which erasure touches. So an orphan under authorization_ref_id has no lawful explanation at all, and one under scope_id has exactly one: revert removing an event. One shape beside these is neither a finding nor clean: a row whose authorization_channel is outside the six values 05c §9 lists keeps its word and loses its table, so there is nothing for the id to be counted against, and it is reported separately rather than as an orphan. Of the three, only entity_id could name a row erasure does delete — a person_attribute row, or one of the audience_operand leaves the erasure removes — and whether it ever does is settled by nothing in this corpus: entity_type, the column that would say which table the id belongs to, is declared in 05c §9's field table with an empty note and is given a list of tables nowhere. 00-conventions §4 and 06b §4 say exactly what an erasure deletes and neither says what is written into this trail, so no page states which writes produce an access_log row at all. The exception is therefore written wide enough to cover the case, and a reader should expect the erasure arm of it to report nothing until somebody answers that.

    audit_log.record_id is the fifth of these columns and no count walks it, which is a decision rather than an oversight. An audit row is built to outlive the row it describes. Its skeleton is permanent and only its payloads expire (D-088), and its fields are as immutable as the access trail's (05c §9 states the guard for one trail and carries it across to the other), so a removal in a business table must leave a reference behind; and the orphan is not merely tolerated down there, it is load-bearing — 06b §5's check that a redacted person's payloads are empty finds the rows it exists to test by their table_name and record_id precisely because those two survive the erasure that deleted the row behind them, and revert's entries name a deleted row by design. A count over this column would report both erasure and revert as integrity failures, which is worse than no check at all, because the first false alarm teaches whoever reads the report to ignore the real one. What stands in its place is the pair of checks that read the property the column was ever a proxy for: that an erased person's payloads are empty, and that nothing past the window still carries one.

    The dangerous one of the four is field_conflict.entity_id, and it is dangerous for a reason the other three do not share. A conflict row is a question put to a person — one field a merge could not decide, sitting unresolved in the queue 01b §10 ages at thirty days — and an entity_id naming nothing is that question being unanswerable. The reading nobody has written down before now is the likeliest one: the import recorded a conflict against a row that is not there, and every decision taken on the strength of that conflict inherited the mistake. Revert explains some of them, since entity_table holds person and membership and revert removes both, and its per-row entries settle which of the two paths was here; a row outside those two tables, or with no removal behind it, is not untidiness but a merge that decided something about a record that never existed. None of this belongs on the permissions tab: the tab lists rules, and not one of these four columns is a rule — and putting a legal absence on a page about broken things is how a broken one comes to be read past.

    Checks 3, 4, 5, 6 and 9, and one half of 7, are the ones to open often. None of them sends anything, and no page may say otherwise: what a check owes is a row on a screen, and urgency is a property of the report rather than a message. Why that is said here rather than assumed: a sentence wiring five checks and half of a sixth to alerts sat above this list and named no report at all, so it survived every count of sentences about system.admin — most of what a grep for the promise matches survives the test for the same reason, a report described as urgent is not a message, and what this page lost was that framing sentence plus half of check 7 (D-164).

    • 3 and 4 are the reports that stand in for the database rules that do not exist. A row in either is not data drift — it is a save-path check that stopped running.
    • 5 and 6 are the reports for the two restrictions that have no mechanism enforcing them: a deny that denies nothing, and an office granted without the membership operand. Both are lists a human reads, and both are the entire remaining control on their failure.
    • 9 is the report that distinguishes a planned change from an incident — a new holder of system.admin is one or the other, and this list, read by whoever opens it, is the only thing here that says which. What it does not do is reach that person on its own: no mail is sent when its result changes, and there is no mailbox this sentence could have named (D-164). Its second column reads as a warning when it is empty, which is a different kind of finding: the authority exists and nobody can use it, which is the state the written procedure in domain/02 §3 is for — a procedure that keeps the one name it names, since a procedure needs a person where a notification does not (D-126).
    • Check 7 is the entry on this list whose two halves are read on different schedules. Its empty half — a grant reaching nobody — is inert and belongs on a weekly list. Its wide half, a grant that got wider because something under a - stopped resolving, is the only entry in §11 that describes authority increasing, and it is the half to open the day it is non-empty rather than on a schedule. What it reports is not what the granter's ceiling refuses, and the two are worth keeping apart: this half widens because an expression changed shape under a grant nobody rewrote, while D-163's ceiling refuses a row naming more than its writer holds at the moment it is saved (05 §6) — a different cause at a different moment. No report stands behind that ceiling and none was called for: the control is the refusal, and what the trail answers afterwards is who did this. Splitting 7 is not tidiness: a single report containing both halves has the wide row sitting between nineteen inert ones, which is how a widening gets read past.
    • Checks 15 and 16 are CI assertions, not reports. They are the automated guards on the two rules most likely to be "simplified" away when someone optimizes the resolver: the refusal of a malformed expression at the write, and the refusal to compute a set where a predicate will do. Both fail the build rather than silently changing who can do what, and both live in code rather than in the schema, which is why neither can be a migration. With nesting, 15 guards a graph rather than a row, and it guards two things: cycles, and not emptying something that is named. The acyclicity walk is therefore the only structural guard on this module, and check 15's half 3 is the assertion that nobody quietly adds a second one inside the read path.
    • Where these go. The permissions page has a tab (D-109). Broken holds the rules that name something deprecated, hidden or disabled or that resolve to nobody — checks 1, 2, 3, 7's empty half, 12, 13, 14 and 18's second half all land there — and Unusual holds rules that resolve correctly and look odd, which is where 6 lives. Unusual also gains a line of keys — each live api_key with what it is granted, when it was last used, and whether the person in its owner_person_id still has an account — because a permanent outside authority is exactly the kind of correctly-configured oddity a tab is for (D-120). There is no age threshold on that line: a bound somebody might want to change belongs in a column, and inventing one is not this page's call. Check 7's wide half and check 9 are reports on a screen and not messages to a person, and that is stated rather than glossed: both describe authority getting bigger while nobody was editing a grant, and this design still sends nothing to anybody, so the honest claim is that these are the two a person is expected to have opened recently (D-164). Being read is enough here because of what the ceiling took off the table: nothing can be written that hands out more than the writer holds, so neither report can be surprised by an escalation, and every change of hands that does happen carries the name of the person who did it — granted_by, required, no empty to read. No report covers how far a permission has been handed around, and none was called for: the ceiling is the save, the trail is the answer to who did this, and check 7's wide half — the entry a reader will find nearest to this claim — is about an expression widening under a grant nobody rewrote, which is a different thing (D-163). Checks 20 and 21 land in Broken beside 3, 4 and 13 — one is a save-path refusal that got through, the other is authority that reads as live and is not. Checks 19 and 22 go to neither tab: they are facts about the schema and about the resolver, not about a rule, and the place either can be enforced is a migration review or a CI assertion. The tab is not a guard in D-081's sense — nothing is blocked — but it is where the person writing the rule already is, which a report on a schedule never was.

    12. What day one looks like¶

    Nothing in this section is a starter set. The platform ships a language and no opinions; everything an organization would recognize as its configuration — every office, every audience, every grant — is written by somebody on the first day rather than shipped on the last one (D-132, applied by D-150).

    This section and ../appendix/permission-catalog.md used to be the same list written twice, and they drifted. The list this section kept is gone, which removes the second copy and not the argument. With no wildcard, a code the catalog advertises and no grant names is a capability nobody can be granted, and the permission editor is the only place the gap shows. Nothing in the schema pairs codes with roles, so there is no per-role list to compare a catalog row against: a documented code that nothing grants is invisible to anything but a report. Integrity check 13 reads the grants for exactly that reason (D-068), and on a system's first week it reports nearly everything in the catalog — which is what "not yet granted" looks like when a report is honest about it.

    There is no SQL check for this — one side is a Markdown file. The discipline is the check: when adding a permission, add it in both places in the same edit, and treat a catalog row that no grant names as a bug of the same class as a missing migration. The reconciliation is mechanical enough to script: a diff of the codes the catalog lists against the codes that exist. Anything in the catalog and not in the database is a permission that cannot be granted; anything in the database and not in the catalog is an undocumented capability. Both directions of the gap can be present at the same time.

    Not in the catalog, named rather than quietly dropped, each with what to use instead: the dependent.* codes — a guardian's authority is a right_level on the relationship, not a bundle of permissions (D-074); scope.expose and scope.exposure.review — the table they guarded is not in this schema (D-097); system.gate_exempt — there is no gate to waive, membership is an operand (D-100); every position.* code and the appointment workflows behind them (D-100); and the codes about bodies rather than people — a unit's renaming, restructuring and closing, and participation in a sub-unit — since there is one unit and it is a scope (D-097). role.assign, role.unassign, role.create, role.view, role.edit and role.delete are in the catalog and are aimed at role_holder; role.edit reaches nobody's authority, only its name and description (§3).

    Day one, in order, because the order is the only part that is not the organization's choice.

    1. One account, one grant, one code. An ordinary access_grant row: this person × system.admin × the unit. Nothing else in the system is configured, and nothing else needs to be — system.admin satisfies every check, so the same person already holds role.create, audience.manage and access_grant.create for the purposes of the next three steps (D-150). There is no bootstrap mechanism: no special column, no second kind of actor, no migration that knows it is installing an organization. This row is the first entry in audit_log and the first row check 9 reports, and both of those are correct rather than incidental. The granter's ceiling asks this row nothing new, and it is worth saying which way round that is: the account the row names holds system.admin at the unit, so the origin of all authority satisfies the rule rather than being waved past it (D-163).
    2. An office is a role row and it confers nothing. Name it, describe it, order it — then aim a grant at ROLE(x), because that is the moment the office gains a permission (D-100).
    3. An audience is an expression tree, written in §8's language, and it is worth naming only if something will name it (AUDIENCE(x)). A one-operand audience is usually not worth a row: the operand EVERYONE and the operand MEMBERS are writable anywhere, and the two audiences that used to stand for them are gone (D-153).
    4. A grant is one code, one scope, one expression, one effect — and the grant editor reads the catalog, which is the document this section deliberately does not duplicate.

    The catalog is the checklist, and ten of its codes are held by nobody at first: event.cancel, event.delete, event.organizer.manage, event.question.manage, the four guardianship.*, person_group.edit, person_group.end. Read them as not yet granted — that sentence is the whole reason the catalog exists as a document rather than as a dropdown. Four of the ten are event.* codes and every event's organizers hold them on that event from the moment it is created (D-151); what remains true, and what the list means, is that nobody holds any of them at the unit until somebody writes a grant that says so.

    counselors is a worked example, and the argument for it is about a table rather than a row. The name appears throughout this design inside expressions — MEMBERS * ROLE(counselors) — and every one of those was always an example of composing a grant, which is how they should still be read. What is no longer true is that the platform writes the office. D-100's reason for choosing role over person_group survives untouched: a permanent, organization-wide population is the opposite of D-098's definition of a group ("a temporary set of members that do events together"), and which table it lives in decides the sensitivity that every safeguarding convention in this area hangs from (D-100, D-005). That argument is about where a set may live; it never needed the platform to populate one. The consistency requirement goes with it, and so does its emptiness: MEMBERS * ROLE(counselors) is only as correct as the roster, so the import reconciliation of D-090 counts people marked as counselors in the corpus against role_holder rows written — and on a first run there is no such role, so the reconciliation has nothing to reconcile and reports nothing, which is a report whose subject arrives later rather than a check that is broken (D-154).

    No office holds any of the four api_key.* codes, and no office should. Whoever holds system.admin already satisfies those checks because system.admin satisfies every code (D-124), so granting them to an office would move the capability to install a permanent outside authority into a row nobody chose, on an office whose purpose is something else (D-122). It arrives by an ordinary grant or it does not arrive — and now that is the only way anything arrives.

    What §12 fixes, and still only fixes, is the shape rather than the list. A system. permission is applies_to = unit, so it can never arrive through an item grant. That is not a configuration choice and it is not a shipped row's property either — it is a column on the code, the structural guarantee that a shared item cannot hand someone authority over the permission system, carried by a value rather than by a resolver branch (§2).

    What ships, in one list, because "nothing is seeded" is a sentence that needs its exceptions. The platform ships three vocabularies and the enums, and no configuration:

    • The permission vocabulary, spanning people, accounts, membership, groups, audiences, roles, guardianship, item grants, audit, legacy import, reporting, the thirteen event.* codes, messaging, and the four api_key.* codes of 05e §15 — api_key.view, api_key.create, api_key.rotate, api_key.end, every one applies_to = unit. The one complete list is ../appendix/permission-catalog.md; this document keeps no second copy of it, because two copies drift for exactly the reason above.
    • grant_scope_type: unit (the only row that is not item-scoped), event, person_group, role, and document (deferred).
    • selector_type: thirteen rows — the thirteen operands of §8's language — every one of them shipped and implemented in the evaluator, because there is no fourth combination and no third kind (§8, The selector registry, whose table is the language: the count is only the cheap form of the check that no operand exists anywhere else). This registry is what both the grant editor's dropdown and the parser's reserved words read, which is what D-101 means by the language becomes data — a new operand is a decision entry, a seed row and a resolver arm in one release, never a row typed into a screen and never a row shipped ahead of the code that evaluates it. AUDIENCE is the newest operand anyone designed (D-103). OLDER and YOUNGER are the only rows whose argument is not an entity reference: it is an integer, and their arms ship in the same release as their rows on the rule above, which is why the merge and orphan scans of §11 walk five argument kinds and not six (§8, A hand-named person is now a keyless reference, D-107). Refused, and therefore absent (§8): GRANTS, and LIST — a hand-written set of people is a sum of PERSON(x) leaves, not an operand (D-105).
    • Nothing else — and the sentence is worth finishing, because three things used to be in this list. Offices, audiences and grants are written by people; §12's first four steps are the order, and the three paragraphs below say who writes each of the three, and what the two deleted audiences were for.
    • The effects and the enums. allow and deny arrive with the schema, as do the two values of applies_to and the two of right_kind. None of them is editable at runtime: a comparison the organization can edit is a security control with no owner, and there is no level comparison to seed at all (D-099).

    What the two named audiences were, and what replaces them: nothing. everyone held the expression EVERYONE and all_members held MEMBERS; both had a code, because a code is how another audience names one (D-103), and §11's check 12 is still the net for the leaf side of that rule — an AUDIENCE leaf pointing at an audience with no code is unsayable as a constraint and unkind as a resolution. What is gone is the rows, not the operands: an audience whose entire content is EVERYONE is worth a row exactly when somebody intends to name it, and naming is one ordinary write. Three names keep being asked for, and each of them is something smaller or nothing at all — unit_participants is MEMBERS; unit_leaders is ROLE(x), the shape §8's evaluation rules are written against, and an expression that resolves to nobody is silent while every grant aimed at it looks granted, which is the sentence to read before naming an office you have not written yet; and guardians_of is nothing — a guardian's authority is the guardianship channel's right_level over the child, not a set an expression can name, which is why GUARDIANS is not one of the thirteen operands (D-113), and a bound GUARDIANS on a grant about that person is unsavable on every scope that exists because person is not a grant_scope_type. Two refusals went out with the two rows — do not add a person to a seeded audience, do not offer to edit everyone's expression — and the category they were guarding does not need the rows to be true: an expression is not a member list, audience_member is not a table (§8), and a hand-written set of people is a sum of PERSON(x) leaves rather than a membership (D-153).

    What the shipped answer-view grant was, and who writes it now: whoever creates the event. "event.answer.view on an event, aimed at ORGANIZERS" used to arrive with the platform, and this section explained it as "one grant in the seed rather than one per event" — which was false, because a bound operand is legal only on an item-scope grant and one row cannot cover events that do not exist yet (08a §8 had already said so, in the other direction). The act that creates an event writes twelve item-scope allows beside the event row, in the same transaction, all aimed at ORGANIZERS: every event.* code except event.create, which is applies_to = unit (D-151). "Answers are read by that event's organizers" is still a row a reader can find, narrow or delete rather than a sentence the resolver implements, it is still the worked example of a bound operand — item-scoped, argument-less, meaning the organizers of whichever event this grant is on — and it is still written without MEMBERS and must not be "corrected" to include it, because an organizer appointed for one weekend is not required to be a paying member (D-102, amending D-061). D-062 is not contradicted: the appointment still grants nothing by itself, because an operand is a set and not a grant, and adding a cook changes the set rather than the twelve rows. What the bundle now contains besides the answer row is the part a reader should stop on: event.organizer.manage and event.grant_access are in it, so an organizer may add an organizer and may grant access to that event without holding anything at the unit — the widening the catalog marks ⚠ is reachable from inside the event, and D-151 states that as the cost it is.

    And one question this section used to leave open is now unaskable rather than answered. It asked whether audience.code should be required on an is_system audience rather than merely seeded on two of them. There is no is_system column anywhere in the design (D-152) and no seeded audience, so the rule would have nothing to apply to that was not an ordinary audience somebody named because they meant to (D-153).

    A few of the surviving codes carry a decision in their shape, and those are worth naming:

    • person.merge and person.redact are separate codes, not flavours of person.edit. They are separate for reach, not for irreversibility. person.redact is irreversible — that is what an erasure is. person.merge is not: reversing a merge is a supported operation (D-087), with the undo written as its own audit entry. What both codes share is that they act on every row of a person's life rather than on one field, which is why they are their own codes — and with no person.admin to imply them (D-068), a role that reaches them does so by listing them, visibly.
    • person.view reaches the whole record. There is no privileged corner of the record for it to stop outside: whoever holds it over a person reads their descriptive values — the allergy list, the insurance number, the note about who the child actually lives with — on the same grant that reads their name (09-attributes.md §4, D-083). A grant of it at the unit reaches every member in the organization, because that is what "at the unit" means: nothing in the model reproduces "access was granted by the body that knows these children" — the loss is recorded in §5 and in D-097. It is therefore the widest read permission in the system, and the catalog's sensitivity mark is where that has to be visible (D-086): the honest mark is the top tier, worded around whose data a grant exposes rather than around a category of fields, because there are no field categories (D-083).
    • audit.view is graded against what the trail quotes, not against what a log is usually for. audit_log carries before and after images, and since D-085 those images are the only place a child's past descriptive values exist; reading history has to sit in the same tier as reading a person. D-088 bounds the exposure to 24 months and fixes nothing, and the bound is the realistic control for an organization of this size rather than an argument that the mark is right — see §9 and AT-4 for why two years is not a short interval when the question is about a child.
    • attribute.define is the narrow half of a deliberate pair: values are open to anyone who may already edit the person, so that the fact gets recorded, and codes are held by few people, because the codes are what make the data queryable (09-attributes.md §2). An ordinary permission — no namespace, no resolver branch, no structural consequence.
    • person_group.member.manage is how "joining a group is somebody else's act" is said (D-098, carrying D-095): held at the unit, where it reaches every group, or granted on one group as an item. There is no self-scoped variant and none will be added — nobody writes themselves onto a roster. Its counterpart for offices is role.assign 🔒🔒, and the gap between the two marks is the whole content of D-100's "why two tables".
    • role.unassign is one of the only two things that end authority (the other is a holder row's valid_to), because a role has no period (D-053) and nothing forces a holder row to end (D-071).
    • membership.terminate expels, and is restricted as such; membership.lapse is an administrative end for non-payment. Neither changes what a role grants — there is no membership gate for them to act through. A lapse changes what MEMBERS means, which is a different thing, in a different place.
    • event.presence.mark stays a separate code from event.manage_participants on purpose, and event.register_self is the eligibility rule (D-060) rather than an expression of one. The difference the two codes mark is a volunteer leader is handed the register without being handed the roster, and that difference is two grant rows.
    • There is no wildcard at all, and nothing implies anything. A guardian's authority is right_level = write on the relationship, not a permission (D-074); the code families dependent.* and *.admin are not in this catalog. So an office that should hold a new permission must have one written down for it — check 13 is the net, and reading it is the whole of the follow-up.
    • Reporting ships coarse, and is left open on purpose. Only report.view and report.export exist. Whether reporting is per-report or one permission with row-level filtering is still open (catalog §12). Do not ship both shapes; pick one when reporting is designed.

    system.admin is deliberately a single top-level permission, not a per-resource one. Holding it satisfies everything, and check 9 in §11 reports its holders — a list to open, since nothing here would tell anybody that it had changed (D-164). Keeping the most dangerous capability concentrated, and visible in one short report, is safer than spreading equivalents of it across every resource. system.admin is a permission code, not a level — there are no levels (D-099) — and it is the only permission whose action is admin (§11's check 17 is the assertion that it stays the only one).

    13. Open issues¶

    • One question left about callers that are not people. Round 16 designed the arriving integration and stopped there; round 17 settled the two things it stopped short of — an empty actor column is read as this system acting on its own, with a six-label vocabulary instead of free text (D-125, and check 9 above is its sibling) and the case where nobody who could hold system.admin can reach a screen is a report and a written procedure rather than a mechanism (D-126). What stays open is the other direction: calls going out have no design at all (F-27). 05e §17 states each from this module's side, and none of the three was ever answered by adding a column to api_key — a sweep is not a caller and should not have to authenticate.
    • Which grants an organization writes with MEMBERS in the expression, and which without — the question this file used to ask as "which starter grants name MEMBERS", which has no starter grants to ask about any more. role has no requires_membership switch to carry an answer (D-100), so it is answered per grant rather than per role, with check 6 (§11) as the net. One case the design does answer: the twelve grants an event creation writes are written without MEMBERS, because an organizer appointed for one weekend is not required to be a paying member (D-151).
    • Whether the API should refuse a check that names an item for a unit-only code (§2). applies_to is deliberately a save-time rule, and D-099 says so in as many words, so the mismatched grant cannot exist — but a caller that asks can(person, 'event.create', 'event', 1204, …) gets the unit's answer rather than an error. Assumption, not a ruling: the honest answer is a refusal at the API layer naming the code and the scope, because a caller that asks that question has a bug worth surfacing. Nothing in D-097..D-103 settles it. Round 16 gave that word a second sense and changed this answer not at all: a call made with a key asks can_key(api_key, 'event.create', 'event', 1204, …) and is refused the same way, by the same layer, for the same reason (05e §16, D-116).
    • selector_depth_limit (§8): moot — there is no such parameter to give a default (D-105). What the question was reaching for is live: a bound on height does not bound what an expression actually costs, which is how many audiences it reaches — a depth limit of 3 still permits a wide flat sum of twenty AUDIENCE() leaves and prices each one at a fetch. Neither shape is bounded. F-21 is closed on exactly that point — nothing bounds what an expression costs, and at the stated size that is accepted rather than merely unaddressed — so what remains open is what would make somebody wish there were a limit. D-112 answers it with a stated size and a trigger (a few thousand people, or a thousand registrants on one event) at which the unbounded cost stops being affordable, rather than with a parameter. Inventing a default number nobody asked for is not this page's call; naming the size at which the answer would change is. The standing report of §8 and §11's half 2 is what a real number would eventually be argued from.
    • Nothing computes an expression's fingerprint (§8): refused, not deferred (F-14, D-110). Two expressions with the same meaning are two different row sets, and "you already granted exactly this set on that item" does not fall out of storage — that is accepted, not mitigated. A watered-down version (a derived fingerprint, a warning, never a refusal) is refused with it, because computing one means deciding that two expressions mean the same thing, and this module computes who is in a set, never what a string means. A fingerprint is a semantic-equality function wearing a warning badge: either it is exact, which is undecidable without evaluating both sides, or it is a hash of a normalized string, which two spellings of one set will fail to match — a warning wrong in both directions.
    • The per-item reach preview (§8) is a screen nobody has designed. PLACED means different people on different events, so the editor's expanded set must be computed for an item and say so on screen (D-102). The expanded set is a requirement (D-091), and for a bound operand it depends on an input the grant does not contain. Which item the editor picks by default — the grant's item, an event the writer chooses, the next event with registrants — is not decided anywhere.
    • WHITELISTED (§8) is not seeded, and no selector will be: there is no stored state to evaluate (F-20). The candidate readings — source = staff, promotion off the waitlist, a new column on event_registration — are not narrowed, and that is the answer rather than an evasion: an operand with no state to read resolves to nothing, and picking a meaning in order to seed a row would invent an events feature from the authorization module. The need for "these few people" arrives anyway and is served today: write grants, or a GROUP(x), or PERSON(a) + PERSON(b). The discipline stays — a row is not seeded so that a question cannot become a word in a grammar by being typed often enough.
    • PERSON(x) is a seeded row (argument_type = person); the class of bug behind it is the open item. §12 states the one count that matters — how many rows selector_type holds — cheap to check, and checked here because a registry that prose contradicts is a fiction (D-104). What is open is the class, not this operand: nothing in this module, or in this repository, compares the dotted tokens these documents write against the seeded registries they describe, so the same drift will happen again in whichever table is written next. D-104 adopts a hand-run report over the documents as the answer, and states plainly that a report nobody runs is a convention — there is no CI here to make it a guard, and no layer of this spec can tell a writer that PERSON( had no row behind it.
    • The LIST gloss, and the proposed rename of that operand to ADDED (§8): moot — there is no such operand (D-105). Neither the gloss nor the rename has a subject: LIST is not an operand of this grammar, so there is nothing to rename and nothing to explain.
    • Whether two people editing one audience is handled by a lock, a queue, or nothing (§8). Editing an audience is one expression edit, so two clerks editing one audience can collide, and a silent lost update removes somebody's access without any row recording that it happened. D-105 states the obligation — an optimistic-concurrency check or a queue — and puts it on the editor rather than on the schema; there is no membership table left to hold such a rule. Nothing in this document decides which of the two it is, and nothing detects the failure after the fact: the audit trail records the write that happened, not the one that was overwritten.
    • Whether a person merge repoints every leaf that named the absorbed person, and who tests it (§8, §11 check 2). The requirement is D-105's and is not open; what no layer can express is a constraint behind it, so the register puts it on the write path with §11 check 2 beneath it. selector_arg_id has no foreign key (D-011), so the merge reassignment table has to be told about audience_operand the way it was told about every other person-referencing table, in all five argument kinds that name an entity, and the orphan scan that would otherwise catch it is both late and blind — late because it runs nightly, blind because a merge that leaves the absorbed row in place produces no orphan at all. It is shape 3 for exactly that reason, and it is the item on the register where the failure direction is a grant that denies everybody: EVERYONE - PERSON(x) with an un-repointed x.
    • Whether the reference listing is actually cheap (§8, §10). D-103 registers the assumption: "which live grants name this audience, and at what depth" is one indexed query over the leaf rows, cheap at this organization's size, unverified at any size. It is on the save path of a screen a person is standing at, and it is load-bearing for a policy and not only for a screen: dropping exactly the compilations that embed a changed expression (D-114) needs this listing run in its reverse direction, transitively rather than one hop at a time (§10). If the import corpus's row-count estimates are wrong there is no blunt instrument to fall back on — there is nothing to invalidate for everyone at once — so what stands here is D-112's trigger and this bullet.
    • A nested audience's past reach is not reconstructable, and that is the answer (§8, Three named sets): the record of whom a grant reached is the expression (D-110, closing F-17). GROUP(x) answers "was she in it on 1 June 2024?" from its dated rows and AUDIENCE(x) does not, and that is not a gap, because the system never promised the answer — what it keeps is the words, and D-109's rule that nothing a rule names is deleted is what keeps them evaluable. What is logged as history is a rendering on a date, not a roster; a roster would store, against D-088's window, a per-person record of people who were never granted anything.
    • Whether membership belongs in grant_scope_type (§6). It is not seeded, and that is an inference from what D-097 and D-099 list rather than a ruling.
    • Whether valid_to should be mandatory for high-authority holder rows and long-lived item grants (§4, §6).
    • Polymorphic scope_id vs a grantable_item supertable (§6) — a real fork, covering selector_arg_id too.
    • How long a permission_cache entry may live (§10): there is no such table, so there is no lifetime (D-114). No TTL is being asked about, because there is no row to put one on: expires_at is not a column of §10 and ruleset_version is, as a compilation key bumped by writes to audience_operand and selector_type (F-6, D-111). Nothing is open here. The affordability question F-6 ended on is answered by D-112's stated size and trigger, and there is no rebuild job to afford.
    • Cache vs a materialized effective-permission table (§8, §10): dissolved, not decided — F-7. A rebuild of cached answers and a materialized effective_permission table are the same job with two names, which is why the pair is recorded as dissolved rather than answered — and a dissolved question is the kind that comes back if nobody writes down that it dissolved, with "history, not performance" exactly where it would come back from. What is left of the pair is the history side alone: there is no rebuild to confuse with a history table, a table of today's answers is not a record of 2011, and invariant 19 is the thing a return has to argue with.
    • Retention policy for access_log — legal input required (F-8).
    • Whether access_log needs human annotation (recommend a separate table if so).

    Settled, stated as answers. A role may not be held by a rule (F-12, D-100). An audience composes other sets through an expression whose leaves name other sets, and AUDIENCE() is the form that settled it (D-101, D-103); there is no inclusion edge table in this model — the edges are leaves (D-091). A saved rule is reusable by name only if it has a code (D-103). Permissions do not depend on membership status through any switch: membership is an operand, and the posture is opt-in per grant (D-100).
