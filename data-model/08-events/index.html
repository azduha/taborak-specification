    Data Model — Events¶

    event, event_organizer, event_registration, event_question, event_answer.

    Domain rationale: ../domain/07-events.md.

    Nothing here is provisional. This module was designed against the authorization model rather than beside it, and every hook it uses — access_grant scoped to an item, grant_scope_type, audiences and their selectors — was already in place and seeded. The tables below fill those hooks; they do not extend the model.

    Round 10 removed one thing this module was built around: an event has no owning unit (D-102). event.org_unit_id is gone, can_event() is gone, and the unit-authority rule that every event permission used to be reached through is gone. What the module uses instead is a set of selectors that bind to the event being checked, specified in §8.

    1. Why these five tables, and no event_series¶

    Table What it is
    event The occasion. A date, a registration window, an optional capacity — and no owner (§2)
    event_organizer Who is running it — an appointment on the event, not a grant (§5)
    event_registration One person's answer: attending, or not attending. Unanswered is the absence of a row
    event_question What this event asks registrants
    event_answer What one person said to one question

    No recurrence. A weekly meeting is a group — a person_group with dated member rows (D-098) — not an event (../domain/07-events.md §1). Adding event_series would mean every downstream table — registrations, capacity, presence, organizers, questions — needs a second possible home, and the feature that needed recurrence is already modelled.

    No event_status column. Visibility is the permission model; cancellation is a fact (../domain/07-events.md §10).

    2. event¶

    Fields

    Field Kind Notes
    id surrogate id Internal only
    public_id external identifier, required Unique. Generated when the event is created
    title text, required
    description text, optional The committee's own notes — internal
    public_note text, optional Shown to registrants. Separate from description, which is internal: "bring a sleeping bag and a torch" vs. the committee's own notes
    location text, optional Free text: a camp site, an address, "the usual place"
    location_detail free-form jsonb, optional {lat, lon, meeting_point, …} when known
    starts_at instant in time, required An instant, not a date. A Thursday group meets at 5pm; a camp starts on Saturday morning. The instant carries a timezone, and the timezone is the organization's, recorded rather than assumed
    ends_at instant in time, required An instant, not a date, for the same reason
    all_day boolean, required Default false. Display only — an all-day camp still has instants underneath
    registration_opens_at instant in time, optional NULL = open as soon as the event is visible. The event is visible to whoever holds event.view, which after D-102 normally includes everyone holding it at the unit — see ../domain/07-events.md §10 for what that does to the private-by-default draft. So NULL is a reasonable default and wrong for a jamboree whose sign-up should not open before the dates are fixed
    registration_closes_at instant in time, optional NULL = when the event starts. This is the "unlimited" case: registration stays open until the thing happens
    capacity integer, optional NULL = unlimited. Bed count, bus seats, fire-safety limit. Enforced as a WAITLIST threshold, not a block, and a staff registration may exceed it (../domain/07-events.md §8)
    waitlist_deadline instant in time, optional When an unpaid registration at a full event releases its place to the waitlist (§6). NULL = never releases. Only meaningful when the event has a fee AND a capacity; ignored otherwise. This is the ONE automatic transition in this module — see §6 for why it is accepted and what it costs
    fee_schedule_id reference to fee schedule, optional NULL = this event is free, which most are. Set = a fee applies; registering creates a fee_obligation (§6). The amount and currency live in fee_schedule, not here — events do not price themselves
    cancelled_at instant in time, optional Cancellation is a FACT, not a status, and this is the point where the "no status column" reasoning deliberately diverges: revoking grants would hide the cancellation from the registrants, who are exactly the people who must be told. A cancelled event stops accepting registrations and KEEPS every registration row — those rows are the record that the camp was planned and who was coming
    cancelled_by reference to person, optional Who cancelled. Set exactly when cancelled_at is set
    cancel_reason text, optional Free text, and it may be absent ("cancelled — see email")
    created_at timestamp, audit time
    created_by reference to person, optional Who created the row. Not an owner — created_by is attribution, and D-005 still holds that a permission is never derived from an identity
    updated_at timestamp, audit time, optional
    updated_by reference to person, optional
    import_batch_id reference to import batch, optional Set on imported rows

    Rules

    • ends_at is later than starts_at.
    • capacity is either absent or greater than zero.
    • When both registration_opens_at and registration_closes_at are set, the close is later than the open. When either one is absent nothing is required of the other — each is independently meaningful on its own.
    • cancelled_at and cancelled_by are set together or not at all. A cancellation has a who and a when, or neither. The reason is free text and may be absent ("cancelled — see email").
    • waitlist_deadline may be set only when both capacity and fee_schedule_id are set. A waitlist deadline is meaningless without a capacity to fill or a fee to pay, and stating this prevents a column that silently does nothing.
    • public_id is unique.
    • No column of event names a scope. There is no owner, no holding group, no creating unit, and no rule anywhere in this module that reads one (§8).

    Indexes

    • Upcoming events by starts_at, and events by registration_closes_at — both restricted to rows that are not cancelled. Every "what is happening" and "what is still open" list excludes cancelled events, so the cancelled ones are simply not in the index.

    There is no owner column¶

    ~~org_unit_id — reference to org unit, required. EXACTLY ONE owning unit, and it is never absent.~~ Deleted by D-102. The column's note used to carry the argument that forced it: a joint camp is one unit's event that another unit's children register for via an audience grant, and two owners would have created an exception to "the root may not read a sub-unit's events" shaped exactly like a joint camp, with no principled place to stop. That argument was sound while D-049 was alive. D-097 deleted the sub-units, D-049 with them, and there is nothing left for the column to protect.

    An event is an item in grant_scope_type under the code event, and nothing more. A grant at the unit reaches every event; a grant on one event reaches that event and nothing else; event.create has applies_to = unit, so writing it on an event is refused when the grant is saved, with the reason in the message (D-099).

    The deletion leaves no residue in this file, which is worth recording as a fact rather than a hope. There is no index on an owner (the lists above are the whole set), no check in §10 that reads one, no cascade, and no rule in §5 or §8 that compares one. The people connected to an event are reached through event_organizer and event_registration, which point at the event directly and never needed the owner.

    Import consequence. The one-off import owes event rows and event_registration rows and it owes no owner column — one less thing to invent a value for (D-090, D-102). It does owe the per-event seeded grant in §8, which is the residue the deletion does leave.

    No status column, and why that is not an omission¶

    Nothing is stored that can be derived. "Is this event over?" is ends_at in the past. "Is it cancelled?" is cancelled_at set. "Needs attention now" — the list an admin screen runs — is every event with cancelled_at absent and ends_at not yet past, ordered by starts_at.

    completed is derived, never stored, so there is no state to keep consistent and no job to move rows between states. Draft is not a state either: publishing is an access_grant, not an UPDATE. A status column and a permission system that both claim to answer "who may see this?" will eventually disagree, and the one that gets enforced is whoever wrote the last IF.

    One clause of the old argument went with the owner column. ~~A new event has no grants beyond its organizers, so nobody else can see it~~ — with no owner, a fresh event is visible to everybody already holding event.view at the unit, which is the normal case. Privacy is therefore an act rather than a default; see ../domain/07-events.md §10.

    Why fee_schedule_id and not an event_fee table¶

    The fee amount, currency and validity already live in fee_schedule (07-finance.md §2), which is temporal — so a 1998 camp's fee recomputes correctly from the 1998 schedule. An event_fee table would duplicate that and immediately drift. An event points at the schedule that prices it.

    3. event_organizer¶

    The absence of a valid_to is deliberate. This is a roster, not a period: you are on the list, or you are not. An organizer who drops out is removed (recorded in audit_log), because "was Jan an organizer of that camp?" must have one answer, not a set of intervals.

    Fields

    Field Kind Notes
    id surrogate id Internal only
    event_id reference to event, required The event this person is on. Deleting the event removes its organizer rows — the one cascade in this design, and guard 2 in §8 is what makes it safe
    person_id reference to person, required
    organizer_role text, optional lead, assistant, cook, driver, medic, quartermaster — free text. NOT a controlled vocabulary: every organization labels these differently, and a closed list here would be a guess of the kind D-095 refused for reason codes. (This note pointed at D-054 until D-097 deleted the unit-type vocabulary it argued about; the argument is unchanged and the living precedent for "the system does not ship somebody's vocabulary" is D-095.)
    is_primary boolean, required Default false. The person the parents are told to call. At most one per event — a uniqueness rule the schema can express, so it is a constraint and not a report (Rules, below)
    sort_order integer, required Default 0. Display order for the list. Cooks before drivers is a real preference and not something to derive
    note text, optional
    added_by reference to person, optional Who put them on the roster
    created_at timestamp, audit time

    Rules

    • One row per person per event — the (event_id, person_id) pair is unique, over all rows.
    • At most one organizer of an event has is_primary set. The rule covers every row of the event; rows where the flag is not set are unrestricted, so an event may have any number of ordinary organizers and exactly one primary.
    • Removing an organizer is a removal of the row, not the ending of a period, and audit_log is where the history of it lives. There is nothing to overlap, so there is no no-overlap rule here.

    Cascade on delete here, and nowhere else in this data model. It is justified because event_organizer is a roster of assignments on the event, not a business record: a deleted event has no organizers in the domain sense either. In practice nothing deletes an event — the deletion policy is temporal closure, and cancellation sets cancelled_at. The cascade exists so that a mistaken INSERT into a draft event can be cleaned up without leaving orphan rows, and it is the only cascade in the design. Deleting an event that has registrations is refused outright (§8, Guard 2), and the refusal belongs in the database rather than in the delete path: the reference from event_registration to event carries no cascade, so an import or a hand-written fix meets the same wall the screens do. A refusal only the screens knew about would delete the record of who was coming.

    Organizers are appointments, not grants¶

    event_organizer is the domain answer to "who is running this camp?" — the labelled, ordered list that parents see. It is deliberately not an access_grant, and D-062 is untouched by round 10 (../domain/07-events.md §5):

    • A grant has no room for organizer_role = 'cook'.
    • "Who is running this camp?" should not be answered by reading the permission table.
    • Revoking a grant to remove a cook would also revoke their ability to see the event at all, which is not what "they are no longer cooking" means.

    Authority to act on the event does not come from this table. It comes from a live allow — at the unit, which reaches this event, or on this event — and never from a role or an appointment conferring anything by itself (D-005).

    What did change is what this table is now aimed at. It is the extension of the selector ORGANIZERS, so a grant can name the people running an event without any of them being granted anything by being listed (D-102). An operand is a set, not a grant — the same sentence data-model/05 §8 repeats for named sets generally, and it is why D-062 survives the deletion of the mechanism that used to make organizers matter. See §8 for the seeded grant that aims at this table.

    4. event_registration¶

    One row per person per event. Two stored values; "unanswered" is the absence of a row.

    Fields

    Field Kind Notes
    id surrogate id Internal only
    event_id reference to event, required
    person_id reference to person, required person_id, NOT membership_id — the reasoning unit_participation gave and D-098 carried over to person_group_member, and here it is stronger. An event's roster must survive independently of how membership is recorded, and imported historical attendance has no membership row to point at. A 1998 camp roster is participation, and an inferred open-ended membership would put every one of those children inside MEMBERS today — see the note below
    response enum: attending / not_attending, required TWO values. unanswered is written NOWHERE. It is the absence of a row, so "who has not replied yet?" is a subtraction, not a stored state (../domain/07-events.md §3). Returning someone to unanswered deletes the row, which audit_log records — the honest act, and the one that leaves least behind
    responded_at timestamp, required Default now. When the ANSWER was given, which may differ from when it was recorded. A phone call on Tuesday entered on Thursday has two dates and both matter
    source enum: self / staff / guardian / import, required Default self. How this person got here, and the audit answer to "how did they get in?". staff is written by a person holding event.register_other, and it bypasses the registration window and the waitlist deliberately (§5, Guard 1): whoever has the permission may register anyone. guardian is acting-under-guardianship; the acting person is in access_log
    registered_by reference to person, optional NULL when source is self. Set otherwise: which organizer, or which guardian
    is_waitlisted boolean, required Default false
    waitlist_position integer, optional Order within the waitlist. Assigned on insert when the event is at capacity, and rewritten on promotion. See §5
    is_confirmed boolean, required Default false. Registration is not the same as a held place. An event with NO fee confirms immediately on registration; an event WITH a fee confirms on payment (§6). This is the "payment confirms the place" rule, and it is the only place in this module where money changes a registration's meaning
    confirmed_at instant in time, optional Set exactly when is_confirmed is true
    was_present boolean, three-valued NULL = not yet marked — no register was taken. true = turned up. false = marked absent. THREE-VALUED ON PURPOSE: "we did not take a register" and "we took one and they were not there" are different facts, and only one is a safeguarding signal. For a camp this is the record of who was actually in the organization's care, and it cannot be reconstructed afterwards (§9). It is deliberately not the basis of any selector — PRESENT(<event>) is refused, and why is in §8
    presence_marked_by reference to person, optional The person who took the register. Held by whoever has been allowed event.presence.mark — deliberately a separate code from event.manage_participants, not a rung beneath it: after D-099 there is no ladder for one permission to sit below another, and that is the stronger form of the same protection. The volunteer at the door is not also the person who can delete a child from the roster, because they were granted one code and not the other
    presence_marked_at instant in time, optional When the register was taken
    fee_obligation_id reference to fee obligation, optional Set when the event has a fee_schedule and this registration created an obligation. The reverse pointer from fee_obligation.event_registration_id also exists (§6) — both directions, because each is asked a different question: "what does this person owe for this camp?" and "what is this obligation for?"
    created_at timestamp, audit time
    updated_at timestamp, audit time, optional
    updated_by reference to person, optional
    import_batch_id reference to import batch, optional Set on imported rows

    Rules

    • One row per person per event, full stop — the (event_id, person_id) pair is unique over all rows. This is what makes "unanswered = absence" work: there is exactly one place an answer could live.
    • A not_attending row has is_waitlisted false and is_confirmed false. A decline is not waitlisted and not confirmed; otherwise a "no" could hold a place on the waitlist, which is nonsense.
    • is_confirmed is true exactly when confirmed_at is set.
    • is_waitlisted is true exactly when waitlist_position is set.
    • Presence is marked all together or not at all: was_present, presence_marked_by and presence_marked_at are either all present or all absent, and was_present absent is the same condition as the other two absent. A partially-set trio is a bug, not a state.

    Indexes

    • The set the capacity test counts — an event's registrations whose response is attending and which are not waitlisted. Capacity is compared against exactly this set (§5), and the other registrations of an event must not slow it down. This index is also exactly the extension of the PLACED selector (§8), so the audience the capacity rule counts and the audience a grant may name are the same rows, served by the same index — no second index and no second definition.
    • An event's waitlist in waitlist_position order, restricted to waitlisted rows — which is the extension of ON_WAITLIST (§8).
    • An event's registrations by was_present, restricted to rows where presence has been marked at all. Note that this index serves a report (§9) and no selector: the rows it is missing are precisely the unmarked ones, and that is the reason PRESENT is refused.

    Why person_id, not membership_id¶

    The argument unit_participation made (03-membership.md §5, before D-097 deleted it) and D-098 transferred to person_group_member, and it is stronger here. An imported 1998 camp roster names children who have no membership row to point at. With the corpus being large and number-bearing (D-056), linking to membership would make those rows unrepresentable.

    And the harm moved rather than went away. It used to be argued through the membership gate, which made a 1998 camper a current member with authority today. The gate is deleted (D-100), and the same harm now runs through the selector: MEMBERS is evaluated live on the checked date, so an inferred open-ended membership puts every one of those children inside MEMBERS today, and every live grant whose expression contains MEMBERS reaches them. An open-ended row is the dangerous object under both models; only the mechanism changed.

    The trade-off, stated: no database constraint can enforce "only members may register", and none is wanted — eligibility is capability (../domain/07-events.md §4), and capability is a grant, not a membership row.

    5. Capacity and the waitlist¶

    Capacity is a threshold, not a block. Registering for a full event succeeds and produces a waitlisted row.

    Is this event at capacity? The question is asked of one event and answered only from the registrations it has: count its attending, non-waitlisted registrations — its PLACED set (§8) — and compare that count with its capacity. An event with no capacity is never full — with no capacity set there is nothing to reach, and the answer is no.

    The placing rule runs before the row is written, once per row, on every insert, so that EVERY insert path obeys it — self-service, staff, guardian and import alike. Application-level placement would let one of the four paths forget, and the forgotten one would be the one that matters. The order of these steps is a rule: the decline branch settles all four flags and ends the rule, and the capacity test is counted before confirmation is decided, because confirmation is a property of the place the earlier steps gave the row.

    1. Read the event the registration names.
    2. A decline never occupies a place. If response is not attending, set is_waitlisted false and waitlist_position absent, set is_confirmed false and confirmed_at absent, and stop here — none of what follows applies to a "no".
    3. Waitlisting is a SELF-SERVICE outcome. Waitlist the row when all three of these hold: source is self; the event has a capacity; and the event's attending, non-waitlisted registrations already number at least that capacity. Then set is_waitlisted true and waitlist_position to one past the highest position already on that event's waitlist — 1 when the waitlist is empty. If any of the three fails, set is_waitlisted false and waitlist_position absent. A staff registration is admitted even past capacity: the organizer who knows there are two spare tents is not to be blocked by a number they cannot edit mid-camp (../domain/07-events.md §8, D-065). The overrun is permitted, attributed, and REPORTED (§10, check 5).
    4. Confirmation: immediate when there is no fee to wait for. If the event has no fee_schedule_id, set is_confirmed true and confirmed_at to now. Otherwise set is_confirmed false and confirmed_at absent — §6, payment confirms the place.
    5. Write the row carrying those flags.

    The rule runs on insert only; a later edit of the row does not re-run it. Promotion and the release below write the same flags deliberately.

    The source = 'self' disjunct is the whole of "organizers may register anyone", made mechanical. Removing it silently reverses the answer: every staff registration would be waitlisted behind self-service ones, and the leader adding a child on the day would be told the camp is full when they can see two spare beds. Note what this rule does not consult: not a level, not a role, and since D-102 not an owning unit. source is a stored fact written by whoever holds event.register_other, and the capacity rule reads the fact.

    Promotion, which is a deliberate act¶

    Promotion is not automatic — no trigger, no job. An organizer picks someone from the waitlist:

    1. Take the one registration this person holds at this event — the pair names exactly one row (§4).
    2. Clear the waitlist on it: is_waitlisted false, waitlist_position absent.
    3. Set is_confirmed and confirmed_at by exactly the test the placing rule uses: confirmed now when the event has no fee_schedule_id, unconfirmed with no confirmed_at when it has one.

    The promotion deliberately bypasses the capacity test: the whole point of promoting is that a place has freed up, and re-testing would just fail again.

    Promotion writes the same two flags the placing rule would have, so a promoted registration and an admitted one are indistinguishable afterwards — which is correct, because the difference between them is when, not what.

    When an unpaid registration releases its place¶

    If waitlist_deadline is set, an unpaid registration at a full event releases its place to the waitlist at that moment. This is the one automatic transition in this module, and it is recorded as such. The release is scoped as narrowly as the rule can be: only at a full event, only with a fee configured, only past the deadline, only unpaid, and never a staff registration (which is admitted by hand and by a human who can see the roster).

    1. Take every registration that is attending, not already waitlisted, source self, and not confirmed.
    2. Keep only those whose event has a fee_schedule_id, has a waitlist_deadline, has that deadline already past, and is not cancelled.
    3. Move each one onto the waitlist: is_waitlisted true, waitlist_position one past the highest position already on that event's waitlist — 1 when the waitlist is empty.
    4. Take the place back: is_confirmed false, confirmed_at absent.

    Why this is accepted despite the design's habit of avoiding automatic transitions. The design has spent real effort keeping state changes deliberate (D-023, D-040), and "payment confirms the place" reintroduces one. It is a deadline, not a sweep: it applies to a narrow conjunction, it is opt-in per event (waitlist_deadline is NULL by default, so most events never run it), and the state it produces is visible — the person is on the waitlist, not silently deleted. The alternative, no deadline at all, means a place is held forever by someone who never paid, which is worse.

    6. Payments and confirmation¶

    Registering creates a fee obligation; payment confirms the place.

    Creating the obligation runs after the registration row is written, so that the registration has an id to be pointed at. The order is a rule: the obligation cannot be created before the registration it belongs to exists, and the registration's fee_obligation_id cannot be written before the obligation does.

    1. Read the event the registration is for.
    2. If the event has no fee_schedule_id, or the registration is not attending, stop — a free event owes nothing, and a place someone declined owes nothing.
    3. Read the fee schedule the event points at.
    4. Create one fee_obligation for this registration, carrying: person_id taken from the registration; event_registration_id set to the registration; the event's fee_schedule_id; the event's title as the description; the event's start and end as the obligation's period; the schedule's amount and currency; and a due date of the event's waitlist_deadline, falling back to the event's starts_at when it has none.
    5. Write the new obligation's id into the registration's fee_obligation_id.

    The pointer that had to be restored. D-057 removed the household arm from the exactly-one rule over fee_obligation's target columns, leaving two of them (membership or membership request, never both). An event fee needs an arm back — and this time it is a real arm with data behind it, not the dormant hedge the household column was.

    The arm lives in fee_obligation and is stated there in full (07-finance.md §2): exactly one of membership_id, membership_request_id and event_registration_id is set on every obligation. Still exactly one, not "at most three" — every obligation is for exactly one thing: a membership period, a membership request, or one person's place at one event. The per-person choice is deliberate, because the fee is flat and per person (D-037) and a family price would need the household grouping designed again first. Obligations carrying the event arm are indexed on event_registration_id, restricted to the rows where it is set.

    Confirming on payment¶

    confirm_event_place(obligation) is called by the payment flow. It is not a rule on fee_obligation's status — the payment module owns that transition, and a rule there would make every fee, membership or event alike, confirm an event place.

    1. Take the obligation the call names.
    2. Follow its event_registration_id to the registration it pays for.
    3. Confirm that registration only when it is attending and not waitlisted — in the selector vocabulary, only when it is PLACED (§8); a waitlisted person stays waiting until promoted (§5), so paying does not by itself place them.
    4. Confirming means setting is_confirmed true and confirmed_at to now.

    confirm_event_place is deliberately an operation the finance module calls, not a rule hanging off fee_obligation's status change. The argument is about ownership and does not depend on where the code lives: anything that fires because a fee became paid fires for membership fees and event fees alike, and "the fee is paid" means something different in each case: a membership activates (D-040), an event place confirms. Two transitions, two owners.

    Free events confirm immediately — see the placing rule in §5. An event with no fee_schedule_id has nothing to wait for, and requiring "confirmation" for a free hike would be a state with no meaning.

    7. event_question and event_answer¶

    Fields — event_question

    Field Kind Notes
    id surrogate id Internal only
    event_id reference to event, required The event that asks it. A question is defined per event, never shared (§7)
    label text, required Tent preference, Dietary requirements
    help_text text, optional
    position integer, required Default 0. Display order
    data_type enum: text / long_text / integer / decimal / bool / date / choice / multichoice, required
    choices list of text, optional For choice and multichoice only. An ordered list on the question rather than a child table: the options are a property of the question, they are ordered, and they are never referenced by anything else
    is_required boolean, required Default false. The person REGISTERING must answer. Not a gate on registration itself: a form that blocks sign-up is a form nobody completes, and the organizer would rather have the registration and chase the answer
    applies_to enum: attendee / organizer / all, required Default attendee. Who is asked. Organizers may be asked things attendees are not (T-shirt size for the leaders' shirts) and vice versa
    valid_from date, required Default today
    valid_to date, optional NULL = still asked. A question can be retired after people have answered it. Answers survive (an answer is never removed with its question), because "what did they say?" must outlive "do we still ask this?"
    created_at timestamp, audit time
    created_by reference to person, optional

    Rules — event_question

    • choices is present exactly when data_type is choice or multichoice, and never otherwise. Stated as an equivalence rather than a one-way requirement so that a text question cannot carry a stray choices list that the UI might honour.
    • valid_to is either absent or later than valid_from.

    Fields — event_answer

    Field Kind Notes
    id surrogate id Internal only
    question_id reference to event question, required
    person_id reference to person, required Who ANSWERED — for a child, the child. The person who submitted on their behalf is in access_log and in registered_by, not here. Answers are about the person the question concerns
    value free-form jsonb, required Typed by question.data_type. One loose value rather than a column per type: the alternative is eight nullable columns only one of which is ever set, which is the shape 01-identity.md §6 rejected for person_contact
    answered_at timestamp, audit time Default now
    answered_by reference to person, optional

    Rules — event_answer

    • One answer per question per person — the (question_id, person_id) pair is unique over all rows.
    • An answer is not removed when its question is retired: there is no delete rule from event_question to event_answer.

    Answers as rows, not JSONB on the registration¶

    This is the choice that makes the feature worth having. The whole reason to collect "dietary requirements" is to be able to answer "who needs a gluten-free meal, and how many?" — and that is a question the data must answer directly: for one event and one question, take every answer given to it, group the answers by the value given, and count each group, largest group first.

    With answers stored as a JSONB blob on the registration, that becomes JSON traversal, an index that does not help, and a report nobody writes. The cost is one row per answer — which is exactly the number of things the organization must act on.

    Reusable question libraries were considered and rejected¶

    A shared pool of question definitions — question_code, assigned to events — is structurally the requirement machinery removed in D-044. It earns its keep only when the same question must mean the same thing across events, and tent preference does not: what one camp asks and what another needs are allowed to differ. Per-event definitions keep them from having to agree, and avoid reviving a removed pattern for a benefit nobody asked for.

    Health facts, and the discipline this requires¶

    An event form is how the people running an event find out what they need to know about the people who came. It used to be the only way. D-085 ended that, and the guidance below is still worth reading as a warning rather than a nicety — anything a form asks is read by whoever runs that event, and the number of such people is decided by whoever creates the event (D-061, ../domain/07-events.md §12).

    Round 10 moved that sentence from the resolver into a row. "Read by whoever runs that event" is now a seeded grant — event.answer.view on the event, aimed at ORGANIZERS (§8). That makes the warning checkable in a way it was not before: the number of people who can read an event's answers is a grant plus the roster in §3, and both are readable.

    This sentence's reason has now been rewritten twice, and the second rewriting killed the claim. It began as "the dependent.* namespace is unreachable by unit leaders"; D-074 deleted that namespace and the claim survived on a better reason — no event.* permission includes the medical record, and no wildcard is left to sweep it in (D-068). Both halves are now gone: there is no medical record (D-083), and the facts that would have been in one are attributes on the person, which a person holding person.view at the unit can read — and after D-097 the unit is the only scope there is, so that grant reads everyone's (09-attributes §4). A claim that had outlived two of its reasons should not be repaired a third time; it is stated as what is now true:

    • The form is no longer the ceiling on what an organizer may know. An organizer who holds person.view may already have read the allergy. Any document implying the contrary was quietly making a privacy promise the model does not keep.
    • What the form is for changed accordingly — it asks now, about this event, of a person who may not be in the system at all, and its answer carries a date. That is a genuine property the record does not have: a recorded attribute says what somebody believed, once, at no particular time. Whether the two should meet at all is AT-1, and the recommendation there is a confirmation pass rather than a silent prefill, precisely because a stale health fact that arrives looking authoritative is worse data than an asked question.
    • Nothing in the data model distinguishes a preference from a condition, and now nothing could: D-083 refused the category. "Vegetarian" and "coeliac" are both data_type = 'text' in event_answer.value, so the line is what an organizer types into label — form design guidance, not an enforced constraint:
    Belongs on an event form Belongs on the person, as an attribute
    What the organizers need on the day, for this event Diagnoses, medication, allergies, conditions
    What a visitor who is not in the system must supply Anything already recorded, curable and audited on the record
    T-shirt size for a camp that is ordering shirts now Anything whose value outlives the event that asked

    Asking a returning camper to restate a recorded allergy at every event is not a privacy measure; it is the same fact, fresher in one table and unmanaged in it. The honest reading of this section is that the event answer is where a health fact lands when the organization has not collected it properly — and the fix is the record plus a confirmation pass, not a cleverer form.

    Open: the retention policy for answers. A dietary answer citing a medical condition is data of exactly the same class as everything else the organization holds about a person — D-083 settled that there is no specially-sensitive category, not that this data is insignificant — and there is no policy for how long answers survive their event. See EV-2, which notes that until it is answered the weakest-protected copy of a health fact is the freshest one.

    8. Projections and guards¶

    The unit-authority rule, and can_event() — both deleted¶

    ~~A permission is satisfied at ('event', E) if it is satisfied at the event's owning unit ('org_unit', E.org_unit_id) AND the event's owner is that same unit.~~ Withdrawn by D-102, which deleted event.org_unit_id (§2) and with it the whole rule, together with D-063's artifact-and-child distinction. can_event(person, permission_code, event, at) is deleted; every event check goes through the ordinary can() and nothing else.

    Who enforces it now — can(), with no event-shaped clause in it. The resolver matches scope exactly, exactly as before, and the gap D-063 was written to close cannot open: the only non-item scope is the unit, and a grant at the unit reaches every item of every type (D-099). The person whose job is to run the organization's camps passes a check at ('event', 42) because their allow is at the unit, not because anything tested the event.

    D-063's reasoning, kept because the problem it named is still a problem. The old design refused to let authority inherit from a body down to that body's events, and bought a narrow rule instead of a wide one, on the grounds that inheritance's blast radius grows with every restructure while an owner column's does not. Both halves of that pair are gone: there are no bodies and no restructures (D-097), so there is nothing left to keep narrow. What replaced the distinction is not inheritance and not a test — it is the absence of an intermediate scope. Between the unit and an event there is now nothing to inherit through, which is the same outcome D-063 was reaching for by way of a rule.

    D-063's two-way door, spent. It promised that "deleting the second can() call is the whole change, and it needs no data migration", because nothing had been written to access_grant to make the rule work. Round 10 collected on that: deleting the rule is the whole change and needed no migration. The door back is narrower now — an owner column, a resolver tier that reads it, and the checks this section deletes — and the bound selectors below would survive it unchanged, because an ownership grant and a bound operand answer different questions.

    Selectors that bind to an event¶

    Six sets describe the people connected to an event, and each is a selector that binds to the item being checked — written with no argument inside an item-scope grant, and with an explicit event in every other context. They are seeded rows of selector_type, the registry of data-model/05 §8, and that registry is what makes the two write-path rules below checkable rather than a matter of tact (D-101, D-102).

    The four attendance tiers, defined over event_registration columns and nothing else:

    Operand Definition Read it as
    ATTENDED response is attending said yes to this event
    PLACED response is attending and is_waitlisted is false holds a place — the capacity set (§5)
    CONFIRMED PLACED and is_confirmed is true the place is paid for, or the event was free
    ON_WAITLIST response is attending and is_waitlisted is true waiting for a place

    These are definitions, not four new ideas, and their shape is arithmetic on two existing columns: CONFIRMED ⊆ PLACED, PLACED and ON_WAITLIST partition ATTENDED, and a not_attending row is in none of them. Nothing is a level and nothing orders anything else; CONFIRMED is not "more" than ON_WAITLIST, it is a different conjunction. The extension of PLACED is the set §5 counts against capacity, and the same partial index serves both (§4).

    ORGANIZERS is the fifth, and its definition is the roster in §3 — the labelled, ordered, domain answer to "who runs this", evaluated over event_organizer rows for the event checked. There is no sixth, and this page printed one until round 13. The GUARDIANS that sat in that sentence was never an operand at all, in either spelling: a guardian's authority is a right_level ∈ none | view | write held over a child, read off the guardianship row when the check is about someone other than the actor, and it is not a set that the expression language resolves (D-113, D-074). Counting it alongside these five was the error, not a narrower way of stating the channel — which is why the paragraph below already called PRESENT the obvious sixth.

    PRESENT(<event>) is refused. An operand over was_present is the obvious sixth attendance tier and it is not available, and the reason is the failure direction: was_present is NULL until somebody takes a register, so a grant aimed at PRESENT would revoke a child's access to their own camp photos because a volunteer forgot to tick a box. The column is a safeguarding signal and is three-valued on purpose (D-067); keeping it out of the selector language is what keeps it meaning "a person recorded this" rather than "this is who may see things". Where presence is needed it is needed as a report (§9), and the report is honest about the rows it does not have.

    WHITELISTED does not exist. There is no stored state to name: the nearest facts are source = 'staff' (an organizer entered them) and promotion off the waitlist. Until the organization decides which of those it means, or adds a column, the operand is not available and the name is not reserved (§11).

    Two binding rules, both refused when the grant is saved, both naming the operand in the message:

    1. A bound (argument-less) operand is legal only on an item-scope grant. At the unit there is no item for it to bind to, so a grant at the unit whose expression names PLACED, ATTENDED, CONFIRMED, ON_WAITLIST or ORGANIZERS is refused. The explicit form (PLACED(<event>)) remains legal at the unit, and it means the same words with the event written down — which is the difference between the two, not an accident of parsing.
    2. A bound operand is legal only on a matching item type. PLACED on a person_group grant is refused, because that item is not an event. This is selector_type.argument_type checked against grant_scope_type at the write — which is the reason D-101's registry is doing real work and not merely tidying a table.

    A consequence of rule 1 worth naming for whoever builds the editor: an audience is a stored row and a grant is a different stored row, so an audience whose expression contains a bound operand is perfectly storable and simply cannot be aimed at a unit-scope grant. The refusal lands on the grant, where D-102 puts it, and the audience browser should show which scopes an expression is usable at rather than letting the save discover it (../domain/07-events.md §7).

    The seeded grant: event.answer.view on an event to ORGANIZERS. This is where D-061's "answers are read by that event's organizers" now lives — a row in access_grant, not a clause in the resolver, which is the same move D-102 made to the whole of unit authority over an event. It is aimed at a set, so it does not contradict D-062 and does not make event_organizer a grant table: adding a cook to the roster changes a set, and the grant keeps pointing at the set. The registered spelling of the code is the catalog's event.answer.view, singular answer, which D-102 now uses too — it wrote event.answers.view while the entry was new, and the two spellings were one code, not two.

    Assumption: a grant's scope is the unit or exactly one item, and a bound operand is legal only on an item-scope grant, so the seeded grant cannot be one row for every event. This module reads it as a seed template instantiated by the event-creation path, which writes one item-scope grant on each new event; the one-off import owes the same row for every event it writes, or an imported camp's organizers cannot read that camp's answers. D-102 does not say who writes the row. Integrity check 1 in §10 is the net.

    The preview requirement this creates. "Who does this grant reach?" stops being a property of a grant row once an operand binds: PLACED is different people on different events. The editor must therefore compute the expansion for an item and name the item it computed against, and ~~the cache key for a bound operand must include the item~~ — the answer cache that had a key is deleted (D-114), but the rule survives it at the layer below: the item is bound at resolution, so nothing expanded while computing one item may be reused for another. Stated as a requirement in ../domain/07-events.md §7. That expansion is not capped or deferred, and the ground is now stated rather than assumed: a few dozen registrants on a typical event and a big camp on the order of two hundred is a preview nobody feels — a size stated, not measured, with a named trigger to reopen it (D-112).

    A write to event_registration is not a ruleset write — and since D-114 that buys it no staleness whatsoever. ~~There is one cache policy and three triggers — rebuilt nightly in full, immediately on any write to the ruleset, and on explicit request — with no per-entry TTL and no invalidation table to get right (D-111). The ruleset is the grant and expression rows, the permission registry, the guardianship rows, role_holder and person_group_member; event_registration is not in it. So marking a register, confirming a place, or promoting somebody off the waitlist changes who is in ATTENDED, PLACED, CONFIRMED and ON_WAITLIST and rebuilds nothing: a cached answer behind those four tiers may be up to one night stale, by design. This is the module where an implementer would most confidently assume the opposite, so it is stated here rather than only in the authorization page. What stays immediate is everything a person actually does to authority — revoke, deny, close a grant period, end an assignment — because every one of those is a ruleset write.~~

    What is true now: marking a register, confirming a place, flipping is_confirmed or promoting somebody off the waitlist changes who is in ATTENDED, PLACED, CONFIRMED and ON_WAITLIST, and the change is visible on the next check — the one after the write, with no job in between — because a check resolves the expression against live rows and there is no cached answer left to sit behind the roster (D-114). The same is true of ORGANIZERS, which reads the organizer rows and not the registration table at all: five bound operands, five live reads, and a birthday crossing OLDER(n) moves an answer on exactly the same footing as a registration write does. Immediacy here is by construction, not by policy: nothing maps a person to an answer anywhere in the schema, so there is no row that could be a night old. And this module was right to be uneasy about the paragraph above. Four tiers computed from four registration tables, with the boundary of what counts drawn in a different file from the read path it had to describe, is precisely the shape that made the cache untenable — the deletion this page reports arrived because lists like that one omitted membership while membership.terminate ⛔ was the most safeguarding-shaped write in the catalog. What survives of the old vocabulary, said precisely: a registration write is still not a ruleset write, now in the narrowed sense that it changes no rule's text, and ruleset_version — which keys a compiled expression, not an answer — is bumped by audience_operand and selector_type alone, so a registration write is not a ruleset write at all now, in the only sense the phrase still has. "Not a ruleset write" no longer buys a night of staleness; it says which two-table bump set you are not in, and nothing more. And the rule whose mechanism just went has to say who enforces it now (D-081), which is the question this paragraph would otherwise leave hanging: nobody enforces it, because there is nothing left to invalidate. The old sentence's job — "a registration change reaches an answer" — is now done by the read path itself, and a page cannot opt out of a read path the way it can forget to add a row to a list.

    Guards¶

    Guard 1 — the registration window. No registration row may be created for an event whose window does not admit it. The guard runs inside the transaction that inserts the row, on every insert path — and since there is nothing left to attach it to, that coverage is now a requirement on the paths rather than a property the database supplies for them. Steps 4 and 5 read the event's own dates and step 2 exempts a source value, so no constraint states this rule and no report would catch a violation the way a window violation should be caught: at the write. The order is a rule: "there is no such event" must be settled before anything reads the event's dates, and the staff carve-out must be answered before the checks it overrides.

    1. Read the event the registration names. If there is no such event, refuse the row — a registration cannot name an event that does not exist.
    2. If source is staff, admit the row and stop here. Staff may always register, including at a cancelled event (to record who had been coming) — they are acting deliberately and are attributed.
    3. Otherwise refuse the row if the event is cancelled (cancelled_at is set).
    4. Refuse it if registration_opens_at is set and has not yet arrived.
    5. Refuse it if the effective close has passed — registration_closes_at, or starts_at when registration_closes_at is absent. This is where "NULL = open until the event starts" is enforced.
    6. Admit the row.

    Guard 2 — an event with registrations cannot be deleted. Deleting an event is refused as soon as the event has any registration row at all, and the refusal says what to do instead: cancel it (set cancelled_at) so the record of who was coming survives. Cancellation is the mechanism.

    Guard 2 is what makes the cascade in §3 safe. Organizers cascade when an event is deleted — but an event that anyone registered for cannot be deleted at all. So the cascade can only ever fire on a draft with no registrations, which is the only case where losing the roster is harmless.

    9. The three queries that matter¶

    Who has not replied yet?¶

    "Unanswered" is a subtraction (../domain/07-events.md §3). The subtrahend is who the event is open to — which, for an open event, is an audience.

    The question asked of one camp is: every person who may register for it and has not answered. The audience is the eligible set, the registration table is the answered set, and the answer is the difference between them, listed by preferred name. What makes the question answerable at all:

    • The eligible set is evaluated, not stored: it is the people named by the live allow grants of event.register_self — at the unit, which reaches this event, or on this event — through their audiences, assessed as of the day the question is asked, not as of the day the grant was written. A child who joined a group last week is on this list; a child who has left is not.
    • Only live allows count, and a person against whom a live deny of the same code applies is not eligible however many allows reach them — deny is absolute, and an eligibility list that ignored it would chase people who were deliberately excluded (D-013).
    • Where the grant's expression contains a bound operand, the eligible set is computed against this event, which is the only thing it can mean (§8).
    • The answered set is one row per person at most (§4), so the subtraction cannot leave the same person on the list twice.
    • People who have been merged away are excluded, so a tombstone never turns up on a list somebody is being asked to chase.

    This is the query that would be impossible if unanswered were a stored value, because the eligible set — an audience, evaluated as a rule — is what defines the question. Storing "unanswered" rows would mean enumerating an audience into rows, and re-enumerating whenever a child joins a group.

    Who is actually coming?¶

    Four numbers about one event, in one answer, all counted over that event's attending registrations: how many are not waitlisted (coming), how many are waitlisted (waiting), how many are unconfirmed and not waitlisted (holding a place without having paid), and the event's capacity. An event with no registrations still has to produce the row, with zeros.

    The four numbers an organizer needs, in one row: coming, waiting, holding a place without having paid, and the limit. attending > capacity is the overrun, and it is visible here rather than prevented (§10 check 5).

    The first two of the four are PLACED and ON_WAITLIST counted rather than listed, and the third is PLACED minus CONFIRMED. The selector definitions in §8 and the counts here are one set of facts stated twice on purpose: the screen and the grant must not be able to disagree about who "coming" means.

    Who was actually there?¶

    For one camp, the attending registrations listed with each person's preferred name, birth date and was_present, with the unmarked listed first — the unmarked sort ahead of both a mark and an absence recorded as false, because the unmarked are the work remaining. This is the camp roster as a safeguarding record, not a plan.

    NULLS FIRST puts the unmarked at the top, which is the work remaining. Once every row is true or false, this is the answer to "who was in the organization's care at that camp" — and it is the reason was_present is three-valued rather than a boolean defaulting to false.

    This report has no selector twin, and that is the point. Nothing in the selector language computes over was_present, so no grant can reach fewer people because the register was never taken. §8 states the refusal; this query is the reason it matters.

    10. Integrity checks¶

    Invariants to verify

    1. A bound selector on a grant that cannot bind it. Counts live grants whose expression contains ATTENDED, PLACED, CONFIRMED, ON_WAITLIST or ORGANIZERS in argument-less form and whose scope is the unit, or whose scope is an item of a type other than the operand's argument_type. Both rules are refused on the write path (§8), so a non-zero result is evidence about the code, not the data: somebody added a path that saves a grant without going through the check, and a grant like this resolves to the empty set and silently authorizes nobody.
    2. An event whose organizers hold no seeded answer-view grant. Counts non-cancelled events that have at least one event_organizer row and no live allow of event.answer.view on that event aimed at ORGANIZERS. The seeded grant is written by the code that creates the event (§8), so the failure shape is the one check 10 knows well: an event imported or created by a path that forgot, where the organizers cannot read the answers of the camp they are running, and every row they left behind is individually correct.
    3. An event with no organizer. Counts events that are neither cancelled nor already begun and have no event_organizer row at all — an event nobody is running: either abandoned mid-setup, or a data-entry error. Not a rule on write, because an event is legitimately created before its organizers are named.
    4. A registration held by a person who has been merged away. Counts registrations whose person carries a merge pointer. The merge should have repointed them; a non-zero result catches the ones it missed.
    5. An event running over its stated capacity. Counts, for each non-cancelled event that has a capacity, its PLACED registrations, and reports the events where that count exceeds the capacity. PERMITTED — a staff registration may exceed deliberately (../domain/07-events.md §8) — so this is a report, not an error. A pattern of overruns means the capacity numbers are wrong, not that the rule is.
    6. An unpaid registration holding a place past the waitlist deadline. Counts attending, non-waitlisted registrations on a non-cancelled event whose waitlist_deadline has passed and whose fee obligation stands at unpaid, partially_paid or overdue. It should be empty once the release in §5 has run — a non-empty result means the job is not running.
    7. An answer to a question the person was never registered for. Counts answers whose person has no registration for the event that owns the question. Either the registration was deleted, or the answer was written against the wrong person.

    8. Presence marked on a registration that declined. Counts not_attending registrations whose was_present is not absent. Contradictory: you cannot have been present at a thing you said you were not attending. Nothing above forbids the combination, so this is a written prohibition and a check rather than a guard — a prohibition nobody runs is a convention, not a guarantee.

    9. A registration outside its event's registration window. Counts registrations whose registered_at falls before the window opens or after it closes, excluding the ones an organizer recorded deliberately (source = 'staff', whose window is the event's own period). Guard 1 in §8 is supposed to make the first two shapes impossible, and there is no constraint behind that guard — a window spans two columns of two tables, so the check runs inside the writing transaction or nowhere (F-10 shape 3). A non-zero result is therefore evidence about the code, not the data: someone added a second path that places a registration.

    10. A fee-bearing event with registrations and no obligations. Counts non-cancelled events that require a fee and have at least one registration, where no fee_obligation exists for some of those registrations. The obligation is created by the code that places the registration (§6); there is no rule attached to the registration row that would create it, so a path that forgets produces a person with a confirmed place and no bill — invisible to every check here, because every row it left behind is individually correct. Money-versus-roster reconciliation (§6) is the same discovery arriving later and more expensively; this is the version worth running nightly.

    Checks 1, 2 and 10 are the same shape and should be read as one warning. Each tests whether a piece of code that nothing else depends on actually ran: the grant save, the event creation, the placing rule. Each will read empty on correct data and each is the kind of bug that a schema change never surfaces, because every row a forgotten step leaves behind is individually valid.

    Check 5 is the important one to read correctly. It will produce rows, and that is not a failure — exceeding capacity is a permitted, attributed act (../domain/07-events.md §8). What the report is for is the pattern: an event that overruns every year has a capacity number that is wrong, and the fix is to change the number rather than to start refusing people.

    Numbering note: checks 1 and 2 were rewritten in place rather than dropped, and 3–10 keep the numbers other files cite them by.

    11. Open issues¶

    Tracked in ../open-questions.md under G. Events.

    • ~~The age ceiling on an open event.~~ Settled: there is none (D-070). No min_age/max_age on event, no age branch anywhere in the registration path. If it is ever revisited the shape is a new seeded selector operand, not a column on the row.
    • ~~Whether event.manage_participants should split.~~ It did, into event.presence.mark — no longer "a level lower", because there are no levels, but a separate code, which is the same protection stated in the only vocabulary D-099 leaves (§4, EV-5).
    • What else should be seeded to ORGANIZERS. D-102 seeds event.answer.view and nothing else, so an organizer who holds no unit-scope grant can read the answers of a camp they are running and can do nothing else at it. Whether that is the intended shape or an omission is not settled, and this module has not seeded more on its own initiative (§3, §8).
    • Who writes the per-event seeded grant. Read as a template the creation path and the import both instantiate; D-102 does not say (§8, check 2).
    • WHITELISTED. No stored state to name, so no operand and no reserved name (§8).
    • Retention of event_answer. Answers end with the event and there is no policy saying when (§7). This used to be argued from the answer being health data, which D-083 left without a referent: it is personal data, which makes the question ordinary rather than answered — and sharper, since the same sentence recorded as a person_attribute follows a different retention rule on purpose (EV-2).
    • Cancelled events and fees. Cancelling keeps the registrations. Whether it releases the obligations, refunds them, or neither is the finance module's decision (§6). That decision has since been taken for events (D-076): cancelling voids the outstanding requests and money that already arrived waits in the unmatched queue (07-finance.md §2b).
    • was_present as a safeguarding record. Whether presence needs its own retention or its own permission, given what it is (§9 of the domain doc). D-102's refusal of PRESENT makes the second half of that question sharper: presence now governs nothing about access, which is either why it needs no permission of its own or why its retention is all that is left.
    • Whether organizers should be access_grants after all. D-102 settled the mechanism — a set named by a selector, aimed at by grants — without changing D-062's answer that the roster is not itself a grant. What remains open is smaller than it used to be: whether more codes should be seeded to ORGANIZERS, which is the question above (../domain/07-events.md §5).
    • Waitlist notification. Promotion is deliberate; telling the promoted person is not designed. It belongs to the communication module.
